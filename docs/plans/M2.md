# M2 · Planning 与 Agent Factory — 任务分解（D52，Henry 2026-10-17 批准）

范围来自 `docs/ARCHITECTURE.md` §20 的 M2 行：Planner proposal contract 与 DAG 校验（M1-02 已交付契约与校验，M2 接 Planner 本身）；plan 审批流（M1 已有人工审批，M2 保持人工）；AgentSpec、ContextPackage、`attempt_bindings`；Scheduler 与预算；attempt-launcher；`axiom attempt *` 与 submit 结算路径；Candidate 快照。再加上 D46 列出的 M1 遗留项。M3（独立验证）、M4（集成 / Approval / 完成）不在本里程碑内：M2 结束时 Task 的终点是 `SUBMITTED`，`verification_runs` 只写 `QUEUED`。

**M2 出口标准**（§20 + D46 遗留）：
1. 在 `fixture-v1` 上：Goal → Planner 提案（模型提案，`provenance.kind = 'model'`）→ 人工批准 → `mission start` → Scheduler 自动放行 ≥ 3 个 READY Task **并行** → 3 个 Attempt 各自 `RUNNING → SUBMITTED`，每个 Submission 绑定不可变 Candidate（commit + tree hash），`verification_runs` 各一条 `QUEUED`；
2. 伪造 / 过期 / 重复 / 不匹配的 SUBMISSION 被拒（Orca 拒绝码 + `mutation_receipts`），**不改任何状态**（Task stage、Attempt、Candidate、audit 之外的表逐字节不变）；
3. 三种 provider 各完成至少一次 `RUNNING → SUBMITTED`：确定性测试 provider（D49）必有；真实 provider 以 Henry 的 Mac 上实际安装的为准——Henry 确认（2026-10-17）：Codex、Claude Code（`claude`）、Gemini CLI（`gemini`）三者都已安装并登录，M2-11 的宿主 smoke 各跑一次；
4. 应用重启时正在 `RUNNING` 的 Attempt 不丢、不重复启动：`live` → 继续；`unverifiable` → 保持 RUNNING 到 policy 时限后 `ABANDONED`；`exited` 且无 Submission → `FAILED` → 按 `retryPolicy` 由 Scheduler 起新 Attempt 或 Task `BLOCKED`；
5. 映射 §4b 的 M2 新增拦截点（workerStop / Abandon / Release / Retain / TerminalUserInput、ask / reply、群发、federation）每行一个测试；`axiom attempt *` 的每个动词有 capability 校验测试；
6. `docs/decisions/DEFERRED.md` 逐条核对（DEF-2 的触发点"Settings / Integrations UI 排期"在 M2 内不触发——M2-10 只恢复文案；DEF-3 仍在首个发布前）。

前置 Decision（随本计划一并提出，2026-10-17 全部 ACCEPTED）：**D48** Planner v1 的形态、**D49** 确定性测试 provider、**D51** 集成基线 ref 的创建时点（D6 的细化）、**D50** `REQUEST_SUBTASK` 的 V1 策略、**D52** 本分解。已 ACCEPTED 且本里程碑直接依赖的：D4（候选快照）、D6 / D6a（分支模型与 `attempt_bindings`）、D9（消息类型）、D10（Scheduler 是唯一派发者）、D11 / D16（Worker 通道 = `axiom attempt *`）、D14（session party + `{kind:'system'}` creator）、D15（栅栏与收据）、D45 / D47（托管 CI 与干净 typecheck）。

## 固定约定（所有 M2 brief 共用）

- 内核改动只许 additive、service-only 的可选入参；RPC schema 不变；`orchestration.workerStart` 的 RPC 路径对 Mission Run 继续被 M1-07 拒绝（D10）。
- Attempt 身份 = Orca dispatch id；不建 Attempt 表 / 枚举；`attempt_bindings` 只做 `dispatch_id ↔ seq ↔ branch ↔ spec / context` 映射（D6a）。
- 所有 `axiom.attempt.*` 走 envelope `orchestrationCapability`；拒绝复用 Orca 的 `LifecycleRejectionCode`，不新造拒绝码（`mission_managed` 除外）。
- 内容寻址：AgentSpec / ContextPackage / Artifact 的 id 都是 sha256；同输入同 id；数据库只存引用与 hash，大内容进 `<userData>/axiom/artifacts/`。
- 提供者相关：V1 不新增 API key 存储；Worker 用用户既有的 provider 认证；D49 的测试 provider 只在测试 / e2e 可选用（产品里不可见）。
- 验证门同 M1（`pnpm test <targets>`、干净 `tc:*`、`check:code-quality:changed`、完整 `pnpm lint`、renderer 任务加 design-system 门）+ 托管 `axiom-ci.yml` 第二信号；内核 seam 的 Task 把 `src/main/runtime/rpc/methods/orchestration src/main/runtime/orchestration src/main/axiom` 全部列进 targets。
- 文档：枚举改动先改术语表并记 Decision；每个 Task 回填 `docs/reference/control-plane.md` 与映射的对应节（不等到 M2-11）。
