# M4 · Controlled Integration 与交付 — 计划（D89、D92）

> 这个文件是计划，不是日志（D89 第 8 条）。每个任务的状态至多三行，加一个验证记录的链接；过程写在验证记录里。设计依据：`claude/m4-design-draft-v1.md`（2026-11-14）。

## 1. 范围与出口

范围与出口标准以 `docs/ARCHITECTURE.md` §20 的 M4 行为准：串行合入队列（单候选，合到最新集成头）、合并树回归、冲突或回归失败回到原 Task 修复（D79）、一次交付批准（绑定 commit）、交付（PR 或本地合入）、完成门禁与 CompletionReport、全对象重启恢复。

出口三条：两个各自通过、合并后失败的候选，后合入的那个回到原 Task 修复并最终合入；未经批准不会交付；CompletionReport 能解释"为什么完成"。另加：Controlled fixture 的全部 manifest 场景可复现。

今天的起点：表 `integration_batches`、`approvals`、`decisions` 已建，没有写入方；没有任何代码把 Task 推到 `INTEGRATION_READY` 或 `INTEGRATED`，也没有代码把 Mission 推到 `FINALIZING`、`READY_FOR_APPROVAL` 或 `COMPLETED`；集成分支在 Mission 开始时创建，之后不动。

## 2. 已定的设计（D92）

一批的流程：Task `VERIFIED` 且上游都已 `INTEGRATED` → `INTEGRATION_READY`，同一事务里往 outbox 放一条 `integration.apply` → 从集成头建临时工作树，`merge --no-ff` 候选 → 冲突则记下冲突文件、中止合并、Task 回 `NEEDS_FIX`；否则在合并提交上跑合并树回归 → 失败则 Task 回 `NEEDS_FIX`，修复从合并提交出发；环境问题有界重试，仍不行成为 Mission 级的待处理项，不归咎 Task；通过则集成头用"旧值必须等于预期"的方式前进到合并提交，Task → `INTEGRATED`，调度器重算下游。

串行靠 outbox 的道，同一 Mission 一次一个，顺序按验证通过的先后。每一步先落库再动 git。集成头只由这一个执行器写，前进前先查它没有被任何工作树检出。候选在提交时钉到 `refs/axiom/candidates/<id>`，合并提交钉到 `refs/axiom/batches/<id>/merged`。

| 条 | 决定 |
|---|---|
| a | 批准点只有交付前一次；`AWAITING_APPROVAL` 留在枚举里，V1 不用 |
| b | 合并树回归 = `setupCommands`、该 Task 自己的验收命令、新键 `integrationGates`（默认取最高一档门）；差异门与防篡改门不再跑 |
| c | 集成分支不压缩历史，`--no-ff` 合并提交 |
| d | 开 PR 后进入"已交付、等合并"，只读回读 CI 与评审状态；PR 合并才 `COMPLETED`；自动唤醒修复在出口之后 |
| e | 目标分支漂移只在收尾时对齐一次 |
| f | 桌面上调预算即批准，同一事务记一条已用的 Approval |
| g | 同一仓库同一目标分支只允许一个执行中的 Mission |
| h | 没有远程时，只在能快进且目标分支没被检出时本地合入，否则停下问人 |
| i | M4 之后的顺序由上手的发现决定（D89 第 3 条） |

合并树回归的记录复用验证记录：`verification_runs` 加一个可空的 `batch_id`，不出现第二套"运行"。验证记录里要记下当时的基点。

## 5. 写 brief 之前的探查

验证者在本机做，只读或在临时仓库里：Git 2.25 下 `merge --no-ff --no-commit`、冲突文件读取与 `merge --abort` 的行为；`update-ref` 带预期旧值前进一个没被检出的分支；内核的 `createManagedWorktree` 用一个 commit 加自定义分支名建临时工作树，以及移除时对未合并分支的处理；`hostedReview.create` 对一个已推送、但不是当前检出分支的分支能不能开 PR；PR 合并后（普通合并、squash、rebase）有无 `gh` 各能怎样确定地认出"已合并"。前两项 2026-11-14 在 git 2.43 下跑过，结果与设计一致；git 不会拒绝对一个正被检出的分支做 `update-ref`，所以执行器必须先查。

## 6. 风险

到 M4-8 之前 Axiom 只在 `axiom/*` 命名空间里写引用；交付是第一次碰目标分支，所以批准绑定 commit、会过期、目标一动就作废，三条都不能省。合并树回归在关键路径上，`integrationGates` 要能配得轻。环境失败不能算到 Task 头上。M3-06 一行曾经变成 14 个任务，M4 的每一行都可能这样，所以有 §3 的任务数预算。
