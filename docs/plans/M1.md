## M1-01 的结论（2026-10-17，供 M1-05 / M1-08 / M2 的 brief 引用）

- 合成 id：`axiom-mission-<uuid v4>`，`isOrcaSessionId` 校验后持久化到 `missions.coordinator_orca_session_id`；每个 Mission 一个，永不复用；重启只加载，不重建 Run（同 id 再建会解绑旧 Run、bump `consumer_generation`）。
- M1-05：Mission ↔ Run 创建的原子性——`createRun` 自带 `BEGIN IMMEDIATE`，先写一个事务/崩溃测试再决定是否需要 `createRunInTransaction`；Task 物化用 `createTask({ spec, deps: [], runId })`（Orca 立即 `ready`，不带终端 lineage）；Orca `ready` ≠ 允许派发。
- M1-07：Mission Run 内非空 `deps` 一律拒绝（会 `pending` 并被 `promoteReadyTasks` 解锁）；`runUse --takeover-legacy` 会 bump 生成号、fence 掉 Control Plane 消费者。
- M1-08：用 `getOrCreateRunDelivery` / `acknowledgeRunDelivery` 处理整批后再 ack（at-least-once，效果需幂等）；`requireCurrentConsumer` 校验生成号；`notifyMessageArrived` 只唤醒已注册的 waiter，不是持久消费——启动时先 drain 积压再注册 waiter；只消费 `run:<runId>`，未绑定 Run 的 `session:<id>` 直邮仅 `getUnreadMessages(address)` 可读（是否需要由 M2 决定）。
- M2（来自 M1-07）：§4b 之外还有作用于 Attempt / Worker 的入口要在 M2 纳入守卫——`orchestration.workerStop` / `workerAbandon` / `workerRelease` / `workerRetain` / `workerTerminalUserInput`、`ask` / `reply`（question_threads）、群发路由（`@worktree:` 可跨 Run）、federation 分支；守卫模块 `src/main/axiom/admission/mission-managed-run-guard.ts` 的 `caller: 'control_plane'` 只能由进程内的 attempt-launcher 传入。
- M2（Scheduler / attempt-launcher）：`startLocalWorker` 的 service-only additive 入参 `dispatchCreator?`、`worktreeId?`、`branchNameOverride?`、`preambleBuilder?`、`dispatchMaxDepth?`、`callerIdentity?`（见 `orca-mapping.md` §4a 与 `docs/review-evidence/axiom-m1/D14-session-party-spike.md` 的 seam 表）；Control Plane 同时传 `coordinator` 与 `callerSession`，`params.from = caller.address`；内核自己的新建 worktree 路径里 dispatch 先于 worktree，M2 必须写明自己的顺序与失败清理（D6a 的序号分支名不变）。
