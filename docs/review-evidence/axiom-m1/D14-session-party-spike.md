Date: 2026-10-17. Author: Codex Worker, attempt M1-01-1. Inspected checkout: `6995e3eef1b1c5adb12787e1eeb55adb3979e66c` (also `main` at task start). Tests exercise the checked-out Orca-derived kernel, including the already-landed M0 changes; this is not a separate checkout of the upstream tag.

D14's session-party foundation holds: a synthetic identity can own a Run, materialize empty-dependency Tasks, and consume durable Run deliveries without an agent-session record or a terminal. The current `startLocalWorker` is not yet the complete D14 adapter: its required `from` selects a session creator, not a system creator, and its preamble teaches the old worker protocol. M2 must explicitly address these seams. No production files were changed and no terminal, agent, or full `startLocalWorker` invocation was launched.

## Identity recommendation

Mint `axiom-mission-<UUID v4>` once per Mission using the main-process standard library, validate with `isOrcaSessionId`, and persist the bare id in `missions.coordinator_orca_session_id`. The 50-character spelling uses only the accepted letters, digits and hyphens, avoids both reserved terminal prefixes, distinguishes service identities from ordinary sessions, and has UUID collision resistance. Do not use the colon-containing `axiom:mission:<missionId>` spelling as a session id. Sources: `src/shared/agent-session-record.ts:154`, `src/shared/orca-session-address.ts:27`, `src/shared/orca-session-address.ts:29`.

The Run stores that bare id with null handle/pane. The caller's address is `session:<id>`; `sessionId` and `orcaSessionId` both contain the bare id, and `workspaceId` is the Mission repository workspace. `src/main/axiom/kernel-contract/session-party-run.test.ts:55` constructs this full typed caller and tests the real party and binding functions. No cast is used to brand an id: tests reuse `testOrcaSessionId`, which calls the production predicate.

Never reuse an id for a different Mission or create another Run with the same id during restart. The old Run is unbound, its generation increases, and its old consumer is fenced. Distinct Mission ids leave each other's Run untouched. Restart loads the existing Mission id and Run id; it does not repeat creation. This is stronger than simply retaining a session-looking string in memory.

## Restart and mailbox findings

The two persistence tests use unique temporary directories, a real on-disk `OrchestrationDb`, explicit `close()`, a new DB instance on the same path, and cleanup in `afterEach`. The Run test recovers the same id, coordinator fields and generation. The delivery test restarts with an outstanding batch, replays its original delivery identity/messages, acknowledges it, receives another message, then reopens again and recognizes the first acknowledgement as a duplicate. No rebind, session record or recreated Run is needed in these tests.

The remembered coordinator address survives reopen too. Run-scoped mail addressed to `session:<id>` is stored under the Run mailbox and is consumed with the ordinary generation fence. A direct inbox DB function does exist: `getUnreadMessages('session:<id>')`. The test demonstrates its separate unbound-mail case. It does not have Run-delivery semantics: `getOrCreateMailboxDelivery` for that address fails because `O/db/messages/mailbox-consumer.ts:24` supports Run or dispatch consumers, not session-address consumers. M1-08 should consume Mission events from `run:<runId>`; M2 can decide whether other direct session mail is useful.

The notification test proves matching waiter wake-up, not a persistent subscription. `notifyMessageArrived` leaves the DB message unread. M1-08 must register/re-register its consumer and drain durable backlog even if no notification was observed. Processing followed by ack can replay across a crash; idempotent Control Plane effects remain M1-06/M1-08 work. These DB tests do not prove runtime restart, Mission side-table recovery, scheduler recomputation, or execution-host liveness reconciliation from Architecture §16.1.

## Contradictions and downstream questions

1. The Mission row in `docs/reference/orca-mapping.md:17` still specifies synthetic handle/pane `axiom:mission:<missionId>`. It contradicts accepted D14 and the proven null-handle session binding. Follow D14; M1-10 should correct the mapping. No source-of-truth document was edited outside this Task's allowed paths.
2. Mapping §4a at `docs/reference/orca-mapping.md:124` says workerStart requires `getCurrentRunForPane` and resolves the caller through a terminal. The checked-out handler actually uses `getCurrentRunForCoordinator` (`W/workers.ts:38`), and the tested workspace helper accepts the session workspace. Retain the identity/consumer checks in the trusted adapter; do not carry the stale pane-only description forward.
3. D14's “no from required” wording applies to validated RPC caller normalization (`R/orchestration-session-caller.ts:254`), not a direct service call. Synthetic ids fail the RPC record lookup. A supplied session address satisfies the schema in-process but selects a session creator. D14's intended system creator therefore needs the explicit internal override described above. This does not refute the session-party design; it refutes a claim that current launch wiring already implements it.
4. The D6a rationale says dispatch ids are created after worktrees (`docs/decisions/DECISION_LOG.md:53`). Current local new-worktree launch commits `createStartingWorkerDispatch` at `W/local-worker-start.ts:108` before `placeWorkerAgent` at `:141`; the latter passes that existing dispatch id into worktree creation (`W/worker-start-agent-placement.ts:116`). The stated ordering fits the planned Axiom precreated-worktree flow, not every existing kernel path. The accepted sequence-based branch naming remains unchanged. M2 must document its own ordering and failure cleanup; no branch or Decision was changed here.
5. M1-05 must decide how to atomically persist Mission ↔ Run creation. Static inspection shows `O/db/runs/run-create.ts:25` owns a literal `BEGIN IMMEDIATE`, whereas `docs/plans/M1.md:22` calls for lifecycle transaction composition. Nested composition is not tested in this spike. Before implementation, add a focused transaction/crash test; if a composable entry is required, propose `createRunInTransaction` (or an explicit internal transaction option) through the existing DB boundary. Do not assume the current method is savepoint-aware, and do not work around it with ad-hoc SQL.
6. M1-08 must decide who registers the Run waiter, how restart drains backlog before waiting, and how durable effects deduplicate a replayed batch. The fence persists; it does not on its own elect a unique consumer process when two services share the same generation. Admission/takeover guards and consumer ownership remain separate work.
7. M2 must decide whether unbound direct session mail needs handling, and validate precreated worktree ownership, branch identity and cleanup using the existing worktree service. Required proposed inputs: `worktreeId`, `branchNameOverride`, service-only `dispatchCreator`, and service-only `preambleBuilder`; also consider the internal `dispatchMaxDepth` and `callerIdentity` propagation described in the seam table. Existing `from`, `callerSession` and `coordinator` must be populated consistently.

No test overturned D14's core choice, so this report does not propose replacing it with a terminal party or a real agent session. The integration gaps and stale documentation should be incorporated into M1-05/M1-08/M2 briefs; a Decision amendment is for the phase controller, not an unapproved change by this Worker.
