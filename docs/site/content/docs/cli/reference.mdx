The `axiom` CLI talks to a running Axiom runtime. Use it when a shell script or agent needs to inspect worktrees, launch terminals, open files, automate the built-in browser, or report progress back into Axiom.

## Verify the runtime

Register the CLI under [Settings → General → Axiom CLI](/docs/settings), then check that it can reach Axiom.

```bash
command -v axiom
axiom status --json
```

If Axiom is not already running:

```bash
axiom open --json
axiom status --json
```

Use `--json` when another tool will parse the result. Human-readable output is for quick terminal checks.

## Selectors

Most commands accept selectors instead of requiring long IDs:

```bash
axiom repo show --repo id:<repoId> --json
axiom worktree show --worktree active --json
axiom worktree show --worktree path:/abs/path/to/worktree --json
axiom worktree show --worktree branch:feature-name --json
axiom worktree show --worktree issue:123 --json
```

`active` and `current` resolve to the enclosing Axiom-managed worktree from the shell's current directory or terminal context. Use explicit selectors in scripts that may run outside the target worktree. For remote runtimes, prefer full server-side selectors such as `id:<repoId>::<absolute-worktree-path>` or `path:<absolute-server-path>` because the local shell's current directory may not exist on the runtime host.

## Choose a host

List every machine the current Axiom host can target and the selector for each one:

```bash
axiom host list --json
```

The result includes this machine, its registered [SSH targets](/docs/ssh), and paired [Remote Axiom Servers](/docs/remote-servers). Use `--host local` for this machine, `--host ssh:<target-id>` for an SSH target, and `--environment <server-name>` for a paired server. SSH rows include the detected remote platform (`linux`, `darwin`, or `win32`) after the target connects; older or disconnected targets report `platform unknown`. They also include `connected` and, when known, the SSH lifecycle `connectionStatus`. If you put a machine name on the wrong selector, Axiom reports the matching machine and the flag to use instead of returning an empty result.

`--host` also takes the bare name shown in the `name` column, on either axis — `--host trader-local` reaches the same machine as `--host ssh:ssh-1783599077486-fyasux`. Names resolve only when they are unique: a name held by two SSH targets, by two paired servers, or by one of each is refused, and the error hands back the id form for each candidate — `--host ssh:<target-id>` for an SSH target and `--host runtime:<environment-id>` for a paired server. Use those to settle it, since `--environment <server-name>` cannot separate two servers sharing a name.

## Runtime commands

```bash
axiom open --json
axiom status --json
axiom serve --port 6768 --pairing-address 100.64.1.20 --json
```

`axiom serve` starts a runtime server in the foreground without opening the desktop window. Use it for [Remote Axiom Servers](/docs/remote-servers) or headless environments, and stop it with `Ctrl-C`.

## Repos

```bash
axiom repo list --json
axiom repo add --path /abs/path/to/repo --json
axiom repo show --repo id:<repoId> --json
axiom repo set-base-ref --repo id:<repoId> --ref origin/main --json
axiom repo search-refs --repo id:<repoId> --query main --limit 10 --json
```

Set the repo base ref before creating lots of worktrees so new tasks branch from the right place by default.

## Worktrees

```bash
axiom worktree list --repo id:<repoId> --json
axiom worktree ps --json
axiom worktree current --json
axiom worktree show --worktree active --json
axiom worktree create --repo id:<repoId> --name fix-login --json
axiom worktree create --name child-task --agent codex --prompt "Investigate the flaky login test" --json
axiom worktree set --worktree active --comment "reproduced failure; testing token refresh fix" --json
axiom worktree set --worktree active --workspace-status in-review --unread --json
axiom worktree rm --worktree id:<worktreeId> --force --json
```

When `worktree create` runs from inside an Axiom-managed worktree, Axiom records the new worktree as a child when it can infer the relationship. Pass `--parent-worktree active` to be explicit, or `--no-parent` when the new work is independent.

`worktree set --unread` puts the unread dot on the workspace in the sidebar, the same one Axiom shows when an agent finishes; `--read` clears it.

Agent startup flags:

```bash
axiom worktree create --name review-api --agent claude --setup run --json
axiom worktree create --name quick-check --agent codex --prompt "Summarize the diff" --setup skip --json
axiom worktree create --name hidden-setup --setup inherit --json
```

`--agent` launches the selected agent in the first terminal. `--prompt` sends initial work to that agent. `--setup run|skip|inherit` controls repo setup hooks; `inherit` follows the repo policy.

Link issues and reviews using the existing workspace metadata:

```bash
axiom worktree create --repo id:<repoId> --name review-task --pr 123 --json
axiom worktree create --repo id:<repoId> --name gitlab-task --gitlab-issue 42 --gitlab-mr 77 --json
axiom worktree set --worktree active --gitlab-issue '#42' --gitlab-mr '!77' --json
axiom worktree set --worktree active --gitlab-issue https://gitlab.example.com/group/project/-/work_items/42 --json
axiom worktree set --worktree active --pr null --gitlab-mr null --json
```

`--pr` is a GitHub pull request number. `--gitlab-issue` accepts an issue number or `#42`; `--gitlab-mr` accepts a merge request number or `!77`. Numbers must be positive safe integers. The GitLab flags also accept HTTP(S) issue or merge request URLs, including self-hosted instances and nested groups. The URL's host and project must match the workspace's stored GitLab source context or the repository's stored remote. If that identity is missing or different, the command fails before updating metadata. A URL cannot choose another project, change the checkout, or fetch a review branch.

Omitting a flag leaves its link unchanged. On `set`, literal `null` clears only the named link; `create` refuses `null`. Each provider has separate fields, so setting a GitLab issue or merge request preserves GitHub and Linear links.

Folder-based repositories can store numeric links through these commands, but a number does not supply a provider host or project. Without existing source context or a stored remote, pasted GitLab URLs are refused and provider details or clickable links may be unavailable. These flags use fields already supported by the runtime; an older runtime that predates a field may ignore it, so check `worktree show --json` after writing to an older host.

## References

A workspace can link multiple reviews and issues, including sources outside its repository.

```bash
axiom reference list --worktree name:api --json
axiom reference add https://github.com/acme/api/pull/5123 https://linear.app/acme/issue/STA-1234 --worktree name:api --json
axiom reference remove https://github.com/acme/api/pull/5123 --worktree name:api --json
axiom reference remove --key '<key-from-list>' --worktree name:api --json
axiom worktree create --name fix --reference https://github.com/acme/api/pull/5123 --reference https://linear.app/acme/issue/STA-1234 --json
axiom reference find STA-1234 --json
```

- **Writes:** full URLs only; no custom shorthand. `remove --key` supports older entries without URLs. Source-unknown legacy links cannot match an exact URL; native issue keys remain searchable when stored. Duplicate adds and absent removals are no-ops. Unrelated links and current selection are preserved. Older hosts without safe delta merging refuse writes.
- **Create:** repeat `--reference`; incompatible with `--pr`, `--issue`, `--linear-issue`, `--gitlab-issue`, and `--gitlab-mr`. References persist before setup or agent startup.
- **Find:** a full URL or native issue key; bare numbers are rejected. Keys search all matching sources. Reads stored metadata, without provider requests or conversation searches. Use `axiom search` for conversation text.
- **Scope:** `--worktree` selects a worktree or folder workspace. Find also accepts `--repo` instead, plus `--include-archived` and `--limit` (default 50 workspaces). `truncated: true` means more matched. Remote selectors refer to the execution host; `current` is local only.
- **Output:** list returns `references` with opaque `key` and `selected`; writes also return `changes`. Worktree show/list/ps retain `linkedItems`. Find returns workspace matches and agents with `linked`, `liveness`, and available `terminal`/`mailbox` addresses. `linked: false` means ownership is unknown; sharing a workspace is insufficient evidence.

Choose an agent from `find`, then use its exact address:

```bash
axiom terminal send --terminal '<terminal-from-find>' --text 'Status?' --enter
axiom orchestration send --to '<mailbox-from-find>' --subject 'Status?' --type question
```

Mailboxes are `dispatch:<id>` or `orca_session_id:<id>`; a `run:<id>` addresses a coordinator. Find never sends messages or assigns ownership. Adding references from a shell does not associate that shell with an agent.

## Terminals

```bash
axiom terminal list --worktree active --json
axiom terminal show --terminal <handle> --json
axiom terminal read --terminal <handle> --json
axiom terminal read --terminal <handle> --screen --json
axiom terminal read --terminal <handle> --cursor <cursor> --limit 1000 --json
axiom terminal send --terminal <handle> --text "continue" --enter --json
axiom terminal wait --terminal <handle> --for tui-idle --timeout-ms 300000 --json
axiom terminal create --worktree active --title "tests" --command "npm test" --json
axiom terminal split --terminal <handle> --direction horizontal --command "npm run dev" --json
axiom terminal rename --terminal <handle> --title "runner" --json
axiom terminal set-pane-title --terminal <handle> --title "reviewer" --json
axiom terminal switch --terminal <handle> --json
axiom terminal close --terminal <handle> --json
axiom terminal close --worktree active --all --json
```

Omit `--terminal` to target the active terminal in the current worktree. Read before sending when you are not sure what the terminal is waiting for.

Close stops the process as part of removing the terminal. Use `--terminal <handle>` for one
terminal, or `--worktree <selector> --all` to durably close every terminal in exactly that
workspace, including its saved layouts and agent-resume records. Use workspace Sleep when those
terminals should resume later. If the execution host cannot confirm that every PTY stopped, bulk
close returns a failing `unverifiable` result rather than claiming the processes exited.
`terminal stop` remains only for compatibility with older tooling.

<Callout title="Terminal handles">
  Terminal handles are runtime-scoped. If Axiom restarts or a command reports a stale terminal
  handle, run `axiom terminal list --json` and reacquire the handle.
</Callout>

`terminal list` reports each terminal's `executionHostId` when Axiom can verify it, plus a result-level `hostScope` with covered and omitted host IDs. Treat a missing host identity or scope as **unverifiable**, not local. A missing terminal is evidence that it exited only when its execution host is listed in `hostScope.hostIds`.

By default, `terminal read` returns the accumulated output stream with terminal escapes stripped. Programs that redraw lines can therefore appear as stacked fragments. Use `--screen` when you need the currently rendered frame; the response's `source` identifies `stream`, `screen`, or `screen-unavailable`. Screen reads have no history to page, so `--screen` and `--cursor` are mutually exclusive.

For long output, use cursor reads. Save `nextCursor` from one stream read, then pass it back with `--cursor` to fetch only new output.

## Files

```bash
axiom file open src/App.tsx --worktree active --json
axiom file open src/App.tsx --line 42 --column 7 --worktree active --focus --json
axiom file diff src/App.tsx --staged --worktree active --json
axiom file open-changed --mode both --worktree active --json
```

Paths are relative to the selected worktree. `--line` and `--column` are 1-based; a column requires a line. Positions are applied when you select the file, or immediately with `--focus`. Markdown switches to source view for positioning. Older hosts open the file without positioning. `open-changed` reads git status and opens changed files in edit, diff, or both modes. Tabs open without changing what you are looking at; pass `--focus` to be brought to them.

## Built-in browser

Browser commands control Axiom's embedded browser tab for the selected worktree. They do not control Chrome, Safari, or the Axiom desktop UI.

Use a snapshot -> act -> snapshot loop:

```bash
axiom goto --url http://localhost:3000 --worktree active --json
axiom snapshot --worktree active --json
axiom click --element @e3 --worktree active --json
axiom fill --element @e1 --value "user@example.com" --worktree active --json
axiom wait --text "Welcome" --worktree active --json
axiom screenshot --worktree active --json
```

Refs such as `@e3` come from `snapshot`. Re-snapshot after navigation, tab switches, clicks that change the page, and any stale-ref error.

Tab and capture commands:

```bash
axiom tab list --worktree active --json
axiom tab create --url http://localhost:3000 --worktree active --json
axiom tab switch --index 1 --worktree active --json
axiom capture start --worktree active --json
axiom console --limit 50 --worktree active --json
axiom network --limit 50 --worktree active --json
axiom full-screenshot --worktree active --json
axiom pdf --worktree active --json
```

Use `axiom exec --command "<agent-browser command>" --json` only for browser actions that do not have a typed Axiom command yet.

Browser device emulation:

```bash
axiom set device --name "iPhone 12" --worktree active --json
axiom screenshot --worktree active --json
```

## Mobile emulator

The mobile emulator commands control iOS Simulator devices through Axiom's worktree-scoped bridge. Use them instead of raw `serve-sim` or `simctl` when an agent is operating from inside Axiom, so lifecycle and active-device state stay attached to the current worktree.

```bash
axiom emulator list --worktree active --json
axiom emulator attach "<device-name-or-udid>" --worktree active --json
axiom emulator tap 0.5 0.7 --worktree active --json
axiom emulator type "hello" --worktree active --json
axiom emulator gesture '[{"type":"begin","x":0.5,"y":0.8},{"type":"move","x":0.5,"y":0.4},{"type":"end","x":0.5,"y":0.2}]' --worktree active --json
axiom emulator button home --worktree active --json
axiom emulator rotate landscape_left --worktree active --json
axiom emulator exec --command "tap 0.5 0.7" --worktree active --json
axiom emulator kill --worktree active --json
axiom emulator shutdown --worktree active --json
```

Coordinates are normalized from `0` to `1`. Prefer `tap` for single taps, and use `gesture` for drags or multi-step touch input. Pass `--device <udid-or-name>` or `--emulator <id>` when a script must target a specific simulator instead of the worktree's active emulator.

## Linear

The `axiom linear` surface is what agents use via the `orca-linear` skill (legacy install name `linear-tickets` still works). Prefer `--json`. Linked worktrees resolve with `--current`.

### Read

```bash
axiom linear issue --current --full --json
axiom linear issue ENG-123 --comments --children --relations --activity --json
axiom linear search "auth bug" --workspace all --json
axiom linear list --filter assigned --limit 10 --json
axiom linear list-issues --team ENG --state started --assignee me --json
axiom linear list-issues --query auth --updated-at -P7D --cursor <cursor> --workspace <id> --json
axiom linear team list --json
axiom linear team states --team ENG --json
axiom linear team labels --team ENG --json
axiom linear project list --query launch --json
```

`--full` expands comments, children, attachments, relations, and activity. Section flags (`--comments`, `--children`, `--attachments`, `--relations`, `--activity`) work individually.

### MCP-style write

```bash
# Create or update (omit id/--current to create; requires --team and --title on create)
axiom linear save-issue --team ENG --title "Fix auth" --priority high --json
axiom linear save-issue ENG-123 --state "In Progress" --assignee me --json
axiom linear save-issue --current --project null --due-date null --json

axiom linear relation add ENG-1 --related ENG-2 --type blocks --json
axiom linear relation remove ENG-1 --related ENG-2 --type related --json
```

`save-issue` labels **replace** the full label set (Linear MCP `save_issue` semantics). Literal `null` clears assignee, estimate, due date, project, or parent.

### Field helpers (still valid)

```bash
axiom linear status set --current --to "In Progress" --json
axiom linear assignee set --current --me --json
axiom linear priority set ENG-123 --to high --json
axiom linear estimate set --current --to 3 --json
axiom linear due-date set --current --to 2026-08-01 --json
axiom linear label add --current --label backend --json
axiom linear comment add --current --body "Investigating regression" --json
axiom linear attach --current --url https://example.com/repro --title "Repro" --json
axiom linear create --title "Flaky login test" --team ENG --priority high --json
```

Run `axiom linear --help` or `axiom skills get orca-linear` for the version-matched list. Pass an explicit issue id (e.g. `ENG-123`) when a script may run outside an Axiom-linked worktree.

## Skills (local, no runtime required)

List bundled guides, print a version-matched guide, or install/update hybrid skill packages without the desktop Settings UI:

```bash
axiom skills list
axiom skills get orca-cli
axiom skills get orchestration --references
axiom skills get orchestration --reference recovery-and-cleanup
axiom skills get orchestration --full
axiom skills install --skill orca-cli --skill orchestration
axiom skills install --all --dry-run
axiom skills update --all
```

`install` / `update` shell out to the same `npx skills` commands Settings uses. They do not contact the Axiom runtime. See [Axiom skills](/docs/cli/skills#keep-skills-up-to-date).

## Account (host-local runtime)

On a headless host running Axiom (`axiom serve` or the desktop app), add managed Claude/Codex accounts when the remote client cannot use **Add account** (remote runtime scope disables that button):

```bash
axiom account list
axiom account add                 # Claude by default
axiom account add --agent codex
```

`account add` runs `claude login` / `codex login` in **this** terminal on the host, then registers the captured credentials with the local runtime. Codex uses device authorization so the browser can finish on another machine. Run these on the machine that owns the accounts — not through a client-only remote session.

## Automations, environments, and hooks

Scheduled prompts:

```bash
axiom automations list --json
axiom automations create --name "Daily review" --trigger daily --time 09:00 --prompt "Review open changes" --provider codex --repo id:<repoId> --disabled --json
axiom automations run <automationId> --json
```

Remote runtime environments:

```bash
axiom environment add --name work-laptop --pairing-code "axiom://pair?code=..." --json
axiom environment list --json
axiom environment rm --environment <selector> --json
```

Agent status hooks:

```bash
axiom agent hooks status --json
axiom agent hooks on --json
axiom agent hooks off --json
```

## Agent habits

- Prefer `--json` for automation and agent calls.
- Prefer selectors over parsing UI labels.
- Read terminal state before sending input unless the next input is obvious.
- Use worktree comments for progress checkpoints. See [Worktree checkpoints](/docs/cli/worktree-checkpoints).
- Use [Orchestration](/docs/cli/orchestration) for tracked multi-agent dispatches instead of ad hoc terminal prompts.
