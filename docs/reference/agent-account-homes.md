# Agent account homes

D83 decision 2 (method A), including its 2026-10-25 revision, governs Codex account homes on macOS and Linux. Official Codex login, account selection, refresh and quota handling remain in Orca's account services. An account's `CODEX_HOME` is `<userData>/codex-accounts/<id>/home`, with the existing ownership marker.

Axiom lays out that home at account lifecycle and launch preparation boundaries. It replaces `config.toml` with an Axiom header, the home's existing project trust and attributable Orca status-hook approvals, `[features]` disabling apps and plugins, allowlisted MCP tables, user-skill disable entries, and the existing daemon socket guard. The file is written atomically, owner-only, when its bytes change. Temporary model/settings changes are replaced at the next layout. Project trust for account launches goes only to that account's config.

The layout unlinks only former resource symlinks whose targets are inside the system Codex home. It does not remove regular resource files or directories, follow configuration symlinks, or recursively delete anything. `auth.json`, sessions, logs and state databases belong to Codex and remain untouched. `hooks.json` retains only Orca's status hooks; their approvals follow their retained positions. Launch reconciles that status hook in place. The old config-promotion baseline is removed. Host account launch and selection no longer start the session-history bridge.

`GlobalSettings.codexAccountHomeAllowlist` defaults to `{ skills: [], mcpServers: [] }` and is read at every layout. Skills are names immediately under `~/.agents/skills`; discovered, unlisted `SKILL.md` paths receive `[[skills.config]]` with `enabled = false`. Repository `.agents/skills` remains project content. MCP names select full `[mcp_servers.<name>]` tables and their descendants from the system `config.toml`, read only; missing names are reported. V1 has no plugin or user-hook allowlist and no allowlist UI (M3-09).

The layout returns the config SHA-256, each copied MCP block's SHA-256, missing server names, absolute disabled/enabled user-skill paths, retained hook-approval keys, and removed resource-link names. It reads no system-home resources and writes nothing into the system home. A non-regular config or hooks file, unreadable input, or concurrent replacement refuses layout rather than following or overwriting an external file.

Workers use the runtime's read-only launch-home resolver. Headless Codex Workers pin an account home's `CODEX_HOME` in the wrapper's `/usr/bin/env` operands, after the login shell, and always pass `-c features.hooks=false`; interactive sessions keep Axiom's status hook. Before launch, a ChatGPT token whose `last_refresh` is missing or at least 7 days old is checked again under the existing home process lock and refreshed once through a short-lived app-server (`account/read`, `refreshToken: true`). API-key logins need no refresh. A failed refresh is recorded without credential contents or error text and the launch continues for D68 classification. `attempt.headless_prepared` and `attempt.started` carry the requested/effective combination: harness version, home path, config and MCP hashes, enabled user-skill digests, disabled-skill and hook-approval counts, and token status. Missing allowlisted entries, an unknown version or a failed refresh produce one `attempt.launch_mismatch` audit; unmanaged homes are unchanged and do not produce a mismatch. TUI Attempts record `adapter: 'none'` until their harness adapter exists (DEF-42).

Windows hosts and WSL account homes retain the existing mirror and hook behavior until V1.x (D67). The system-default lane and shared mirror home also retain their current behavior in M3-08c. M3-08d removes those lanes and the remaining system-home hook, auth and session-history writes, including one-time cleanup of Axiom's old status hook. Claude migration is M3-08b; orcad remains unchanged.
