# Agent account homes

D83 decision 2 (method A), including its 2026-10-26 revisions, governs Codex account homes on macOS and Linux. Official Codex login, account selection, refresh and quota handling remain in Orca's account services. There is no system default on these platforms: clearing or removing the active account leaves no selection. Older IPC/RPC clients may still send nullable selection parameters; the account handlers refuse `accountId: null` with `system_default_retired` without changing the schema, and the RPC transport preserves that code. An account's `CODEX_HOME` is `<userData>/codex-accounts/<id>/home`, with the existing ownership marker.

Axiom lays out that home at account lifecycle and launch preparation boundaries. It replaces `config.toml` with an Axiom header, the home's existing project trust and attributable Orca status-hook approvals, `[features]` disabling apps, plugins and remote plugins, allowlisted MCP tables, user-skill disable entries, and the existing daemon socket guard. The file is written atomically, owner-only, when its bytes change. Temporary model/settings changes are replaced at the next layout. Project trust for account launches goes only to that account's config.

The layout unlinks only former resource symlinks whose targets are inside the system Codex home. It does not remove regular resource files or directories, follow configuration symlinks, or recursively delete anything. `auth.json`, sessions, logs and state databases belong to Codex and remain untouched. `hooks.json` retains only Orca's status hooks; their approvals follow their retained positions. Launch reconciles that status hook in place. The old config-promotion baseline is removed. Host account launch and selection no longer start the session-history bridge.

`GlobalSettings.codexAccountHomeAllowlist` defaults to `{ skills: [], mcpServers: [] }` and is read at every layout. Skills are names immediately under `~/.agents/skills`; discovered, unlisted `SKILL.md` paths receive `[[skills.config]]` with `enabled = false`. Repository `.agents/skills` remains project content. MCP names select full `[mcp_servers.<name>]` tables and their descendants from the system `config.toml`, read only; missing names are reported. V1 has no plugin or user-hook allowlist and no allowlist UI (M3-09).

The layout returns the config SHA-256, each copied MCP block's SHA-256, missing server names, absolute disabled/enabled user-skill paths, retained hook-approval keys, and removed resource-link names. It does not mirror system-home resources or write into the system home; the allowlisted MCP and skill-discovery reads described above remain. A non-regular config or hooks file, unreadable input, or concurrent replacement refuses layout rather than following or overwriting an external file.

Workers use the runtime's read-only launch-home resolver. Headless Codex Workers pin an account home's `CODEX_HOME` in the wrapper's `/usr/bin/env` operands, after the login shell, and always pass `-c features.hooks=false`; interactive sessions keep Axiom's status hook. Before launch, a ChatGPT token whose `last_refresh` is missing or at least 7 days old is checked again under the existing home process lock and refreshed once through a short-lived app-server (`account/read`, `refreshToken: true`). API-key logins need no refresh. A failed refresh is recorded without credential contents or error text and the launch continues for D68 classification. `attempt.headless_prepared` and `attempt.started` carry the requested/effective combination: harness version, home path, config and MCP hashes, enabled user-skill digests, disabled-skill and hook-approval counts, and token status. Missing allowlisted entries, an unknown version or a failed refresh produce one `attempt.launch_mismatch` audit; macOS/Linux Workers refuse missing or legacy homes with `no_account`. Planner and Worker provider selection filters Codex with `no_account` after `not_installed` and before `not_certified`; the refusal points to Settings › Accounts. Quota polling skips an empty selection, and read-only structured-session resolution also refuses it. TUI Attempts record `adapter: 'none'` until their harness adapter exists (DEF-42).

The four Codex egress defaults are pinned off at both launch boundaries (D83 ⑥, D57): `check_for_update_on_startup = false` is top level, before the first preserved table; `[features]` sets `remote_plugin = false`; `[analytics]` and `[feedback]` each set `enabled = false`. Headless argv repeats these as `-c check_for_update_on_startup=false -c analytics.enabled=false -c feedback.enabled=false -c features.remote_plugin=false`, alongside hooks off, network off and the existing workspace-write sandbox. These pins do not alter the user's config. The Worker protocol explains that the sandbox has no network or package store, prohibits dependency installation there, and assigns setup commands to verification; unavailable checks must be reported as failed with a note.

On macOS/Linux, Axiom no longer creates or syncs `<userData>/codex-runtime-home/home`, promotes settings or plugin registrations back to the user, copies auth back, installs or reconciles status hooks in the real home, backfills/heals its session index, or starts account-home session bridges. System and legacy-mirror history remain discoverable for viewing; local resume/fork preparation refuses those homes. Read-only session discovery, AI Vault, usage, allowlisted MCP table copying and the D56 custom-provider guard remain. A plain Workbench shell with no account gets no injected home or hook reconciliation; a `codex` typed there uses the user's home and does not report Axiom status. Sessions with a selected account keep that account home and its Axiom hook.

At desktop startup, `codexRealHomeCleanupDone` gates one cleanup on macOS/Linux. Before removing any Axiom-owned hook entries from the user's `hooks.json`, it saves the original bytes under `<userData>/codex-real-home-hooks/hooks-<timestamp>.json`. It uses the existing managed-command matcher, preserves all other entries and metadata, and never edits the user's `config.toml` approval tables. Absent, unreadable, malformed or symlinked hook files record `nothing_to_do`. It also walks owned host-account `sessions/` directories without following symlinks and unlinks only account-side files whose device and inode match a file under the user's own sessions directory. The user-side file is untouched. The completion audit is `[codex-real-home-retirement] { hooks: 'removed' | 'nothing_to_do', unlinkedSessions: <count> }`; a failed backup/write leaves the marker unset for a later retry. Once marked, startup never repeats the cleanup.

Windows hosts and WSL account homes retain Orca's system-default selection, mirror, auth synchronization, hooks and session bridges until V1.x (D67; D83 ruling ①). Their compatibility modules remain behind explicit platform/home checks. Claude migration is M3-08b; the Skills page is unchanged. No orcad-specific or remote-host implementation is part of M3-08d (DEF-43); non-WSL remote hosts already share the account layout service under D83's 2026-10-25 revision, and credentials remain on the execution host. Remote sign-in/delivery validation stays with DEF-43.
