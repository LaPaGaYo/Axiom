## Risks / limitations / follow-ups
- The gate is per Axiom profile: an existing profile that used Codex before this change starts with no activation and will not refresh Codex hooks at startup until the user launches Codex, installs hooks from Settings, or adds an account (the launch path grants on demand, so nothing is lost, but a user who only ever types `codex` into plain shells gets no status hooks until then). Documented in the evidence doc; a follow-up could offer a one-time "activate from existing hooks" prompt — a product decision, not M0.
- `opencode` launches do not activate `opencode-go` (exact id equality by design); `minimax` has no launch id. Usage polling for those starts only via a user-initiated path that records them, or manual refresh.
- The background e2e cannot observe the focused-window usage poller or `gh auth status` on a host without `gh`; those gates rest on unit tests. A foreground capture is an M0-exit item.
- `pnpm run typecheck:e2e` remains red on main for pre-existing reasons (hygiene item from M0-08).
- Pipeline lessons: sidecar assertions must be validated against the candidate's own fixtures before use; Workers must not run `oxfmt`/`pnpm format` over Markdown; `config/tsconfig.cli.json` enumerates main-process files, so any new module imported from the CLI-reachable graph needs an include entry (second occurrence of TS6307 in this milestone); repository-wide audit tests (`src/main/global-fetch-call-site-audit`) belong in every sidecar's targets because the focused targets never include them and the full suite only runs at the end.
