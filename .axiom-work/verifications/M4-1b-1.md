- **What is looked at first** (2, steps 1 and 2). `eligibility` in `integration-apply.ts` reads the Mission, the Task, the candidate and the candidate's batches. A missing or terminal Mission, a missing or foreign Task or candidate, a candidate that is not `ACTIVE`, a Task that is neither `INTEGRATION_READY` nor `BLOCKED` out of it, and a batch of the candidate in a status other than `QUEUED`, `APPLYING` or `SUPERSEDED` end the effect `done` with nothing written. - **The database first** (steps 3 and 4). The head is read through `runtime.showRepo('id:<repoId>')`, refused unless `isRepoOnCatalogHost`, with `rev-parse --verify refs/heads/axiom/integration/<missionId>^{commit}` in the catalog's path, not in the Mission's recorded one. `beginBatch` then repeats the whole eligibility read inside one transaction: a `QUEUED` batch moves to `APPLYING` with the head just read; an `APPLYING` batch with that base is taken as it is; an `APPLYING` batch with another base throws `integration_head_moved` and writes nothing; with no open batch one is inserted as `batch_` + 32 hex characters, `APPLYING`. Each run that gets this far appends `integration.batch_started` `{ status, baseCommit, candidateId }`.
- **The scratch worktree** (steps 5 to 7, `integration-scratch.ts`). Leftovers are found in the runtime's listing by directory name — `integrate-<batchId>` or that plus a numeric suffix — and removed with `force` and `waitForBackgroundRemoval`. The new worktree comes from `createManagedWorktree` with verification's flags, the name `integrate-<batchId>`, the branch `axiom/integrating/<batchId>` and, as its base, the full ref `refs/heads/axiom/integration/<missionId>`, so that the kernel records a local base for the branch. `HEAD` is read back and must equal the batch's base (otherwise `integration_head_moved`), the branch name is read back from git and kept, and `HEAD` is detached with repository hooks off. The candidate is then pinned from inside that worktree with M4-1a's `pinCandidateRef`; anything but `pinned` fails the try (`candidate_unpinned`).
- **The merge** (steps 8 and 9, `integration-merge.ts`). Every write goes through one function that points `core.hooksPath` at an empty temp directory, removed afterwards, with a timeout of 120 seconds; reads have 30. The merge is `-c user.name=Axiom Control Plane -c user.email=axiom@localhost -c commit.gpgsign=false -c rerere.enabled=false -c gc.auto=0 -c merge.log=false -c merge.verifySignatures=false merge --no-ff --no-edit --cleanup=verbatim -m 'axiom: integrate <candidateId>' <commit>`, with the process environment plus both git dates set to the batch's creation time. What happened is read from git, not from the exit code alone: after a zero exit, an unchanged `HEAD` means the head already contained the candidate, and otherwise the new commit must have exactly the parents (base, candidate); after a non-zero exit, `MERGE_HEAD` and a non-empty list of unmerged paths (`diff --name-only --diff-filter=U -z`) mean a conflict; everything else is `merge_failed`, after an abort when `MERGE_HEAD` exists. Notes that do not change the verdict:

- (a) **A stale request leaves an open batch open.** When a run got as far as `APPLYING` and failed, and the Task is then cancelled or the candidate superseded before the next try, that try ends `done` and the batch stays `APPLYING`. An open batch of one candidate defers every other candidate of the Mission, so the queue would wait for good. This is how the brief describes step 1, not a deviation of the Worker, and it cannot happen before M4-2b, because nothing enqueues the effect. **M4-2a-2 must close it** — a request that has become stale supersedes its own open batch — before M4-2b turns the queue on; it is written into the M4-2a-2 row of the plan.
- (b) `eligibility` lists the three terminal Mission statuses instead of using `TERMINAL_MISSION_STATUSES`, which six other modules use. The lists are equal today. M4-2a-2 edits this function and takes the constant.
- (c) The write function removes its empty hooks directory in a `finally`; if that removal failed after a successful merge, the try would fail with `merge_failed` and the next one would produce the same commit again. The same note as for M4-1a's pin.
- (d) **After an interrupted run the temporary branch stays, in the real runtime.** The fixture hands out an existing branch of the requested name and later removes it with the kernel's git function. The full runtime does more: when a branch of that name still stands on its base and is checked out nowhere it reuses it (`canCheckoutExistingLocalBranch`) and marks the worktree `preserveBranchOnDelete`, and a worktree so marked is removed without deleting its branch — and without a `preservedBranch` in the answer, so no `integration.cleanup_failed` is written. A process that was killed during a merge therefore leaves `axiom/integrating/<batchId>` behind for good: the next run reuses it and the kernel keeps it. One stale branch on an old head per interrupted merge; nothing reads it and no later batch has its name. The brief's ground truth missed this rule and title 8 shows the branch gone only because the fixture stops below the runtime. Recorded in the M4-4 row of the plan (sweeping what an interrupted merge leaves); the first run of this path on the real runtime comes with the e2e spec of M4-2b, which must check that no `refs/heads/axiom/integrating/*` is left after a normal run.

## Not covered

- Nothing enqueues `integration.apply` and nothing ends `TESTING`: a second candidate of a Mission waits until M4-2. Until the head moves, a conflict can only come from a test or from a person who moves the integration branch.
- After a conflict the next Attempt starts from the integration head without the candidate's work, and its context says only that the previous candidate is no longer active. The pre-merged baseline and the conflict evidence of D79 are M4-3.
- The kernel creates the worktree and deletes its branch with the repository's hooks on; a `post-checkout` or `reference-transaction` hook that fails there fails every try. The full runtime also asks GitHub for a pull request of the temporary branch's name, sets `push.autoSetupRemote` when it is set nowhere, and puts the repository's symlinks and `.worktreeinclude` files into the worktree; the unit tests run the kernel's git functions, not those parts.
- With a git older than 2.38 the kernel cannot prove that the temporary branch carries nothing and keeps it (`integration.cleanup_failed`, `branch_preserved`); the tests ran with git 2.54.
- `onExhausted` runs once: a process that dies between the last failed try and it leaves the batch `APPLYING` and the Task `INTEGRATION_READY` beside a failed effect until something enqueues the effect again (M4-2b). A temporary worktree of a batch whose effect is `done` or `failed` is not swept at boot (M4-4).
- One `integration.apply` row stops the effects of every Mission in a version that does not know the kind; going back to such a version with pending rows is not supported.
- A temporary worktree is visible in the sidebar while it exists and a person can delete it there.
- No test runs the executor on the full runtime: worktree naming, branch reuse and `preserveBranchOnDelete`, the terminal provider and background removal are below the fixture (note d). The Mission specs do not reach the executor, because nothing enqueues the effect.
