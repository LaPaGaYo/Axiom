# M3-06-2 resume probe — real harnesses under Axiom's headless Worker launch (verifier, 2026-11-10)

Authority: D88 (the original-session layer waits for a real-harness probe; clean evidence puts M3-06-2c in V1) and the probe checklist in `claude/interrupted-continuation-discussion-v1.md` §5. Henry, 2026-11-10: "同意，可以跑". Scope as reported to him: the two smoke logins only, at most six short runs per provider, no deliberate quota use, evidence limited to exit codes, event types, field names and whether a resume continued, no product code change.

Result in one paragraph. Both harnesses resume an interrupted headless session under the argv Axiom launches Workers with: Claude Code 2.1.312 after SIGTERM and SIGINT, Codex 0.163.0 after SIGTERM and SIGKILL. The session id is unchanged, the conversation is remembered (a passphrase given only in the first prompt and never written to disk came back in the final reply), and a resume started in a different directory works and writes there. Claude accepts a pre-assigned session id; Codex does not. Codex's own rollout file carries a structured rate-limit record after every model call, with the reset time. After a resume, both harnesses report cumulative cost / usage figures that must not be summed per Attempt.

## The checklist, item by item

1. **Claude after SIGTERM.** Exit code and stream tail as documented (143, no result for the turn). Resume in the same worktree, with the same account home and the same `--settings` / `--managed-settings` / `--strict-mcp-config` works. `CLAUDE_CODE_RESUME_INTERRUPTED_TURN=1` makes the CLI itself continue the interrupted turn (`resume_reason: "interrupted_turn"`) and then answer the prompt, but in text `-p` mode a prompt is still required. Cost and usage after a resume: `total_cost_usd`, `modelUsage` and `duration_api_ms` are totals for the whole conversation (session A: 0.296 at c2b, 0.340 at c5); `usage`, `model_usage_since_last_result`, `num_turns` and `duration_ms` describe the run. An interrupted run emits no `result`, so its own spend is visible only as part of the next run's totals. Resume by transcript path across **account homes** was not tested (one login); across **working directories** it works by id and by path.
2. **Codex `exec resume`.** Its own options are `-c`, `--json`, `-o`, `-m`, `--last`, `--all`, `--skip-git-repo-check`, `--ephemeral` and a few more; `-s`, `-C`, `--color` and `--add-dir` are not among them. They are accepted as `exec` options placed before the word `resume` (no parse error), and the resumed turn could write in the worktree; whether a different `-s` or `-C` on a resume overrides what the session recorded was not isolated (in x5 the process also ran in the new directory). The prompt can come from stdin (`-`). A killed session resumes. The rollout file `<CODEX_HOME>/sessions/YYYY/MM/DD/rollout-<local time>-<thread id>.jsonl` has, after every model call, an `event_msg` / `token_count` line whose payload holds `info {last_token_usage, total_token_usage, model_context_window}` and `rate_limits { limit_id, limit_name, primary { used_percent, window_minutes, resets_at }, secondary, credits { has_credits, unlimited, balance }, individual_limit, spend_control_reached, plan_type, rate_limit_reached_type }`. `resets_at` is epoch seconds. The smoke login showed one window (`window_minutes` 10080) and `secondary: null`; `rate_limit_reached_type`, `individual_limit` and `spend_control_reached` were null.
3. **Limits in the streams.** Claude emits one `rate_limit_event` per run: `status: "allowed"`, `rateLimitType: "seven_day"`, `overageStatus`, `overageDisabledReason`, `isUsingOverage`, `resetsAt`, and `unifiedWindows.seven_day { utilization, resetsAt, status }`. No `five_hour` window appeared at the smoke login's low usage. A limit actually being hit was not observed on either harness — by design, nothing was exhausted.
4. **Taking over a worktree in the kernel.** Not part of this probe: no product code ran. On the harness side both a resume in the same directory and one in a new directory work.
5. **Pre-assigned session id.** Claude: `--session-id <uuid>` works together with the Worker argv. Codex: no such option (`--thread-source` only classifies a thread); the id arrives in the first stdout event, within about a second.
6. **Codex resume parameters.** Covered by item 2: both spellings work — the Ekko Studio form (options after `resume`, sandbox through `-c sandbox_mode=…`) and the form that keeps Axiom's exec options in front of `resume`.
7. **Kernel rate-limit service.** Answered before the M3-06-2a brief; not a harness question.

## What follows for the remaining tasks

**M3-06-2a-2 (prevention).** Codex's reset time needs no network: the Worker's own rollout file has it, structured, fresh as of the last model call. Axiom already records the thread id (`providerSessionId`) and launches with the account home, so the file can be found without listing other sessions. No kernel refresh and no provider activation is involved; the question whether a Mission may trigger a usage refresh no longer has to be answered for this task. Two cautions for the brief. First, the fields at an actual limit were not observed (`rate_limit_reached_type`, `used_percent` at or above 100, whether the failing call still writes a `token_count`), so the structured read is optional evidence beside today's text fallback, never a replacement. Second, the same object and the file's `session_meta` carry account state and identifiers (`plan_type`, `credits.balance`, `creator_account_id`, `creator_user_id`): a reader may extract window, reset and reached fields only and must not persist or log anything else.

**M3-06-2c (resume the harness session).** The harness side is clean for both providers, so by D88 the task is in V1. Inputs for its brief: the launch forms above; a prompt is always required; the session id stays the same unless one asks for a fork (`--fork-session`, `codex exec fork`: not tested); a resume in a new directory works, but the history still names the old absolute paths, so either the continuation prompt states the new root or the Attempt takes over the old worktree (the kernel-side question of item 4, to be answered by reading the kernel's worktree and dispatch code); sessions live in the account home, so a changed account selection or a cleaned home means no resume and the fallback is the M3-06-2b snapshot; Claude can be told its session id before the first event, Codex cannot; Codex's stderr line about a missing tool-call output is noise, not a failure; per-Attempt cost must come from the per-run fields (Claude: `usage` / `model_usage_since_last_result`; Codex: a delta — x5's `turn.completed.usage.input_tokens` was 258,886 against x2's 219,964 although x5 was a three-step turn, so the figure reads as the thread's running total; the rollout's `token_count.info` has both `last_token_usage` and `total_token_usage`).

**M3-06-3 (rule supervisor).** "Preserve, then SIGINT, then SIGTERM" is meaningful for Claude: SIGINT ends the turn with a `result` in under 0.1 s. Its exit code is 0 while `is_error` is true, so the exit code alone says nothing. Codex answers SIGINT with exit 1, no terminal stdout event and a `turn_aborted` rollout line; SIGTERM simply kills it. Every interrupted session that was resumed continued (Codex after SIGINT was not resumed). In the product the harness runs under the kernel's terminal and a wrapper; what the kernel's stop actually delivers is for that brief to verify.

**Failure classification (M3-06-2a, merged).** A Claude run ended by SIGINT exits 0 with a failed `result` whose `terminal_reason` is `aborted_tools`; the current rules would call that an eventful unrecognised failure (`unknown`, failed). Nothing sends SIGINT today; when the supervisor does, its stop has to be settled by the stop path, not by the exit classifier. The stream types new in this CLI version (`command_lifecycle`, `system/task_started`, `system/task_notification`, `system/thinking_tokens`) are ignored by the existing parsers.

## Not covered

Claude after SIGKILL; a Codex resume after SIGINT; resume across account homes; the shapes when a usage limit is really hit, on either harness; forks; the kernel launching a resume (no product code ran); Linux. The signals went straight to the harness's process group, not through the kernel's stop.

## Evidence handling

Recorded: exit codes and signals, timings, event and item type names, key names with value types, the per-run token and cost figures the CLIs print, which files existed in the scratch repositories, and booleans (same session id, passphrase recalled).
