### How the failure was injected

The exit spec's injected failure (S1) has no real-harness analogue, so the chain got a repository gate: `axiom-change-note-gate.mjs` fails a candidate whose changed non-test `.ts` files under `src/` do not start with `// Change-Note: …` and prints the fix. First design (run 1): the script committed into the fixture clone and listed in `repositoryGates` from the start — **satisfied first time by every Worker**, because the ContextPackage lists the required verification commands (mandatory context) and both the Planner (which put the gate into every `requiredEvidence`) and the Workers simply ran it. Correct product behaviour, no failure. Second design (run 3): the script lives outside the repo (`chain/gates/`), the Mission starts with `verify:full` only, and the desktop adds the gate to `verificationRules.repositoryGates` through `axiom.policy.update` once the first Worker is admitted — a supported user action; verification reads the policy when it claims a candidate (`verification-checks.ts`), so candidates built from the old context fail. In run 3 the poll fired 3 ms after `mission.start`, while the scheduler round was still building contexts, so only T01's context predates the gate; T02's and T03's contexts already listed it and those Workers satisfied it first time. The smoke should add the gate a few seconds after the round instead (noted below); T01 alone still carries the whole loop.

### Defect A — the Planner contract says `requiredEvidence` is prose; the Control Plane runs it

`resolveVerificationPlan` (`src/shared/axiom-contract/verification-rules.ts`) turns every `requiredEvidence` entry into a verification command (`source: 'evidence'`) and the Worker's ContextPackage lists them under "Required verification commands". The Planner prompt's "Minimal example" (`src/main/axiom/context-builder/planner-render.ts`) shows `requiredEvidence: ['Test results']`, the rule line only says "give every Task required evidence commands", and `TaskSpecSchema.requiredEvidence` — the schema behind both the prompt's JSON Schema and the `plan_propose` MCP input schema — has no description. The same model wrote commands in two runs and prose in one; the prose made correct candidates fail and sent three Workers into fix Attempts with nothing to fix. Fix: example + contract sentence + `.describe()` on the schema (deliverable 4 of M3-08i). Not a Planner fault.

### Defect B — a headless Attempt that exits without changing the Candidate is never settled

`submitExit` (`src/main/axiom/execution/attempt-exit-submission.ts`) stores the report and calls `settleSubmission`, whose `axiom_submit` transaction throws `OrchestrationError('invalid_argument', 'candidate_unchanged')` when the snapshot tree equals the Task's ACTIVE Candidate (`attempt-submission.ts:172`, DEF-21 ⑥ from M3-02). That rule is right for the terminal channel, where the live Worker receives the error from `axiom attempt submit` and can keep working; on the headless channel the process has already exited, the error leaves `submitExit`, the watcher stops ("deferred to recovery"), and `reconcileAttempt` rethrows it on every tick (`reconcile_failed`) while `agentExit = { exited: false }` keeps a headless dispatch alive. Nothing writes `attempt.failed`, the Task never reaches `NEEDS_FIX`/`BLOCKED`, the Scheduler never gets another round for it, and the Mission stalls silently — four times in these runs. A second consequence waits behind it: `resolveAttemptBaseline` only looks at the immediately previous Attempt, so once such an Attempt is settled as failed the next one would restart from the integration base (`previous_attempt_not_submitted`) and drop the still-ACTIVE Candidate. Fix: settle the unchanged exit as `attempt.failed {settlement: {kind: 'unchanged'}, reportSummary, limitations}` through the existing retry rule, walk the baseline past unchanged Attempts, and tell the next Worker what the previous one concluded (deliverables 1–3 of M3-08i).

### Observation C — a Task whose scope cannot contain the fix burns its retries

Run 1 and run 3 T02 failed on a test the Planner left out of `allowedPaths`; both Codex Workers reported it precisely (limitations, an unapplied patch Artifact in run 3) and the second fix Worker had nothing legal to do. With defect B fixed the Task ends `BLOCKED (retry_budget_exhausted)` after `maxAttempts`, which is at least honest; the real answer is M3-04b's typed BLOCKED reason from the report → pending item → human widens the scope or triggers a replan (D82 ③), and the M3-04b preamble line "if the failure is outside allowedPaths, say so and stop; do not submit an unchanged tree". Also for M3-04b: both harnesses' Workers borrow the outer workspace's toolchain when their own `node_modules` is empty (Codex on 03:46 and here; Claude in run 2).
