## What the brief can rely on (codex-cli 0.163.0)

- A refused resume is local, immediate and free: the process exits non-zero before it emits any JSONL event — in particular before `thread.started` — and before any model request; the worktree and the rollouts are untouched. On every accepted run `thread.started` is the first event (69–76 ms after the start on a resume, before any network round trip). So 2c can recognise a refused resume deterministically: an in-place resume run that ends without a `thread.started` event. The stderr line (`thread/resume failed: no rollout found for thread id …`, JSON-RPC code -32600) is the explanation to record, not the test.
- Codex does not quietly start a new session for an unknown id. An in-place run whose `thread.started` carries another id was not observed.
- A rollout archived as `.jsonl.zst` is resumed with its context, and Codex turns it back into the plain file. A long wait (a weekly usage reset, say) does not by itself force a new session on this version; Axiom reads the rollout only after a run, when it is plain again.
- A completed session (not only an interrupted one, as on 2026-11-10) resumes in the in-place form.

## Limits

One host, one run, one version: another Codex version must be probed again before in-place continuation is enabled for it (the capability record). The archive was simulated — same directory, the old name plus `.zst`, Codex's index untouched; the real archiver was not observed (it waits seven days), but Codex's index keeping the plain path and the binary's `jsonl.zst` strings agree with the simulation. Not probed: a rollout that exists but cannot be read (truncated or corrupt), a resume while another process still writes the same thread (`thread-writer-locks/`), an explicit `-m` together with `resume`, and a thread Codex itself moved into `archived_sessions/`.
