## For Henry to know (none of it needs a decision now)

- **Nothing a user sees changes yet.** The Missions page does not show the fields; that is M4-5b. The CLI's tables are unchanged; `task list`, `task show` and `mission show` with `--json` print the new keys.
- **Only a Task's latest batch is shown.** When a Task's first batch ended in a conflict or a failed regression and a later candidate got a new batch, the field shows the new one; the earlier one stays in the database and the audit log, and no read lists it.
- **`recordedHead` is the Control Plane's record, not a fresh look at the branch**: the merge commit of the last promotion, else the base written at start — the value a batch start compares the branch with. It can be one promotion behind for a moment, and it does not notice a branch someone moved by hand; the executor notices that when the next batch starts and refuses it.
- **Conflict paths reach every caller that may read Tasks**, an agent session of the Mission included (the read class has no further filter). They are the paths the executor stored: redacted, at most 200.
- These are the verifier's choices and Henry's to overturn: optional fields on existing responses rather than a new method `axiom.integration.list` (no new entry in the caller table, the client or the params catalog; an older client drops the keys); one batch per Task; the name `recordedHead`.
