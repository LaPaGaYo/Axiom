### The one failed spec run

`mission-daemon-lost-continuation` (M3-06-2b-3) opens no page of the Missions view. It reaches the Control Plane through the preload bridge and reads the database: it holds a headless stub Worker, closes the app, kills the profile's daemons, relaunches, and waits for recovery to settle Attempt 1 as an interruption. In this host check its first two waits passed and the third — an `attempt.failed` audit row for Attempt 1 within 150 s of the restart — timed out. Nothing of the failed run is left to read: the next Playwright run wiped `test-results`, and the fixture deletes its profile and its repository.

Why the verdict does not count it against the candidate:

- The candidate changes no file under `src/main`, `src/preload`, `src/shared` or `src/cli` (guards of the sidecar; the rerun launcher checked `git diff --quiet main` on the four before it ran). The code that decides this spec's outcome is main's.
- The spec passed in each of the 18 host checks since it exists (77–79 s every time). The last of them, at 19:17 today for M3-09-4a, ran the same sources under those four directories as this tree. The other specs of this host check took the same time as in that one, so the machine was not slower.
- Three more runs alone on the same tree passed in the usual time.

What the timeout means is known from the probes of M3-06-2b-2 and M3-06-2b-3: recovery settles such an Attempt as an interruption only when the kernel has written its worker `abandoned` / `terminal_missing` from another runtime and the Attempt left no exit marker. An Attempt that left an exit marker the exit path then refused, or one the kernel deferred, ends through another rule and writes no `attempt.failed` — both are listed as not covered in the record of M3-06-2b-3 (an exit marker could appear if the Worker's wrapper outlives its child for a moment while the daemon's process tree is killed; that is a guess). Which of them happened here, or whether the helper found no daemon to kill, cannot be said without the profile. **The cause is not established.**

Recorded: a row `observed` in `.axiom-work/logs/flaky-ledger.tsv` (a second failure of this spec is investigated, not rerun); Jev's triage of the failed run answered p(caused by the candidate) = 0.48 and the evidence label is `flaky`. Follow-ups: the host-check launcher keeps the `test-results` folder of every failed spec run from now on (verifier); the spec should attach the Attempt's audit rows and its worker row when that wait times out (test-only, in the M3-10 row).

## Addendum (verifier, 2026-11-15)

The timeout described under "The one failed spec run" has since been reproduced on purpose and has a cause (`claude/daemon-lost-root-cause-v1.md`; fixed by M3-06-2b-4, merge `3c0f74c60b`). The e2e helper that stops a profile's daemon signals the headless Worker before the Worker's wrapper shell. When the two signals are far enough apart the wrapper writes an exit marker before it dies; after the restart neither recovery path took an Attempt that had both a marker and the kernel's `terminal_missing` verdict, so no `attempt.failed` was written and the spec's wait timed out. With a pause of 400 ms between the two signals the spec failed 2 of 2 runs on main with the error of this record; without the pause it failed once in 77 runs — the run of this record, from which nothing was kept, so that it was this race is an inference.

One sentence above is imprecise. "The code that decides this spec's outcome is main's" holds for the candidate's diff, but it left out one trigger: the renderer's start-up hydration also asks the kernel to recover Worker terminals, and it is part of the app shell that the candidate did not touch either. The verdict is unchanged.
