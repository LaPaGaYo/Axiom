## Objective

A Mission's Run, Tasks and dispatches are owned by the Control Plane. Orca's own RPC verbs must not be able to move them: `taskUpdate` cannot write `completed`, `reset` cannot wipe a database that holds Missions, a terminal cannot `workerStart` / `dispatch` against a Mission Task, a Worker cannot send `worker_done` / `merge_ready` / `dispatch` / `decision_gate` into a Mission Run, nobody but the Control Plane opens or resolves gates on Mission Tasks, no terminal can take over a Mission Run, and no Mission Task may carry Orca `deps`. One guard module, one new error code, one line per handler, and a test for every row of §4b — that is the whole Task. The guards are deterministic (a database lookup, never model output) and additive (non-Mission Runs behave exactly as before).

## Facts you can rely on

- Decision rule: an object is Mission-managed iff its Run id matches a `missions.run_id` (`tasks.run_id`, `dispatch_contexts.run_id`, or the Run itself). `AxiomStore.getMissionByRunId(runId)` (M1-04) answers it; reach the store through `getAxiomControlPlane(runtime)` (M1-06) — never construct a second store.
- Handler entry points (`src/main/runtime/rpc/methods/orchestration/`): `messaging/message-methods.ts` — `orchestration.taskCreate` (~line 151; `deps` parsed by `parseOrchestrationTaskDepsFlag`) and `orchestration.taskUpdate` (~line 241; resolves `run` via `resolveRunScope` then `db.updateTaskStatus`); `runs/reset-methods.ts` — `orchestration.reset` (`--all` / `--tasks` / `--messages`); `worker/workers.ts` — `orchestration.workerStart` (~line 19); `runs/dispatch-methods.ts` — `orchestration.dispatch` (~line 19); `messaging/send-methods.ts` — `orchestration.send` (~line 26; `params.type`, `params.to`, run scope); `gates/gates.ts` — `orchestration.gateCreate` (~85) and `gateResolve` (~132); `runs/runs.ts` — `orchestration.runUse` (~40; `takeoverLegacy` and rebinding a coordinator). Guard **after** the handler has resolved its Run / Task / dispatch (so unknown ids keep their existing `task_not_found` / `run_not_found` errors) and **before** any write.
- Who is the Control Plane? In M1 nothing calls these Orca verbs on behalf of the Control Plane — it uses `OrchestrationDb` in-process (D14, M1-05). So in M1 every RPC caller is "not the Control Plane"; the guard still takes an explicit `caller: 'control_plane' | 'rpc'` argument defaulting to `'rpc'` so M2's attempt-launcher can pass `'control_plane'` from inside the process without a second code path. Do not derive it from any request field: a request can claim nothing.
- Errors: `OrchestrationError` (`src/main/runtime/orchestration/orchestration-error.ts`) with a code that is in the passthrough table of `src/main/runtime/rpc/errors.ts` (M1-06 added the Axiom codes there; add `mission_managed`). Message shape follows the kernel's convention: what was refused, why, and "No effects were applied."; `data: { missionId, runId, taskId?, dispatchId?, verb }`.
- Worker-forbidden message types (§3c / AGENTS.md "Typed Communication"): `worker_done`, `merge_ready`, `dispatch`, `decision_gate` when the message targets a Mission Run — `worker_done` because Axiom settles submissions through `axiom.attempt.submit` (M2), the other three because they carry authority. `heartbeat` and `status` stay allowed (kernel liveness and INFORM). Note the existing `orchestration.send` already settles `worker_done` synchronously (`send-point-to-point.ts`), so the guard must run before that settlement.
- `orchestration.reset`: refuse `--all` and `--tasks` whenever **any** Mission exists (`store.listMissions({ limit: 1 })`), and `--messages` when any Mission exists too (Mission mail is Control Plane state); the message must name `axiom mission cancel` + the Approval path (M4) as the supported route. The run-delete trigger from M1-03 remains the belt-and-braces, not the policy.
- `orchestration.runUse`: refuse when the target Run is a Mission Run, whatever the flags (`--takeover-legacy` or a plain rebind both bump `consumer_generation` and fence the Control Plane consumer — M1-01).
- `taskCreate` with non-empty `deps` inside a Mission Run → refuse (M1-01: non-empty deps make `promoteReadyTasks` unlock Tasks behind the Control Plane's back); `taskCreate` **without** deps on a Mission Run by an RPC caller → also refuse (a Task that has no `task_stages` row is unmanaged — the only Task writer is `axiom.plan.approve`).
- Tests to copy: the method harness used by `src/main/axiom/namespace-rpc.test.ts` and M1-06's method tests; the Mission fixture from `src/main/axiom/mission-controller/controller-fixture.test-support.ts` (create → propose → approve → start gives a Mission Run with 12 Tasks); existing handler tests next to each guarded file show how they stub the runtime.
