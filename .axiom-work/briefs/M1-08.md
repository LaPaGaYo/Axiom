## Objective

Give every Mission a durable, restart-safe consumer of its Orca Run mailbox and a RecoveryService that, at startup and on demand, reloads Missions from the database, resumes consumption under the persisted `consumer_generation`, and recomputes readiness from `task_stages` — so that after an application restart Mission / Goal / PlanRevision / Task / stage are intact and the Control Plane carries on with no memory of the previous process. In M1 nothing yet sends Mission mail (Workers arrive in M2), so the consumer's job is the mechanism: drain → handle → acknowledge, wake on `notifyMessageArrived`, survive restart, never double-apply. Handlers for real message types are M2's; here the only effect of a message is an audit event.

## Facts you can rely on

- Run mailbox API (`OrchestrationDb`, proven by M1-01): `getOrCreateRunDelivery({ runId, consumerGeneration, limit?, wakeTypes? })` → `{ delivery, messages, replayed }` (replays the outstanding batch until acknowledged); `acknowledgeRunDelivery({ runId, consumerGeneration, deliveryId })` → `{ duplicate }`; `requireCurrentConsumer(runId, consumerGeneration)` throws `consumer_fenced` when the generation moved; `getUnreadRunMailbox`; `hasOutstandingRunDelivery`. Delivery is at-least-once: process a whole batch, then ack; a crash between the two replays the batch — your handler must be idempotent (M1: an audit event keyed by message id — check before insert, or make the audit `event` + `objectId` unique per message).
- Wake-up: `runtime.waitForMessage(handle, { typeFilter?, timeoutMs?, signal?, exclusive? })` (`src/main/runtime/runtime-message-waiters.ts`, exposed on the runtime service surface) resolves `'notified' | 'timed_out' | 'cancelled' | 'waiter_exists'` when `notifyMessageArrived('run:<runId>', type)` fires (`orchestration/mailbox-notification-coordinator.ts`) — a waiter must be registered *before* checking the backlog, and notification is not consumption (M1-01). `exclusive: true` gives you "one consumer per mailbox in this process".
- Generation fence: `runs.consumer_generation` is bumped by `runUse` takeover / same-id `createRun` (M1-07 refuses both for Mission Runs, but a fenced consumer must still stop cleanly, log, and mark the Mission `BLOCKED` with reason `consumer_fenced` rather than fight).
- Boot: the desktop wires runtime services in `src/main/startup/main-process-runtime-service.ts` → `configureRuntimeServices(runtime)` (called after `app.ready` from `main-process-ready-runtime.ts`), the headless daemon in `src/main/orcad/orcad-entry.ts` right after `new OrcaRuntimeService(...)`. Both files are strongly typed (not in `config/ts-nocheck-baseline.txt`). Add one call in each: `startAxiomControlPlane(runtime)`; stop on `app.once('will-quit', …)` (desktop) / the daemon's shutdown path. `runtime.getOrchestrationDb()` is lazy and opens the database on first call — calling it at boot is fine there (userData is final after `app.ready`).
- Control Plane instances: `getAxiomControlPlane(runtime)` (M1-06) returns `{ store, missions }` per database; extend that object with `recovery` and `consumers` rather than adding a second accessor.
- Controller: `MissionController.recomputeReadiness(missionId)` (idempotent, DB-derived), `listMissions`, `blockMission`, `getMission`. Store: `listMissions({ status? })`, `appendAuditEvent`, `listAuditEvents`.
- Tests: file-backed `OrchestrationDb` in a temp dir (pattern in `kernel-contract/session-party-run.test.ts`), a runtime stub exposing only `getOrchestrationDb`, `waitForMessage`, `notifyMessageArrived` (reuse the small stub from `run-mailbox-notification.test.ts` / the real `RuntimeMessageWaiters` + `OrchestrationMailboxNotificationCoordinator` — do not build a fake runtime), fake timers for the long-poll timeout.
