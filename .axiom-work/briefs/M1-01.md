# Task M1-01 — D14 mapping verification spike: the Control Plane as a session party on the frozen Orca kernel (tests + report only)

You are a Worker on the Axiom project (a product fork of Orca). Read `AGENTS.md` (including the Lazy Senior Dev Mode section), `docs/ARCHITECTURE.md` §8.4 and §16.1, `docs/reference/orca-mapping.md` §2 (the Mission / Task / Message rows), §4a, §4b, §5 and §9 items 10, 13, 14, Decisions D6a, D10, D14 in `docs/decisions/DECISION_LOG.md`, and `docs/plans/M1.md`.

## Objective

D14 (ACCEPTED) says the Control Plane takes part in orchestration as a **session party**: each Mission gets a synthetic Orca session id (persisted in `missions`), used as the Run coordinator (`createRun({ coordinatorHandle: null, coordinatorPaneKey: null, coordinatorOrcaSessionId })`); the Control Plane constructs an `OrchestrationSessionCaller` in-process and calls service / DB functions directly (never the RPC dispatcher with a session claim); dispatch creator `{ kind: 'system' }`; `workerStart` later gets additive `worktreeId` / `branchNameOverride` params. M1-05 (MissionController) and M1-08 (mailbox consumer + RecoveryService) will be built on these assumptions.

Your job is to **prove or refute each assumption with tests against the real `OrchestrationDb` and the real functions, without changing production code**, and to write a report that the M1-05 / M1-08 / M2 briefs can cite file:line. Where an assumption holds, the test stays as a permanent regression test ("kernel contract"). Where it does not, say exactly what would.

## Facts you can rely on

- Party model: `src/main/runtime/orchestration/orchestration-party.ts` — `resolveOrcaSessionParty(id, db)` returns, for an id that is not a recorded structured worker, a *chat* party `{ terminalHandle: null, paneKey: null, orcaSessionId, address: 'session:<id>' }` and does not need any session record; `resolveDeclaredCallerParty` refuses a chat named by address (irrelevant in-process). `orchestration-caller-identity.ts` — `OrchestrationSessionCaller` = identity + `sessionId` + `workspaceId`; `hasRunBindingKey`, `mailboxAddressOf`, `runCoordinatorKey`, `runBoundToCoordinator`. `src/shared/orca-session-address.ts` — `isOrcaSessionId` = `/^[A-Za-z0-9_-]{8,128}$/` and not prefixed `term_` / `structworker_`; `src/shared/orca-session-address-test-fixture.ts` has `testOrcaSessionId`.
- Run creation: `src/main/runtime/orchestration/db/runs/run-create.ts` (`unbindOtherRunsForCoordinator`, then `rememberRunCoordinatorHandle(id, 'session:<id>')`). - Worker-start seams that consult the caller (M2 will call `startLocalWorker`, `src/main/runtime/rpc/methods/orchestration/worker/local-worker-start.ts`): `resolveDispatchCallerWorktreeId(runtime, params.from, callerSession)` (`rpc/methods/orchestration-caller-workspace.ts`: a session caller's `workspaceId` wins, `showTerminal` is not called); `resolveDispatchCreator(runtime, params.from, callerSession)` (`rpc/methods/orchestration/runs/dispatch-creator.ts`: no `from` → `{ kind: 'system' }`; a handle-less session caller → `{ kind: 'session', orcaSessionId }`); `db.createStartingWorkerDispatch({ creator, maxDepth, taskId?, taskSpec, taskRunId, taskCreatedByTerminalHandle: coordinator?.terminalHandle ?? undefined, … })`; `deliverAndSettleWorkerStartReadiness({ coordinatorHandle: params.from, … })` and `buildDispatchPreamble` (`src/main/runtime/orchestration/preamble.ts` writes "Your coordinator's terminal handle is: <from>" into the Worker's first prompt). `WorkerStartParams.from` is *required* by the shared zod schema (`src/shared/rpc-contract/orchestration-worker-start-params.ts`, "Missing --from").
