# Task M3-09-4c-2b — the Mission page shows a Mission's policy and lets a person change how many Tasks run at once and what verification runs (the first renderer half of the policy editor; who plans and who works is M3-09-4c-2c; renderer only: no main-process, contract or CLI change)

Planner brief, 2026-11-23 (verifier; prepared 2026-11-21, the confirmation added on Henry's word of 2026-11-23). A Mission's policy decides, among other things, how many Tasks run at once and which commands verification runs before and after a Task's own checks — the setup commands that install a repository's dependencies, and the gates of each risk level. No control in the interface can change any of it: a person who brings a repository that needs `pnpm install` before its tests can only set that through the CLI, and the page does not even show what is stored. M3-09-4c-2a moved the write into the MissionController. This Task builds the first half of the editor on the Mission page: a **Policy** section that shows these values and, for a Mission that is not finished, a form that changes them. The other half — who plans, who works, which providers are usable and why, and the entry from the pending item that says no provider is eligible — is the next Task and is not started here.

2. **The write** (`axiom.policy.update`, desktop only; `src/shared/axiom-contract/policy-params.ts`). `PolicyUpdateParams` is strict: `missionId` and `patch`; `patch` is strict with the optional keys `routing`, `verificationRules`, `concurrencyLimit` (a positive integer), `readinessThreshold` and `budget` (any `budget` key is refused). A `verificationRules` object in the patch **replaces the stored one whole**, parsed strictly by `VerificationRulesSchema`; a key left out of it gets the schema's default. The answer is `{ policy }`. A committed update requests one admission round. No Mission status is checked.
3. **The rules** (`src/shared/axiom-contract/verification-rules.ts`). `Policy.verificationRules` is typed as a record of JSON; it is parsed with `VerificationRulesSchema` when it is used. The keys this Task edits: `setupCommands` (a list of commands, default empty), `repositoryGates` (the optional lists `low`, `medium`, `high`), `integrationGates` (an optional list) and `timeBudgetMinutes` (a positive integer, default 30). The schema has nine other keys; this Task carries them through and does not name them. What the lists mean: a Task's verification runs the setup commands, then the Task's own acceptance commands, then the gate list of the Task's risk level (none when the key is absent; a gate that is already among the earlier commands is not run twice); the check of a merge runs the setup commands, the acceptance commands and then `integrationGates` — or, when that key is absent, the first list that exists of `high`, `medium`, `low`. So an absent key and an empty list are not the same: an empty `integrationGates` means no gate on the merged tree, and an empty `high` stops the fallback there. A stored rules object can fail the schema (a Mission created through the CLI with a bad policy file): `PlanTaskDetails.tsx` says so with the key `missions.planPolicyInvalid`.

## Outcome

The Mission page has a **Policy** section directly after Supervision. It shows how many Tasks run at once, the setup commands, the gates of each risk level, the gates on the merged tree and the time budget of verification, as the Control Plane stores them. For a Mission that is not in a terminal status a person can open a form in place, change these values and save; the page first asks, naming what is about to change, and writes only after the person confirmed (Henry, 2026-11-23); the change goes through `axiom.policy.update`, and the section then shows what the page's next read of the policy answers. A field the person did not touch is not written; every other key of the rules, and the routing, stay exactly as stored.
