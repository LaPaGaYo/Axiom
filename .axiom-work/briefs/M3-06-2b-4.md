# Task M3-06-2b-4 — An Attempt lost with its daemon is preserved and settled as an interruption even when its wrapper left an exit marker (recovery, main process; one e2e case; no contract, renderer or kernel change)

Planner brief, 2026-11-15 (verifier). D88 revision ③ says that a headless Attempt whose terminal is gone after a restart — the kernel's `terminal_missing` verdict — is preserved and settled as an outside interruption. The M3-06-2b-3 brief narrowed this to Attempts whose directory holds no exit marker, and left the others on the counted path with nothing preserved (`docs/reference/control-plane.md` says so in several places). That leaves an ending in which an Attempt gets no `attempt.failed`, no snapshot and a spent retry: the exit path refuses it because the kernel has already closed its dispatch, and the lost-daemon branch refuses it because the marker exists. On 2026-11-14 this was reproduced on the host on purpose (ground truth 6). This Task removes the narrowing: the kernel's verdict decides, the marker becomes evidence.

Read first: `AGENTS.md` (Remote Execution and Process State; Task and Attempt Rules; Code Quality; Lazy Senior Dev Mode), D88 with its revisions of 2026-11-11 and the line of 2026-11-14 in `docs/decisions/DECISION_LOG.md`, `docs/reference/control-plane.md` ("Interrupted Attempt continuation", from the paragraph that begins "Recovery 仅对两种旧 runtime 的 headless 结束" to its limitations; "Recovery（M2-08）", row b of its table and the paragraph that begins "M3-06-2b-3 只改变 b"), `docs/reference/orca-mapping.md` (the two paragraphs on `terminal_missing`), the entry "重启丢失 daemon / `terminal_missing`" in `docs/GLOSSARY.md`.

## Ground truth (verifier; every fact here was read in the code and re-checked by a read-only fact-check)

1. **The decision.** D88 revision ③ (2026-11-11): "重启时连守护进程也没了：认内核的 `terminal_missing` 结论，归为外因打断（不计入 `maxAttempts`、走等待阶梯）并保全，然后按 ②" — new worktree, new session, continue from the snapshot. It names no condition about an exit marker. The revision line of 2026-11-14 says so explicitly and settles the finished-Attempt case (deliverable 3).
2. **The branch.** `reconcileAttempt` in `src/main/axiom/recovery/attempt-reconciliation.ts`: for a headless Attempt whose Task is `RUNNING` it first calls `submitExitedAttempt` (`:115-132`); later, when the Attempt's own worker row is in a terminal kernel state (`:171-200`), the lost-daemon branch runs only if all three hold: `headless`, `isRestartTerminalMissing(worker, runtimeId)` and `!(await hasAcceptedExitMarker(dispatchId))` (`:173-177`). It captures (`captureRecoveryAttempt(ctx, binding, 'terminal_missing')`, `:178`), re-checks that the ending is still current and the verdict still stands, and calls `settleRecoveryDaemonLoss`. Otherwise the generic ending follows (`:189-199`). Nothing else on the way has a marker condition: not `captureRecoveryAttempt`, not `recoveryEndingStillCurrent`, not `settleRecoveryDaemonLoss`, not `settleInterruptedAttempt`.
3. **Its helpers**, `src/main/axiom/recovery/attempt-daemon-loss.ts` (49 lines): `isRestartTerminalMissing` (headless, `state === 'abandoned'`, `stage === 'terminal_missing'`, `runtime_epoch !== runtimeId`); `hasAcceptedExitMarker` (reads `exit-code` in the Attempt directory through `readHeadlessFile`, accepts `/^-?\d+\s*$/` exactly as `submitExitedAttempt` does; a read error other than a missing file throws, which fails this reconciliation pass; its only caller is `:176`); `settleRecoveryDaemonLoss` (one transaction `recovery_daemon_loss`: the audit `attempt.failed { reason: 'terminal_missing', lastError, failure: { class: 'unknown', retryable: true, source: 'absent' }, evidence: 'runtime_restarted', settlement: { kind: 'interrupted' } }`, `attempt.preserved` when something was captured, `settleInterruptedAttempt`).
4. **Why the exit path cannot take such an Attempt.** `resolveHostAttempt` (`src/main/axiom/execution/attempt-authority.ts:158-206`) requires the dispatch to be `dispatched` and the worker `ready` or `start_unknown`. The kernel's `reconcileMissingWorkerTerminal` (`src/main/runtime/orchestration/db/worker-dispatch/worker-terminal-recovery.ts:37-113`) has made the dispatch `failed` (or `circuit_broken`) and the worker `abandoned` / `terminal_missing`. `submitExit` catches the refusal and answers `'unchanged'` (`attempt-exit-submission.ts:55-60`) — before it reads the marker (`:74`).
5. **What main does with it.** `settleRecoveryTerminal(ctx, binding, worker, 'attempt_abandoned', 'kernel_failed', undefined)` (`attempt-recovery-endings.ts:29-68`): for an `abandoned` worker it writes no `attempt.failed`, records no preservation (none was captured) and settles with the reason `attempt_abandoned` — counted. With `maxAttempts: 1` the Task ends `BLOCKED` (`retry_budget_exhausted`).
6. **Host evidence** (verifier, 2026-11-14, `claude/daemon-lost-root-cause-v1.md`). The e2e helper that stops a profile's daemon signals the headless Worker before the Worker's wrapper shell. With a pause of 400 ms between the two signals the wrapper writes `143` into `exit-code` before it dies; after the restart the worker row is `abandoned` / `terminal_missing`, and the pass 60 s after boot writes `task.stage NEEDS_FIX (attempt_abandoned)` then `BLOCKED (retry_budget_exhausted)` — no `attempt.failed`, no `attempt.preserved`. `mission-daemon-lost-continuation` then times out waiting for `attempt.failed` (2 of 2 runs; the control run without the pause passes). Without the pause the spec failed once in 77 runs with the same error; nothing was kept from that run, so that it was this race is an inference. The boot pass wrote nothing in the two forced runs: by the time stamps its exit path was overtaken by the kernel's verdict inside its own transaction (inferred, there is no log line).

## Outcome

After this Task, a non-Planner headless Attempt whose own worker row is `abandoned` / `terminal_missing` from an earlier runtime is preserved and settled as an interruption whether or not its directory holds an exit marker; when the marker holds an integer, the audit keeps it as `exitMarker`. The next Attempt continues from the snapshot in a new worktree with a fresh session, as after any lost daemon. Everything else behaves as on main.

## Deliverables

1. **The rule.** The lost-daemon branch no longer depends on the marker. The marker is still read where it is read today — before the capture, with the acceptance rule that exists — and a read error other than a missing file still fails the pass there, with nothing captured and nothing written (title 5). When the marker holds an accepted integer, `attempt.failed` gains one key, `exitMarker: <that integer>`; when there is no marker or it holds something else, the audit is exactly what main writes. The audit never gains `exitCode`; `reason`, `lastError`, `failure`, `evidence` and `settlement` do not change (ground truth 7 is why). To carry the integer you may change the name and the return type of `hasAcceptedExitMarker` and give `settleRecoveryDaemonLoss` a parameter; both stay in `attempt-daemon-loss.ts`, and `attempt-reconciliation.ts` stays their only user.
2. **Nothing else moves.** Capture before the transaction, the two re-checks after the capture, the transaction's content and order, the refund, the wait ladder and the three-in-a-row limit, the `stopped` path of a pending stop, TUI Attempts, same-runtime verdicts, abandonment by Axiom, Planner Attempts: as on main. The exit path is not touched: when it settles an Attempt before the kernel's verdict exists, that ending stands; when the verdict overtakes it, its pass fails as today and the next pass settles the Attempt by this rule (limitations, see Report).
3. **A finished Attempt is no exception in V1** (Henry, 2026-11-14, D88 revision line): a marker of `0` — even with a complete report in the directory — does not make a Submission here. The work is preserved, the Attempt is an interruption, the next Attempt continues from the snapshot. Record it as a limitation in the docs and the report.
4. **Tests** with exactly the titles of Acceptance.
5. **e2e.** A second test in `tests/e2e/mission-daemon-lost-continuation.spec.ts`, sharing the first one's set-up through a function in that file. It launches with `holdExitSubmission: true`; once the first Attempt has reached its stall it writes `143` and a newline into that Attempt's `exit-code` (through a temporary file and a rename, as the wrapper does), which the running app leaves alone because of the hold; it restarts with `stopDaemons: true` and the hold kept (see below); then it waits until the Attempt is settled either way — an `attempt.failed` audit for it, or a `task.stage` audit of its Task with the reason `attempt_abandoned`. Its first assertion after that wait says that no stage reason is `attempt_abandoned`; then: the worker row `abandoned` / `terminal_missing`; the `attempt.failed` audit as in the first test plus `exitMarker: 143` (extend the schema, ground truth 9); `attempt.preserved` with the partial file and a snapshot ref that resolves; the stages `NEEDS_FIX (interrupted)` and `READY (retry_after_interruption)`; a second Attempt started from that snapshot (`baseline` as in the first test) in another worktree. It does not wait for a Submission: with the hold kept, the second Attempt's own ending is held too. To keep the hold across the restart, `FixtureRestartOptions` gains one optional field and the relaunch in `axiom-fixture-mission.ts` honours it; without the field a restart behaves exactly as today (`tests/e2e/helpers/axiom-fixture-restart.unit.test.ts` may gain a case). No other helper changes. List in the report every field and selector the new test asserts and where each comes from.
6. **Docs.** Every place of ground truth 10: the condition goes; where the audit's shape is given, `exitMarker` is described as an optional integer that is evidence only — it is not exit evidence for in-place continuation, which D88 revision ③ keeps closed after a lost daemon; the limitations are stated (deliverable 3; the exit path settling first; an Attempt that had failed by itself gets one uncounted retry). `terminal_missing` stays an audit reason, not a lifecycle state.
7. **Report** `.axiom-work/reports/M3-06-2b-4-<seq>.md` (see Acceptance).
