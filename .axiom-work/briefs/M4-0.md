# Task M4-0 — Before the integration queue: start is checked first, one Mission per repository and target branch, a reused integration base must be an ancestor of the target, two back-edges in the contract (D92 g and the M4-0 row of `docs/plans/M4.md`, approved by Henry 2026-11-15; contract and main process; no renderer, CLI or e2e change)

Planner brief, 2026-11-15 (verifier). M4 builds the serial integration queue on the integration branch a Mission gets when it starts. Four things about that start are not safe to build on yet. `axiom.mission.start` creates the branch and writes an audit row before it checks that the Mission may start at all. A Mission on a repository that is not on this machine can start, although verification then answers `INCONCLUSIVE` for every candidate. Two Missions can execute on the same repository and target branch at once. And an integration branch that already exists is reused without asking whether it still belongs to the target's history (D51 asked for that check and left it to M4). This Task fixes those four, and adds the two Mission transitions D70 decided and the contract never got. It writes no integration code. (The commit that carries this brief also makes "the Control Plane does not import Electron" a lint rule: `pnpm lint` now refuses an import of `electron` in a file under `src/main/axiom`. That part is done; `.oxlintrc.json` is not yours to edit.)

Read first: `AGENTS.md` (Control Plane Boundary; Integration and Promotion; Git and Worktree Safety; Code Quality; Lazy Senior Dev Mode), `docs/plans/M4.md` (§2 and the M4-0 row), `docs/decisions/DECISION_LOG.md` (D51, D70, D92 g), `docs/reference/control-plane.md` (the row of `integration-base.ts` in the module table; the paragraph that begins "`axiom.mission.start` RPC 在同步 `startExecution` 事务前").

## Ground truth (verifier, 2026-11-15; read in the code at main `0dc875b3c2` and checked there by a second read-only pass; this brief sits on main `b0683ab21d`, where M3-09-4c-1 has since added one three-line method, `policyUpdated`, to `mission-controller.ts` and changed `policy.ts` and `scheduler.ts` — nothing that is named below)

1. **The start today.** The handler (`src/main/runtime/rpc/methods/axiom/mission.ts`, the method `axiom.mission.start`) reads the Mission, awaits `ensureIntegrationBase({ repoPath, targetBranch, missionId })`, appends the audit `integration.base_created` or `integration.base_reused` with `after: { sha }` through the store, and only then calls `missions.startExecution(missionId)`. Nothing before the git call looks at the Mission's status. `MissionController.startExecution` runs in one write transaction: a status that is neither `PLANNED` nor `EXECUTING` throws `MissionControllerError('illegal_transition', { missionId, from, to: 'EXECUTING' })`; then `moveMission(ctx, missionId, 'PLANNED', 'EXECUTING')` — which throws `stale_state` with `{ missionId, from: 'PLANNED', to: 'EXECUTING', actual }` for a Mission that is already `EXECUTING` — then `recomputeReadiness`, and — when a scheduling callback is wired — one scheduling request with the trigger `mission_start` once the write has committed. So today a start of a Mission that is not `PLANNED` is refused with the right error, but after a branch may have been created and an audit row written.
2. **The integration base** (`src/main/axiom/execution/integration-base.ts`, 44 lines; its only caller is that handler). `git rev-parse --verify --quiet refs/heads/axiom/integration/<missionId>`: when it succeeds the function returns `{ sha, created: false }` at once — no look at the target branch; exit code 1 means the ref is absent and the function goes on; any other failure throws `OrchestrationError('integration_base_unavailable', 'Cannot read the integration base.')`. Then `git rev-parse --verify refs/heads/<targetBranch>` (failure: `target_branch_not_found`) and `git branch <integration> <sha>` (failure: `integration_base_unavailable`), returning `{ sha, created: true }`. Git runs through `gitExecFileAsync(args, gitOptionsForWorktree(repoPath))`; a rejected call carries the exit status as a numeric `code`. Nothing in `src/main/axiom` calls `merge-base --is-ancestor` yet; `src/main/axiom/verification/candidate-diff.ts` shows how this code base tells exit statuses apart.
3. **What "not on this machine" means today.** Verification already decides it: `isLocalVerificationRepository(repo)` (`src/main/axiom/verification/verification-checks.ts`, exported) is `isRepoOnCatalogHost` (`src/shared/execution-host.ts`): true only when the repo's `executionHostId` is empty or the local one AND its `connectionId` is empty. Verification reads the repo with `runtime.showRepo(`id:${mission.repoId}`)` and answers `INCONCLUSIVE` / `environment` / `remote_repository_unsupported` otherwise. `axiom.mission.create` stores `repoId` and `repoPath` from `runtime.showRepo(p.repo)` and checks nothing about the host.
4. **Missions and their repository.** A Mission row has `repoId`, `repoPath`, `targetBranch`, `status` and `previousStatus` (set while the Mission is `PAUSED` or `BLOCKED`: the status it was suspended from; a Mission suspended twice has `PAUSED` or `BLOCKED` there, and the full history is only in the `mission.status` audits). `store.listMissions({})` returns every Mission (it filters by `repoId`, `status` and a cursor, takes an optional limit — none by default — and orders by `created_at, id`; the creation time has a resolution of one second and ids are random). There is no query by repository and branch, and none is needed: the table is small.
5. **Errors.** `MISSION_CONTROLLER_ERROR_CODES` (`src/main/axiom/mission-controller/controller-context.ts`) is the list of codes a `MissionControllerError(code, data)` may carry. The RPC layer passes every code of that list through with its `data` (`src/main/runtime/rpc/errors.ts` spreads the list into its pass-through set), and `src/main/axiom/rpc-reads.test.ts` checks that for each code of the list. `errors.ts` itself is at its length limit: **do not edit it**. The Missions page prints a refusal as `code: detail`, where the detail of a `MissionControllerError` is `data.reason` when the data has one and no `errors` list (`src/renderer/src/components/missions/mission-error-text.ts`).
6. **The contract.** `MISSION_TRANSITIONS` (`src/shared/axiom-contract/lifecycle.ts`) has `FINALIZING: ['READY_FOR_APPROVAL', 'PAUSED', 'BLOCKED', 'FAILED', 'CANCELED']` and `READY_FOR_APPROVAL: ['COMPLETED', 'PAUSED', 'BLOCKED', 'FAILED', 'CANCELED']`. `docs/GLOSSARY.md` §4.1 and `docs/ARCHITECTURE.md` §6.1 have listed `FINALIZING → EXECUTING` and `READY_FOR_APPROVAL → FINALIZING` since D70. No production code moves a Mission into or out of those two statuses yet, so the edges change no behaviour today. `src/shared/axiom-contract/lifecycle.test.ts` checks every pair of statuses against its own table `missionRows` (it has `FINALIZING: ['READY_FOR_APPROVAL']` and `READY_FOR_APPROVAL: ['COMPLETED']`), and compares the status vocabulary — not the transitions — with the fenced block of GLOSSARY §4.1.
7. **Tests that are models, and exact expectations.** `src/main/axiom/execution/integration-base.test.ts` (two titles; git is `vi.mock`ed; its first title asserts the three git calls of a creation and then that a reuse makes **exactly one** call). `src/main/axiom/execution/integration-base-rpc.test.ts` (`ensures the integration base before starting (%s)`: real RPC dispatch on `rpcFixture`, whose `ensureIntegrationBase` is a spy and whose `runtime.showRepo` answers a local repo `{ id: 'repo-fixture', path: '/fixture', … }`; the mock asserts that the Mission is `PLANNED` while it runs). `src/main/axiom/rpc-mission.test.ts` (`preserves controller error codes and data` starts an `ANALYZING` Mission and expects `illegal_transition` with `data.from`). `src/main/axiom/mission-controller/mission-controller.test.ts` (`starts only the three roots and rejects a second controller start as stale`). `src/main/axiom/mission-controller/mission-lifecycle.test.ts` (`checks public Mission commands from %s without changing illegal states`: for every status, a `startExecution` that is not legal throws `illegal_transition` — `stale_state` for `EXECUTING` — and leaves the row and the audits untouched). `src/main/axiom/mission-controller/persistence-audit.test.ts` (the ordered audit of create, propose, approve and a controller start — no base events there). **Tests that start a second Mission in the same database**: `planned(f, proposal)` (`src/main/axiom/mission-controller/controller-fixture.test-support.ts`) always creates with `createInput` — repository `/repository`, target branch `main` — and four files start further such Missions while the first still occupies the target — `mission-controller/account-cooldown-adjustment.test.ts` (two more, in `beforeEach`), `agent-factory/account-cooldown.test.ts` (one), `outbox/mission-effect-executors.test.ts` (one), `outbox/attempt-continuation.test.ts` (the helper `otherMission()`, up to three in one test) — and no other test does (a read-only pass over every start path on 2026-11-15: the other unit tests, the RPC fixtures and the e2e specs start one Mission per database). With deliverable 3 those further starts would be refused (deliverable 6 says what to do about it). One set-up fact: the controller of `fixture()` always mints the same session id, so a second `planned(f)` on it fails with `synthetic_session_id_invalid` before anything else; the four files create each further Mission with `planned({ ...f, controller: new MissionController(f.db, f.store) })`.

## Outcome

After this Task: `axiom.mission.start` on a Mission that may not start touches neither git nor the audit; a Mission whose repository is not on this machine is refused at start with a reason; a second Mission on the same repository and target branch is refused while the first occupies it, by the controller itself and therefore atomically; an existing integration branch is reused only when it is an ancestor of the target branch; and the contract admits `FINALIZING → EXECUTING` and `READY_FOR_APPROVAL → FINALIZING`. A `PLANNED` Mission on a local repository with a free target starts exactly as on main.

## Deliverables

1. **The contract.** `MISSION_TRANSITIONS` gains `'EXECUTING'` in the `FINALIZING` row and `'FINALIZING'` in the `READY_FOR_APPROVAL` row. Nothing else in `src/shared` changes. `lifecycle.test.ts`: its `missionRows` gets the same two entries, and one new title (Acceptance, title 5).
2. **One function decides whether a Mission may start**, in a NEW module under `src/main/axiom/mission-controller/` (suggested: `mission-start-guard.ts`, `assertMissionStartable(ctx, missionId)`, synchronous, no write). In this order: (a) the status — not `PLANNED` and not `EXECUTING`: `illegal_transition` with `{ missionId, from: <status>, to: 'EXECUTING' }`; `EXECUTING`: `stale_state` with `{ missionId, from: 'PLANNED', to: 'EXECUTING', actual: 'EXECUTING' }` — the code and the data a caller gets on main; (b) the target: when another Mission occupies the same repository and target branch, `mission_target_busy` with `{ missionId, heldBy: <that Mission's id>, repoPath, targetBranch, reason }`, where `reason` is one English sentence that names the holding Mission's id (the Missions page shows it). "Same repository" is the same `repoId` OR the same `repoPath`, compared as stored; "same target branch" is the same `targetBranch` string. **A Mission occupies its repository and target branch** when its status is `EXECUTING`, `REPLANNING`, `FINALIZING` or `READY_FOR_APPROVAL`, or when it is `PAUSED` or `BLOCKED` and its `previousStatus` is not one of `DRAFT`, `ANALYZING`, `PLAN_REVIEW`, `PLANNED` — so a Mission suspended twice (its `previousStatus` is itself `PAUSED` or `BLOCKED`) and one with no `previousStatus` count as occupying: when the row cannot say, the answer is the careful one. The Missions are read with the existing `store.listMissions`; no new store method, no SQL. When several Missions occupy the target (possible only for rows written before this rule), `heldBy` is the first in the store's order, whichever that is.
3. **The controller enforces it.** `MissionController.startExecution` calls that function as the first statement of its transaction, in place of its own status check; the rest of the method is unchanged. This is what makes the rule atomic: of two starts on one target, the second to commit is refused.
4. **The handler checks before it acts.** `axiom.mission.start`: (1) the function of deliverable 2, through one small public method of `MissionController` (suggested `assertStartable(missionId)`; a read, no transaction) — one call, before anything else; (2) the repository: `runtime.showRepo` with the Mission's `repoId`, exactly as verification asks, and when `isLocalVerificationRepository` (imported, not copied) says no, `MissionControllerError('repository_not_local', { missionId, repoId, reason })` with one English sentence as `reason`; (3) then, as today, `ensureIntegrationBase`, the audit, `startExecution`. A refusal in (1) or (2) creates no branch, writes no audit and leaves the Mission as it was. The two new codes are added to `MISSION_CONTROLLER_ERROR_CODES` (after `synthetic_session_id_invalid`); nothing else is needed for them to reach a client.
5. **A reused integration base must be an ancestor of the target.** `ensureIntegrationBase`: when the integration branch exists, read the target branch (`target_branch_not_found` when it is missing — also on this path now) and run `git merge-base --is-ancestor <existing sha> refs/heads/<targetBranch>`; exit 0: return `{ sha: <existing>, created: false }` as today; exit 1: `OrchestrationError('integration_base_unavailable', …)` with a message that contains `not an ancestor`; any other failure: `integration_base_unavailable` with the message of today. The branch is never moved, reset or deleted. The creation path is unchanged.
6. **Tests** with exactly the titles of Acceptance, under both runners. Existing tests keep their assertions; three kinds of change to existing test files are allowed and nothing else: `lifecycle.test.ts` as in deliverable 1; the reuse half of the first title of `integration-base.test.ts` (the calls a reuse makes now); and, in the four files of ground truth 7, giving every Mission after the first a target branch of its own — different from that of every Mission that still occupies its target, so three Missions need three branches; for that, `planned` in `controller-fixture.test-support.ts` may take an optional third argument that overrides fields of `createInput` (the override lives in that test-support file, not in a product file).
