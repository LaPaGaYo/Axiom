# Task M3-09-3a — Mission UI: Mission Home lists what needs a person and the Task table says what each Task waits on (D86 items 2 ③ and 3, DEF-22 ⑮ (2); renderer only)

Planner brief, 2026-11-13 (verifier). The Task page can now do everything the pending view lists for a Task. Mission Home still counts "pending items" from pending messages alone and its Task table shows only a stage. This part makes Mission Home read the Control Plane's pending view: one list of what needs a person, in the Control Plane's order, each row saying what it is, why it waits, how many Tasks it blocks and what the Control Plane would accept — and the Task table says what every Task waits on. Acting stays where it is: a row opens the Task, the Task page has the controls. One small thing rides along: the adjust form closes after an adjustment that went through (a gap in the brief of M3-09-2b-3). Timed refresh is the next part (M3-09-3b); the supervision level and the "while you were away" summary are M3-09-3c.

Read first: `AGENTS.md` (UI and Product Experience), `docs/STYLEGUIDE.md` (UX rule 4 — "one pending item says what to do, why, and what happens if it is left undone"), `docs/GLOSSARY.md` §4.4a, `docs/reference/control-plane.md` ("Task 等待与 Mission 待处理项（M3-09-1）"; "Task 页的人工处置与重验（M3-09-2b-2）"; "Task 页的调整与取消（M3-09-2b-3）").

## Ground truth (verifier, 2026-11-13, main `494a450c01`; every fact here was read in the code, the specs or the documents at that commit)

1. **Mission Home today.** `src/renderer/src/components/missions/MissionHome.tsx` (193 counted lines; region "Mission Home") renders the status badge, the Goal, "Progress" (`data-testid="mission-progress"`, `mission-attempt-progress`, the stage counts), "Pending items", "Next step" and `MissionActions` (five buttons derived from the Mission's status). Its "Pending items" section counts and lists only the pending `QUESTION` / `REQUEST_SUBTASK` **messages** (the required prop `pendingMessages`; a link button per message that selects the message's Task), then a sentence about proposed plans, the reason of a `PAUSED` / `BLOCKED` Mission, or `No plan awaiting review.`. For an `EXECUTING` Mission "Next step" still says `{{running}} Attempt(s) running, {{submitted}} submitted — verification arrives in M3.` (key `missions.executingNext`; six catalogs carry that English text, `pt` has no such key).
2. **The Task table.** `TaskStageTable.tsx` (65; region "Tasks" and table "Tasks"): two columns, `Task` (title and id as text) and `Stage` (`TaskStageBadge`: the stage badge with `data-task-stage`, and "Execution projection: …"); a row carries `data-task-id` and `aria-selected` and selects its Task on click, Enter or Space. There is no button in the table.
3. **The pending view** (GLOSSARY §4.4a; `src/shared/axiom-contract/mission-pending.ts`, `src/main/axiom/read-models/mission-pending.ts`, `pending-items.ts`, `pending-task-items.ts`): `axiom.mission.pending { missionId }` → `{ missionId, items }`, already sorted by the Control Plane (blocking first, then by how many Tasks an item blocks, then kind, then `since`, then id). An item is `{ id, kind, objectId, taskId?, reason, summary?, blocking, blocks, actions, since, waitingOn? }`.
   - `kind`: `mission`, `plan_review`, `question`, `human_review`, `task_blocked`, `subtask_request`, `follow_up`, `stall_notice`, `supervision_proposal`.
   - `reason`: the Mission's status (`ANALYZING`, `PLANNED`, `PAUSED`, `BLOCKED`) or `budget_exhausted` for a `mission` item; `PLAN_REVIEW` for a `plan_review` item; the reason of the Task's wait for a `human_review` or `task_blocked` item; `question`, `REQUEST_SUBTASK`, `follow_up` for the three message kinds; `stalled` for a `stall_notice` and a `supervision_proposal`.
   - `actions`: method names from `PendingActionSchema`, fourteen in all — `axiom.mission.start / resume / plan / cancel`, `axiom.plan.approve / reject`, `axiom.message.answer / resolve`, `axiom.verification.resolve / rerun`, `axiom.task.adjust / cancel`, `axiom.policy.update`, `axiom.supervision.resolve`.
   - `blocks`: 0 for an item that is not blocking; the number of unfinished Tasks of the Mission for a blocking item without a Task; for a blocking item with a Task, the unfinished Tasks among that Task and everything that depends on it (the Task itself is counted).
   - `waitingOn`: every item with a `taskId` carries that Task's `waitingOn`, whatever its kind — for a `question`, `subtask_request`, `follow_up` or `stall_notice` item it describes the Task, not the item; a `mission` item carries one only for an exhausted Mission budget (`on: 'budget'`, with `budget`).
   - `since` is an ISO time. For a Task refused for `no_eligible_provider` it is the time of the latest refusal, and every admission round that refuses again writes a new one; a round runs at boot for every executing Mission.
   - A terminal Mission has no items.
4. **Who reads the view today.** `task-evidence-read.ts` (40): `readTaskEvidence(missionId, taskId)` calls `axiomClient.missionPending({ missionId })` among its four settled reads and keeps the items of the Task (`pendingItems`, `pendingError`). Mission Home never sees the view. The call `axiomClient.missionPending(` appears once in the non-test files of the missions folder.

## Outcome

Opening a Mission, a person sees at once what needs them: every item the Control Plane lists, most blocking first, each saying what it is, why it waits, how many Tasks wait behind it and what can be done — and one click opens the Task where the controls are. The number shown is the number of rows. The Task table says for every Task what it waits on and whether that needs a person. Nothing new can be done from Mission Home: the Task page, the plan panel and the Mission buttons stay the places to act.
