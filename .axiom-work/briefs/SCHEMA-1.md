# Task SCHEMA-1 — Axiom's own schema version: one row that says which Axiom schema a database has, a numbered chain of Axiom steps whose first step is the baseline, and the column probe at open becomes part of that step (the "Axiom 的 schema 版本号" row of `docs/plans/M4.md`; D93 item 2; the kernel's schema directory only; nothing a caller of the database can observe changes)

Planner brief, 2026-11-16 (verifier). Henry saw the approach on 2026-11-16 and approved it ("9.b 一张一行的表", the rest as the verifier recommended; the revision line under D93 in `docs/decisions/DECISION_LOG.md`, committed with this brief). The orchestration database has one version number, SQLite's `user_version`, and Axiom's schema steps share that chain with upstream's. Upstream has since used the numbers 44 to 46 for steps of its own, so the last full sync had to renumber Axiom's steps and the next one must do it again. To stop that from growing, everything Axiom added after v46 came in without a number: four tables with their indexes and triggers through "create when missing" DDL, one column through a probe at open. That works only for pure additions, and nothing in a database says which Axiom wrote it. This Task gives Axiom a version of its own: one row in one new table, a chain of numbered Axiom steps that runs after the kernel's chain, and a first step — the baseline — that is everything Axiom has added to existing tables so far. For every database that exists today the baseline changes nothing; it stamps the row. The kernel's `SCHEMA_VERSION` stays 46 and the kernel's chain is not touched. What the application does when it finds a stamp newer than it knows is a separate Task (SCHEMA-2); this one only leaves such a stamp alone.

Read first: `AGENTS.md` (Execution Kernel Boundary; Code Quality — "Add database migrations for durable schema changes"; Lazy Senior Dev Mode), `docs/plans/M4.md` §3 (the "Axiom 的 schema 版本号" row), `docs/decisions/DECISION_LOG.md` D93, `docs/reference/control-plane.md` §3 (持久数据) and `docs/reference/orca-mapping.md` §6 (已落地迁移), `.axiom-work/verifications/M4-2a-1-1.md` (why `batch_id` took no number).

## Ground truth (verifier, 2026-11-16; read in the code at main `d2510eaac8`)

1. **Opening the database.** `OrchestrationDbCore`'s constructor (`src/main/runtime/orchestration/db/orchestration-db.ts`) sets four pragmas, then calls, in this order: `createTables`, `migrate`, `createRunCoordinatorAddressTriggers(this.db)`, two backfills and a settlement reconcile that also take `this.db`, two more Run-coordinator calls and `hardenOrchestrationDatabaseFiles`. Several of those are plain functions that take `this.db`; `createTables`, `migrate` and the two Run-coordinator calls are functions with a `this` parameter, called with `this as unknown as OrchestrationDb`. Product code opens the database in one place (`src/main/runtime/workspaces/persisted-surfaces/automation-operations.ts`); about 200 test files open databases of their own, most of them `:memory:`.
2. **`createTables`** (`db/schema/create-tables.ts`) executes, on every open, the core DDL, the graph DDL and `createAxiomTablesSql()` in one `exec`, then `ensureAxiomColumns.call(this)`, the mailbox indexes and the derived-delivery SQL. `createAxiomTablesSql()` (`db/schema/create-axiom-tables-sql.ts`) is `CREATE TABLE IF NOT EXISTS` for 18 tables, then `AXIOM_INDEXES_AND_DELETE_TRIGGERS_SQL`, then the supervision SQL of `create-axiom-supervision-sql.ts` with three more tables — 21 in all, and every index and trigger is `IF NOT EXISTS` too, so tables, indexes and triggers that are missing are supplied on every open, whatever the version. `create-axiom-tables-sql.ts` has 297 counted lines of the 300 `max-lines` allows, and `axiom-tables-migration.test.ts` is exactly at its 800: neither file can take an addition, and neither is changed by this Task.
3. **The kernel's chain** (`db/schema/migrate.ts`). Reads `user_version`, lets `resolveOrchestrationMigrationStartVersion` (`orchestration/orchestration-schema-version-skew.ts`) correct it, returns when it is at or above `SCHEMA_VERSION` (46, `db/contract-constants.ts`), otherwise runs every step inside one `BEGIN IMMEDIATE` … `COMMIT` (a failure rolls back and is thrown) and writes `user_version`. Three of its steps are Axiom's: `migrate-v44.ts` (runs the index and trigger SQL), `migrate-v45.ts` (`agent_specs.spec` and `mission_policies.routing`, each `TEXT NOT NULL DEFAULT '{}'`, added when `hasColumn` says they are missing) and `migrate-v46.ts` (five columns of `verification_runs`: `runtime_epoch TEXT`, `claim_count INTEGER NOT NULL DEFAULT 0`, `worktree_id TEXT`, `started_at TEXT`, `finished_at TEXT`, each probed). A database that reports 43 to 45 gets upstream's v43 once more (builds before UPSTREAM-3 used those numbers for Axiom's steps). The skew resolver lists the seven columns of v45 and v46: a database stamped 45 or 46 that lacks one of them is replayed from version 6 (a stamp above `SCHEMA_VERSION` is returned as it is, without a probe).
4. **The unnumbered column.** `db/schema/ensure-axiom-columns.ts` (M4-2a-1) adds `verification_runs.batch_id TEXT` when `hasColumn` says it is missing: probe first, then `BEGIN IMMEDIATE`, probe again, `ALTER TABLE … ADD COLUMN`, `COMMIT`. Its comment says why it has no number. Fresh databases get the column from the DDL, as the last column.
5. **Existing tests.** `db/schema/axiom-tables-migration.test.ts` holds an independent contract of every Axiom table and its columns in `TABLE_COLUMNS` ("do not derive this from the DDL"; 21 entries; its first title and one `toHaveLength` say 21), 15 indexes and 6 triggers; its helper `axiomSchema()` compares the `sqlite_master` rows of those tables across reopen; one title sets `user_version = 47` and expects everything to stay as it is. `db/schema/ensure-axiom-columns.test.ts` opens databases through `OrchestrationDb` only — it does not import `ensure-axiom-columns.ts` — and proves `batch_id` appears at open on a version 46 and a version 45 file; it stands for an older database by dropping the column from one the current build made. The upgrade titles of `axiom-tables-migration.test.ts` do the same with the columns of v45 and v46 and a lowered `user_version`, which the kernel's chain then repairs. Two Axiom test-support files compare the rows of whole databases before and after an operation (`read-models/pending-evidence.test-support.ts` lists every table, `execution/submission-fixture.test-support.ts` all but the mutation receipts): one constant row more does not change what they prove.
6. **The application's version.** `src/shared/app-environment.ts`: `hasAppEnvironment()` and `getAppEnvironment().getVersion()`; the desktop and `orcad` both install an environment before the database is opened, and `src/main/runtime/orchestration/cli-command.ts` already imports that module from this directory tree (it asks `isPackaged()`, not the version). Under the unit runners a setup file (`config/scripts/vitest-host-ports-setup.ts`, in `setupFiles`) installs a fake environment before every test — its version is `'0.0.0-test'` — and exports `installFakeAppEnvironment(overrides)`.
7. **Reset.** `db/reset/orchestration-reset.ts` deletes from a fixed list of kernel tables; Axiom's rows go through the delete triggers. It does not enumerate tables.
8. **The table census.** `src/shared/wsl-move/wsl-move-dispositions.test.ts` ("lists every SQLite table the app creates, by database") reads every source file under `src/main` that is not a test and contains `CREATE TABLE`, requires that set of files to be exactly the keys of `SQLITE_SCHEMA_FILE_DATABASES`, and every table name it finds to be a key of `SQLITE_TABLE_DISPOSITIONS` — both in `src/shared/wsl-move/wsl-move-storage-dispositions.ts`. Every Axiom table so far was added to the `orchestration` list there; rows that are only a schema version or bookkeeping use `notApplicableDisposition(62)` (`profile_state_meta` there, `schemaVersion` in `wsl-move-dispositions.ts`). The census is a text search: it counts every occurrence of the words in every file under `src/main` whose name does not end in `.test.ts(x)` or `.spec.ts(x)`, comments and `*.test-support.ts` files included — the table `won` in that list comes from a comment in `migrate.ts`.
9. **Pins of earlier Tasks** (run by the union script, on any tree). `SCHEMA_VERSION = 46` in `contract-constants.ts`; no file `db/schema/migrate-v47.ts`; some file of `db/schema` that is neither a test nor named `migrate*` contains `ADD COLUMN`, and one contains `BEGIN IMMEDIATE`; `batch_id` in `create-axiom-tables-sql.ts`; the text `started_at finished_at batch_id` and two titles in `axiom-tables-migration.test.ts` (`upgrades v45 verification rows and reopens idempotently with transparent downgrade probes`, `preserves a future version stamp and remains transparent to the downgrade probe`); the title `adds batch_id to an existing verification_runs table at open and keeps the schema version` somewhere under `db/schema`; `version: 45` exactly twice and `version: 46` at least five times in the skew resolver. And UPSTREAM-4's rule: no file under `src/main/runtime/orchestration/db` imports from `src/main/axiom`.

## Outcome

Every database this build opens carries one row that says "Axiom schema version 1": written on the first open, never rewritten while it is current. A later Axiom schema change is one more numbered step with a test that upgrades from the version before it, independent of upstream's numbers. The probe that added `batch_id` is no longer a special case beside the chains: it is part of step 1, with the seven columns of v45 and v46, so the day a sync removes Axiom's steps from the kernel's chain the baseline still supplies them.

## Deliverables

1. **The table** `axiom_schema`: `id INTEGER PRIMARY KEY CHECK(id = 1)`, `version INTEGER NOT NULL`, `upstream_version INTEGER NOT NULL`, `app_version TEXT`, `updated_at TEXT NOT NULL DEFAULT (datetime('now'))`. One row at most; no index, no trigger, no `mission_id` (it is not Mission data, and deleting a Run or a Mission must not touch it). Its `CREATE TABLE IF NOT EXISTS` lives in the new file of deliverable 2, with its only reader and writer, and is executed there on every open — `create-axiom-tables-sql.ts` has no room for it (ground truth 2) and stays as it is.
2. **NEW `src/main/runtime/orchestration/db/schema/axiom-schema-steps.ts`** — exported constants and exported function declarations over the database handle (the type `Database.Database` from `../../../../sqlite/sync-database`), no method on the class; at most 110 non-blank lines; no type assertion except `as const` (see Rules); the words `CREATE TABLE` exactly once, in the DDL and in no comment (ground truth 8):
   - `AXIOM_SCHEMA_VERSION` — the number of the last step; 1 in this Task. `AXIOM_UPSTREAM_SCHEMA_VERSION = 43` — the last step of upstream's numbered chain that this build's kernel chain contains.
   - `readAxiomSchemaVersion(db): number` — the `version` of the row; 0 when there is no row; anything that is not a positive integer counts as 0. It expects the table to exist, which it does on every database the constructor has opened.
   - `migrateAxiomSchema(db, appVersion?): void` — first executes the table's DDL; then returns, without a write, when the stored version is at or above `AXIOM_SCHEMA_VERSION` (a stamp from a newer Axiom is left exactly as it is). Otherwise: `BEGIN IMMEDIATE`; read the version again under the lock; run every step above it, in order; write the row; `COMMIT`. Any failure rolls back and is thrown — the same contract as the kernel's `migrate`. Writing the row: when there is none, insert `id = 1`, `version = AXIOM_SCHEMA_VERSION`, `upstream_version = AXIOM_UPSTREAM_SCHEMA_VERSION`, `app_version`, `updated_at`; when there is one, update `version`, `app_version` and `updated_at` only — `upstream_version` belongs to the kernel's chain and is not rewritten here. `app_version` is the second argument; when the argument is left out it is the installed app environment's version, and NULL when no environment is installed (`hasAppEnvironment()`), so the constructor passes nothing.
   - Step 1, the baseline: for each of these eight columns, add it when a `PRAGMA table_info` probe says it is missing (read the probe's rows through `db.prepare(…).all()`, whose rows are typed; `db.pragma(…)` answers `unknown` and would need a cast) — `agent_specs.spec` and `mission_policies.routing` (`TEXT NOT NULL DEFAULT '{}'`), `verification_runs.runtime_epoch` (`TEXT`), `claim_count` (`INTEGER NOT NULL DEFAULT 0`), `worktree_id`, `started_at`, `finished_at`, `batch_id` (`TEXT`) — the definitions `migrate-v45.ts`, `migrate-v46.ts` and `ensure-axiom-columns.ts` use, in that order. Tables, indexes and triggers are not part of the step: the DDL of ground truth 2 supplies them on every open.
   - These fragments are literal — the sidecar looks for them as written: `CREATE TABLE IF NOT EXISTS axiom_schema`, `CHECK(id = 1)`, `upstream_version INTEGER NOT NULL`, `app_version TEXT`, `export const AXIOM_SCHEMA_VERSION`, `export const AXIOM_UPSTREAM_SCHEMA_VERSION = 43`, `export function migrateAxiomSchema`, `export function readAxiomSchemaVersion`, `BEGIN IMMEDIATE`, `ROLLBACK`, `ADD COLUMN`, and in `orchestration-db.ts` the call `migrateAxiomSchema(this.db)`.
   - One comment at the list of steps states the two rules every later step must keep: a step probes before it changes anything, so a database that lost its row is repaired by running all steps again; and a step never removes or redefines something an earlier build's DDL creates when missing, because an older build that opens the database would put it back.
3. **Wiring.** `orchestration-db.ts`: one import and one call, `migrateAxiomSchema(this.db)`, directly after the `migrate` call — Axiom's chain runs after the kernel's, because an Axiom step may depend on a kernel column and never the other way round. `create-tables.ts`: the `ensureAxiomColumns` call and its import go. `ensure-axiom-columns.ts` is deleted (plain `rm`). **What this changes for a test:** the column probes used to run on every open; now they run when the stamp is missing or old. A test that takes a baseline column away from a database the current build made must take the stamp away too, or the database does not stand for an older one. `ensure-axiom-columns.test.ts` therefore gains one statement next to the place where it drops `batch_id` — it deletes the row of `axiom_schema` — and nothing else in it changes: its name, its title and every assertion stay.
4. **The census.** `src/shared/wsl-move/wsl-move-storage-dispositions.ts` gains two entries and nothing else: the new file in `SQLITE_SCHEMA_FILE_DATABASES` as `'orchestration'`, and `orchestration.axiom_schema` in `SQLITE_TABLE_DISPOSITIONS` as a row of its own — `tables('orchestration', ['axiom_schema'], notApplicableDisposition(62, <one sentence: one bookkeeping row with the schema version, no path in it>))` — not in the long `rewrite-desktop` list, because nothing in it is rewritten when a project moves.
