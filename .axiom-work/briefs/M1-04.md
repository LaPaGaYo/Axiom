## Objective

One strongly typed store, constructor-injected with the existing `OrchestrationDb`, that owns every SQL statement against the seven M1 tables — `missions`, `goal_revisions`, `plan_revisions`, `task_stages`, `mission_task_edges`, `mission_policies`, `audit_events` — and nothing else. No business rules: transition legality, readiness, numbering policy and audit *content* belong to MissionController (M1-05); the store offers compare-and-set writes so M1-05 can make transitions transactional and idempotent. No RPC, no runtime access, no migrations, no renderer.

## Facts you can rely on

- `OrchestrationDb` (`src/main/runtime/orchestration/db/orchestration-db.ts`; `new OrchestrationDb(':memory:')` in tests) exposes the raw `SyncDatabase` as `.db` (`prepare(sql).get/all/run`, `exec`, `isTransaction`). `getOrchestrationDb()` lives in a `@ts-nocheck` runtime module, so Axiom code never calls it: the store takes the instance in its constructor (`constructor(private readonly db: OrchestrationDb)`), exactly as orca-mapping §8 prescribes. A later Task adds the single `getAxiomControlPlane()` accessor.
- Transactions: `runLifecycleWriteTransaction(db.db, 'axiom_<op>', () => …)` (`src/main/runtime/orchestration/db/lifecycle-write-transaction-runner.ts`) — `BEGIN IMMEDIATE` at top level, a `SAVEPOINT` when already inside a transaction, so store operations compose inside a caller's transaction. Savepoint names must match `/^[a-z][a-z0-9_]*$/`.
- Ids: `generateId(prefix)` (`db/generated-id.ts`) → `<prefix>_<12 hex>`; use `mission`, `goalrev`, `planrev` prefixes; Task ids are Orca's (`createTask` mints them — M1-05 calls Orca first, then inserts the stage row); edge rows are keyed by task ids; `audit_events.sequence` is `AUTOINCREMENT`.
- Row reads: `SyncDatabase` refuses to cache `SELECT *` — spell out column lists (see `db/row-column-lists.ts` and its test, which pins list ↔ schema against a migrated database). Rows come back untyped; the repository forbids `as` casts in new code except `as const` (`SAFETY:` comments for unavoidable ones). Do not cast rows: parse them. Define one zod row schema per table (snake_case, in `src/main/axiom/db/<table>-rows.ts` or one `axiom-rows.ts` if it stays under the `max-lines` gate) and a small `row-codec.ts` with `readRow(schema, value)` / `readRows(schema, values)` that `schema.parse`s and converts to the camelCase contract objects (`Mission`, `GoalRevision`, `PlanRevision`, `TaskEdge`, `Policy` from `mission-objects.ts`; `TaskStageRecord` and `AuditEvent` are new store types — put their zod schemas in `src/shared/axiom-contract/mission-objects.ts` only if the renderer/CLI will need them (TaskStageRecord yes: `taskId`, `missionId`, `planRevisionId`, `stage`, `previousStage`, `spec`, `retryPolicy`, `attemptCount`, `updatedAt`; AuditEvent yes, minimal). JSON columns are `JSON.parse`d then validated by the contract schema; invalid stored JSON throws a clear error naming table/row/column.
- Timestamps: let SQLite default `created_at` / `updated_at` with `datetime('now')`; set `updated_at = datetime('now')` on every UPDATE.
- The DDL has no CHECK constraints on enum columns (M1-03, by design): the store validates every enum through the contract zod schemas before writing (`MissionStatusSchema.parse(...)` etc.). `mission_policies.nested_worker_max_depth` is CHECK-pinned to 1.

   - goal / plan revisions: `insertGoalRevision(body, { missionId, status })` → the inserted `GoalRevision` with `revision = (max revision of the Mission) + 1`, computed inside a savepoint; `getGoalRevision`, `listGoalRevisions(missionId)`, `updateGoalRevisionStatus({ id, from, to })` CAS; the same five for plan revisions (`insertPlanRevision` also takes `supersedesId?`), plus `updatePlanRevisionStatus({ id, from, to, rejectedReason? })`;
