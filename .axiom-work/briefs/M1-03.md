## Objective

Add every Axiom side table the architecture needs for M1–M4 in one additive migration, v43, so later milestones only add columns (v44+) and never bump the schema for a new table. Fresh databases get the tables from `createTables`; an existing v42 database gets them from `migrateV43`; nothing in any existing Orca table, CHECK enum, trigger or view changes. No store code, no RPC, no renderer: M1-04 writes the SQL that uses these tables.

## Facts you can rely on

- Entry points: `src/main/runtime/orchestration/db/schema/create-tables.ts` (`createTables` runs `createCoreTablesSql()` + `createGraphTablesSql()` on every open, all `CREATE … IF NOT EXISTS`), `schema/migrate.ts` (chain in one `BEGIN IMMEDIATE` transaction, `user_version` bumped to `SCHEMA_VERSION` at the end), `schema/migrate-v42.ts` (the pattern to copy: `if (current >= 42) return`, guarded `ALTER TABLE … ADD COLUMN` via `this.hasColumn`, `CREATE INDEX IF NOT EXISTS`), `db/contract-constants.ts` (`SCHEMA_VERSION = 42` with the version-history comment lines), `schema/schema-column-probes.ts` (`hasColumn`). The downgrade/skew probe `src/main/runtime/orchestration/orchestration-schema-version-skew.ts` (`hasCompletePostV6Schema`) probes columns of Orca tables only; new tables are transparent to it and must stay that way (do not add Axiom tables to `POST_V6_COLUMNS` / `VERSIONED_POST_V6_COLUMNS`).
- Conventions in the existing DDL (`create-core-tables-sql.ts`, `create-graph-tables-sql.ts`): snake_case; `TEXT PRIMARY KEY` ids; timestamps `TEXT NOT NULL DEFAULT (datetime('now'))`; JSON in `TEXT` columns with `DEFAULT '[]'` / `'{}'` where a default makes sense; **no `FOREIGN KEY` / `REFERENCES`** (upstream uses none; foreign keys are not enabled); cleanup of dependent rows via `AFTER DELETE` triggers (`ADDITIVE_LIFECYCLE_DELETE_TRIGGERS_SQL` in `create-graph-tables-sql.ts`). Use `CREATE TRIGGER IF NOT EXISTS` for the new triggers (they are new names, so the "drop and recreate by name" dance of v42 is not needed).
- Tests to copy: `schema/structured-pointer-schema-migration.test.ts` (seed a database stamped at the previous version in a temp dir, open `OrchestrationDb`, assert `user_version === SCHEMA_VERSION` and behaviour), `orchestration-all-start-versions-migration.test.ts` (loops `0 … SCHEMA_VERSION-1`, will cover v43 automatically — it must keep passing), `orchestration-orca-session-column-migration.test.ts` (sqlite_master assertions). `new OrchestrationDb(':memory:')` works for fresh-DB tests; use `mkdtempSync` temp dirs for file tests (Windows-safe pattern in those files).
- Why no CHECK constraints on Axiom status columns: the upstream lesson (`migrate-v39.ts`, orca-mapping §6) is that widening a CHECK means rebuilding the table, and old binaries crash on unknown enum values. Axiom enum validation happens in `src/shared/axiom-contract` (zod) at every write boundary (M1-04+), so the DDL takes `TEXT NOT NULL` for every status/stage/kind column. Put that reason in a `// Why:` comment at the top of the DDL module. The one exception is a literal, never-widened column: `mission_policies.nested_worker_max_depth INTEGER NOT NULL DEFAULT 1 CHECK(nested_worker_max_depth = 1)` (D11 / C7 pins it to 1).
