M3-03 checks *which paths* a Candidate changes (scope, secrets, dangerous paths). M3-04 made the fix loop automatic: a failed Candidate is handed back to a Worker whose context says "do not weaken, skip or delete tests". Nothing enforces that sentence yet — a Worker can make the checks pass by skipping a test or deleting an assertion. This Task adds deterministic *content* rules on the same three-dot diff, sends such Candidates to a human, and closes the non-code path (a Task without `requiredEvidence` must deliver Artifacts and is never PASSed by repository gates alone). No kernel (Orca) change, no schema migration, no renderer change, no new dependency.

## Objective

1. **Removed lines in the Candidate diff** (`verification/candidate-diff.ts`): `parsePatch` collects the removed lines of each path into `removedText: Map<string, string>` exactly as it collects `addedText` (same section pairing — a `T` entry owns two sections; only lines inside hunks; the `--- a/…` / `+++ b/…` headers come before the first `@@` and are never content). An incomplete patch (`patchComplete: false`) keeps both maps empty, as today.
2. **Content tamper rules** — new pure module `verification/test-tampering.ts`: `detectTestTampering({ changes, addedText, removedText, testPathPatterns, allowedPaths })` → findings `{ path, rule, count }[]` sorted by path, then rule. A *test file* is a path matching any `testPathPatterns` entry (the shared `matchesPathPattern` semantics of `path-patterns.ts`). Counts are **net per file**: occurrences in added lines minus occurrences in removed lines (so moving or reformatting a line is neutral). Rules:
   - `test_file_deleted` (count 1): a test file whose change status is `D` — **except** when an added (`A`) test file has exactly the same content (pure move / rename: the deleted file's removed text equals the added file's added text), or when an `allowedPaths` entry, normalised, equals that exact path (the Task was told to delete it).
   - `test_skip_added`: in a test file, the net number of skip / focus / pending markers is positive. Markers (JavaScript regular expressions, global, ASCII only):
     `/\b(?:describe|it|test|suite|context|bench)\.(?:skip|only|todo|skipIf|runIf|fails)\b/g`, `/\b(?:xit|xtest|xdescribe|xcontext|xsuite|fit|fdescribe|ftest)\s*\(/g`, `/@pytest\.mark\.(?:skip|skipif|xfail)\b/g`, `/\bpytest\.skip\s*\(/g`, `/@unittest\.skip/g`, `/\bt\.Skip(?:f|Now)?\s*\(/g`.
   - `assertions_reduced`: in a test file that is not deleted, the net number of assertion calls is negative (count = the decrease). Assertion patterns: `/\b(?:expect|assert)(?:\.\w+)*\s*\(/g`, `/\bassert[A-Z]\w*\s*\(/g`, `/^\s*assert\s/gm`, `/\.should\b/g`, `/\bt\.(?:Error|Errorf|Fatal|Fatalf|Fail|FailNow)\s*\(/g`.
   - `suppression_added`: in **any** file, the net number of lint / type-check / coverage suppressions is positive. Pattern: `/(?:eslint-disable|oxlint-disable|biome-ignore|@ts-ignore|@ts-nocheck|@ts-expect-error|#\s*noqa\b|#\s*type:\s*ignore|pylint:\s*disable|\bnolint\b|istanbul\s+ignore|c8\s+ignore|v8\s+ignore)/g`.
   Findings never store matched text (paths, rule names and counts only).
3. **Gate integration** (`diff-gate.ts`, `verification-verdict.ts`, `verification-settlement.ts`): `evaluateDiffGate` runs the tamper rules when the patch is complete; a finding gives `INCONCLUSIVE(test_tampering)` (escalation `human`), ranked after `diff_too_large` and before `dangerous_change` (secret / scope FAILs and `checks_failed` still win — then the findings travel as evidence into the fix loop). `summarizeDiffGate` adds `tampering` (list capped like the others) and `counts.tampering`; `gateAuditFindings` adds `tampering` for `test_tampering`. New `VerificationRules` key **`testPathPatterns: string[]`**, default `['**/*.test.*', '**/*.spec.*', '**/__tests__/**', '**/test_*.py', '**/*_test.py', '**/*_test.go']`; a policy value replaces the default list (like `dangerousPathPatterns`). Policy update and the CLI rules file pick the key up through the shared schema.
4. **Worker Artifact checks and non-code Tasks** — new module `verification/worker-artifacts.ts`, called from `runVerificationChecks` after the plan has run: read the Candidate's Submission (`store.getSubmissionByDispatch(candidate.attemptId)`) and check every Artifact id in `report.artifacts`: readable through `artifacts.read` (else `unreadable`), non-empty (`empty`), text media types (`text/*`, `application/json`, `application/*+json`) decode as UTF-8 with a fatal decoder (`invalid_utf8`), JSON media types parse (`invalid_json`). Record `verdictDetail.artifacts = { required, checked: [{ id, kind, mediaType, bytes, problem? }], counts }` (list capped at 50) for **every** run; `required` is true for a non-code Task.
   - A **non-code Task** is one whose `requiredEvidence` is empty after trimming (repository gates and setup commands may still run).
   - Verdict (`decideVerificationVerdict` gains the non-code flag and the artifact result): for a non-code Task, no referenced Artifact → `FAIL(artifact_missing)`; an `empty`, `invalid_utf8` or `invalid_json` Artifact → `FAIL(artifact_invalid)`; both ranked right after `checks_failed`. An `unreadable` Artifact is the store's problem, not the Worker's: `INCONCLUSIVE(environment)` with `detail: 'artifact_unreadable'` and escalation `human`, ranked with the diff-unavailable `environment`. Otherwise a non-code Task is **never PASS**: where the old rules would give `PASS` or `INCONCLUSIVE(no_checks)`, give `INCONCLUSIVE(non_code)` with escalation `human` for `nonCodeTasks: 'human_confirm'` and `rules.inconclusiveRouting` for `'artifact_only'`. `non_code` replaces `no_checks` (update its tests and docs). For code Tasks the Artifact result is evidence only and never changes the verdict.
   - Final precedence (D65 revision ⑨): `secret_detected` → `scope_violation` → `checks_failed` → `artifact_missing` / `artifact_invalid` (non-code) → `environment` (diff unavailable, or a non-code Artifact unreadable) → `diff_too_large` → `test_tampering` → `dangerous_change` → `environment` (environmental check) → `flaky` / `known_flaky` → `environment` (skipped check) → `non_code` → `PASS`. `policy_invalid` is unchanged.
5. **Fix-loop evidence** (`context-builder/previous-attempt.ts`): when the failed run's `verdictDetail.diff.tampering` is non-empty, add `Test tampering findings (path, rule, net count):` with one line each and `Restore the removed tests or assertions and remove the added skips or suppressions; the next verification applies the same rules.`; when `verdictDetail.artifacts` reports problems for a non-code Task, add `Artifact problems:` with `id (problem)` lines. Keep every existing line and bound.
6. **Contracts** (one sentence each, appended to the existing M3-03 sentences): Worker contract in `render.ts` section 4 — `Deleting or skipping tests, removing assertions from a test file, or adding lint, type-check or coverage suppressions sends the Candidate to human review (test_tampering).    - new `tests/e2e/mission-tamper-gate.spec.ts` (skeleton of `mission-diff-gate.spec.ts`: setup install via `--verification-rules-file`, `holdWorkers`, `runVerification`, `maxAttempts: 1`, `extraAllowedPaths: ['src/domain/date.test.ts', 'src/domain/guards.test.ts', 'src/domain/clock.test.ts']`): T01 `test-skip`, T02 `assertion-drop`, T03 `suppression` → each run `INCONCLUSIVE` with `verdictDetail` `{ reason: 'test_tampering', escalation: 'human' }`, every check `pass` (the tampering is caught although the tests pass), `diff.tampering` equal to `[{ path: 'src/domain/date.test.ts', rule: 'test_skip_added', count: 1 }]`, `[{ path: 'src/domain/guards.test.ts', rule: 'assertions_reduced', count: 1 }]`, `[{ path: 'src/domain/clock.test.ts', rule: 'suppression_added', count: 1 }]`, `diff.scopeViolations` empty; Tasks stay `VERIFYING`; a `verification.inconclusive` audit per run carries the same `tampering`; three submissions, no error lines.
