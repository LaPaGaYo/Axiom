# Task M3-06-2a-3 — A Codex usage limit waits for the reset time Codex itself recorded (D88 item 6 and its 2026-11-10 revision row)

Planner brief, 2026-11-10 (verifier). M3-06-2a made an interrupted Task wait; M3-06-2a-2 made that wait an account-level cooldown. For Claude the wait ends at the reset time the provider reported. For Codex there is no reset time: the wait is one ladder step, the cooldown lasts as long, and every Task still reaches `BLOCKED('environment')` after its own three interruptions — about six minutes after a five-hour window ran out. **This Task gives a Codex usage limit its reset time: a bounded, read-only look at the Worker's own session record (rollout), interpreted by the kernel's existing classifier** (D88 revision row of 2026-11-10: the source is the Worker's own rollout, not the kernel's polled snapshot). Nothing else changes: the class still comes from the text rule, and a missing or unreadable record leaves exactly today's behaviour. Not here: pacing before a limit is reached; any read of the kernel's polled rate-limit state; preserving the interrupted worktree (M3-06-2b); resuming the harness session (M3-06-2c); supervisor rules (M3-06-3).

## Ground truth (verifier, 2026-11-10, main `ea70828e97`; every function named here was read in full unless marked)

1. **Where a Codex failure is classified and settled.** `execution/attempt-exit-submission.ts` `submitExit` (async) reads `events.jsonl` after the exit marker, parses it (`parseHeadlessWorkerEvents`, which returns the first stdout event's `thread_id` as `providerSessionId`) and, for a failed exit, calls `execution/attempt-exit-failure.ts` `settleHeadlessExitFailure(runtime, { attemptId, provider, eventsText, events, … })` — its only caller. That function is synchronous: it calls `classifyHeadlessFailure({ eventsText, provider, now })` (`execution/attempt-failure-classification.ts`, pure, never throws) and then runs one transaction `headless_exit_failure` (fail the dispatch, audit `attempt.failed` with `failure`, settle). For Codex the classifier has only the text halves: the quota half (`quota | rate.?limit | usage limit | insufficient.credit | 429` on the last error) gives `{ class: 'usage_limit', retryable: true, source: 'text' }` with no `resetsAt` and no `window`.
2. **What a reset time does once it is on the failure.** `execution/attempt-interruption.ts` `settleInterruptedAttempt` copies `failure.resetsAt` onto the `attempt.continue` payload and `execution/interruption-policy.ts` `interruptionDueAt` uses it for `dueAt` (reset + 60 s; only when `now < reset ≤ now + 8 days`, else the ladder). The Task-level `backoff` (M3-06-2a) and the account cooldown (M3-06-2a-2, `agent-factory/account-cooldown.ts`: until the latest waiting `dueAt`) follow from that `dueAt` without further code. `src/shared/axiom-contract/attempt-failure.ts`: `resetsAt` is an ISO datetime allowed only on `usage_limit`; `window` is `session | weekly | weeklyModel | credits`.
3. **Which account home the Attempt ran with.** The audit `attempt.headless_prepared` (object id = the dispatch id) stores `combination.effective.codexHome = { kind: 'account', path }`. `execution/attempt-account.ts` `readAttemptAccount` (M3-06-2a-2) already finds and parses that row with zod, but returns only the one-way key `{ provider, key }`; the path itself is not exposed. A headless Codex Worker is launched only with a `kind: 'account'` home (`execution/headless-worker-launch.ts`), never with `~/.codex`.
4. **The kernel already interprets Codex limit windows.** `src/main/codex/codex-usage-limits.ts` `CodexUsageLimits`: `observe(kind, payload)` keeps the account's usage as last reported when `kind` is `'notification:account/rateLimits/updated'` and `payload.rateLimits.limitId` is absent or `'codex'` (another limit id is one model's own bucket and is ignored; updates are merged, and the merge skips only `undefined`, so a `null` window replaces an earlier one). `failure(payload)` returns the `usageLimitReached` fact only for an app-server `error` frame whose `error.codexErrorInfo` is `usageLimitExceeded` or `rateLimitExceeded`; its `usageLimit { window?, resetsAt? }` (`resetsAt` in epoch ms) comes from a private rule — every window with `usedPercent >= 100` must reset, the latest reset is the one, none when a spent window gave no reset; `rateLimitReachedType` ending in `credits_depleted` names the window `credits`. The fields are the app-server's camelCase: `limitId`, `primary` / `secondary` `{ usedPercent, windowDurationMins, resetsAt (epoch seconds) }`, `rateLimitReachedType`, `planType`. No public method returns the limit without an error frame. Verified by running the unmodified class on rollout-shaped records mapped to those names: one spent five-hour window → `{ window: 'session', resetsAt }`; a single spent weekly window → `{ window: 'weekly', resetsAt }`; two spent windows → the later reset and no window; a spent window without a reset → the window only; nothing spent, no records, or records under another limit id → no `usageLimit`; a later record with `secondary: null` drops an earlier spent secondary.

## Outcome

After this Task, when a Codex Worker dies on a usage limit and its own session record shows which window is spent and when it resets, the Task waits until that time (plus the existing slack), the account cools until then, and the next Attempt starts by itself — the same behaviour Claude has had since M3-06-2a. When the record is missing, unreadable or shows no spent window, everything is exactly as today: the ladder and three strikes.

## Deliverables

1. **Reader** (new module under `src/main/axiom/execution/`; read-only, bounded, never throws). Input: the account home path of this Attempt, the Codex thread id, the Attempt's start time, a clock. Output: `{ window?, resetsAt? }` or nothing.
   - **Locate.** Thread id: accepted only as a plain token (no path separator, no dot segment, no glob character, bounded length). File: `rollout-*-<thread id>.jsonl` in the date directories from the Attempt's start day to today (local time) under `<home>/sessions`; the resolved file must lie inside `<home>/sessions` (a symlink that leaves it reads nothing); if several match, take the most recently modified. Read at most the last 256 KiB of that one file and drop a leading partial line.
   - **Extract** from `event_msg` / `token_count` lines only, and from their `rate_limits` only: `limit_id`, `primary` and `secondary` (`used_percent`, `window_minutes`, `resets_at`), `rate_limit_reached_type`. Nothing else in the file is kept past the parse, logged, audited or returned — not `plan_type`, `credits`, `limit_name`, `info`, `session_meta`, nor any message.
   - **Interpret** with the kernel class, not with code of your own (ground truth 4): map those fields to the app-server names — a window that is `null` stays `null` —, feed each record in file order through one `CodexUsageLimits` (`observe('notification:account/rateLimits/updated', { rateLimits })`), then ask `failure({ error: { codexErrorInfo: 'usageLimitExceeded' } })` and take its `usageLimit`. Axiom code compares no percentage, chooses no window and names no window.
   - **Failure semantics**: no thread id, an unsafe id, no home, no file, an unreadable or malformed file, a kernel exception — no evidence. Never a thrown error, never a write into the account home, never a delay beyond the bounded read.
2. **Settlement.** Only when the Worker is Codex and the M3-06-2a text rule classified the failure `usage_limit` does the host consult the reader; a Claude Worker and every other Codex failure never open a file. The account home comes from the launch audit of this dispatch (extend `attempt-account.ts`: one audit read serves both the key and the path; the path still reaches no effect, audit or log). The evidence is gathered before the `headless_exit_failure` transaction opens — nothing is awaited inside it. With evidence, the `failure` gains `window` as returned and `resetsAt` only when `now < resetsAt ≤ now + 8 days` (the existing bound); the audit, the continuation payload, its `dueAt` and with it the account cooldown follow through the existing code. `source` stays `text`: the text decided the class. A rollout never decides or changes the class and never turns a `failed` into an interruption.
3. **Stub and E2E** (host, verifier-run; you cannot run Electron — see Rules). The Codex stub gains an opt-in interruption mode that speaks the real protocol: it emits `thread.started` first, writes a rollout file where Codex would (ground truth 5) — a `session_meta` line and a `token_count` line with `info: null` whose `rate_limits` has `limit_id: 'codex'`, a spent primary window (`used_percent: 100`, `window_minutes: 300`, `resets_at` several seconds ahead) and an unspent secondary one, plus recognisable decoy values for `plan_type`, `credits.balance` and `session_meta.creator_account_id` — then `turn.failed` with its usage-limit message, and exits non-zero. Opt-in per Task (a marker file, like the existing ones), so the two existing Codex cases of ground truth 6 keep their timing; both helper files are at the line limit, so the new stub code lives in a new helper module that the stub source includes. New second case in `tests/e2e/mission-account-cooldown.spec.ts`, modelled on the first (same Tasks, slot and scenario; that path ran green on the host) but with `interruptionBackoffMs: [100, 200, 300]`, so only the recorded reset can explain a wait of seconds: Task X is admitted and hits the limit once; its `attempt.failed` audit has `failure { class: 'usage_limit', retryable: true, source: 'text', window: 'session', resetsAt }` and contains none of the decoy values; the continuation is `pending` with `dueAt` equal to that `resetsAt`; while it is pending and not yet due, Task Y is `READY` without a binding and its `task.admission_refused` audit reports `account_cooldown` until that `dueAt`; then, without any call from the test, both Tasks get a Submission, Y has exactly one Attempt and its `attempt.admitted` audit is not earlier than that `dueAt`, X has Attempts 1 and 2. Poll for conditions; no sleeps. Cover the new stub mode in the stub's `*.unit.test.ts` (it runs the stub as a process: assert the file's place, its two line kinds and that the reader, given that home and thread id, returns the window and the reset).
