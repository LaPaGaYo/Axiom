## Ground truth (verifier, 2026-11-03, main `cab80692ee`)

1. **Two unlinked lists.** `TaskSpecSchema` (`shared/axiom-contract/mission-objects.ts`) has `acceptanceCriteria: string[]` (prose) and `requiredEvidence: string[]` (since M3-08i: exact shell commands, validated by `validateEvidenceCommands` at `plan.propose` and `REQUEST_SUBTASK`, run verbatim by `resolveVerificationPlan` as `source: 'evidence'` steps). Nothing links a criterion to the command that proves it, so a verdict can only say "checks failed", the fix context lists every criterion under `Not yet demonstrated:` whether it was demonstrated or not (`context-builder/previous-attempt.ts` ~line 268), and the plan reviewer cannot see which criteria are machine-checked at all. The fixture's own decomposition already pairs them (`scenarios/goal/decomposition.json` → `task.acceptance: [{ must, command }]`); `tests/e2e/helpers/fixture-plan-proposal.ts` and `fixtures/axiom-claude-planner-stub.cjs` flatten that pairing into the two lists today.
2. **The non-code path is a side effect of an empty list.** `runVerificationChecks` (`verification/verification-checks.ts`) derives `nonCodeTask = !task.spec.requiredEvidence.some(…)`; `decideVerificationVerdict` (`verification/verification-verdict.ts`) then requires a readable Artifact (`artifact_missing` / `artifact_invalid`) and ends `INCONCLUSIVE / non_code` with `rules.nonCodeTasks` routing. A Task that mixes machine-checkable and human-judged criteria has no representation: either everything is a command or nothing is.

## Outcome

After this Task: a Task's acceptance criteria are objects `{ text, check }` where `check` is `command` (an exact shell command inside the D85 boundary), `artifact` (a readable, non-empty Artifact the submission references) or `human` (only a person can judge it); the Planner contract, the plan validator, `REQUEST_SUBTASK`, the CLI and the plan review panel all speak that shape; `requiredEvidence` is rejected in new proposals and read compatibly from persisted rows; verification builds its plan from the criteria, records a per-criterion result in `verdictDetail.acceptance[]`, ends `PASS` only when every deterministic criterion holds and no human criterion remains, and ends `INCONCLUSIVE` for a human when only human criteria remain; the next Attempt's context shows each criterion's status instead of the whole list, and a failure that has survived several Attempts says so.

## Deliverables

1. **Contract** (`shared/axiom-contract/mission-objects.ts`, new `shared/axiom-contract/acceptance.ts`, `agent-spec.ts`, `message-params.ts`): `AcceptanceCheckSchema = z.discriminatedUnion('kind', [ { kind: 'command', command: Text }, { kind: 'artifact', artifactKind?: ArtifactKind }, { kind: 'human' } ])` and `AcceptanceCriterionSchema = z.strictObject({ text: Text, check: AcceptanceCheckSchema })`, both with `.describe(…)` (what each kind means; `command` entries follow the exact-shell-command rule; `human` only when neither a command nor an Artifact can prove the criterion). `TaskSpecSchema.acceptanceCriteria` becomes `z.array(z.union([Text, AcceptanceCriterionSchema]))` (a bare string is accepted only for persisted rows — see validation) and `requiredEvidence` becomes `z.array(Text).optional()` marked deprecated in its description ("retired by D85 rule 2: put the command on the criterion"). One pure function `resolveAcceptance(spec: Pick<TaskSpec, 'acceptanceCriteria' | 'requiredEvidence'>): AcceptanceCriterion[]` in `acceptance.ts` is the only reader: a string becomes `{ text, check: { kind: 'human' } }`; every legacy `requiredEvidence` command that no criterion already carries becomes `{ text: 'Command passes: <command>', check: { kind: 'command', command } }` appended in order; the result is what every consumer below uses (no consumer reads the raw fields again). `acceptanceCommands(criteria)` returns the deduplicated command list in criterion order. `AgentSpecSchema.acceptanceCriteria` takes the same union (agent-factory passes the resolved criteria; say in the report which content-addressed pins moved). `SubtaskRequestSchema`: `acceptanceCriteria: z.array(AcceptanceCriterionSchema).min(1)`, `requiredEvidence` removed (strict). Unit tests: resolution of strings, objects, legacy commands and the dedupe; schema accepts the three kinds, rejects unknown kinds and a `command` without `command`.
