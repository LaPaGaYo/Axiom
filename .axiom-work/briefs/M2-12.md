## Why (host evidence, `.axiom-work/logs/chain-20261020-075835.log` on the verifier's diag branch)

The M2 exit e2e crashed one Worker's agent process (D49 provider, exit 137 after `ACK`). 120 s later the Task was still `RUNNING`: Orca's PTY runs the agent **inside an interactive shell**, so the agent's exit leaves the shell at its prompt and the PTY `connected: true`; the kernel only fails a dispatch on **PTY** exit (`failActiveDispatchOnExit` in `orca-runtime-subscribe-to-terminal-resize.ts`), and Axiom's `inspectWorkerTerminal` folds a connected PTY to `live`. Screen read of the crashed worker: `… 'codex' '--dangerously-bypass-approvals-and-sandbox' / OpenAI Codex / model: e2e / ACK / henry@… attempt-task_… %` — the prompt is back; `worker-show` reported kernel `state: ready`, `attempt show` `liveness: live`. Nothing turns that into `FAILED` before `maxRuntimeMinutes` (45 by default). Orca itself has no deterministic consumer for this case (its coordinator LLM reads the terminal); Axiom has no coordinator LLM, so the Control Plane must observe the exit from **execution-host evidence** (invariant 9: the execution host owns execution truth; the verdict vocabulary `live / unverifiable / exited` is unchanged).

## Objective

1. **Agent-exit evidence for TUI-lane Attempts (new recovery rule c′, D59).**
   - Runtime accessor (additive, in-process, no RPC): `OrcaRuntimeService.confirmTerminalShellForeground(handle: string): Promise<boolean>` next to `inspectTerminalProcessIncarnationLiveness` in `src/main/runtime/orca-runtime-subscribe-to-terminal-resize.ts` (the chain file is `@ts-nocheck` by convention; keep the method fully typed anyway). Resolve the live PTY id exactly as `getOrchestrationDispatchAuthority` does (`this.getLivePtyForHandle(handle)?.pty.ptyId ?? this.resolveLiveLeafForHandle(handle)?.ptyId ?? null`, inside try/catch). Return `false` when there is no live PTY, when `this.ptyController?.confirmShellForeground` is absent, when the call throws or exceeds `PTY_CONTROLLER_LIST_TIMEOUT_MS` (`withTimeoutResult`), and `true` only when the controller answers `true`. `confirmShellForeground` already reaches the daemon (`daemon-pty-process-inspection.ts` → `daemon-request-router.ts` → `foreground-process-tracker.ts` → `confirmShellForegroundProcess`): fresh process-table proof that the spawned shell owns the PTY foreground (shell row `+`, no stopped descendant; Windows: shell alone in the job). SSH adapters answer `false` → no change for remote workers.
   - New module `src/main/axiom/recovery/agent-exit-observation.ts` exporting `observeAgentExit(ctx: RecoveryContext, binding: AttemptBinding, observation: Awaited<ReturnType<typeof inspectWorkerTerminal>>, worker: WorkerDispatchRow | null | undefined): Promise<{ exited: false } | { exited: true; evidence: 'shell_foreground' }>`. It answers `{ exited: true, evidence: 'shell_foreground' }` only when ALL hold: `observation.status === 'live'`, `observation.exact === true`, `observation.terminal !== null` (PTY lane — structured workers carry `terminal: null`), `worker?.state === 'ready'` (readiness settled: the agent was running when the preamble was accepted; `starting`, `start_unknown`, `stopping`, `stop_unknown`, terminal states never qualify), and `await ctx.runtime.confirmTerminalShellForeground(observation.terminal.handle)` is `true`. Everything else → `{ exited: false }`. No caching, no counters: one fresh proof per reconcile tick is the rule.
   - `reconcileAttempt` (`attempt-reconciliation.ts`): call `observeAgentExit` right after `inspectWorkerTerminal` (both awaits precede the durable re-read — the comment "Inspection and kernel calls await host IO. Always re-read durable authority afterwards" must stay true). When it reports exit, fold `entry.liveness = 'exited'` so the existing branches run unchanged, except that rule c's `attempt.failed` audit `after` gains `evidence: 'shell_foreground'` in this case (reason stays `process_exited`; `failDispatch(dispatchId, 'Worker agent exited without a Submission', { workerProcessExited: true, terminationReason: 'process_exited' })` — the message text may differ from the PTY-exit one so the two cases are distinguishable in `last_error`). `reconcilePlanner` receives the folded entry; in its `exited` branch, `planner.attempt_failed` gains `evidence: 'shell_foreground'` when the exit came from this observation (pass the observation result through, do not re-probe).
   - Nothing changes in `inspectWorkerTerminal`, `foldAttemptLiveness`, `axiom.attempt.show/list` or the fleet projection: they keep reporting the PTY verdict. Document (control-plane.md) that `attempt show` can report `live` for up to one reconcile interval after the agent process exited and that reconciliation is the authority that turns it into `FAILED` + retry.

2. **`attempt.failed` on kernel-first exits (rule b).** When the kernel has already failed the dispatch before reconciliation runs (`failActiveDispatchOnExit` → `worker.state === 'failed'`), the `terminalReasons` branch settles the Task without any `attempt.failed` audit, so a FAILED Attempt can have no failure event. In that branch, when `worker.state === 'failed'` and `lastAttemptAudit(ctx, binding, 'attempt.failed')` is absent, write `attempt.failed` with `{ reason: 'kernel_failed', lastError: worker.last_error ?? null }` inside the same `recovery_terminal` transaction, before `settle(...)`; idempotent across ticks (the `auditAttempt` dedupe plus the `lastAttemptAudit` guard). `stopped` / `abandoned` keep their existing behaviour (their audits are written where Axiom initiated the stop/abandon; a kernel-first stop stays out of scope — say so in the report if you see it matter).

3. **Boot-time scheduling of READY Tasks.** `startAxiomControlPlane` runs `recover()` → `recoverMission` → `recomputeReadiness`, which triggers a scheduler round only when readiness actually moved a Task. A Mission persisted as `EXECUTING` with Tasks already `READY` (e.g. the app quit between a settlement and the next round, or a launch was in flight) therefore gets no round until some later stage change. First write the RED test in `src/main/axiom/control-plane-boot.test.ts` (persisted EXECUTING Mission + READY Task + no bindings → boot → expect one `scheduleRound(missionId, 'resume')`; stub `launch`); then, in `control-plane-boot.ts`, after the consumers are synced, trigger `void plane.scheduler.scheduleRound(mission.id, 'resume')` (with the same `.catch` + `console.warn` pattern as `control-plane.ts`) for every `report.missions` entry whose status is `EXECUTING` and that is not `blocked`. `scheduleRound` coalesces per Mission and audits `scheduler.round` only when it admits or blocks, so a Mission with nothing READY stays audit-silent; the paused / blocked / terminal statuses never get a round. If the RED test turns out GREEN on main (the gap is not real), keep the test, make no boot change, and say so in the report.
