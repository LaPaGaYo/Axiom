# Task M3-06-2a — An interrupted Attempt is classified, does not burn the retry budget, and continues on its own when the cause has passed (D88 items 1–5, D68 item 1)

Planner brief, 2026-11-09 (verifier). D88 splits "what happens to an Attempt that ends without a Submission" into layers. **This Task is the first: classify the failure, stop counting environmental interruptions against the Task, wait (until the provider's reset time, or a short ladder), continue automatically as a new Attempt, and hand the Task to a person when waiting cannot help.** Not here: account-level cooldown and the read-only port onto the kernel's rate-limit state (M3-06-2a-2, next); preserving the interrupted worktree and continuing from it (M3-06-2b); resuming the harness session (M3-06-2c, after a real-harness probe); supervisor rules (M3-06-3).

## Outcome

After this Task, when a headless Attempt ends without a Submission the host records **why** in one typed shape, and three things follow from it deterministically. (a) A failure that is the Worker's own work (`failed`) behaves exactly as today. (b) An environmental interruption that can pass on its own (usage limit, provider outage, the app restarted under the Worker, the harness died before producing any event) does not count against `maxAttempts`; the Task returns to `READY` but is not admitted before a durable not-before time — the provider's reset time when it is known, otherwise a short ladder (1, then 5 minutes) — and at that time a new Attempt (seq + 1) starts by itself. (c) An interruption that waiting cannot fix (sign-in, billing, or the third consecutive interruption) blocks the Task as `BLOCKED('environment')` with a pending item, and a person resumes it with `axiom.task.adjust`. A restart during the wait loses nothing.

## Deliverables

1. **Contract** (`src/shared/axiom-contract/`): a failure schema — `class: 'usage_limit' | 'provider_error' | 'transport_error' | 'permission_error' | 'validation_error' | 'unknown'`, `retryable: boolean`, `resetsAt?` (ISO datetime, `usage_limit` only), `window?` (`session | weekly | weeklyModel | credits`), `source: 'structured' | 'text' | 'absent'`. `EFFECT_KINDS` gains `attempt.continue` with a strict payload `{ taskId, seq, chain, failureClass, resetsAt? }` (`seq` = the interrupted Attempt, `chain` = how many consecutive interruptions this is, from 1). The host-only blocked reason `environment` exists for stored / routed `BLOCKED` messages; the Worker-facing params and the CLI verb still accept only today's three reasons (a Worker cannot declare `environment`).
2. **Classification** (new module under `src/main/axiom/execution/`; pure, never throws — any internal error yields `{ class: 'unknown', source: 'absent' }` and rule (g) below):
   - **Claude, structured.** Feed every `events.jsonl` line through one `ClaudeUsageLimits` instance (ground truth 8) — do not parse `rate_limit_info` yourself. Then, first match wins: (a) the kernel classifier recognised a refusal → `usage_limit`, `retryable: true`, `resetsAt` / `window` from `failure.usageLimit`; (b) assistant `error` ∈ `authentication_failed | oauth_org_not_allowed | account_on_hold | verification_required | cloud_credential_error` → `permission_error`, not retryable; (c) `billing_error` → `usage_limit`, not retryable; (d) `overloaded | server_error`, or a failed result with `api_error_status` 408 / 409 / ≥ 500 → `provider_error`, retryable; (e) `invalid_request | model_not_found | max_output_tokens`, or `api_error_status` 400 / 404 / 413 / 422, or `terminal_reason` `prompt_too_long` → `validation_error`; (f) `api_error_status` 401 / 403 → `permission_error`, not retryable. `source: 'structured'` for all of these.
   - **Codex, text** (no structure exists, ground truth 10): today's regex split in two, nothing added — the quota half (`quota | rate.?limit | usage limit | insufficient.credit | 429`) → `usage_limit`, retryable, no `resetsAt`; the sign-in half (`auth… | unauthori[sz]ed | login | log(ged)? in | invalid.token | 401`) → `permission_error`, **retryable** (text is weak evidence: it gets the ladder and three strikes, never the immediate block). `source: 'text'`. The same two patterns are the fallback for a Claude failure that matched none of (a)–(f).
   - **(g) Otherwise**: no events at all → `unknown`, retryable, `source: 'absent'` (D68: exited before any output); anything else → `unknown`, not an interruption.
   - **Interrupted or failed**: `usage_limit`, `provider_error`, `permission_error` and the no-events case are interruptions; `validation_error` and every other `unknown` are `failed` and keep today's path byte for byte. `transport_error` is in the vocabulary but nothing produces it in this Task (no reliable signal in either stream yet) — say so in the docs.
   - A `resetsAt` is used only when `now < resetsAt ≤ now + 8 days`; otherwise it is dropped and the ladder applies.
3. **Settlement.** In `submitExit`'s failure branch the audit keeps every field it has and gains `failure` (the shape in 1) for interruptions and failures alike; `settlement.kind` stays `interrupted | failed`. For an interruption, one transaction (the existing `headless_exit_failure`) does: `failDispatch`, the audit, `RUNNING → NEEDS_FIX('interrupted')` **reversing the admission's `attemptCount` increment** (after it, `attemptCount` is what it was before this Attempt was admitted; seq numbering is untouched), then either
   - **wait**: `→ READY('retry_after_interruption')` + `effects.enqueue({ kind: 'attempt.continue', key: '<taskId>/<seq>', dueAt, payload })`, where `chain` = 1 + the `chain` of the `attempt.continue` effect keyed `<taskId>/<seq − 1>` if one exists in any status (else 1), and `dueAt` = `resetsAt + 60 s` when known, else `now + [1, 5, 15] min[chain − 1]`; or
   - **block**: when the failure is not retryable, or `chain` would be 3 → `→ BLOCKED('environment')` + a typed `BLOCKED` message for the Task attributed to the interrupted Attempt (`blocked: { reason: 'environment', paths: [] }`, summary naming the class and the count), no effect. An interruption never produces `BLOCKED('retry_budget_exhausted')`.
   The constants (3 consecutive, ladder `[1, 5, 15]` minutes — D68's numbers; the third rung is reachable only if the limit of 3 is raised later —, 60 s slack, 8 days) live together in one module; no policy key in this Task.
   The same settlement applies in `reconcileAttempt`'s `recovery_process_exit` when the Attempt is headless **and** its dispatch belongs to an earlier runtime epoch (`failure: { class: 'unknown', retryable: true, source: 'absent' }`, audit `evidence: 'runtime_restarted'`). Every other settlement path (`launch_pending_orphan`, `launch_rejected`, kernel `failed | stopped | abandoned`, `runtime_budget_exceeded`, `unverifiable_tolerance_exceeded`, the same-epoch process exit, the TUI channel, `unchanged` / declared exits) is unchanged.
4. **Continuation** (`attempt.continue` executor, registered next to the other two): when due it re-reads durable state and asks the Scheduler for a round of that Mission only if the Mission is `EXECUTING`, the Task is `READY` and no Attempt newer than `seq` exists; in every other case it does nothing. It always returns `done` (`maxAttempts` 3, backoff 1 s / 5 s for a throwing round, `onOrphan: 'retry'`). It never launches anything itself and never bypasses a Scheduler check — pending Questions / Approvals, budgets, concurrency and a paused or canceled Mission keep their meaning. **Failure semantics**: a continuation that ends `failed` or `retired` blocks nothing — the Task is simply `READY` and the next round of any trigger admits it.
5. **Admission blocker**: `Scheduler.check` reports skip reason `backoff` for a Task whose `attempt.continue` effect for its latest seq is `pending` with `dueAt` in the future (put the lookup beside `blockingQuestionOrApproval`; add the reason wherever the skip-reason vocabulary is declared and documented). A due or absent effect is no blocker.
6. **A person can override the wait**: `axiom.task.adjust` on a Task that has a pending `attempt.continue` effect retires it in the same transaction (`effect.retired { reason: 'superseded_by_task_adjust' }`), so the next round admits the Task; resuming a `BLOCKED('environment')` Task needs no new code path (ground truth 7) — prove both with tests. `chain` still counts the retired effect (the predecessor *was* interrupted).
7. **Baseline and context**: `resolveAttemptBaseline` walks across an Attempt whose audit says `settlement.kind: 'interrupted'` exactly as it does across `unchanged` (so an interrupted fix Attempt's successor still starts from the failed Candidate, with its verification excerpt); the skipped entry carries the failure class. The next Attempt's context says, in its previous-attempt section, that Attempt N was interrupted before it could submit, by what (`class`), and that none of its uncommitted work was carried over.
8. **E2E (host, verifier-run)**: seam `AXIOM_E2E_INTERRUPTION_BACKOFF_MS` (comma list, read only when the e2e config is enabled, like `AXIOM_E2E_HOLD_EXIT_SUBMISSION`): replaces the ladder and sets the reset slack to 0. Stub scenarios that speak the real protocols: the Claude test provider writes a rejected `rate_limit_event` (`rateLimitType: 'five_hour'`, `resetsAt` a few seconds ahead, unix seconds), a refused assistant message (`error: 'rate_limit'`, `api_error: 'usage_limit_reached'`) and a failed `result`, then exits non-zero; the Codex test provider writes `turn.failed` with a usage-limit message a configurable number of times. New `tests/e2e/mission-interrupted-continuation.spec.ts`, two cases: (i) Claude, structured — Attempt 1 is `interrupted` with `failure { class: 'usage_limit', source: 'structured', resetsAt }`, the Task is `READY` with `attemptCount` 0 and a pending `attempt.continue` due at the reset, Attempt 2 then starts without any call from the test — its `attempt.admitted` audit is not earlier than the effect's `dueAt` — and reaches `VERIFIED` with `attemptCount` 1; (ii) Codex, text — three interruptions in a row end in `BLOCKED('environment')` with one pending `BLOCKED` item and `attemptCount` 0, `axiom.task.adjust` (desktop call) resumes it, the next Attempt reaches `VERIFIED`, `blocked.resolved` is audited. Poll for conditions; no sleeps.
9. **Docs**: `docs/reference/control-plane.md` (classification table as implemented, the settlement and continuation rules, the blocker, the override, limitations), `docs/GLOSSARY.md` (failure classes, `attempt.continue`, skip reason `backoff`, `BLOCKED(environment)`, `settlement.kind` wording), `docs/reference/orca-mapping.md` (the new kernel import: `ClaudeUsageLimits`).
