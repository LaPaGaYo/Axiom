# Task M3-08i — A headless fix Attempt that changes nothing settles; `requiredEvidence` is a list of commands

Planner brief, 2026-11-02 (verifier, from the real-harness fix-loop session; record `.axiom-work/verifications/M3-08-smoke-real-chain.md`, section "Fix loop with real harnesses"). Binding decisions: DEF-21 ⑥ (`candidate_unchanged`, M3-02), D64 (a fix Attempt continues the failed Candidate, M3-04), D68 (exit classification and `settlement.kind`, M3-08e), D65 (verification commands), the Constitution's "Task lifetime is independent of Attempt lifetime" and "LLMs propose; the Control Plane validates". Read `docs/reference/control-plane.md` (the M3-02 `candidate_unchanged` paragraph, the M3-08 headless exit paragraphs, "Previous-Attempt failure evidence") and the record above before starting.

## Ground truth (verifier, 2026-11-02, real Claude Code 2.1.312 Workers and real Codex 0.163.0 Workers on the fixture)

1. **A headless Worker that exits 0 with a valid report but an unchanged tree is never settled.** `submitExit` (`execution/attempt-exit-submission.ts`) stores the report Artifact and calls `settleSubmission`; the `axiom_submit` transaction compares the snapshot tree with the Task's ACTIVE Candidate and throws `OrchestrationError('invalid_argument', 'candidate_unchanged')` (`attempt-submission.ts`, DEF-21 ⑥). That rule was written for the terminal channel, where the Worker receives the error from `axiom attempt submit` and keeps working. On the headless channel the process is already gone: the error propagates out of `submitExit`, the 250 ms watcher stops with `[axiom] Headless exit settlement deferred to recovery`, and every reconciliation tick rethrows the same error (`[axiom] Attempt reconciliation failed`, action `reconcile_failed`; `agentExit = { exited: false }` for headless keeps the dispatch alive). The Attempt stays `RUNNING` with the worker `ready` and the dispatch `dispatched` forever; the Task never reaches `NEEDS_FIX`/`BLOCKED`; the Mission stalls silently. Seen four times in two runs (Codex T02 seq 2; Claude T01 seq 2, T03 seq 2, T02 seq 3): each fix Worker had read the failure evidence, concluded that nothing in its scope needed to change, said so in its report, and exited 0; the attempt branch `axiom/attempt/<task>/<seq>` still pointed at the previous Candidate commit.
2. **The next Attempt would lose the Candidate.** `resolveAttemptBaseline` (`execution/attempt-baseline.ts`) looks only at the immediately previous Attempt: no Submission → `{ kind: 'integration', reason: 'previous_attempt_not_submitted' }`. After an unchanged Attempt is settled as failed, the following Attempt would restart from the integration base although the ACTIVE Candidate (with its latest FAIL run) is exactly what it should continue.
3. **The Planner contract contradicts the Control Plane on `requiredEvidence`.** `resolveVerificationPlan` (`shared/axiom-contract/verification-rules.ts`) runs every `requiredEvidence` entry as a shell command (`source: 'evidence'`), and the ContextPackage lists them as "Required verification commands"; but the Planner prompt's "Minimal example" (`context-builder/planner-render.ts`) says `requiredEvidence: ['Test results']` and `TaskSpecSchema.requiredEvidence` (`shared/axiom-contract/mission-objects.ts`, the schema both the MCP tool and the prompt's JSON Schema expose) carries no description. The real Claude Planner wrote commands in two runs and prose in the third (`"pnpm exec vitest run … output"`, `"pnpm run verify:full output with exit code 0"`); verification ran the prose verbatim — pnpm appended the extra words to the script's last step, vitest took them as file filters, matched nothing and exited 1 — so every root's correct first candidate FAILed while the real gate `pnpm run verify:full` passed, and the Workers then had nothing to fix (ground truth 1).

## Outcome

After this Task a headless Worker that exits without changing the Candidate fails its Attempt within seconds with an audit that carries its own explanation, the retry policy decides what happens next, the following Attempt continues the still-ACTIVE Candidate and is told that the previous Attempt changed nothing, and a Planner reading the contract or the JSON Schema cannot mistake `requiredEvidence` for prose.

## Deliverables

Return a new result `'unchanged_candidate'`; the watcher stops on it, `attempt-reconciliation.ts` treats it like `'failed'` (`liveness: 'exited'`). The existing `headless_exit_failure` branch and the terminal-channel behaviour of `candidate_unchanged` (error returned to the live Worker, Attempt stays RUNNING) are unchanged. Idempotent: once failed, `resolveHostAttempt` throws and `submitExit` returns `'unchanged'` as today; the failed-headless release path (`releaseFailedHeadlessAttempt`) already covers a lost timer. Unit tests in `attempt-exit-submission` for: unchanged → one `attempt.failed` with the fields above, dispatch failed, Task `NEEDS_FIX` then `READY` (maxAttempts not exhausted) or `BLOCKED(retry_budget_exhausted)` (exhausted), worker release scheduled; a second call returns `'unchanged'` without a second audit; a non-`candidate_unchanged` settlement error still rejects.

The returned `candidate` baseline keeps `previousSeq` = the Candidate's Attempt seq and gains `unchangedAttempts: { seq, attemptId, reportSummary: string | null }[]` (ascending seq; empty today). If the walk finds no Submission, the result is `previous_attempt_not_submitted` as today. The launcher's worktree creation and `fix_base_mismatch` check already use the baseline's commit; verify the launch audit `baseline` still records the Candidate. Unit tests: one and two unchanged Attempts before a FAILed Candidate; an unchanged Attempt before a superseded Candidate → integration base; a failed (not unchanged) previous Attempt → `previous_attempt_not_submitted` as before.
