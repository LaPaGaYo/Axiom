Binding decisions: **D85** (this Task's design), DEF-21 ⑥ (`candidate_unchanged`, M3-02 — narrowed by D85 to the terminal channel), D64 (a fix Attempt continues the failed Candidate, M3-04), D68 (exit and verdict classification; `INCONCLUSIVE` reasons and `settlement.kind`), D65 (verification commands and policy), D84 (the MCP channel returns validation issues to the Planner in the same turn), the Constitution's "Task lifetime is independent of Attempt lifetime", "LLMs propose; the Control Plane validates", and "Dependencies, permissions, budgets, and approvals are enforced deterministically". ## Ground truth (verifier, 2026-11-02, real Claude Code 2.1.312 and Codex 0.163.0 Workers on the fixture)

1. **A headless Worker that exits 0 with a valid report but an unchanged tree is never settled.** `submitExit` (`execution/attempt-exit-submission.ts`) stores the report Artifact and calls `settleSubmission`; the `axiom_submit` transaction compares the snapshot tree with the Task's ACTIVE Candidate and throws `OrchestrationError('invalid_argument', 'candidate_unchanged')` (`attempt-submission.ts`, DEF-21 ⑥). That rule was written for the terminal channel, where the Worker receives the error from `axiom attempt submit` and keeps working. On the headless channel the process is already gone: the error propagates out of `submitExit`, the 250 ms watcher stops with `[axiom] Headless exit settlement deferred to recovery`, and every reconciliation tick rethrows it (`[axiom] Attempt reconciliation failed`, action `reconcile_failed`; `agentExit = { exited: false }` for headless keeps the dispatch alive). The Attempt stays `RUNNING` (host projection `liveness: live`) with the worker `ready` and the dispatch `dispatched` forever; the Task never reaches `NEEDS_FIX`/`BLOCKED`; the Mission stalls silently. Seen four times in three runs (Codex T02 seq 2 and seq 3; Claude T01 seq 2, T03 seq 2, T02 seq 3): each fix Worker had read the failure evidence, concluded that nothing in its scope needed to change, said so in its report, and exited 0; `axiom/attempt/<task>/<seq>` still pointed at the previous Candidate commit. Run 3's `chain/electron-main.log` and `attempt-host-evidence.json` hold the live record.
2. **The next Attempt would lose the Candidate.** `resolveAttemptBaseline` (`execution/attempt-baseline.ts`) looks only at the immediately previous Attempt: no Submission → `{ kind: 'integration', reason: 'previous_attempt_not_submitted' }`. After an unchanged Attempt is settled as failed, the following Attempt would restart from the integration base although the ACTIVE Candidate (with its latest FAIL run) is exactly what it should continue.
3. **The Planner contract contradicts the Control Plane on `requiredEvidence`, and nothing bounds what the Control Plane will run.** `resolveVerificationPlan` (`shared/axiom-contract/verification-rules.ts`) runs every `requiredEvidence` entry as a shell command on the host (`source: 'evidence'`, `spawnLocalShellCommand` in the verification worktree), and the Worker's ContextPackage lists them as "Required verification commands"; but the Planner prompt's "Minimal example" (`context-builder/planner-render.ts`) says `requiredEvidence: ['Test results']` and `TaskSpecSchema.requiredEvidence` (`shared/axiom-contract/mission-objects.ts`, the schema behind both the prompt's JSON Schema and the `plan_propose` MCP input schema) carries no description. The real Claude Planner wrote commands in three runs and prose in one (`"pnpm exec vitest run … output"`, `"pnpm run verify:full output with exit code 0"`); verification ran the prose verbatim — pnpm appended the extra words to the script's last step, vitest took them as file filters, matched nothing and exited 1 — so every root's correct first candidate FAILed while the real gate `pnpm run verify:full` passed, and three Workers were sent to fix a plan they cannot touch. The only gate on a model-authored command today is plan approval, which shows no commands before M3-09.
4. **What already exists and must be reused.** `validatePlanProposal` (`shared/axiom-contract/plan-proposal.ts`) returns typed `PlanProposalError`s with `path`; `proposePlan` (`mission-controller/plan-materialization.ts`) turns them into `MissionControllerError('plan_invalid', { errors })`, which the CLI and the MCP tool `plan_propose` hand back to the Planner in the same turn (M3-08h). `checkSubtask` (`messaging/subtask-checks.ts`) is the `REQUEST_SUBTASK` gate with a `Check` vocabulary. `runVerificationCommand` already classifies exit 127 / ENOENT as `environmental: tool_missing`; `verification-plan-runner.ts` applies `retryOnce` / `knownFlaky` per step; `decideVerificationVerdict` (`verification-verdict.ts`) orders the reasons and an `INCONCLUSIVE` run keeps the Task in `VERIFYING` for human disposition (M3-05). `VerificationRulesSchema` is strict, defaulted, and written through `axiom.policy.update` / `--verification-rules-file`; `secretPatterns` already validates regex strings.

## Outcome

After this Task: a headless Worker that exits without changing the Candidate fails its Attempt within seconds with an audit that carries its own explanation, the retry policy decides what happens next, the following Attempt continues the still-ACTIVE Candidate and is told that the previous Attempt changed nothing; a Planner (or a `REQUEST_SUBTASK`) cannot put prose or a shell pipeline into `requiredEvidence` — the proposal comes back in the same turn with the exact path and rule; a plan command that fails because the command itself is wrong ends in `INCONCLUSIVE(plan_invalid)` for a human, never in a fix Attempt; and the contract text, schema and docs say all of this.

## Rules

- Scope: only the paths in `.axiom-work/briefs/M3-08i.verify`; list any test you must touch outside them in the report. Never edit `config/patches/**`, `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`, `mobile/**`; never run `pnpm install/add/remove/rebuild`; never symlink, copy or move `node_modules`; use only this worktree's own toolchain — if a check cannot run here, say so in the report instead of borrowing tools from another directory.
- One authority: settlement stays in `attempt-exit-submission.ts` / `attempt-settlement.ts`; no second state for "unchanged" (the audit is the record); no new lifecycle stage; `attempt.failed.reason` stays `process_exited`, the classification lives in `settlement.kind` (D68, additive). The evidence-command check is one shared function used by both entry points; verification does not re-check at run time (the plan was validated when proposed).
- Deterministic only: no model call, no Decision Engine in any of the new checks.
- The kernel (`src/main/claude`, `src/main/codex`, `src/main/runtime`, `src/main/startup`, the `*-accounts` modules) is not touched and never imports from `src/main/axiom`.
- Redact every Worker-authored string before it enters an audit or a ContextPackage (`redactContext`); never log env values or credentials.
- Policy schema changes are additive with defaults: stored policies without the new keys keep loading; `axiom.policy.update` and `--verification-rules-file` accept them through the shared schema with no new RPC fields.
- Keep files under `max-lines`; add modules rather than growing files near the limit; no `utils`/`helpers` names; no unchecked assertions.
- Electron/e2e: `ORCA_BACKGROUND_LAUNCH=1`, never reveal windows; the verifier runs the Electron specs on the host, do not attempt Electron in the sandbox.
