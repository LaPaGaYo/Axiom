## Ground truth (verifier, 2026-10-28, Claude Code 2.1.312 on the real smoke account)

1. **The printed Claude recipe is un-allowable.** The Planner prompt tells Claude to run `axiom plan propose --mission M --attempt A --file /dev/stdin --json <<'AXIOM_PLAN_JSON' … AXIOM_PLAN_JSON`. Claude Code's Bash safety analysis refuses that command before any rule is consulted — "brace with quote character (expansion obfuscation)": the unquoted `{"…"}` of the JSON heredoc body — so the `Bash(axiom plan propose --mission M --attempt A --file:*)` allow rule never matches, the request goes to `canUseTool`, and the Mission session's `denyPermission` denies it (`attempt.permission_denied {toolName: Bash}` ×3 in both smoke passes). The real Planner had no output channel at all; the e2e stub never showed this because it executes the recipe itself with `/bin/sh -c`, outside Claude's permission system. Probe: `.axiom-work/logs/claude-planner-permission-probe-20261028-210127.txt` (variants A–E).
2. **What is allowable** (`…probe2-20261028-210541.txt`, variants F–L): with an `Edit(//<abs path>/proposal.json)` allow rule the **Write** tool creates that one file outside the worktree, no `--add-dir` needed (F, J, L); the single-line `axiom plan propose --mission M --attempt A --file <abs path> --json` is allowed by the existing prefix rule (F, J, L; it ran and failed only because `axiom` was off the probe's PATH); a Write anywhere else is "ask" and, with no approval surface, denied (G); an `Edit(//<worktree>/**)` deny rule refuses worktree writes outright with "File is in a directory that is denied by your permission settings" (K); a tool-level `deny: ["Write"]` (today's planner settings) disables the Write tool entirely — "No such tool available: Write" — allow rules notwithstanding (H); a `Write(//path)` allow rule is not honoured, only `Edit(...)` path rules govern Write (I). Read-only commands like `cat` are auto-allowed in default mode (D of probe 1); `git log/diff/show` by rule.
3. **Nothing settles a finished structured turn without a proposal.** Recovery rule c′ (D59) fails a terminal-channel Planner whose shell returned to the foreground (`planner.attempt_failed {reason: no_proposal, evidence: shell_foreground}`); the structured channel has no terminal, `policy.budget.maxRuntimeMinutes` is unset by default, and the session stays `ready`/`dispatched`, so the Mission sat in `ANALYZING` for the whole 35-minute test budget after the model gave up. The kernel knows when a turn is over: `claude-session-state-turn-over.ts` (`session_state_changed: idle` — "the authoritative turn-over signal") and `claude-turn-lifecycle-item.ts` / `claude-result-outcome.ts` (the `result` frame's outcome). The Mission pins registry (`claude-mission-session-pins.ts`) is the existing caller-owned seam: `denyPermission(toolName)` is invoked from `ClaudePromptRegistry.register`, which also holds `registration.input`.
4. **Where the Planner's files live.** `planner-claude-launch.ts` already creates `headlessAttemptDirectory(dispatchId)` (`<userData>/axiom/attempts/<dispatchId>`, mode 0700, Axiom-owned, outside every worktree) and writes `planner-settings.json` there; `{{attemptId}}` in the rendered prompt is replaced at launch. `axiom plan propose --file <path> --json` (the codex route) already reads a proposal file.

## Outcome

After this Task a Claude Mission Planner has exactly one allowable way to deliver: write the PlanProposal JSON to `<attemptDir>/proposal.json` with the Write tool (the only path it may write), then run the single-line `axiom plan propose --mission M --attempt A --file <attemptDir>/proposal.json --json`; everything else it might write is refused (worktree) or denied (elsewhere), with the denied tool's input summarized in the audit. And when a Claude Planner's turn ends without a proposal, the Control Plane fails that Attempt within seconds with its own evidence instead of waiting on a budget that may not exist, so `axiom.mission.plan` can be retried. The e2e stub follows the real recipe through the real CLI, and a stub mode exercises the no-proposal settlement.

The worktree path is the Planner worktree's absolute, realpath'd path (macOS `/private/tmp` vs `/tmp`: use `realpath` of the worktree, and state in a comment why). 4. **No-proposal settlement on the structured channel**: `ClaudeMissionSessionPins.onTurnSettled?: (settlement: { outcome: 'success' | 'failure' | 'cancellation' | 'unknown'; isError: boolean; numTurns: number | null }) => void` (additive, optional); the kernel invokes it once per turn end for Mission sessions from the place that already decides the turn is over (`claude-turn-lifecycle-item.ts` for the `result` frame; the idle `session_state_changed` fallback when no result frame came — one call per turn, never two).
