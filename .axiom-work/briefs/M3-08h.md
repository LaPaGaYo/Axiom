## Ground truth (verifier, 2026-10-28, Claude Code 2.1.312 on the real smoke account)

1. **The printed Claude recipe is un-allowable.** The Planner prompt tells Claude to run `axiom plan propose … --file /dev/stdin --json <<'AXIOM_PLAN_JSON' … AXIOM_PLAN_JSON`. Claude Code's Bash safety analysis refuses that command before any rule is consulted ("brace with quote character (expansion obfuscation)": the unquoted JSON braces of the heredoc body), so the `Bash(axiom plan propose …:*)` allow rule never matches and the Mission session's `denyPermission` denies it (`attempt.permission_denied {toolName: Bash}` ×3 in both smoke passes). The real Planner had no output channel at all; the e2e stub never showed this because it executes the recipe itself with `/bin/sh -c`, outside Claude's permission system. Probe: `.axiom-work/logs/claude-planner-permission-probe-20261028-210127.txt`. A file route (Write + single-line command) works today (`…probe2-20261028-210541.txt`) but keeps the proposal channel on two private, version-sensitive layers — Bash analysis and file-path rule semantics — which is why Henry rejected it.
2. **MCP is the channel both harnesses commit to.** SDK 0.3.284 `Options` carries `mcpServers: Record<string, McpServerConfig>` (stdio `{ type: 'stdio', command, args, env }`) and `strictMcpConfig`; the SDK depends on `@modelcontextprotocol/sdk` 1.32.1 (lockfile) — the verifier adds that exact version to `dependencies` on the host before this attempt (commit on main; the sandbox never installs). Claude Code's permission rule for an MCP tool is the exact name `mcp__<server>__<tool>`. Axiom already writes a strict per-Attempt MCP list for Claude (`prepareClaudeAttemptFiles` → `claude-mcp.json`) and `mcp_servers` into the Codex account home layout; both are empty today.
3. **Nothing settles a finished structured turn without a proposal.** Recovery rule c′ (D59) fails a terminal-channel Planner whose shell returned to the foreground; the structured channel has no terminal, `policy.budget.maxRuntimeMinutes` is unset by default, and the session stays `ready` / `dispatched`, so the Mission sat in `ANALYZING` for the whole 35-minute test budget after the model gave up. The kernel knows when a turn is over (`claude-session-state-turn-over.ts`: `session_state_changed: idle` is "the authoritative turn-over signal"; `claude-turn-lifecycle-item.ts` / `claude-result-outcome.ts` read the `result` frame). The Mission pins registry (`claude-mission-session-pins.ts`) is the existing caller-owned seam: `denyPermission(toolName)` is invoked from `ClaudePromptRegistry.register`, which also holds `registration.input`.
4. **How the CLI already speaks for an Attempt.** `axiom plan propose --mission M --attempt A --file …` resolves its caller from the injected agent-session environment (`resolveOrchestrationTerminalHandle` → `readInjectedAgentSessionId`) and calls the orchestration mutation `axiom.plan.propose` `{ missionId, planRevision, attemptId, from }`; the host binds the caller to the dispatch and validates the proposal. The structured child env names this app's CLI launcher by absolute path in `ORCA_CLI_COMMAND` (`structured-session-child-env.ts`) and puts its directory first on PATH. CLI commands are declared in `src/cli/specs/axiom-*.ts` (allowed flags) and loaded through `src/cli/axiom-handler-groups.ts`; new root names need `CLI_COMMAND_NAMES` — so the new command is a subcommand of the existing `attempt` root.

## Outcome

After this Task a Claude Mission Planner has exactly one way to deliver: call the MCP tool `plan_propose` on Axiom's own stdio server (`axiom attempt mcp`), which hands the proposal to the Control Plane over the existing RPC as the Attempt, returns the validation result to the model in the same turn, and persists nothing by itself. The prompt contains no shell command and no file convention; the permission rule is one tool name. When a Claude Planner's turn ends without a proposal, the Control Plane fails that Attempt within seconds (c″) and a default runtime budget backs it up, so a Mission never waits on a silent session. The e2e stub follows the real path through the real server, and a stub mode exercises the no-proposal settlement.

## Deliverables

1. **`axiom attempt mcp --mission <id> --attempt <id>`** (`src/cli/specs/axiom-attempt.ts` spec with `allowedFlags: [...GLOBAL_FLAGS, 'mission', 'attempt', 'from']`; handler in a new `src/cli/handlers/axiom/attempt-mcp.ts`, registered under the `axiom-attempt` group): a stdio MCP server built on `@modelcontextprotocol/sdk` (`McpServer` from `server/mcp.js`, `StdioServerTransport` from `server/stdio.js`; server name `axiom`, version from the app). It registers one tool, `plan_propose`, with `inputSchema: { proposal: PlanProposalSchema }` so the model sees the real schema (if a zod construct does not convert to JSON Schema, simplify the exported shape only — not the validation — and say so in the report). The handler calls exactly what `plan propose --attempt` calls today: `callOrchestrationMutation(client, flags, 'axiom.plan.propose', { missionId, planRevision: proposal, attemptId, from })` with `from` from `resolveOrchestrationTerminalHandle(flags, cwd, client, 'from')`. Tool result on success: text JSON `{ ok: true, planRevisionId, status, taskCount, edgeCount }`; on any failure: `isError: true` with text JSON `{ ok: false, error: { code, message, issues? } }` taken from the RPC error — never throw out of the handler, never print anything but MCP frames to stdout (the CLI's `printResult` is not used; diagnostics go to stderr), never log env values. The process ends when stdin closes. Unit tests with a fake runtime client: success mapping, validation-error mapping (`issues` preserved), RPC failure mapping, no stdout noise.
2. **Planner pins carry the server** (`planner-claude-launch.ts`): `mcpServers: { axiom: { type: 'stdio', command: <launcher>, args: ['attempt', 'mcp', '--mission', missionId, '--attempt', dispatchId], env } }` and `strictMcpConfig: true`. `<launcher>` is the absolute CLI launcher the kernel resolves for structured children (the value `structured-session-child-env.ts` writes to `ORCA_CLI_COMMAND`; resolve it through the same kernel function, never a bare `axiom`); when it does not resolve, the launch fails with `planner.launch_failed { reason: 'cli_launcher_unavailable' }` instead of launching a Planner that cannot deliver. `env` carries exactly the variables the CLI needs to find the runtime and to be recognized as this Attempt (the `ORCA_*` connection variables and the injected agent-session variables the structured child env sets — list them in the report), nothing else. Kernel seam: `ClaudeMissionSessionPins` gains `mcpServers: Readonly<Record<string, McpStdioServerConfig>>` (frozen like `env`); `ClaudeStructuredSdkOptions` (the Pick in `claude-structured-launch-resolution.ts`) adds `'mcpServers' | 'strictMcpConfig'`; the mission spread sets `mcpServers: missionPins.mcpServers, strictMcpConfig: true`. Permission rules in `planner-settings.json`: `allow: ['Read', 'Grep', 'Glob', 'LS', 'Bash(git log:*)', 'Bash(git diff:*)', 'Bash(git show:*)', 'mcp__axiom__plan_propose']`, `deny` unchanged (`Edit`, `Write`, `MultiEdit`, `NotebookEdit`, `WebFetch`, `WebSearch`) — the Planner is read-only again; the `Bash(axiom plan propose …:*)` rule is gone. Unit test the rendered settings and the pins for a sample attempt.
3. **Prompt recipe (Claude branch of `planner-render.ts`)**: replace the heredoc section with: deliver by calling the MCP tool `plan_propose` with `{ "proposal": <complete PlanProposal> }` — the only output channel; the tool answers `ok` or a list of schema issues; fix and call again (the Control Plane keeps one PlanRevision per Attempt); do not create, edit or commit files, do not run commands beyond the read-only git ones. Keep the "Minimal example" and the rules. The codex branch (file + `axiom plan propose --file`) is unchanged; `plannerProposalCommandPrefix` stays for it.
4. **No-proposal settlement on the structured channel (c″)**: `ClaudeMissionSessionPins.onTurnSettled?: (settlement: { outcome: 'success' | 'failure' | 'cancellation' | 'unknown'; isError: boolean; numTurns: number | null }) => void` (additive, optional); the kernel invokes it once per turn end for Mission sessions from the place that already decides the turn is over (the `result` frame; the idle `session_state_changed` fallback when no result frame came — one call per turn, never two). Axiom's `createClaudePlannerLaunch` registers it: if the dispatch has no `planner.proposed` audit, append `planner.attempt_failed { reason: 'no_proposal', evidence: 'turn_settled', outcome, isError, numTurns }` (deduplicated like c′) and call `stopPlanner(runtime, store, { missionId, dispatchId }, 'no_proposal')`; the Mission status is not changed (as c′), `axiom.mission.plan` preflight then admits a new Planner Attempt. Transactional and idempotent against the 60 s reconciliation. **Budget backstop**: `planner-reconciliation.ts` uses `policy.budget.maxRuntimeMinutes ?? PLANNER_RUNTIME_BUDGET_MINUTES` (exported constant, 30) for Planner bindings only, so a live Planner whose turn-over signal never arrives is still stopped as `runtime_budget_exceeded` (D60 / D68). Unit tests for both.
