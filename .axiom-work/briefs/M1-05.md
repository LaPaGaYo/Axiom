## Objective

The first authoritative Control Plane service: `MissionController` in `src/main/axiom/mission-controller/`. It creates Missions bound to an Orca Run through the synthetic session party (D14, verified by M1-01), owns the Mission / GoalRevision / PlanRevision state machines, materializes an APPROVED PlanRevision into Orca `tasks` rows (`deps: []`, D10) plus `task_stages` (D2) and `mission_task_edges`, performs Task stage transitions through the legality table, recomputes readiness deterministically from the database, and writes an audit event for every mutation. It does **not** start Attempts (M2), does not consume the run mailbox (M1-08), does not register RPC (M1-06), and does not guard Orca entry points (M1-07). Everything it does must be restartable: no in-memory state that is not derivable from the tables.

- Contract (M1-02): enums and `isLegalMissionTransition` / `isLegalTaskStageTransition` in `lifecycle.ts`; object schemas in `mission-objects.ts`; `validatePlanProposal` in `plan-proposal.ts` returns `{ ok: true, order }` (deterministic topological order) or `{ ok: false, errors }`; `PlanProposeParams = { missionId, planRevision, provenance }` — you validate `{ ...planRevision, provenance }`. Readiness threshold per edge: `INTEGRATED` (default) or `VERIFIED` (satisfied by `VERIFIED`, `INTEGRATION_READY`, `INTEGRATED`).
- State machines (architecture §6.1–§6.3, glossary §4): Mission `DRAFT → ANALYZING` when repository + target branch are bound and a GoalRevision is ACTIVE (a user-authored Goal is ACTIVE at creation, so `createMission` ends in `ANALYZING` in the same transaction, with both audit events); `ANALYZING → PLAN_REVIEW` on `proposePlan`; `PLAN_REVIEW → PLANNED` on `approvePlan` (materialization); `PLAN_REVIEW → ANALYZING` on `rejectPlan`; `PLANNED → EXECUTING` on `startExecution` (the user action; policy auto-start is M2); `PAUSED` / `BLOCKED` store the previous status in `missions.previous_status` and `resume` / `unblock` return exactly there; `CANCELED` from any non-terminal state. Task: `DEFINED → READY` by readiness only; `* → BLOCKED` stores `previous_stage`; `BLOCKED → previous_stage`; `* → CANCELED`. In M1 no stage beyond `READY` is reachable except through the generic transition API (M2–M4 call it); keep the API generic and tested for every legal row anyway.
- Readiness (§8.1 / glossary §4.4): a `DEFINED` Task becomes `READY` iff every upstream edge meets its threshold ∧ its PlanRevision is APPROVED ∧ Mission is `EXECUTING` ∧ no blocking Question / Approval (none exist in M1 — leave an explicit hook returning "none") ∧ `attempt_count < retryPolicy.maxAttempts` ∧ Mission budget not exhausted (policy `budget.maxAttempts` vs the sum of `attempt_count`; other budget dimensions are M2). `recomputeReadiness(missionId)` is pure-from-DB, idempotent, deterministic (process Tasks in id order), returns the Task ids it moved, and never moves a Task backwards.
- Replanning is M5: approving a second PlanRevision while one is APPROVED (`inherit / cancel / rebind`) is out of scope — refuse with `replan_not_supported` and a `ponytail:` comment naming M5 as the upgrade path. `axiom.task.create` (MINOR_ADJUSTMENT / FIX_TASK) is also M3/M4 — do not implement; `cancelTask` is in scope.
- Errors: one `MissionControllerError extends Error` with a `code` from a closed `as const` list (`mission_not_found`, `plan_revision_not_found`, `task_not_found`, `illegal_transition`, `stale_state`, `plan_invalid`, `plan_pending`, `plan_not_proposed`, `replan_not_supported`, `mission_not_executing`, `synthetic_session_id_invalid`) and a `data` object (ids, from/to, validation errors); M1-06 maps these to RPC errors.
