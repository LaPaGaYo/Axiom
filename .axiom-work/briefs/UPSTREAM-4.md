## Ground truth (verifier, 2026-11-11, code as on main `df22ff55e7`; every function named here was read in full)

1. **SQLite temp storage and rollback** (upstream `f0e7eaa070`, #38358, 2026-11-05, "let worker_done settle when SQLite cannot write a temp file"). `src/main/runtime/orchestration/db/orchestration-db.ts` sets `journal_mode = WAL`, `synchronous = NORMAL` and `busy_timeout = 5000` and nothing for `temp_store`, so SQLite keeps savepoint and statement journals in temp files. In `lifecycle-transition.ts`, `beginLifecycleWriteTransaction` opens `SAVEPOINT <name>` inside a transaction and `BEGIN IMMEDIATE` otherwise, and `rollbackLifecycleWriteTransaction` always runs `ROLLBACK TO` + `RELEASE`, or `ROLLBACK`. `lifecycle-write-transaction-runner.ts` `runLifecycleWriteTransaction` rolls back in its `catch` and rethrows. When SQLite has already ended the whole transaction itself (disk full, an I/O error, a full or unwritable temp directory), that rollback throws ("cannot rollback - no transaction is active", or "no such savepoint") and its error replaces the real one. Every Axiom write goes through this path: `src/main/axiom/db/axiom-store.ts` `transaction(savepoint, operation)` calls `runLifecycleWriteTransaction(this.db.db, 'axiom_<suffix>', operation)` (43 call sites outside tests). Upstream's fix: `temp_store = MEMORY` next to the other pragmas, and `rollbackLifecycleWriteTransaction` returns without running SQL when `!db.isTransaction`. An existing test in this repository already uses a `CREATE TEMP TRIGGER … RAISE(…)` to force such failures (`src/main/codex/codex-structured-journal-settlement-rollback.test.ts`).

2. **The empty daemon pid record** (upstream `220347cae0`, #39825, 2026-11-09; upstream's files live under `src/main/daemon/endpoint/identity/` and `src/main/daemon/launch/`, ours directly under `src/main/daemon/`). `daemon-pid-file-parse.ts` `parseDaemonPidFile`: the legacy bare-integer branch does `Number(trimmed)` and accepts any finite number, so an empty or whitespace-only record parses as pid 0 — and the publisher creates the file before writing it, so a crash during publication leaves exactly such a record — while `-3` or `1.5` parse too. `daemon-stale-kill.ts` `killStaleDaemon`: such a record becomes `recordedOwner`; the fenced `unlinkOwnedDaemonPidFile(pidPath, 0, null)` never matches, the record stays, and every later daemon start fails its exclusive publish with `EEXIST`. The reclaim of a record that does not parse (`unlinkDaemonPidFileWhen(pidPath, (content) => parseDaemonPidFile(content) === null)`) runs before the endpoint probe. `daemon-endpoint-probe.ts` exports `endpointIsProvenDead`. Callers that already treat `pid <= 0` as "no daemon pid": `daemon-host-relocation.ts`, `daemon-newer-protocol-hold.ts`. Tests: `daemon-health.test.ts` (`describe('killStaleDaemon ownership decisions')` with `it('removes a malformed pid record')`), `daemon-pid-file-parse.test.ts` (three tests).

3. **The nearly spent Codex usage window** (upstream `71404c99be`, #40992, 2026-11-11; upstream's file is `src/main/codex/structured/catalog/codex-usage-limits.ts`, ours `src/main/codex/codex-usage-limits.ts`). `CodexUsageLimits.limit()` keeps only windows whose `usedPercent` is at least 100. The last rate-limit report often trails the rejection by the request that went over (it shows 97, say), so the reset is lost. Upstream: `failure()` passes whether the code is `usageLimitExceeded` into `limit(rejected)`; when no reported window is at 100, windows whose reset already passed are dropped, and the fullest remaining window counts as spent if it is at least 90 (`NEARLY_SPENT_PERCENT`); `rateLimitExceeded` keeps the old rule. The Axiom path: `src/main/axiom/execution/codex-rollout-limit.ts` `interpretTail` replays the Worker's own rollout `token_count` records as `notification:account/rateLimits/updated` and calls `limits.failure({ error: { codexErrorInfo: 'usageLimitExceeded' } })`; `attempt-exit-failure.ts` calls it only when `provider === 'codex'` and the Attempt is already classified `usage_limit`. Today a 90–99 report gives no reset and the Attempt waits on the ladder. The other kernel user is `codex-structured-journal-generic-frames.ts`. (T3 Code fixed the same edge in its #27791 by reading usage again from the app-server; Axiom's egress rule forbids that read, so a rejection of the very first request, with no report at all, keeps today's ladder.)

4. **Git remote error redaction** (upstream `0ded87821d`, #36205, 2026-10-29, the `src/shared` half). `src/shared/git-remote-error.ts` `stripCredentialsFromMessage` runs two global regexes over the raw message; `formatSubmodulePushFailureDetail` and `normalizeGitErrorMessage` redact text that can still contain ANSI escape sequences, and an escape sequence inside a URL's userinfo defeats the patterns, so a credential survives into the error text. `stripAnsiEscapeSequences` exists in `src/shared/ansi-escape-sequences.ts`. ## Objective

Port the four behaviours, each with tests that fail on main and pass after the port:

2. `rollbackLifecycleWriteTransaction` does nothing when SQLite has already ended the transaction (`!db.isTransaction`), so the error that ended it reaches the caller — for a top-level transaction and for a savepoint inside one. No other change to the lifecycle runner.

6. `git-remote-error.ts`: escape sequences are stripped before redaction in `formatSubmodulePushFailureDetail` and `normalizeGitErrorMessage`; `stripCredentialsFromMessage` removes `user:password@` after every URL scheme and `token@` after `http://` / `https://`, keeps the rest of each URL, and runs in time linear in the message length.
