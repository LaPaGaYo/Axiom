# Task M4-5b — the Missions page shows what integration did: an Integration block on the Mission page and the merged-tree regression on the Task page (the M4-5b row of `docs/plans/M4.md`; renderer only, on the fields M4-5a put on the read side; new strings in `en` and `zh` only, D94)

Planner brief, 2026-11-18 (verifier). Since M4-2b a verified Task is merged into its Mission's integration branch, tested on the merged tree and promoted, and since M4-5a the read side says so: every Task of `axiom.task.list` / `axiom.task.show` can carry `integration` (its latest batch) and `axiom.mission.show` can carry `integration` (the branch and the recorded head). Nothing shows any of it. The Missions page says "Awaiting integration" and then "Integrated"; where the work went, which commit holds it, what the merged tree was tested with, and — when a merge conflicts or a regression fails and the Task is `READY` or `BLOCKED` again — why, a person can find only in the database. This Task builds the interface on M4-5a's fields: one block on the Mission page and one section on the Task page. It changes no main-process, contract, CLI or kernel file and adds no request the main process does not already answer.

Read first: `docs/PROJECT_CONSTITUTION.md`, `AGENTS.md` (UI and Product Experience; Cross-Platform Requirements; Lazy Senior Dev Mode), `docs/STYLEGUIDE.md` (Color roles; UX rules, above all "No green without evidence"), `docs/reference/control-plane.md` (the subsections `### Integration read model（M4-5a）`, `### Task 页的验证记录读取（M3-09-2）` and `### Mission 页的定时刷新（M3-09-3b-2）`), `.axiom-work/verifications/M4-5a-1.md`.

2. **Regression runs.** A merged-tree regression is a verification run that carries a `batchId` (`VerificationRunView` in `src/shared/axiom-contract/verification-params.ts`). `axiomClient.listVerificationRuns({ missionId, batchId })` answers the runs of that batch in creation order; without `batchId` — what the Task page asks today, `{ missionId, taskId }` — batch runs are left out. A batch usually has one run and can have more (an inconclusive run stays and the retry adds one; an interrupted run ends `CANCELED`). Its `verdictDetail` reads with `readVerdictRecord` (`src/shared/axiom-contract/verdict-record.ts`) like a candidate's: phase, verdict, reason, `checks`, the verdict Artifact. The commit it ran on is the batch's `mergeCommit`, not the run's `candidateCommitSha`. Its verifier is `IntegrationController`. A regression has no human route: the requests behind "Resolve review" and "Rerun verification" are for candidate runs and must not be offered for a batch run.

## Outcome

On the Mission page a person sees where the Mission's verified work goes and how far it is: the integration branch, the commit recorded as its head, and one row for each Task integration has touched — what its latest batch says and which merge commit holds it. On the Task page a person sees, for the Task's latest batch, its status in the Control Plane's own word with a short gloss, the commit it started from and the merge commit, the files that conflicted when the merge did, and the merged-tree regression: every run of that batch, and for the newest run the commands with their results and output. A Task no batch names and a Mission that was never started look exactly as they do today, and so does the whole page against a main process older than M4-5a.
