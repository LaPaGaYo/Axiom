Read `AGENTS.md` (Execution Kernel Boundary, Task and Attempt Rules, Worker Submission Contract, Remote Execution and Process State), `docs/plans/M3.md` (the section "V1 精简后的 M3": exit 9 and the M3-08 row), `docs/decisions/DECISION_LOG.md` **D82** (decision 3), the 2026-10-25 revision lines of **D58**, **D63** and **D57**, and **D14**, **D59**, **D68**, **D73**, **D76**. Work the ponytail way: reuse what exists, make the narrowest change that meets the criteria.

Today a Worker runs in Orca's terminal mode as the interactive Codex TUI with Orca's default arguments (for codex that is `--dangerously-bypass-approvals-and-sandbox`), gets its preamble pasted into the TUI, and submits by calling the `axiom` CLI from its own terminal. D82 makes Workers black boxes: one headless `codex exec` per Attempt, in a sandbox, prompt on stdin, final message = report, and the host submits on the Worker's behalf when the process exits. Our own development pipeline already runs Workers exactly this way — read `.axiom-work/run-codex.sh` (`codex exec -s workspace-write --color never -C <dir> -o <last-message> <prompt>`, then the launcher commits the worktree). This task brings that recipe into the product, inside Orca's existing worker lifecycle. The Planner, Claude Code (M3-08b) and Axiom-managed agent config directories (M3-08c) are out of scope.
