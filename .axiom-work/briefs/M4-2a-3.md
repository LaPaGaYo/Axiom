# Task M4-2a-3 — Promotion: after a passed regression the executor advances the integration head to the merge commit, the batch becomes `PROMOTED` and the Task `INTEGRATED` (third part of the M4-2a row of `docs/plans/M4.md`; D92, approved by Henry 2026-11-15; main process only; no store, contract, renderer, CLI, RPC-file or e2e change)

Planner brief, 2026-11-16 (verifier). M4-2a-2's executor ends a passed regression with the batch in `PROMOTABLE` and the integration head where it was. This Task finishes the batch. Before a batch starts, the executor checks that the integration head is the commit the database recorded. After a pass it makes sure that no worktree has the integration branch checked out, advances the branch to the merge commit with an expected old value, and records `PROMOTED` and `INTEGRATED` in one transaction — the first time a Task of this product reaches `INTEGRATED`, which is what its dependents wait for. Between the ref and the database the ref decides: a batch whose merge commit already is the integration head is recorded as promoted by whichever try or exhaustion finds it, and is never abandoned. And the git calls of the integration directory can no longer leave the directory they were given. **Still nothing enqueues `integration.apply`**: the switch is M4-2b, so every existing flow behaves as on main.

Read first: `AGENTS.md` (Non-Negotiable Architecture Invariants 4, 6, 7, 8, 11; Integration and Promotion; Destructive Actions; Git and Worktree Safety; Code Quality; Lazy Senior Dev Mode), `docs/plans/M4.md` §2 (the flow paragraph and the paragraph that starts "串行") and §5, `docs/reference/control-plane.md` — "Integration apply（M4-1b）", "Integration regression（M4-2a-2）" and "Effect outbox (M3-06)", `.axiom-work/verifications/M4-2a-2-1.md`.

## Ground truth (verifier, 2026-11-16; read in the code at main `d1a306bc93`)

1. **What a try of `integration.apply` does today** (`src/main/axiom/integration/`). `applyIntegration` (`integration-apply.ts`, 153 lines) first closes the Mission's dead open batches — `closeStaleIntegrationBatches` in `integration-request.ts` (186 lines), transaction `integration_stale_batches`: a batch is dead when its Mission is missing or terminal, its candidate is missing, not `ACTIVE` or another Mission's, or that candidate's Task is neither `INTEGRATION_READY` nor `BLOCKED` out of it; whatever its status, `PROMOTABLE` included, it is superseded with the reason `request_stale` and its open runs are cancelled. Then `eligibility` (same file): `done` for a stale request and for a candidate that has a batch in any status but `QUEUED`, `APPLYING`, `TESTING`, `SUPERSEDED` — so a `PROMOTABLE` or `PROMOTED` batch ends the request; `later` (30 s) for a Task that is `BLOCKED`, a Mission that is not `EXECUTING`, or another candidate's open batch; otherwise `ready` with the candidate's open batch, if any. `readIntegrationHead` (`integration-scratch.ts`) finds the repository through `runtime.showRepo`, insists that it is on this machine, and reads the branch; it answers the commit only. `beginBatch` (transaction `integration_begin`) asks `eligibility` again, inserts an `APPLYING` batch or moves a `QUEUED` one **with whatever head it was given** as `baseCommit`, and for a batch found in `APPLYING` or `TESTING` only compares the head with its base (`integration_head_moved`). Leftovers are removed, a scratch is made and detached, the candidate merged and the merge commit pinned (`integration_merged` → `TESTING`), and `runIntegrationRegression` (`integration-regression.ts`, its transactions in `integration-regression-state.ts`) runs the plan and settles it in `integration_regression_verdict`: `PASS` → `PROMOTABLE` with the audit `integration.batch_promotable`, `FAIL` → `FAILED` and the Task goes back, `INCONCLUSIVE` → the try fails. It answers `done`, `stopped` (the scratch is left and the try answers `{ later: now }`) or `interrupted` (the request was no longer current: own run cancelled, scratch returned, `{ later: now }`). Then `returnIntegrationScratch` hands the scratch back to the kernel and the try answers `done`. `abandonIntegration` (`integration-request.ts`; the executor's `onExhausted`, which must never reject) supersedes every open batch of the effect's candidate — a `PROMOTABLE` one included — in transaction `integration_abandoned`, cancels their open runs, and blocks the Task with `integration_unavailable` when it is `INTEGRATION_READY`. **Nothing writes the integration head.**
2. **The integration head and its record.** `ensureIntegrationBase` (`src/main/axiom/execution/integration-base.ts`) creates `refs/heads/axiom/integration/<missionId>` when a Mission starts; each call of `axiom.mission.start` then appends one audit event — `integration.base_created`, or `integration.base_reused` when the branch was already there — with actor `MissionController`, object kind `mission`, the Mission's id as object and `after: { sha }`. The event is appended before the transaction that moves the Mission to `EXECUTING`, so a start that loses there leaves its event and the next start writes another: the latest one counts. A Mission starts only out of `PLANNED` and never returns there, so these events precede every batch. Nothing has written that ref since: the scratch is made from it under a temporary branch, the pins live under `refs/axiom/`. The ref is read by `readIntegrationHead`, by the launch of an Attempt (its worktree is made from the branch, so it starts at whatever the head is then), by the diff gate (`readCandidateDiff`: from the merge base of head and candidate), by the Planner's launch, and by the continuation of an interrupted Attempt in its old worktree (`execution/in-place-worktree.ts`: without a preserved snapshot it continues there only while the branch still stands at the commit that Attempt started from; otherwise the Attempt is launched afresh). No code of Axiom checks the integration branch out.
3. **Git, probed by the verifier** (git 2.43; 2.54 on the verifier's machine). `update-ref <ref> <new> <old>` refuses when the ref is not at `<old>` or `<new>` names no commit, and it does **not** refuse a branch that a worktree has checked out — the files of that worktree would then disagree with their branch. `for-each-ref --format='%(refname)%00%(objectname)%00%(worktreepath)' <ref>` prints one line for an existing ref and none for a missing one; its last field is the path of the worktree that has the branch checked out — the repository's main worktree counts, and so does a linked worktree whose directory was deleted but never pruned — and is empty otherwise (git 2.23 and later). A ref that is a symbolic ref is written **through**: `update-ref` moves the branch it points at, and `%(symref)` names that branch. A `reference-transaction` hook runs on every ref update — a commit, `git worktree add`, `update-ref` — unless hooks are off, and one that exits non-zero aborts the update. And a git command run in a directory that has no `.git` of its own walks up and works on a repository above it; with `GIT_CEILING_DIRECTORIES` set to the parent of that directory git answers "not a git repository" there, while a repository root or a linked worktree given the same setting works as before. The git runner takes a caller's `env` in place of `process.env`, not on top of it (`src/main/git/command-runner/git-exec-file.ts`).

## Outcome

After this Task one try of `integration.apply` that reaches or finds `PROMOTABLE` ends with the integration branch at the batch's merge commit, the batch `PROMOTED` and the Task `INTEGRATED`; the next batch of the Mission starts from that merge commit and from nothing else. A head that is not the recorded one starts no batch. A branch that some worktree has checked out is not moved. Whatever a crash, a refused transaction or an exhausted effect left behind, a batch whose merge commit is the integration head ends `PROMOTED`. A block or a cancellation that the executor sees before it touches the branch stops the promotion; one that comes later — or any, when the merge commit already is the head — keeps the Task where the person put it, and the batch still says what the ref says.

## Deliverables

1. **`advanceIntegrationHead`**, a new export of `src/main/axiom/execution/integration-base.ts` — the one place of the product that moves the integration branch. `advanceIntegrationHead({ repoPath, missionId, from, to })` answers `{ advanced: true }` or `{ advanced: false, reason }` with the reason `checked_out`, `moved` or `unavailable`; it never throws, and nothing git printed is in its answer. It reads `refs/heads/axiom/integration/<missionId>` once — the branch's commit, whether it is a symbolic ref, and the worktree that has it checked out, from one `for-each-ref` (take the line of exactly this ref). Then, in this order: the branch cannot be read, does not exist or is a symbolic ref → `unavailable`; it is already at `to` → advanced, and nothing is written; it is not at `from` → `moved`; a worktree has it checked out → `checked_out`. Otherwise one `update-ref <ref> <to> <from>` with hooks off, as `pinCommit` turns them off, and then the branch is read again and the answer follows what it says: at `to` → advanced; still at `from`, or unreadable → `unavailable`; anything else → `moved`. Both ids are checked with `GitObjectIdSchema` before git runs (a bad id is `unavailable`) and every git call has a timeout.
2. **A batch starts only from the recorded head.** The recorded head of a Mission is the commit named by the latest — by `sequence` — of these audit events of the Mission: `integration.batch_promoted` (deliverable 3; its merge commit) and `integration.base_created` / `integration.base_reused` (ground truth 2; its `sha`, object kind `mission`, the Mission's own id). The step that starts a batch — inserts one, or moves a `QUEUED` one to `APPLYING` — does so only when the head it was given is the recorded head; otherwise, and when there is no such event or it names no commit id, it throws the fixed code `integration_head_unexpected` and writes nothing. A batch found in `APPLYING` or `TESTING` keeps today's rule (`integration_head_moved` unless the head is its base). Mark the lookup with a `ponytail:` comment — it reads every event of the Mission once per batch start, and a filtered store query is the upgrade when Missions grow.
3. **Promotion.** Only when the regression of this try passed — its verdict's transaction made the batch `PROMOTABLE` — or on the path of deliverable 5 (a); a failure, a conflict and every other end of a try answer as today. After the scratch was returned, the try goes on:
   1. It looks at the request once more as a try does at its start: the Mission `EXECUTING`, the Task `INTEGRATION_READY`, the candidate `ACTIVE` and theirs, this batch `PROMOTABLE`. When that no longer holds, nothing is written and the try answers `{ later: <now> }` — no try is spent, and the next try decides: it waits for a blocked Task or a paused Mission, or closes a dead batch.
   2. `advanceIntegrationHead` from the batch's `baseCommit` to its `mergeCommit`, in the path of the Mission's repository as `readIntegrationHead` finds it. `checked_out` fails the try with the fixed code `integration_branch_checked_out`, `moved` with `integration_head_moved`, `unavailable` with `integration_head_unavailable`; nothing else is written then, and the batch stays `PROMOTABLE`.
   3. One transaction (`integration_promoted`): the batch `PROMOTABLE` → `PROMOTED` (the fixed code `integration_batch_stale` when the store refuses); the Task → `INTEGRATED` through `missions.transitionTaskStage` (actor `IntegrationController`, reason `integration_promoted`) when it is `INTEGRATION_READY` and the batch's candidate is `ACTIVE` and its own — otherwise the Task is left exactly as it is; one audit `integration.batch_promoted` on the batch with the status, the base commit, the merge commit, whether the Task was integrated, and whether the record was caught up from the ref (deliverable 4). The try answers `done`.
4. **Between the ref and the database the ref decides.** Whenever the Mission has an open batch in `PROMOTABLE`, a try reads the integration head before anything else — before M4-2a-2's dead batches are closed — and records every such batch whose merge commit **is** that head as promoted: the transaction of 3.3, with its audit marked as caught up. This holds for a batch of any candidate of the Mission and whatever became of its Task or its Mission: a Task that a person blocked or cancelled in the meantime keeps its stage, the batch is `PROMOTED` all the same, and such a batch is never superseded — not as a dead batch and not at exhaustion. When the head cannot be read, the try fails with the code it has today before it closes any batch. `abandonIntegration` does the same before it supersedes anything: when its candidate has an open `PROMOTABLE` batch it reads the head; a batch whose merge commit is the head is recorded as promoted; a `PROMOTABLE` batch is left open when the head could not be read; and the Task is blocked only if it is still `INTEGRATION_READY` after that. It still never rejects, whatever the read or the store does. One function for the try and for exhaustion.
5. **Going on from `PROMOTABLE`, and a Task that was left behind.** (a) A request whose candidate has an open batch in `PROMOTABLE` that deliverable 4 did not settle is ready, not done: no `integration.batch_started` is written; the leftovers of the batch are removed as today; no scratch is made, nothing is merged and no regression runs; the head the try read must be the batch's `baseCommit` (`integration_head_moved` otherwise); and the try goes on at 3.1. (b) A request whose candidate has a `PROMOTED` batch while its Task is `INTEGRATION_READY` and the candidate `ACTIVE` — a block was lifted after deliverable 4 had recorded the batch — moves the Task to `INTEGRATED` in one transaction (same actor and reason, no second `integration.batch_promoted`) and answers `done`. That is bookkeeping for a head that has already moved: it waits neither for a paused Mission nor for another candidate's batch. Every other finished batch answers `done` as today.
6. **Git stays in the scratch it was given.** `readIntegrationGit` and `writeIntegrationGit` run git with `GIT_CEILING_DIRECTORIES` set to the parent of their `cwd` — set, not appended — on top of the whole environment they use today (`process.env` where they pass none; ground truth 3). In a scratch directory that lost its `.git` git then fails instead of walking up into a repository above it — the user's own, when the workspace directory lies inside one. One call is exempt: `readIntegrationHead` runs in the repository's own path and keeps today's environment, so that nothing changes for a repository path that is not a repository root; give the helper a way to leave the ceiling out for that call and use it nowhere else. Nothing else about the two helpers changes.
