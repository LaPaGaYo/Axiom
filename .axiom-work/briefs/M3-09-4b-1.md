# Task M3-09-4b-1 — Acceptance criteria that hold a secret are refused where they are written (security policy approved by Henry 2026-11-14; contract and main process, one renderer test, no renderer product change)

Planner brief, 2026-11-14 (verifier). A human-written rationale is checked for secrets when it is written (`secret_in_rationale`). The text of a Task's acceptance criteria and the commands in them are not: they are stored as given and shown as given on the plan card and the Task page, and three audit rows keep them as given. This Task refuses them at the write paths — a plan proposal, the creation of a Task, the adjustment of a Task, and a subtask request — with the same built-in patterns the rationale check uses, by adding the rule to the ONE function all of those paths already call (`validateTaskAcceptance`). Because the Missions page predicts refusals with that same function, the adjust form says it before sending without any renderer change.

Read first: `AGENTS.md` (Human Approval, last paragraph on secrets; Code Quality; Lazy Senior Dev Mode), `docs/reference/control-plane.md` ("Task spec：逐条验收合同（M3-04b-2）"; "ContextPackage（M2-02）" for the redaction patterns; "替换验收标准（M3-09-4d）", its limitation paragraph; "人工 Task 调整（M3-04b；D70 ② / D78 / D85）"), D65's revision of 2026-10-21 in `docs/decisions/DECISION_LOG.md` (the built-in secret scan and where its patterns come from).

## Ground truth (verifier, 2026-11-14, main `dd4ef18d1d`; every fact here was read in the code at that commit)

1. **The detector.** `src/main/axiom/context-builder/redaction.ts` (32 lines) holds an unexported `SECRET_PATTERNS` list of three built-in patterns — `private_key` (a `BEGIN … PRIVATE KEY` block with its matching `END` line), `provider_token` (one of the prefixes `sk`, `ghp`, `gho`, `github_pat`, `xoxa` / `xoxb` / `xoxp`, then `-` or `_`, then at least 16 characters of `[A-Za-z0-9_-]`, between word boundaries) and `aws_access_key_id` (`AKIA` and 16 characters of `[0-9A-Z]`). `redactContext(text)` replaces every match by `[REDACTED]` and returns `{ content, redacted }`. `detectSecretPatterns(text, extraSources)` returns pattern names (built-in names, then `policy:<i>` for the Mission's `verificationRules.secretPatterns`); only the diff gate calls it. About thirty non-test modules use one of the two. Nothing under `src/shared/axiom-contract` holds this list. (Other subsystems have detectors of their own — crash reports, MCP inspection, verification output; they are separate and not part of this Task.)
2. **`secret_in_rationale`** is `redactContext(rationale).redacted` → `OrchestrationError('invalid_argument', 'secret_in_rationale')`: built-in patterns only, the Mission's `secretPatterns` take no part. `task-adjustment.ts:99-101` is one of its four places (it has no test of its own).
3. **One validator, called everywhere.** `validateTaskAcceptance(task, path)` in `src/shared/axiom-contract/plan-proposal.ts:51-90` returns `PlanProposalError[]` — today `required_evidence_retired`, `criterion_shape` (a criterion that is a string), `acceptance_uncheckable`. `PlanProposalError.code` is a closed union (`:26-40`); an issue is `{ code, severity, message, taskIds?, path? }`. Its callers: `validatePlanProposal` for every Task of a proposal unless `options.persisted` (`:113-115`); `createTask` (`src/main/axiom/mission-controller/task-creation.ts:35-38`); `adjustTask` when the request carries `acceptanceCriteria` (`task-adjustment.ts:129-142`, after the rationale check and the limit checks, before the write); `checkSubtask` (`src/main/axiom/messaging/subtask-checks.ts:99-103`, which turns the one code `acceptance_uncheckable` into the typed check failure of the same name); the CLI's pre-check of a Task file (`src/cli/handlers/axiom/input-files.ts:68-75`); the e2e helper `tests/e2e/helpers/fixture-plan-proposal.ts` (through `validatePlanProposal`; its fixtures hold no hit); and the renderer's draft hook (`src/renderer/src/components/missions/use-task-criteria-draft.ts:55-58`), which shows EVERY issue of the function by its `path` (`['task','acceptanceCriteria', j, 'text']` under the text field of row j, `[…, j, 'check', 'command']` under its command field, anything else under the list) and disables `Apply adjustment` while there is one. 4. **How a refusal leaves.** All three controller paths throw `MissionControllerError('plan_invalid', { errors })`; on the wire that is `{ ok: false, error: { code: 'plan_invalid', message: 'plan_invalid', data: { errors } } }`. The Claude Planner's MCP tool passes `data.errors` on to the model as `issues` (`src/cli/handlers/axiom/attempt-mcp.ts:47-71`); the Missions page words them on its error line (M3-09-4d). `approvePlan` validates the stored plan with `persisted = true` (`plan-materialization.ts:130`), so it does not run `validateTaskAcceptance`.
5. **Commands** are validated after that, in the main process only: `validateTaskCommands` (`plan-validation.ts:28-41`) wraps the shared `validateAcceptanceCommands` and already passes its messages through `redactContext`.
6. **Subtask requests.** `resolveSubtask` (`subtask-resolution.ts:69-100`) runs `checkSubtask` first — a failure is recorded as the audit `subtask.checks_failed { failed }` and returned as `{ resolved: false, failed }`, nothing is thrown — and only then calls `missions.createTask`. 9. **What the patterns do not flag** (by reading them) — six examples: (i) prose about secrets, `No API keys, tokens or passwords appear in logs`; (ii) the name of an environment variable in a command, `node scripts/check-env.mjs OPENAI_API_KEY`; (iii) prose that names the prefixes, `Tokens with the sk- or ghp_ prefix are replaced by [REDACTED]`; (iv) a short prefix in a command, `pnpm test -t "redacts sk-proj tokens"`; (v) a path with the word password, `pnpm test src/auth/password-reset.test.ts`; (vi) a key block's `BEGIN` line without its `END` line. ## Outcome

After this Task, a plan proposal, a new Task, an adjustment or a subtask request whose acceptance-criterion text or command matches one of the three built-in secret patterns is refused before anything is stored, with a typed issue that names the field and the pattern and never the matched text; the adjust form says so before sending. Everything else — stored plans and Tasks, their approval, the rationale checks, redaction — behaves as on main.

## Deliverables

1. **One list, in the contract.** A new module `src/shared/axiom-contract/secret-patterns.ts` holds the three built-in patterns — moved verbatim, names, expressions and flags included (`redactContext` relies on the global flag), not copied: after this Task that list exists in exactly one non-test file — and a pure function that returns the names of the built-in patterns a text matches (fresh regular expressions per call, so no `lastIndex` state can leak; an empty array when none). `redaction.ts` imports the list; `redactContext` and `detectSecretPatterns` keep their names, signatures and results, so none of their importers changes.
2. **The rule, once.** `validateTaskAcceptance` gains it: for every criterion that is an object, the `text`, and for a `command` check the `command`, are tested with the function of deliverable 1. Each field that matches yields one issue `{ code: 'secret_in_criterion', severity: 'error', message, taskIds: [task.id], path }` with `path` = `[...path, 'acceptanceCriteria', index, 'text']` or `[...path, 'acceptanceCriteria', index, 'check', 'command']`. The message says which field and which pattern name(s) — for example `Acceptance criterion text matches a secret pattern (provider_token). Remove the secret.` — and never contains the matched text or any part of the criterion. `PlanProposalError.code` gains `'secret_in_criterion'`. The existing three checks, their order among themselves, codes, messages and paths do not change; the new issues come after `criterion_shape` and before `acceptance_uncheckable` is fine, any stable order is. A criterion that is a string and legacy `requiredEvidence` are already refused by their own rules and need no scan.
3. **No change at the call sites.** `task-creation.ts`, `task-adjustment.ts`, `plan-materialization.ts`, `plan-validation.ts`, `subtask-resolution.ts`, the CLI and every renderer product file stay byte-identical: the three controller paths refuse through the `plan_invalid` they already throw, the CLI pre-check and the form's prediction follow by themselves. Approving a plan that is already stored stays possible (`persisted`).
4. **Subtask requests fail their checks.** `checkSubtask` gains the typed failure `secret_in_criterion` beside `acceptance_uncheckable` (same shape: the code of `validateTaskAcceptance` becomes the check name; `Check` gains the member). So a request whose criteria hold a secret ends as `subtask.checks_failed` with nothing thrown and no Task created, on the human path and on the automatic one.
5. **The existing test of ground truth 7** keeps its title and its purpose — `acceptanceForAudit` still redacts criteria that are ALREADY stored — and gets there another way: put the criteria with the secret into the stored spec through the store (`updateTaskSpec`, the way a row written before this Task would look), then adjust WITH clean criteria (the audit carries criteria only then), and check that the `before` side shows the stored criteria redacted, the `after` side the clean ones, and that the audit's JSON does not contain the secret. `acceptanceForAudit` itself stays.
6. **Tests** with exactly the titles of Acceptance, in new files (the one exception is deliverable 5), under both runners.
7. **Docs.** `docs/reference/control-plane.md`: the rule, its code, paths and message shape in "Task spec：逐条验收合同"; one sentence in the ContextPackage section that the built-in list now lives in the shared contract module and is the one list for redaction, the diff gate and this check; in "替换验收标准（M3-09-4d）" the limitation sentence is corrected in both of its clauses — it says the renderer does not check criteria, commands or the rationale for secrets, and that criteria and commands are not checked before storage: after this Task the form predicts the refusal for criteria and commands through the same function and the Control Plane refuses them; the rationale is still not predicted, and `evidenceCommandMessage` in the renderer is still not redacted; in "人工 Task 调整" the new refusal; the subtask check where the checks are listed. No literal that looks like a token in the docs.
8. **Report** `.axiom-work/reports/M3-09-4b-1-<seq>.md` (see Acceptance).
