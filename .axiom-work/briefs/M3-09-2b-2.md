# Task M3-09-2b-2 — Mission UI: a person resolves a review or reruns verification from the Task page (D82, D86 ③, STYLEGUIDE rule 4; renderer and one read-only contract change)

Planner brief, 2026-11-13 (verifier). M3-09-2 made the Task page say why a Task is where it is and show the evidence. This part lets the person act on a review from that page: resolve a `HUMAN_REVIEW` run `PASS` or `FAIL` — with the typed disposition of M3-09-2b-1 when the rule asks for one — or run verification again on the same Candidate. The page offers an action only when the Control Plane's pending view lists it for this Task; a Task that needs nobody shows no control. It also closes three gaps M3-09-2 left on the page. `axiom.task.adjust` and `axiom.task.cancel` are the next part (M3-09-2b-3). Nothing in the main process, the RPC surface or the kernel changes.

Read first: `AGENTS.md` (UI and Product Experience; Human Approval), `docs/STYLEGUIDE.md` (Components — Buttons, Picking the right primitive, Form anatomy; UX rules 1, 3 and 4 — rule 4 "Quiet" is the acceptance yardstick of this Task), `docs/GLOSSARY.md` §4.4a and §4.8, `docs/reference/control-plane.md` ("人工验证处置与同候选重验（M3-05；D82 / D85 / DEF-21 ④）"; "Task 等待与 Mission 待处理项（M3-09-1）"; "Task 页的验证记录读取（M3-09-2）").

5. **Resolve.** `axiom.verification.resolve` (`desktop_only`): strict params `VerificationResolveParams { runId, verdict: 'PASS' | 'FAIL', rationale (trimmed, 1–4000), criteria: number[] (≤ 50, default []), disposition? }` (`verification-params.ts`); result `{ runId, status }`. The run must be `HUMAN_REVIEW` (else `illegal_transition`), the Task `VERIFYING` and the Candidate `ACTIVE` (else `stale_state`); a rationale that looks like a secret is `invalid_argument` / `secret_in_rationale`; a `criteria` index must exist in the run's `verdictDetail.acceptance[]` (`criterion_not_found`); since M3-09-2b-1 the disposition must satisfy `allowedVerificationDispositions(verdict, reason)` (`src/shared/axiom-contract/verification-disposition.ts`, the one shared rule; `reason` is the run's `verdictDetail.reason`): `FAIL` → `['fixed']` (omitted is stored as `fixed`); `PASS` on `acceptance_human` / `non_code` → `[]` (a given disposition is refused, `disposition_not_applicable`); `PASS` on any other reason → `['rejected', 'intentional', 'not_worth']` (omitted is refused, `disposition_required`; `fixed` is `disposition_mismatch`). `PASS` moves the Task to `VERIFIED`; `FAIL` to `NEEDS_FIX` and on (`READY`, or `BLOCKED` when the Attempt budget is used up). A resolved run is final. For a `FAIL`, the next Attempt is told `A human resolved verification run <id> as FAIL: <rationale>` and, for each criterion the person named, `[fail] <criterion> — a human judged this failed: <rationale>` (`context-builder/previous-acceptance.ts`); for a `PASS` the named criteria are only recorded.
6. **Rerun.** `axiom.verification.rerun` (`desktop_only`): strict params `VerificationRerunParams { taskId, rationale (trimmed, 1–4000) }`; result `{ runId, status: 'QUEUED' }` (`verification-rerun.ts`). It needs an `ACTIVE` Candidate, the Task `BLOCKED` or `VERIFYING` with the latest run `HUMAN_REVIEW`, and no `QUEUED` / `RUNNING` run (else `illegal_transition` / `task_not_rerunnable`). A run waiting for review becomes `CANCELED` and gains `verdictDetail.rerun { rationale, by, at }`; a new run is queued on the same Candidate; a `BLOCKED` Task returns to `VERIFYING`.
7. **What the record reader gives.** `readVerdictRecord(run.verdictDetail)` (`src/shared/axiom-contract/verdict-record.ts`, 92 counted lines) returns `reason`, `acceptance[]` (`index`, `text`, `check`, `result`, …), `resolution { verdict, rationale, criteria, by, at, disposition? }`, `rerun`, …; a list entry that fails its schema is dropped by `entries()` without a trace.

## Outcome

On the Task page a person can do what the Control Plane says this Task needs from them about verification, and only that: resolve the review (verdict, the disposition the rule asks for, the criteria the resolution is about, a rationale) or queue a rerun (a rationale). The form cannot disagree with the Control Plane about dispositions because both read the same function; every call reconciles by re-reading; a Task that needs nobody shows no control at all. A stored resolution shows its disposition; a resolved or canceled run no longer says its human criteria need a person; the waiting line's links say what they are; a record with entries the reader could not read says how many.

2. **Reading the pending items of the Task.** The Task read gains the pending items whose `taskId` is the selected Task (one `axiom.mission.pending` call for the Mission, filtered in the renderer; no new read model). 3. **The region "Task actions"** in `TaskDetail`, directly under the waiting line. It is rendered only when a pending item of this Task lists `axiom.verification.resolve` or `axiom.verification.rerun`; otherwise there is no heading, no empty state, no control (rule 4, "Quiet"). It shows one `outline` button per offered action, in the order the item lists them (an action listed by more than one item is offered once): `Resolve review`, `Rerun verification`. A button opens its form in place (`aria-expanded`; one form open at a time; opening moves focus to the form's first control); the form's quiet `Close` button (ghost, STYLEGUIDE rule 3) collapses it without a call and returns focus to the button that opened it. 4. **The form "Resolve review"** (a `form` with that accessible name; `RadioGroup`, `Checkbox`, `Textarea`, `Label` primitives; STYLEGUIDE "Form anatomy"). Refresh to try again.` It shows the run id and the checks' recorded reason verbatim (monospace), then:
   - **Verdict** — radio group `Verdict` with two radios whose accessible names are exactly `PASS` and `FAIL`, nothing preselected. Under the chosen verdict one sentence of consequence, from ground truth 5: for `PASS`, that the Task becomes `VERIFIED` and waits for integration; for `FAIL`, that the Task goes back to be fixed and the next Attempt is told the rationale; for both, that a resolved run cannot be resolved again.
   - **Disposition** — from `allowedVerificationDispositions(verdict, reason)` with the run's recorded reason, and from nothing else: an empty list shows no disposition field and sends none; a list of one shows that value as fixed text (not a choice) and sends it; a longer list shows the radio group `Disposition`, nothing preselected, one radio per value with the value itself (`rejected`, `intentional`, `not_worth`) as accessible name and a gloss beside it, and the form cannot be submitted until one is chosen. Changing the verdict clears a disposition the new list does not allow.
   - **Criteria** — group `Criteria named in the resolution`: one checkbox per entry of the run's `acceptance[]`, accessible name `#<index> · <text>`; optional. One helper line that follows the verdict: for `FAIL`, the next Attempt is told the ticked criteria failed; for `PASS`, the ticked criteria are recorded with the resolution. No group when the record has no criteria.
   - **Rationale** — `Textarea`, required, `maxLength` 4000, label `Rationale`.
   - **Submit** — button `Submit resolution` (`default` variant), disabled while `busy`, without a verdict, without a required disposition, or with an empty rationale. It sends `{ runId, verdict, rationale (trimmed), criteria (ascending), disposition? }`.
5. **The form "Rerun verification"** (a `form` with that accessible name): one sentence from ground truth 6 (the same Candidate is verified again; a run that is waiting for review is canceled), `Rationale` (`Textarea`, required, `maxLength` 4000), button `Queue rerun`, disabled while `busy` or empty.
