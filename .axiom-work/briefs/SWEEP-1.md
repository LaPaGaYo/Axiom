# Task SWEEP-1 — The safety net: every reconcile tick asks for one Scheduler round per executing Mission, and such a round does not repeat a refusal that has not changed (the 调度兜底巡检 row of `docs/plans/M4.md`; D89 item 2; main process only; no store, contract, renderer, CLI, RPC-file or e2e-file change)

Planner brief, 2026-11-16 (verifier). A Scheduler round runs only when something asks for one: a stage change, an adjustment, a policy update, a start, a resume, an unblock, the end of a backoff, or boot. A round that is lost — it rejected, or the thing that changed is outside the Control Plane, like a provider that was installed or signed in after a refusal — is never made up for: `READY` Tasks then wait until some unrelated event happens. M4-2b made this matter more, because integration requests are made by the round too. This Task adds the safety net the plan row asks for: the existing 60-second reconcile tick also asks for one round, with the new trigger `sweep`, for every `EXECUTING` Mission. A round already rereads all durable state, so nothing else is needed for correctness; what is needed is that a round every minute does not fill the audit log when the situation has not changed. Today one thing would: a Task with no eligible provider gets a `task.admission_refused` audit event in every round. A sweep round does not repeat a refusal that is the same as the one the read models already count; rounds asked for by a real event keep writing as they do today. To make room — `scheduler/scheduler.ts` is at the limit of 300 counted lines — the four exported types of that file move, unchanged, into a module of their own.

Read first: `AGENTS.md` (Control Plane Boundary — "Scheduler state is derived entirely from the database"; Code Quality; Lazy Senior Dev Mode), `docs/plans/M4.md` §3 (the 调度兜底巡检 row), `docs/reference/control-plane.md` — "Scheduler admission 与预算（M2-04）", the paragraph on policy updates that says a refusal is appended in every round, "Integration requests（M4-2b）" (its limits), "Recovery（M2-08）" (the reconcile tick), and the two places that list the triggers; `.axiom-work/verifications/M4-2b-1.md` ("Not covered").

## Ground truth (verifier, 2026-11-16; read in the code at main `0a7ea2917f`, and checked a second time by a read-only pass over the code)

1. **Who asks for a round.** `Scheduler.scheduleRound(missionId, trigger)` (`src/main/axiom/scheduler/scheduler.ts`) is called by: the Control Plane's `onScheduleTrigger` hook for every `scheduleAfterWrite` of `MissionController` (`control-plane.ts`: fire and forget, a rejection only leaves `console.warn('[axiom] Scheduler round failed', { missionId, trigger })`; when `adjustTask` retired a usage-limit continuation the controller asks for every other executing Mission as well); the `attempt.continue` effect when a backoff or an account cooldown ends (`outbox/attempt-continuation.ts`: it awaits the round with `stage_change`, a rejection makes the effect retry, and for a usage limit it asks for every other executing Mission too); and `startAxiomControlPlane` (`control-plane-boot.ts`), once per Mission that is `EXECUTING` after recovery, with `resume`. `ScheduleTrigger` is `'mission_start' | 'stage_change' | 'resume' | 'manual' | 'policy'`; `manual` is used by test support only. There is no periodic round.
2. **A round** (`runRound`). Returns at once unless the Mission is `EXECUTING`; `recomputeReadiness`; `requestIntegrations` (M4-2b); then, for each `READY` Task in critical-path order: a `scheduler_precheck` transaction (`check`: Mission budget, Task token budget, attempts, backoff, question, approval, readiness), the concurrency limit, `buildWorkerContracts`, and `admit`. `buildWorkerContracts` (`agent-factory/agent-factory.ts`) first selects the provider — `AgentFactoryError('no_eligible_provider', data)` is thrown there, before any context is built — then builds the ContextPackage and the AgentSpec, both content-addressed: a rebuild of unchanged content inserts no row and writes no audit event. The audit event `scheduler.round` (`after` holds `trigger`, `admitted`, `skipped`) is written only when the round admitted something or blocked the Mission. **What a round that admits nothing can still write** — each a change of the situation, or a retry that exists today:
   - `recomputeReadiness`: a `DEFINED` Task becomes `READY` (stage and `task.stage` event);
   - `requestIntegrations`: a new request for a `VERIFIED` Task, and — every round — the request of an `INTEGRATION_READY` Task whose `integration.apply` effect is missing or has ended (`failed`, `retired`, `done`) is enqueued again with `integration.requested { again: true }`;
   - `check`: the Mission is blocked when its attempt, wall-clock or token budget is exhausted (wall-clock moves with time, tokens with metering), and a Task is blocked when its own token budget is;
   - the refusal of item 3;
   - new contracts when their hashed content changed: a ContextPackage (one row, two artifact files and their rows) and an AgentSpec (one row and `agent_spec.created`). For a Task that is held back only by its provider's cap the contracts are built in every round; they come out unchanged unless, for example, a token budget is set and tokens were used since (a headless contract carries the lines "N used; M remaining", `context-builder/render.ts`), the repository rules at the target branch changed, or another provider's cooldown began or ended (the AgentSpec's `selection.filtered`). With the default policy — no provider caps, no token budget — a waiting Task is stopped at the concurrency limit before anything is built.
   Nothing else is written: no random id, timestamp or elapsed time enters either hash.
3. **The refusal.** On `no_eligible_provider` the round writes `task.admission_refused` on the Task, `after` = the error's `data` (`installed`, `filtered`, and when they apply `accountCooldown` and `roleProviderUnavailable`; built in a fixed order by `agent-factory/provider-selection.ts`, and `accountCooldown[].until` is the continuation's due time, which does not move — so two refusals of an unchanged situation are equal as JSON text, also after the round trip through the audit table) — every round, for every such Task. `docs/reference/control-plane.md` says so ("每轮各追加一条 task.admission_refused，不去重").
4. **Who reads refusals.** `read-models/task-waiting-on.ts` takes the Task's **latest** `task.admission_refused` and counts it only when its `sequence` is greater than that of the Task's latest `task.stage` audit event (`getLatestReadModelAudit`, object kind `task`, object id the Task's id); it reads `accountCooldown[].until` from it. `read-models/pending-task-items.ts` takes the **oldest** refusal after that stage event for "since". `tests/e2e/mission-home-since.spec.ts` pauses and resumes a Mission and then polls until every refused Task has a **newer** refusal (a greater sequence and a later time): the round of a real event must go on writing a refusal each time. That spec is not changed by this Task and must pass.
5. **Coalescing.** While a round of a Mission is in flight, `scheduleRound` only records `active.pending = trigger` and answers the flight's promise; when the round ends — also when it failed — one more round runs with the pending trigger. The last trigger wins.
6. **The tick.** `startAxiomControlPlane` defines `reconcile` (effect recovery, then an outbox kick and `recovery.reconcileAttempts()`; a verification kick), calls it once, then `plane.attemptReconcileTimer = setInterval(reconcile, ATTEMPT_RECONCILE_INTERVAL_MS)` (60 000 ms, `recovery/recovery-service.ts`) and `unref()`s it; after that it schedules the `resume` rounds. `stopAxiomControlPlane` clears the timer. A Mission whose Run binding recovery found lost is `BLOCKED` by then, not `EXECUTING`. `plane.store.listMissions({ status: 'EXECUTING' })` exists (`db/missions-store.ts`; it parses its input and reads SQLite, so it can throw) and is what `attempt-continuation.ts` uses; recovery and token metering call `listMissions({})`.

## Outcome

With nothing else happening, a `READY` Task that can be admitted is admitted within one tick, a verified Task that can be requested is requested within one tick, and an exhausted Mission budget is noticed within one tick when a Task is waiting — whatever became of the round that should have done it. A sweep round that finds the situation unchanged writes nothing beyond what ground truth 2 lists. `scheduler.round` events say `sweep` when the safety net was what admitted something: that is a lost trigger worth looking for.
