# Task M4-2b — The switch: every Scheduler round requests integration of the Tasks that are verified, so a verified Task goes on to `INTEGRATED` and a Task with dependencies runs for the first time (the M4-2b row of `docs/plans/M4.md`; D92, approved by Henry 2026-11-15; main process, the e2e fixture helper and one new e2e spec; no store, contract, renderer, CLI or RPC-file change)

Planner brief, 2026-11-16 (verifier). After M4-2a-3 the executor of `integration.apply` takes a verified candidate all the way: merge at the integration head, regression on the merge commit, the head advanced, the batch `PROMOTED`, the Task `INTEGRATED`. Nothing asks it to. This Task adds the asking. In every Scheduler round, right after readiness is recomputed, each Task that is `VERIFIED`, has a passing run of its active candidate and whose upstream Tasks are all `INTEGRATED` becomes `INTEGRATION_READY`, and an `integration.apply` effect is enqueued in the same transaction; a Task that is back in `INTEGRATION_READY` after its earlier request ended is asked for again. From here on a verified Task is integrated without anybody doing anything, and the Tasks that depend on it become `READY` — until now no Task with a dependency could ever start. The e2e fixture holds this step unless a spec asks for it, exactly as it holds verification, so every existing spec ends where it ends today; one new spec runs the chain through a dependent Task (the plan row said the e2e specs would "change with it": holding the step and adding one spec is the verifier's detail, and the planner commit of this brief rewrites the row).

## Ground truth (verifier, 2026-11-16; read in the code at main `48a6ad00ed`)

1. **What happens after a verdict today.** Two places move a Task to `VERIFIED`, each inside its own transaction through `missions.transitionTaskStage`: `settleVerificationVerdict` (`src/main/axiom/verification/verification-settlement.ts`, actor `VerificationService`, reason `verification_passed`) and `resolveVerification` (`verification-resolution.ts`, actor `user`, reason `verification_resolved`). Nothing reads `VERIFIED` afterwards: `TASK_STAGE_TRANSITIONS` (`src/shared/axiom-contract/lifecycle.ts`) allows `VERIFIED → INTEGRATION_READY | BLOCKED | CANCELED` and `INTEGRATION_READY → INTEGRATED | NEEDS_FIX | BLOCKED | CANCELED`, but no product code writes `INTEGRATION_READY`. `canBecomeReady` (`mission-controller/task-readiness.ts`) lets a `DEFINED` Task become `READY` only when every upstream Task is `INTEGRATED`, so today only the Tasks without dependencies ever run.
2. **Rounds.** Every public `MissionController.transitionTaskStage` (and `createTask`, `adjustTask`, `cancelTask`, start, resume, unblock, a policy update) calls `scheduleAfterWrite`: outside a transaction at once, inside one in a microtask after the commit — and the Control Plane turns that into `scheduler.scheduleRound(missionId, trigger)` (`control-plane.ts`). `Scheduler.runRound` (`scheduler/scheduler.ts`) returns at once unless the Mission is `EXECUTING`, then calls `this.missions.recomputeReadiness(missionId)`, then walks the `READY` Tasks and admits Attempts (awaiting the context and agent contracts per Task). Overlapping calls for one Mission are coalesced: one more round runs after the current one. At boot `startAxiomControlPlane` (`control-plane-boot.ts`) schedules one round per `EXECUTING` Mission that recovery did not block. There is no periodic round.
3. **The request the executor expects** (`src/main/axiom/integration/`, `src/shared/axiom-contract/effects.ts`). An effect of kind `integration.apply` whose key is the candidate's id and whose payload is strictly `{ taskId, candidateId }`. The outbox runs one effect per kind and Mission at a time, the one due first, then by row (`ORDER BY due_at, rowid`), so requests of one Mission are served in the order they were enqueued. A try first settles, for the whole Mission, promotions the ref already shows and closes batches that can never finish; for its own request it then does something only for an `ACTIVE` candidate whose Task is `INTEGRATION_READY`; it answers `later` (30 s) while that Task is `BLOCKED` out of `INTEGRATION_READY`, the Mission is not `EXECUTING`, or another candidate's batch is open; after three failed tries `abandonIntegration` supersedes the batch and moves the Task to `BLOCKED` with the reason `integration_unavailable` — the candidate stays `ACTIVE` and the effect ends `failed`. M4-2a-3 added: a passed batch is promoted — the integration branch advances to the merge commit, and one transaction records `PROMOTED`, the Task `INTEGRATED` and the audit event `integration.batch_promoted` (`after` holds `status`, `baseCommit`, `mergeCommit`, `taskIntegrated`, `caughtUp`); a new batch starts only from the head the Mission's audit events recorded (`integration.base_created` / `integration.base_reused` from the Mission's start, then the latest `integration.batch_promoted`) and fails with `integration_head_unexpected` otherwise; a promotion fails with `integration_branch_checked_out` while some worktree has the integration branch checked out; and a request that finds its candidate's batch already `PROMOTED` while the Task is `INTEGRATION_READY` makes the Task `INTEGRATED` and ends (`finishPromotedRequest`).
4. **`enqueue`.** `EffectOutbox.enqueue` (`outbox/effect-outbox.ts`) needs a caller's transaction (`store.enqueueEffect` throws without one) and wakes the outbox in a microtask. The insert is an upsert on kind and key (`db/effects-store.ts`): a row that is `pending`, `failed`, `retired` or `done` becomes `pending` again, due now, with `attempts` 0 and no `lastError`; a row that is `running` is left as it is. So enqueueing again for a `pending` row would erase its tries and its delay.
5. **How a blocked Task comes back.** `adjustTask` (`mission-controller/task-adjustment.ts`; `controller.adjustTask({ taskId, rationale, actor })`) returns a `BLOCKED` Task to its `previousStage` — also to `INTEGRATION_READY` — with the reason `adjusted`, unless the adjustment changes nothing but the acceptance criteria of a Task that has a candidate (that one stays `BLOCKED`); `rerunVerification` (`verification/verification-rerun.ts`) takes a `BLOCKED` Task with an `ACTIVE` candidate to `VERIFYING` with a new run. Neither enqueues `integration.apply`. So a Task that was blocked with `integration_unavailable` and then adjusted sits in `INTEGRATION_READY` with a `failed` effect, and nothing would ever try again.

A run a person resolved as passed has the status `PASS` like a deterministic one.

## Outcome

In a Mission that is `EXECUTING`, a Task whose candidate passed verification is requested into the integration queue by the next Scheduler round — which the verdict's own transaction schedules — and the executor of M4-2a-3 then merges, tests and promotes it; its dependents become `READY` in the round that the promotion schedules. Requests are made in the order the Tasks were verified. A Task without a passing run of its active candidate, or with an upstream Task that is not `INTEGRATED`, is not requested and nothing is written about it. A Task that returns to `INTEGRATION_READY` after its request ended — a person adjusted it after `integration_unavailable` — is asked for again by the next round. Under e2e the step is held unless a spec turns it on.
