# Task SCHEMA-2 — a database stamped by a newer Axiom is left alone: the Control Plane is not built on it, every request that needs the Control Plane is refused with one code, a reason, two numbers and a next step, and the rest of the application works (the "Axiom 的 schema 版本号" row of `docs/plans/M4.md`, second half; D93 item 2 with its revision line of 2026-11-16; `src/main/axiom` only — no kernel, contract, CLI or renderer product file changes)

Planner brief, 2026-11-17 (verifier). SCHEMA-1 gave every database a row that says which Axiom schema wrote it, and left a row from a newer Axiom exactly as it found it. Nothing reads that row yet. So a build that opens a database a newer Axiom has migrated — the case of installing an older version again after an update — starts its Control Plane on it as if nothing were different: recovery, the outbox, the Scheduler and every `axiom.*` request read and write rows whose meaning this build may not know. Henry decided on 2026-11-16 that such a build stops its Control Plane and says so, rather than warn and carry on (pending item 9 of that day, which also said that kernel orchestration writes are refused there; the revision line under D93). This Task is that stop, at the one place every use of the Control Plane passes through. Terminals, editors, source control and the browser do not pass through it and work as before.

Read first: `docs/PROJECT_CONSTITUTION.md` (invariants 5 to 7), `AGENTS.md` (Control Plane Boundary; Lazy Senior Dev Mode), `docs/reference/control-plane.md` (the subsection `### Axiom schema version（SCHEMA-1）`), `docs/decisions/DECISION_LOG.md` D93 with its revision line, `.axiom-work/verifications/SCHEMA-1-1.md`.

## Ground truth (verifier, 2026-11-17; read in the code at main `3ce68f4c6d`)

(b) Axiom's own modules (execution, messaging, read models, recovery), reached only through an RPC handler or through objects the Control Plane itself built. (c) `admission/mission-managed-run-guard.ts`, called by sixteen kernel verbs — `workerStart`, `workerRelease`, `workerRetain`, `workerStop`, `workerAbandon`, the worker terminal input report, `gateCreate`, `gateResolve`, `send` for the authority-bearing types and for groups, `reply`, `ask`, `taskCreate`, `taskUpdate`, `dispatch`, `runUse`, `reset`: `assertNotMissionManaged` asks the store only once a Run was resolved (a call that names no Run, Task, dispatch or sender returns before; a pane asks only when it was a worker's terminal), `assertTaskCreateAllowed` always asks, `assertResetAllowed` asks for any scope. ## Outcome

On a database whose stamp is above this build's Axiom schema version, nothing of the Control Plane exists: no store, no outbox, no Scheduler, no timer, no consumer, and not one Axiom row is read or written by this build. Every `axiom.*` request that needs the Control Plane, every kernel verb that must ask whether a Mission owns a Run, and every restricted request of an agent session that holds a dispatch answers the same refusal — the code `axiom_schema_newer`, a sentence that says a newer Axiom wrote this database, the two version numbers, and the next step. The application starts, runs and quits as on any database. On a database at this build's version nothing changes.
