# Task REMOTE-1a — a Mission whose target branch has a remote counterpart starts from the remote tip and is finalized against it

**Why.** Until now a Mission reads only the user's local target branch: the integration branch is created on it, finalization compares against it, and delivery stops as soon as the repository has a remote. Henry decided on 2026-11-28 that 0.1 works with remotes (the revision lines of that day under D89 and D92 in `docs/decisions/DECISION_LOG.md`). This Task is the first step: **when the target branch has a counterpart on a remote, that counterpart is what the Mission starts from and what finalization compares with.** It is also the first code of the Control Plane that contacts a remote. It only ever fetches one branch; it never pushes, never writes a local branch of the user, and delivery is not touched (a repository with a remote still stops there; pushing and the pull request are later Tasks).

High-risk class: it reaches the network and writes a remote-tracking ref in the user's repository (what `git fetch` does), and it changes which commit a Mission is built on.

**The rules this Task implements — it does not widen any of them.** If something you need seems to require more than they allow, stop and say so in the report.

- D92 j (revision of 2026-11-28): "目标分支在远端有对应分支时（目标分支配置的上游；没配就是 `origin` 上的同名分支；都没有就按没有远端走），Mission 以远端的那一条为准——开始、收尾、交付前各取一次，只取这一条、不取标签；集成分支建在取到的提交上；本地的同名分支不动" — when the target branch has a remote counterpart (its configured upstream; without one, the branch of the same name on `origin`; with neither, the repository is treated as having no remote), the Mission follows that counterpart: one fetch at start, one at finalization, one before delivery, of that one branch and no tags; the integration branch is created on the fetched commit; the local branch of the same name is not touched. **This Task does the start and the finalization. The fetch before delivery belongs to the Task that opens delivery to a remote (REMOTE-2a).**
- D92 e: the target branch is not followed while the Mission executes. Nothing in this Task fetches between start and finalization.
- D92 h and D70 item 2 are unchanged: a repository without a remote counterpart behaves, byte for byte, as it does today.
- D95 (2026-11-28): what the Orca kernel already has is called, not rewritten; a pure TypeScript piece of T3 Code may be ported with its origin and copyright line in the file header (`NOTICE.md` carries the notice).
- `AGENTS.md`: Git 2.25 is the baseline (no option newer than that); hooks-off git goes through `withHooklessGit`; no force, no deletion of refs; explicit refs everywhere.
- Two refusals of this Task are stricter than those texts and are the verifier's details, which Henry may overrule: a configured upstream that no longer exists on the remote refuses the start (it is not read as "no remote"), and a local branch that holds commits the remote lacks needs an acknowledgement.

## Outcome

A Mission whose target branch has a remote counterpart is started on the commit that a fresh fetch of that one branch brings, whatever the local branch looks like; the caller is told when the remote cannot be read, when the configured upstream no longer exists there, and when the local branch holds commits the remote lacks (those need an explicit acknowledgement). Finalization fetches again and compares the integration branch with the remote tip. Every such step leaves evidence that names the remote, the branch and the commit. A repository without a remote counterpart goes through exactly the code path and writes exactly the records it does today.

2. **Three refusal codes** in `MISSION_CONTROLLER_ERROR_CODES` (literals): `target_remote_unavailable`, `target_remote_branch_missing`, `target_local_ahead`. Each is thrown as a `MissionControllerError` whose `data` holds `missionId`, `remote`, `branch` and a `reason`: one fixed English sentence written by you that says what happened and what the person can do. For `target_remote_unavailable`, `data` also holds `failure`, one of `authentication`, `unreachable`, `repository`, `timeout`, `reference_lock`, `local_reference`, `unknown` (literals). Known limits of this Task, to be written into the documentation section: a repository that has `origin` cannot start a Mission while `origin` is unreachable, even for a branch that was never pushed; only `origin` is tried when no upstream is configured; a branch that exists only on the remote cannot be a target; the Planner still works on the local branch, because planning happens before the start; a Mission that stays in `FINALIZING` fetches on every scheduler round, and a fetch that hangs costs up to a minute for each of the effect's three attempts; when a fetch fails at finalization the page shows only `finalization_unavailable` (the fixed sentence with the `failure` word is the error text the outbox keeps for the effect); the Missions page cannot yet send the acknowledgement (REMOTE-1b), so a start that needs it can be refused there with `target_local_ahead` and no way to go on from the page; an older build cannot read a finalization record that carries `targetRef`; a remote that itself prints git's wording for a missing branch is read as not having the branch.
