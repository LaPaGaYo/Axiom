# Task M3-09-3b-2 — the Missions page follows the Control Plane by itself: a quiet timed read (renderer)

Planner brief, 2026-11-14 (verifier). Second half of M3-09-3b. M3-09-3b-1 made the page safe to re-read every few seconds — a pending row's start no longer moves between reads, and the read the page did not show is gone. This part adds the re-read itself: while the Missions page is open in a visible window it reads the Control Plane again every five seconds, without going busy and without touching what the person is doing.

Read first: `AGENTS.md` (UI and Product Experience — "UI state is never authoritative project state"; Execution Kernel Boundary — reuse before new infrastructure), `docs/STYLEGUIDE.md`, `docs/reference/control-plane.md` ("Mission 首页的待处理项（M3-09-3a）", "Mission 首页的起始时间（M3-09-3b-1）"), `tests/e2e/AGENTS.md`.

## Ground truth (verifier, 2026-11-14, main `88a2695ba0`; every fact here was read in the code, the tests or the specs at that commit)

1. **How the page reads today.** `useMissionsPageController` (`use-missions-page-controller.ts`, 239 lines; the sidecar of M3-09-3b-1 holds it at 250 or fewer) has one read, `refresh`: it raises a generation counter, sets `loading`, reads the Mission list and — through `readMission` (`mission-read.ts`) — the selected Mission and Task, drops the response when a newer read or a changed selection has moved the generation on, clears the page error on success, and on failure reports it (the page's error line and a toast). It runs when the page mounts, when the selection changes, when the person presses `Refresh Missions`, and after every mutation (`mutate` always re-reads). `busy` is `loading`, an open confirmation, or a mutation in flight.
2. **What a read does to the page.** While `loading` is set, `MissionsPageSurface.tsx` marks the grid `aria-busy`, and every control is disabled through `busy` — including fields a person may be typing in: the rejection reason of a proposed plan (`PlanReviewPanel.tsx`, `disabled={busy}`), the answer box of a pending message (`MessageTimeline.tsx`), the fields of the Task forms. A field that becomes disabled loses focus. That is right for a read the person asked for and wrong for one the page starts by itself.
3. **What survives a re-render.** Form state is local to the components, and their keys are stable across reads (`TaskDetail` by Task id, the plan panel by plan id, the action forms by the pending item's object id); `TaskDetail` moves focus only when the Task id changes. `TaskVerificationActions` and `TaskQuietCancel` close a form when a read no longer offers its action — existing, tested behaviour that this Task does not change.
4. **Where the page lives.** `AppWorkspaceShell` renders `MissionsPage` only while the Missions view is the active one; leaving the view unmounts the page.
5. **The kernel's timer.** `installWindowVisibilityInterval` (`src/renderer/src/lib/window-visibility-interval.ts`) is what the kernel's panels poll with (ports, checks, rate limits, the Automations page). It calls a callback every `intervalMs` only while `document.visibilityState` is `visible`, stops while the window is hidden, calls the callback once at the moment the window becomes visible again — and once, synchronously, when it is installed in a visible window — and returns a function that stops it. The Automations page tests replace the module with a double (`automations-page-test-harness.tsx`).
6. **The timer pin.** Six sidecars (M3-09-2 to M3-09-3b-1) assert that the non-test files of the missions folder contain neither `setInterval` nor `setTimeout`. Calling the kernel helper keeps that true as long as its `setIntervalFn` option is not passed (the option's name contains the pinned text).
7. **Existing tests count reads.** `MissionPendingRead.test.tsx` and the controller test assert exact numbers of calls after mount and after each refresh, and they load the real helper module.
8. **E2E.** No Mission spec depends on a stale page; six of them click `Refresh Missions` after changing state through `desktopCall`, which keeps working. Under `ORCA_BACKGROUND_LAUNCH=1` the window is never shown; specs that need a visible document set it on the page (`tests/e2e/helpers/resource-manager-visible-fixture.ts`: a getter for `document.visibilityState` and a `visibilitychange` event). A Mission can be created and a plan proposed through `desktopCall` without anything starting to run (`mission-home-since.spec.ts` does both before it approves the plan), and nothing limits a repository to one Mission. A proposed plan puts the field `Reason for rejection` and the buttons `Approve plan` / `Reject plan` on the page, inside the region `Plan review`.
9. **A wrong sentence of the last brief.** The brief of M3-09-3b-1 said audit times have one-second precision. Only audits written without a time do; the scheduler passes its own clock, so refusal audits carry milliseconds. `mission-home-since.spec.ts` therefore waits one wall-clock second it does not need (the `expect.poll(() => Date.now(), …)` before `Resume Mission`), under a comment that repeats the error.

## Outcome

While the Missions page is open in a visible window, what it shows is at most a few seconds behind the Control Plane, without the person pressing anything; a read the page starts by itself never disables a control, never takes focus and never raises a toast; and when such a read fails the page says so and waits for the person.

## Deliverables

1. **A timed read.** While the page is mounted it re-reads on the kernel's `installWindowVisibilityInterval`, every 5 000 ms; the interval is installed once for the life of the page — the helper calls its callback each time it is installed, so re-installing it when state changes would read again — and stopped when the page unmounts. It is the read `Refresh Missions` makes — the list, the selected Mission, the selected Task, through the same `readMission` — under the same generation rule, and what it puts on the page is what a manual read would put there. Hidden windows and the immediate read on becoming visible are the helper's doing; nothing is added for them.
2. **Quiet.** A timed read does not set `loading` and does not make the page `busy`: the grid is not `aria-busy`, no control is disabled, the loading line does not show, no toast is raised.
3. **Only when the page is idle.** A tick does nothing while any of these holds: a read is unanswered (the person's, the one after a mutation or a selection, or an earlier timed one); a mutation is unanswered; a confirmation is open; the create dialog is open; or the last read failed and no read other than a timed one has succeeded since. The call the helper makes when it is installed must not become a second read at mount — the existing tests count the reads.
4. **A failed timed read.** The page keeps the data it shows; the failure goes to the page's error line in the same `code: message` form a failed manual read uses, without a toast; and by 3 the timed reads then stop until a read started by the person, by a selection or by a mutation succeeds. A timed read that succeeds does not touch the error line.
5. **The spec of the last part.** In `tests/e2e/mission-home-since.spec.ts` the wall-clock wait before `Resume Mission` and its comment are removed (ground truth 9); nothing else in that spec changes.
6. **E2E** (host, verifier-run): a new spec `tests/e2e/mission-home-refresh.spec.ts`, set up through `desktopCall` the way `mission-home-since.spec.ts` is up to the proposal — the fixture clone, `repo.add`, `axiom.mission.create`, `axiom.plan.propose` — with no approval and no start, so nothing runs. On the page: the Missions view, the Mission selected, the document made visible on the page side as `resource-manager-visible-fixture.ts` does it (the window itself stays hidden). From there the spec never clicks `Refresh Missions`. Responses are parsed with the contract schemas; every wait for something to appear is an assertion with a timeout.
   - **The page follows.** A reason is typed into `Reason for rejection` and the field has focus. A second Mission is created through `desktopCall`: its id appears in the `Mission list` navigation by itself. The field still holds the text and is focused (`toBeFocused`), and `Approve plan` is enabled.
   - **Not while hidden.** The document is set hidden the same way and a third Mission is created; after two and a half intervals its id is still not in the list. The document is set visible: the id appears.
   - **The selected Mission follows too.** The plan is approved through `desktopCall`: the heading of the `Plan review` region shows `APPROVED` and the `Reason for rejection` field is gone, by itself.
   - The spec attaches one screenshot of the `Plan review` region after the first step, the typed reason in it (`captureDetail` with the region name), taken after the focus assertion.
   - The report lists every asserted selector and field with its source.
7. **Docs.** `docs/reference/control-plane.md` gains a short section "Mission 页的定时刷新（M3-09-3b-2）" after the M3-09-3b-1 one: the interval and the helper it rides on, that a timed read is the manual read without the busy state and the toast, the idle rule of deliverable 3, what a failed timed read does, and the limits listed under "Report".

## Non-goals

Updates pushed from the main process; a setting for the interval; a "last updated" time or any other sign of the timed read on the page; retry or backoff after a failed read; keeping a form open when a read no longer offers its action, or when part of a read failed (both stay as they are for every read); changing what `Refresh Missions` or the read after a mutation does; new copy or catalog keys; the supervision controls and the "while you were away" summary (M3-09-3c).
