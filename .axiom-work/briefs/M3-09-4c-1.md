# Task M3-09-4c-1 — A policy update is followed at once by one admission round (scope approved by Henry 2026-11-14; main process, with its own e2e spec; no renderer or CLI change)

Planner brief, 2026-11-15 (verifier). A person can change a Mission's policy — who works, how many Tasks run at once, the verification rules — through `axiom.policy.update`. The scheduler, however, only looks at a Mission when something else happens: a Task changes stage, the Mission is resumed, the app restarts, a continuation comes due. So a Task that waits only because of the old policy — no provider it may use, the concurrency limit reached — keeps waiting after the policy has been fixed, and the pending view goes on naming a reason that is no longer true. The view even lists `axiom.policy.update` as the thing to do. This Task makes a committed policy update request ONE admission round for its Mission, and makes sure a round that is running at that moment cannot swallow the request. Who may change a policy, and what may be changed, stay as they are.

## Ground truth (verifier, 2026-11-15; read in the code at main `9b69b9a5a9`; on main `9cf9adb426`, where this brief sits, `mission-controller.ts` has three more lines in `rejectPlan` (M3-09-4b-2), so its line numbers after that method are three higher and it has 250 counted lines; the other files named here are unchanged, and the sidecar was dry-run on that code)

1. **The write.** `axiom.policy.update` is `desktop_only` (`src/main/axiom/authority/caller-authority.ts:25`); its parameters are `{ missionId, patch }` with a strict patch of `routing`, `verificationRules`, `concurrencyLimit`, `readinessThreshold` and a `budget` key kept only so that it can be refused (`src/shared/axiom-contract/policy-params.ts:7-17`). The handler (`src/main/runtime/rpc/methods/axiom/policy.ts:28-68`, the file has 69 lines) refuses `VERIFIED` (`threshold_not_supported`) and any `budget` key (`approval_required`) before it writes, then runs ONE `store.transaction('policy_update', …)` that reads the policy (`mission_not_found` when the Mission or its policy is missing), stores the merged policy and appends the audit `policy.updated { before, after }`, and returns `{ policy }`. It writes through the store directly, not through `MissionController`; it has no check of the Mission's status and no check whether anything changed; **it requests no scheduling**. The transaction is the outermost one on this path, so the row and the audit are durable when it returns. A replayed request (same request id, completed receipt) does not run the handler again.
2. **How rounds are requested.** The one entry point is `Scheduler.scheduleRound(missionId, trigger)` (`src/main/axiom/scheduler/scheduler.ts:69-99`). `ScheduleTrigger` is the union `'mission_start' | 'stage_change' | 'resume' | 'manual'` on one line (`:19`, 84 columns). The trigger is recorded durably only in the audit `scheduler.round { trigger, admitted, skipped }` (the wiring also logs it when a round fails), which is written only when the round admitted something or blocked the Mission on its budget (`:223-229`). There is no periodic admission pass and no timer in the scheduler (an earlier pin forbids one).
3. **Coalescing.** One flight per Mission (`scheduler.ts:51`, `:69-99`): a call that arrives while a round runs stores `active.pending = trigger` (only the latest is kept) and returns the running flight's promise; when the round ends the loop runs one more round for the pending trigger. **When the running round throws, the loop ends with it and the pending trigger is dropped** — the flight is deleted in `.finally` and its promise rejects.
4. **Who requests rounds today.** `MissionController.scheduleAfterWrite(missionId, trigger, wakeOthers?)` (`src/main/axiom/mission-controller/mission-controller.ts:70-108`, private): outside a transaction it calls the `onScheduleTrigger` dependency at once; inside one it remembers the Mission's last audit row and, in a microtask, calls the dependency only if that row was committed. Its callers are the controller's own methods (`createTask`, `adjustTask`, `startExecution`, `resumeMission`, `unblockMission`, `transitionTaskStage`, `cancelTask`, and `recomputeReadiness(missionId, admissionChanged)` — the typed-question answer passes `true` because answering changes admission without moving a stage, `src/main/axiom/messaging/question-answer.ts:54-55`). The dependency is wired in `src/main/axiom/control-plane.ts:87-93`: `scheduler.scheduleRound(missionId, trigger)` with a `.catch` that logs `[axiom] Scheduler round failed`. Two other sources call the scheduler directly: the `attempt.continue` effect and the boot pass (`resume`).
5. **What a round does with the policy.** `runRound` (`scheduler.ts:160-231`) returns at once unless the Mission is `EXECUTING`; for each READY Task it reads the policy fresh (`check`, `:101-134`), skips on `concurrency` when the running count has reached `policy.concurrencyLimit`, builds the contracts, and `admit` (`:233-304`) re-reads everything under the write lock and answers `stale` when the policy changed since the pre-check. Nothing caches a provider choice between rounds. One round can admit several Tasks. An admission moves the Task to `RUNNING` through `missions.transitionTaskStage` inside its transaction (`:288`), so on the wired controller every admitting round is followed, in the same flight, by one `stage_change` round that finds nothing more to do.
6. **Where a policy change makes a running round throw.** `buildWorkerContracts` (`src/main/axiom/agent-factory/agent-factory.ts:196-223`) picks the provider (`selectWorkerProvider`, which reads the policy), awaits the context build, then builds the AgentSpec (`build`, which reads the policy again) and throws a plain `Error('Worker provider changed during admission')` when the two disagree (`:219-221`). `runRound` passes on every error except `AgentFactoryError('no_eligible_provider')` (`scheduler.ts:202-208`), which it records as the audit `task.admission_refused` and a skip. So a routing change that commits between those two reads ends the round with a rejection — and, by fact 3, drops a trigger that arrived meanwhile.
7. **What the person sees while a Task waits** (`src/main/axiom/read-models/task-waiting-on.ts:36-64`, `pending-task-items.ts:40-50`): a READY Task whose latest `task.admission_refused` is newer than its latest stage audit waits on `admission` / `no_eligible_provider`, and the Mission's pending view lists it as `task_blocked` with the actions `axiom.policy.update` and `axiom.task.cancel`; a READY Task while the running count has reached the limit waits on `admission` / `concurrency` (no pending item). Both are computed from the policy and the audits as they are now, so after the policy is fixed the first stays wrong until a round runs.

## Outcome

After this Task, a successful `axiom.policy.update` is followed at once by one admission round for that Mission, recorded with the trigger `policy`: a Task that waited only for a provider it may use, for the concurrency limit or for a provider's cap starts without any other event, and one that still cannot start gets a fresh refusal, so what the person reads is true again. A refused or rolled-back update requests nothing. A trigger that arrives while a round is running is honoured even when that round throws. Everything else about policy updates and about admission is as on main.
