# Task M4-2a-2 — The merged-tree regression: after the merge the executor runs the Task's checks on the merge commit, and the batch becomes `PROMOTABLE` or `FAILED` (second part of the M4-2a row of `docs/plans/M4.md`; D92 b, approved by Henry 2026-11-15; main process, store and contract; no renderer, CLI, RPC-file or e2e change)

Planner brief, 2026-11-16 (verifier). M4-1b's executor merges one verified candidate into a scratch worktree made from the Mission's integration head and stops with the batch in `TESTING`. M4-2a-1 gave a verification run a `batchId`, taught the verification service to leave such runs alone, and added `integrationGates` with `resolveIntegrationPlan`. This Task joins the two: in the same try, once the batch is `TESTING`, the executor runs the regression in the scratch worktree at the merge commit and records it as a verification run of that batch. A pass makes the batch `PROMOTABLE`; a failure makes it `FAILED`, retires the candidate and sends the Task back; an inconclusive run fails the try, and three such tries end as M4-1b's exhaustion does. A batch found in `TESTING` after an interruption is taken up again. The executor also learns to stop: the outbox hands every executor a signal that its `stop` aborts. Two gaps of M4-1b are closed on the way (ground truth 3). **The integration head still does not move**: promotion, `PROMOTED` and `INTEGRATED` are M4-2a-3, and the switch that sends verified Tasks into the queue is M4-2b — so no product path enqueues `integration.apply` yet and every existing flow behaves as on main.

## Outcome

After this Task one try of `integration.apply` that reaches or finds `TESTING` runs the merged-tree regression in the scratch worktree, on the merge commit, and leaves one verification run of the batch that says what ran and how it ended. `PASS` → the batch is `PROMOTABLE`, the Task stays `INTEGRATION_READY`, the integration head is where it was. `FAIL` → the batch is `FAILED`, the candidate `SUPERSEDED` without a successor, the Task `READY` again or `BLOCKED` when its tries are used up. `INCONCLUSIVE` → the batch stays `TESTING`, the try fails, and the third failed try ends as today. A stopped outbox ends a running regression within seconds without spending a try. Every try first closes the open batches of its Mission that can never finish. And no existing reader of verification runs sees a batch's run unless it asks for that batch.

3. **The regression**, in one or more NEW modules under `src/main/axiom/integration/` (suggested `integration-regression.ts`; `integration-apply.ts` has 66 lines to spare, so the checks of a request and the regression cannot both live in it — split by concern, name files after what they hold). The executor's dependencies gain `artifacts` (`createControlPlane` passes the store it already has; that call is the only change in `control-plane.ts`). Given a batch in `TESTING`, its Mission, Task and candidate, the scratch worktree checked out at the batch's merge commit, the effect and the signal:
   1. Read the Mission's rules (`VerificationRulesSchema.safeParse` of the stored policy's `verificationRules`). When they do not parse, no command runs and the verdict is `INCONCLUSIVE` with the reason `policy_invalid`.
   2. One transaction (`integration_regression_started`): check that the batch is `TESTING`, the Task `INTEGRATION_READY` and the candidate `ACTIVE` and theirs — otherwise the regression is no longer current (see 5); cancel every `QUEUED` or `RUNNING` run of this batch (`CANCELED`, `finishedAt`, an audit `integration.regression_canceled` with the run id and the reason `regression_retried`); insert a run of this batch (`QUEUED`, verifier `IntegrationController`) and claim it with the effect's `leaseEpoch` as its `runtimeEpoch` and the verifier `IntegrationController`; store its `commands` (the plan's commands, redacted as verification does) and a `verdictDetail` of `{ phase: 'checking', baseline }`, where `baseline` is `{ kind: 'integration_merge', batchId, baseCommit, mergeCommit }`; audit `integration.regression_started` with the batch's status, the run id, the merge commit and the number of commands.
   3. The plan is `resolveIntegrationPlan(task.spec, rules)`; the deadline is now plus `rules.timeBudgetMinutes`. Run it with `executeVerificationPlan` in the scratch worktree, with the signal and an `assertCurrent` that ends the regression when the signal is aborted (stopped, see 5) or when it is no longer current: the run is not `RUNNING` under this claim any more, the batch not `TESTING`, the Task not `INTEGRATION_READY`, or the candidate not `ACTIVE`.
   4. The verdict comes from `decideVerificationVerdict` — the same function, so a regression command is judged exactly as a verification command — with a clear gate, `nonCodeTask` false, an empty artifact check and no acceptance entries. The diff gate, the tampering check, the Worker's artifacts and the acceptance evaluation are not run (D92 b). Two corrections on top of it: when the scratch worktree no longer stands at the merge commit after the plan (`rev-parse HEAD`, or it cannot be read), the verdict is `INCONCLUSIVE` with the reason `environment` and the detail `scratch_changed`, whatever the commands said — a verdict is about the merge commit or it is not a verdict; and a `PASS` of a plan without any command carries the detail `no_commands` (a Task without command criteria in a repository without gates has nothing to run; that is a pass, and the record says that nothing ran). The stored verdict has no `escalation`: nobody reviews a regression.
   5. Write one evidence artifact (`kind: 'evidence'`, JSON, `createdBy: 'IntegrationController'`, related to the run, the Task, the candidate and the batch) with what `runVerificationChecks` stores for a candidate run that applies here — verdict, checks, tools, tool versions, run, Task, candidate, epoch, claim, deadline, start and finish — plus the batch id and `baseline`.
   6. One transaction (`integration_regression_verdict`): the checks of 2 again, and the run still `RUNNING` under this claim — otherwise the regression is no longer current and nothing is written. Update the run: status, `finishedAt`, `commands`, `toolVersions`, and a `verdictDetail` of `{ phase: 'verdict', …verdict, baseline, verdictArtifactId, evidenceArtifactIds: [it], checks }` with the per-check fields verification stores. Then, by verdict:
      - `PASS`: the batch → `PROMOTABLE`; audit `integration.batch_promotable` (status, run id, merge commit).
      - `FAIL`: the batch → `FAILED`; the candidate and the Task are settled exactly as a conflict settles them, with the reason `integration_regression_failed` in place of `integration_conflict` (candidate `SUPERSEDED` without a successor and its `candidate.superseded` audit; Task `NEEDS_FIX`, then `READY` with `retry` or `BLOCKED` with `retry_budget_exhausted`) — one function for both, `settleIntegrationConflict` keeps its name and its behaviour; audit `integration.batch_failed` (status, run id, the verdict's reason).
      - `INCONCLUSIVE`: the batch stays `TESTING`; audit `integration.regression_inconclusive` (status, run id, the verdict's reason). After the transaction the try throws `regression_inconclusive`.
   A batch's run gets **no** `verification.*` audit event; its events are the `integration.*` ones above, on the batch (`auditIntegration`). The run rests in `PASS`, `FAIL`, `INCONCLUSIVE` or `CANCELED`; it never goes to human review.
4. **The executor goes on from `TESTING`.** (a) After `integration_merged`, the same try runs the regression in the same scratch worktree, which stands at the merge commit. (b) A request whose candidate has an open batch in `TESTING` is ready, not done: `beginBatch` refuses it when the head it read is not the batch's `baseCommit` (`integration_head_moved`), changes no status and writes no `integration.batch_started`; the leftovers are removed and a scratch made as today; after the existing comparison of its head with the base, the scratch is checked out detached at the batch's stored merge commit (through `writeIntegrationGit`, hooks off; a failure is the fixed code `merged_commit_unavailable`) and the regression runs. (c) A request whose candidate has a batch in `PROMOTABLE` answers `done` and changes nothing — M4-2a-3 takes it from there. (d) `PASS` and `FAIL` answer `done`; the scratch is returned as today in every case but a stop.
5. **Three ways a regression ends without a verdict.**
   - **Stopped.** The outbox's signal is aborted — before the regression starts (then no run is inserted) or during it (the plan runner kills the running command). The try answers `{ later: <now> }` — no try is spent — **without** returning the scratch and without settling anything: a run that exists stays `RUNNING`, the batch `TESTING`, and the next try removes the leftover worktree and cancels that run (3.2). A try that finished its work before it noticed the signal ends normally.
   - **No longer current** (3.2, 3.3, 3.6): somebody else changed the batch, the run, the Task or the candidate while the regression ran — a person blocked or cancelled the Task, the Mission was cancelled. The regression stops, cancels its own run if that is still `RUNNING` under its claim (audit `integration.regression_canceled`, reason `regression_interrupted`), the scratch is returned, and the try answers `{ later: <now> }`: no try is spent for what a person did, and the next try decides — it closes the batch (6), waits (a blocked Task), or runs the regression again.
   - **Broken.** Any other error of the regression fails the try with the fixed code `regression_unavailable`; the scratch is returned; a run that exists stays `RUNNING` until the next try cancels it.
6. **A try first closes the batches that can never finish.** An open batch is dead when its Mission is terminal, its candidate is missing or not `ACTIVE`, or its candidate's Task is missing or neither `INTEGRATION_READY` nor `BLOCKED` out of it. Before a try looks at its own request, it supersedes every dead open batch of its Mission — its own candidate's or another's — in one transaction (`integration_stale_batches`): the batch's `QUEUED` and `RUNNING` runs are cancelled as in 3.2 with the reason `request_stale`, and `integration.batch_abandoned` is written with the reason `request_stale`; afterwards the leftover worktrees of those batches are removed, best effort. A try that finds nothing dead writes nothing. Then the request is looked at as today (so a stale request answers `done`, and a request behind another candidate's live batch still waits). `abandonIntegration` cancels the open runs of the batches it supersedes in the same way (reason `integration_unavailable`); share the code. `eligibility` uses `TERMINAL_MISSION_STATUSES`.
