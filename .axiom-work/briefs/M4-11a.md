# Task M4-11a — the Mission page shows how a Mission was judged complete: a Finalization section and, on request, the completion report (the first half of the M4-11 row of `docs/plans/M4.md`; renderer only, on fields the read side already answers; new strings in `en` and `zh` only, D94)

Planner brief, 2026-11-20 (verifier). Since M4-6a a Mission whose Tasks are settled is finalized: the Control Plane reads the two branches, evaluates the completion gate and records what it found; since M4-10 a finalization that passes writes a completion report and the Mission waits for the delivery Approval; since M4-8a a granted Approval can deliver. None of that judgement can be read in the interface. `axiom.mission.show` answers the finalization record on every refresh of the Missions page and the page throws it away; the report is an Artifact that only an RPC call reads. A person who is asked to approve a delivery — the buttons come with M4-11b, the next Task — would approve what they cannot see. This Task puts the judgement on the Mission page, read-only: one section that shows the finalization record, and the completion report when the person asks for it. (`docs/ARCHITECTURE.md` §15, D71, names the completion report as a card of the Mission conversation; that conversation is not built in 0.1, and the plan's M4-11 row puts the report on the Mission page, where M4-5b put the integration block.) It changes no main-process, contract, CLI or kernel file, adds no request the main process does not already answer, and offers no action that changes anything.

Read first: `docs/PROJECT_CONSTITUTION.md`, `AGENTS.md` (UI and Product Experience; Cross-Platform Requirements; Lazy Senior Dev Mode), `docs/STYLEGUIDE.md` (Color roles; Components; UX rules, above all "No green without evidence"), `docs/reference/control-plane.md` (the subsections `### Mission finalization（M4-6a）`, `### Completion report（M4-10）`, `### Mission 页的集成块与 Task 页的合并树回归（M4-5b）` and `### Mission 页的定时刷新（M3-09-3b-2）`), `.axiom-work/briefs/M4-5b.md` (the last Task that built a block of this page; this brief follows its shape).

## Ground truth (verifier, 2026-11-20; read in the code at main `101da45544`)

1. **The record.** `src/shared/axiom-contract/mission-finalization.ts`: `MissionFinalization` is one of two shapes told apart by `outcome`. Both carry `targetBranch`, optional `targetHead` and `integrationHead` (commits: 40 hexadecimal digits, or 64 in a SHA-256 repository), an optional `gate`, and always `at` (UTC ISO 8601). `ready` adds optional `reportArtifactId` and `reportSha256`, which appear together or not at all (a ready record written before M4-10 has neither). `stopped` adds `reason`, one of `target_branch_moved`, `target_branch_not_found`, `integration_head_unexpected`, `completion_gate_failed`, `finalization_unavailable`. `gate` is the ordered list of `FINALIZATION_GATE_IDS` — eight ids, or the first seven in a record written before M4-10 — and each item is `{ id, pass, evidence, detail? }`: `evidence` is the ids or commits the Control Plane judged by, cut at 200, and `detail` is its own text for an item that did not pass, when it has one (Task ids, `blocking Approval`, `#0, #2` for uncovered criteria, `active Goal unavailable`; three of the items never carry one). Only a record whose gate was evaluated carries one (`src/main/axiom/finalization/mission-finalize.ts`): a `ready` record, where every item passed, and a `stopped` record with the reason `completion_gate_failed`. The other four reasons stop before the gate: `integration_head_unexpected` and `target_branch_not_found` carry the integration head and no target head, `target_branch_moved` carries both commits, and `finalization_unavailable` carries the target branch alone.
   What each item checks (`src/main/axiom/finalization/completion-gate.ts`): `tasks_settled` — every Task is in a terminal stage and at least one is `INTEGRATED`; `candidates_verified` — the candidate of every integrated Task has `PASS` as its latest verification; `batches_promoted` — the batch of every integrated Task is `PROMOTED` and its latest merged-tree regression is `PASS`; `integration_head_recorded` — the integration branch is at the commit the Control Plane recorded; `target_branch_contained` — the target branch is contained in the integration branch; `no_open_questions` — no question or gate is pending on a Task in a stage a question can block (`DEFINED`, `READY`, `NEEDS_FIX`, `RUNNING`, `BLOCKED`) and no Approval blocks the Mission; `goal_criteria_covered` — every acceptance criterion of the active Goal is covered by an integrated Task; `limitations_recorded` — the submission of every integrated Task's candidate is on record.
2. **Where it is.** `axiomClient.showMission` (`src/renderer/src/lib/axiom-client.ts`) already parses the answer with `MissionResponseSchema`: `{ mission, approval?, integration?, finalization? }`. `finalization` is there once a finalization was recorded after the Mission last entered `FINALIZING`; it stays while the Mission is `READY_FOR_APPROVAL` and after the Mission has ended — `COMPLETED`, and also `CANCELED` or `FAILED`, because the read does not look at the status; it is gone again when the Mission returns to `FINALIZING` until the next finalization is recorded; a Mission that never reached `FINALIZING` and a main process older than M4-6a send none. `readMission` in `mission-read.ts` takes `{ mission, integration }` out of that answer, so the record never reaches a component. 3. **The report.** When a ready record names a report, `axiomClient.readArtifact({ id })` answers `{ meta, contentBase64 }` (`src/shared/axiom-contract/artifact-params.ts`): `meta.kind` is `completion_report`, `meta.mediaType` is `application/json` (`completion-report.ts` exports that value as `COMPLETION_REPORT_MEDIA_TYPE`), `meta.sha256` is the hash of the content — the main process compares the stored bytes with it on every read and refuses a damaged Artifact (`artifact_corrupt`), so the renderer does not hash anything. The record's `reportSha256` is the hash the finalization wrote down and the delivery Approval is bound to. The content can be up to 8 MiB and is not chunked. It parses with `CompletionReportSchema` (`src/shared/axiom-contract/completion-report.ts`, strict, `version` 1): `mission` (`id`, `repoId`, `targetBranch`); `goal` (`id`, `revision`, `objective`, `constraints`, `criteria` — each `{ index, text, coveredBy }`, `coveredBy` being Task ids —, `revisions` — each `{ id, revision, status }`); `plans` (each `{ id, revision, status, goalRevisionId, supersedesId?, provenance { kind, actor, model? }, taskIds, risks }`, a risk being `{ id, description, mitigation? }`); `tasks`; `decisions` (ids); `gate` (all eight items); `commits` (`integrationHead`, `targetHead`, `promoted`); `risks` — what the Control Plane derived itself: `{ kind: 'bypass_posture', taskId, seq }` for every Attempt that ran as a terminal agent instead of in the headless sandbox, `{ kind: 'human_resolved_verification', taskId, runId }` for every Task whose verification a person resolved. A Task of the report always has `taskId`, `planTaskId`, `planRevisionId`, `title`, `kind`, `stage`, `attempts` (each `{ seq, branch, agentSpecId, contextPackageId, provider, model, effort, channel?, posture?, candidateId? }`), `runs` (each `{ id, candidateId, status, batchId? }`) and `openQuestions` (each `{ source, id, text }`, `source` being `message` or `gate`), and may have `cancelRationale` when it was canceled (only when the cancel carried a reason); an `INTEGRATED` Task has in addition `candidate` (`id`, `commitSha`, `treeSha`), `summary`, `limitations`, `risks`, `followUps`, `verification` (`runId`, `status`, `verifier`, `toolVersions`, `checks` — each `{ command, result, criteria }` —, optional `resolution { verdict, rationale, at }`, `artifacts`) and `integration` (`batchId`, `baseCommit`, `mergeCommit`, `regressionRunId`, `regressionStatus`). The same file exports `completionReportText(report)`, the report as indented JSON text.

The report repeats them; it does not vouch for them. It also holds them as they were stored: the final message of a headless Worker is redacted before its report is parsed, other texts are kept as written, and this page redacts nothing.

## Outcome

On the page of a Mission that has been through finalization a person sees how it was judged: whether the finalization passed or stopped, and in the Control Plane's own word why; when; the target branch and the two commits that were compared; every item of the completion gate with its result, how many records it was judged by and the Control Plane's detail when it did not pass; and, when a report was written, which Artifact holds it and under which hash. On request the page reads that report, refuses it when it is not the one the finalization recorded, and shows it: the Goal and which Tasks cover each acceptance criterion; every Task with its candidate, its verification, its merged-tree regression and its merge commit; what the Worker of each Task wrote — summary, limitations, risks, follow-ups — and the questions left open, as plain text; the risks the Control Plane recorded itself; the plans with their risks; the commits; and the raw JSON. A Mission without a finalization record looks exactly as it does today, and so does the whole page against a main process that sends none.
