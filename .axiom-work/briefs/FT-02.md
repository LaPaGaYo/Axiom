# Task FT-02 — FlowTask fixture: predefined scenarios, fixture manifest v1, reference Goal decomposition, host qualification (repository `LaPaGaYo/flowtask-fixture`)

You are a Worker in the FlowTask fixture repository (the Controlled Acceptance Fixture of Axiom, D18/D39). FT-01 delivered the application (219 tracked files, 61 test files, `verify:fast` ≈ 2.5 s, `verify:full` ≈ 4 s; every export has a direct test; `src/checks/contracts.test.ts` enforces layering, size and export coverage). FT-02 turns the repository into a **fixture**: scripted scenarios with deterministic expected outcomes, a versioned manifest, a reference Goal decomposition, and a qualification script. The sandbox has **no network**; dependencies are frozen (`package.json` dependency lists and `pnpm-lock.yaml` must not change; you may add scripts). Do not change application behaviour under `src/` except where a scenario patch *intentionally* breaks it — and those patches live under `scenarios/`, never in the tree itself.

## Why these scenarios exist (read before designing)

Axiom's control plane will run Missions against this repository. Its V1 success criteria (architecture §21) include: catching an intentionally introduced test failure and completing a NEEDS_FIX loop; handling two candidates that each pass alone but fail when merged (FIX_TASK / CONFLICT → NEEDS_FIX); recovering or safely retrying after an Agent crash or an `unverifiable` Attempt without starting a duplicate; and rejecting stale submissions without mutating the current Attempt. Real LLM Workers are not deterministic, so the fixture ships **scripted inputs** (patches and a stub worker) whose outcomes are fixed and self-checked. Everything in `scenarios/` is data for the control plane under test; nothing in it runs during `verify:fast` / `verify:full`.

## Deliverables

### 1. `scenarios/` — five scenario folders, each with a `README.md` (what it exercises, the exact steps the control plane performs, the expected observable outcome) and its inputs

| Id | Folder | Inputs | Expected outcome (must be deterministic and self-checked by `scenarios:check`) |
|---|---|---|---|
| S1 `deterministic-failure` | `scenarios/deterministic-failure/` | `candidate.patch` (applies cleanly to the baseline; typecheck and lint still pass; exactly one named unit test fails — pick a real behavioural bug, e.g. monthly recurrence clamping or dependency readiness, not a deleted assertion), `fix.patch` (applies on top of `candidate.patch`; everything green again) | after `candidate.patch`: `pnpm run test:unit` exit ≠ 0 and the failing test's full name is exactly the one recorded in the manifest; after `fix.patch`: `verify:full` green |
| S2 `merge-only-failure` | `scenarios/merge-only-failure/` with two sub-cases: `semantic/` (`a.patch`, `b.patch`: each applies to the baseline alone and passes `verify:full` alone; both apply together without textual conflict, but the combined tree fails a named check — design it so `typecheck` or one named unit test fails, e.g. A changes a service signature/error code and updates its callers, B adds a new caller or test written against the old contract) and `textual/` (`a.patch`, `b.patch`: each applies alone; applying the second after the first fails `git apply --check` — same lines edited differently) | semantic: alone PASS ×2, combined FAIL with the recorded check and message; textual: alone PASS ×2, second apply rejected by git |
| S3 `agent-crash` | `scenarios/agent-crash/` with the stub worker `scenarios/stub-worker/worker.mjs` (see §2) | `worker.mjs --scenario agent-crash --mode crash`: writes a partial file (`src/services/half-written.ts`, recorded in the manifest) then kills itself with SIGKILL → exit code 137 / signal SIGKILL, no report file, dirty worktree; `--mode hang`: writes `scenarios-heartbeat.txt` every second and never exits (the control plane must classify it `unverifiable`/timed out and must not start a duplicate) |
| S4 `retry` | `scenarios/retry/` (`attempt-1.patch`, `attempt-2.patch`) + stub worker | `worker.mjs --scenario retry --attempt 1`: applies `attempt-1.patch` (a plausible but incomplete implementation: e.g. the service change without its test update, so `test:unit` fails with a recorded test name) and writes `REPORT.md`, exit 0; `--attempt 2`: applies `attempt-2.patch` (complete), exit 0; `verify:full` green only after attempt 2 |
| S5 `stale-completion` | `scenarios/stale-completion/` (`first.patch`, `stale.patch`) | `first.patch` applies to the baseline and passes `verify:full` (the integration base moves); `stale.patch` was written against the **original** baseline and touches the same region/contract: after `first.patch` it must either fail `git apply --check` or apply and fail a recorded check — the manifest records which; the README spells out the control-plane expectation: a submission whose candidate was built on the old base must be rejected/rerouted (stale → NEEDS_FIX/rebase), never integrated blindly, and a late submission for a superseded Attempt is rejected with Orca's `stale_dispatch` / `inactive_dispatch` codes without mutating the current Attempt |

Patch rules: unified diffs produced with `git diff`/`git format-patch --no-stat` against the fixture's current HEAD (that HEAD becomes the frozen baseline tag `fixture-v1` after this attempt is merged — patches must apply to it with `git apply`), ASCII only, no timestamps or hashes in the patch body that would go stale (use `git diff`, not `format-patch` headers with commit ids), each patch ≤ 200 lines, each touching ≤ 4 files. Patches may add/modify files under `src/` and `tests/` only.

### 2. `scenarios/stub-worker/worker.mjs` — a deterministic stand-in for an Agent

Node ≥ 22 built-ins only (no dependencies). CLI: `node scenarios/stub-worker/worker.mjs --scenario <id> [--attempt N] [--mode crash|hang|succeed] [--cwd <path>]`. Behaviour is a pure function of the arguments and the scenario files: it applies the named patch with `git apply` (child_process, `--whitespace=nowarn`), writes `REPORT.md` at the repo root in the Worker submission shape (task/attempt ids from args, "candidate: working tree after patch <name>", files changed, "checks run: none — stub"), and exits 0; `crash` writes the partial file then `process.kill(process.pid, 'SIGKILL')`; `hang` loops forever writing a heartbeat (so a watchdog can see it is alive). No timestamps, no randomness, no network. Exit codes: 0 success, 2 usage, 3 patch failed to apply, 137 (by SIGKILL) for `crash`.

### 4. `GOAL.md` + `scenarios/goal/decomposition.json` — the reference Goal

One realistic feature goal for FlowTask that a planner can decompose into **8–15 Tasks with at least 3 independently ready (no dependencies) at the start**, touching every layer. Suggested: "Sprints and planning": sprint entity + validation; storage schema v2 with migration v1→v2; sprint services (create/list/close, assign/unassign tasks, close rules); CLI commands; API routes; a `sprint-burndown` report; saved views filter by sprint; a **real tabular CSV export/import** (one column per field; replaces the current `kind,payload` encoding — independent of sprints); a `plan` report (ready tasks grouped by project — independent); docs; integration tests. `GOAL.md` = the user-facing goal statement with constraints (no new dependencies, all checks stay green, determinism rules, docs updated). `decomposition.json` = tasks with `id`, `title`, `scope` (files/dirs the task may touch), `dependsOn`, `acceptance` (commands + what must be true), `parallelReady` (true for root tasks), `estimatedSize` (S/M/L). This is a *reference* for judging planner output, not the only valid plan — say so in `GOAL.md`.

### 5. `scripts/qualify.mjs` (`pnpm run qualify`) and `scripts/scenarios-check.mjs` (`pnpm run scenarios:check`)

Node built-ins only; both print a JSON report to stdout and exit non-zero on any failed gate.
- `qualify`: toolchain (node major = 22, `pnpm --version` matches `packageManager`), counts (`git ls-files` within 150–500; `*.test.ts` ≥ 20), `verify:fast` twice (wall clock each ≤ 180 s; stdout+stderr byte-identical between runs — run with `--reporter`-independent output, i.e. the deterministic reporter already in place), `verify:full` once (≤ 480 s), working tree clean afterwards except `dist/`; report fields: each gate, measured values, pass/fail, host (`os.platform()`, `os.arch()`, `os.cpus().length`, node/pnpm versions) — no timestamps inside the report other than the measured durations.
- `scenarios:check`: for every scenario in the manifest, materialise a scratch copy of HEAD (`git worktree add <tmp> HEAD` and remove it afterwards, or `git archive | tar -x` into a temp dir — must leave the main checkout untouched), apply the inputs step by step and assert the `expected` block (run the named check, compare exit code / failing test name / message substring; run the stub worker and assert exit code or signal and the dirty file; for `textual` assert `git apply --check` fails); the scratch copy needs `node_modules` — symlink the repo's `node_modules` into it (document this). Total runtime target ≤ 3 minutes on a laptop.
Both scripts get a unit test for their pure parts (gate evaluation, report shaping) under `scripts/*.test.mjs` — add a `test:scripts` script (`vitest run --dir scripts`) and include it in `verify:full`? No: keep `verify:full` exactly as it is (app only); add `"verify:fixture": "pnpm run verify:full && pnpm run test:scripts && pnpm run scenarios:check"` instead.
