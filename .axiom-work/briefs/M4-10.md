# Task M4-10 — a Mission that is ready gets its completion report: one JSON artifact built from the database, named by the finalization record

**Why.** Since M4-6a a finished Mission reaches `READY_FOR_APPROVAL` on seven gate items and one audit event. The Constitution (§6) asks for two more things in `FINALIZING`: known risks and limitations are recorded, and a `CompletionReport` Artifact exists that links the Goal, the plans, the Tasks, the Attempts, the evidence and the promoted commits (`docs/PROJECT_CHARTER.md` §15 lists the eight questions it answers). This Task writes that report when finalization finds the Mission ready, makes the record name it, and makes the Mission ready only in a transaction that has just rebuilt the same bytes — so the report can be re-derived from the database without a model (D91 K0, D86 item 2 ④). It also corrects one item of the gate: `no_open_questions` counts every unanswered question, while the Constitution and the rest of the code speak of *blocking* ones. **This Task renders no Markdown and adds no way to look at the report** other than the existing artifact read (the page that shows it, and the rendering, are M4-11); nothing is approved (M4-7) or delivered (M4-8).

High-risk class: it changes what a completion gate checks and adds a stored format.

## Ground truth (verifier, 2026-11-19; read in the code at main `fb419cf7ba`)

1. **The executor** (`src/main/axiom/finalization/mission-finalize.ts`, 101 lines). `executeFinalization(deps, missionId)` returns at once unless the Mission is `FINALIZING`; reads the integration head and compares it with the recorded one; reads the target branch with two read-only git calls; then calls `completionGate(store, db, missionId, facts)` and **immediately** `recordFinalization(...)` — nothing is awaited between the gate and the write. Its dependencies are `{ db, store, missions, runtime }`; `control-plane.ts` registers it in one line, `registerMissionFinalize({ db, store, missions, runtime, effects })`, right after `registerIntegrationApply({ store, missions, runtime, effects, artifacts })` — the `ArtifactStore` instance is in scope there under the name `artifacts`. `control-plane.ts` has 297 non-blank lines and an earlier Task pins it at 299.
2. **The record** (`finalization/finalization-record.ts`, 56 lines): one write transaction that returns without writing unless the Mission is still `FINALIZING` in the same entry; turns a `ready` outcome into `stopped / integration_head_unexpected` when the recorded head no longer equals the outcome's; parses the outcome with `FinalizationOutcomeSchema`; compares it as JSON with the latest record of the entry (so the order of keys is the schema's); appends the audit event `mission.finalization` when it differs; and for `ready` calls `missions.readyForApproval` in the same transaction.
3. **The contract** (`src/shared/axiom-contract/mission-finalization.ts`, 51 lines): `FINALIZATION_GATE_IDS` (seven ids), `FinalizationGateSchema` (an array of exactly that length whose ids are in that order), strict `ready` and `stopped` objects over the same facts (`targetBranch`, optional `targetHead`, `integrationHead`, `gate`), `FinalizationOutcomeSchema` and `MissionFinalizationSchema` (the same with `at`). `read-models/finalization-reads.ts` parses the stored event with `MissionFinalizationSchema`: **a stored record that does not parse makes `axiom.mission.show` and `axiom.mission.pending` fail for that Mission and stops every later write of a record** (the write reads the previous one), and development databases already hold records written by M4-6a (seven items, no report).
4. **The gate** (`finalization/completion-gate.ts`, 104 lines). `no_open_questions` fails when any Task row has a pending question thread (`store.hasPendingQuestionForTask`), a pending typed question (`store.hasPendingTypedQuestionForTask`) or a pending kernel gate (`db.listGates({ taskId, status: 'pending' })`), or when the Mission has a blocking Approval (`store.hasBlockingApproval`). Everywhere else a question blocks only while its Task is in one of `QUESTION_BLOCKING_STAGES` (exported by `read-models/task-waiting-on.ts`: the stages before admission, `RUNNING`, `BLOCKED`); the pending list (`read-models/pending-task-items.ts`) does not list a question whose Task is terminal. The first ten questions of a Worker's report become typed questions at submission (`execution/submission-items.ts`), so today one unanswered report question stops finalization with `completion_gate_failed` and nothing in the pending list says which question. Three existing tests put a kernel gate on an `INTEGRATED` Task and expect `no_open_questions` to fail: `fails no_open_questions while a Task has a pending question` (`completion-gate.test.ts`), `stops with completion_gate_failed and records the failing items` (`mission-finalize.test.ts`) and `mission.pending lists a stopped finalization as a blocking mission item with cancel as its only action` (`finalization-rpc.test.ts`).
5. **The artifact store** (`src/main/axiom/artifacts/artifact-store.ts`). `put({ missionId, kind, mediaType, related, createdBy, content })` is asynchronous (it writes a file), refuses more than 8 MiB, and returns the existing row when the id exists; the id is derived from the Mission id, the kind and the content hash (for a `createdBy` that does not start with `attempt:`), so the same bytes for the same Mission and kind are the same artifact whoever asks again. `read(id)` re-hashes the bytes. It exports `sha256()`. Its input schema picks `kind` from `ArtifactMetaSchema`. The table's `kind` column has no constraint and `db/artifact-rows.ts` takes the type from `ArtifactMetaSchema.shape.kind`, so a wider kind needs no change under `src/main/axiom/db` and no schema step.
6. **`ArtifactKind`** (`src/shared/axiom-contract/mission-objects.ts`, seven values) is what an Attempt may store (`ArtifactPutParams`, the CLI's `--kind`), what a Task criterion may name (`AcceptanceCheckSchema`) and what the interface lists in its criterion editor (`ArtifactKind.options`; `artifact-params.test.ts` expects seven options and a renderer test compares the editor's list with `ArtifactKind.options`). `axiom.artifact.put` lets an Attempt choose the kind, and `ArtifactPutParams` takes its `kind` by picking it from `ArtifactMetaSchema` — so it widens with the meta schema unless it is set again. `src/main/axiom/verification/worker-artifacts.ts` types the kind of a stored artifact it checked as `ArtifactKind | null`.
7. **What the store can already tell** (no new SQL is needed): `getMission`; `listGoalRevisions`, `listPlanRevisions` (by revision); `listTaskStages({ missionId })` (by Task id; `spec`, `stage`, `planRevisionId` — a row's `taskId` is the kernel's task id, while the id the plan uses, such as `T01`, is `spec.id`; `PlanRevision.tasks` and `planCoverage` speak in plan ids); `listAttemptBindings({ missionId })` (by Task id and seq: `branch`, `dispatchId`, `agentSpecId`, `contextPackageId`); `getAgentSpec(id)` (a row whose `spec` holds `provider`, `model` and `reasoning.effort`); `listCandidates(missionId)` (a candidate's `attemptId` is its Attempt's dispatch id); `listSubmissions(missionId)` and `getSubmissionByDispatch(attemptId)` (`candidateId`, `report` with `summary`, `limitations`, `risks`, `followUps`); `listVerificationRuns` (`status`, `verifier`, `toolVersions`, `batchId`, `verdictDetail` — read it with `readVerdictRecord`, `src/shared/axiom-contract/verdict-record.ts`: `checks`, `resolution`, `verdictArtifactId`, `evidenceArtifactIds`; asked without a `batchId` it returns only the runs that belong to no batch, and a batch's runs come with `{ missionId, batchId }`); `listIntegrationBatches({ missionId })` (in creation order: `baseCommit`, `mergeCommit`, `status`, `candidateIds`); `listDecisions({ missionId })`; `getArtifact` (`sha256`); `listMessages({ missionId, pendingOnly: true })` (pending typed messages and, projected into the same shape, the kernel's pending question threads; a question has `type: 'QUESTION'`, `taskId`, `id` and `question`; pending kernel gates are not in it — they are the rows of `db.listGates({ taskId, status: 'pending' })`, with `id` and `question`); `getLatestReadModelAudit({ missionId, objectKind, objectId, events, stage? })`. A Task's cancel rationale is the `reason` of its `task.stage` audit event to `CANCELED` (object kind `task`). A Worker Attempt's launch is the audit event `attempt.started` (object kind `attempt`, object id the Attempt's dispatch id) whose `after` carries `channel` (`headless` or `tui`) and `posture` (`headless-sandboxed` or `tui-bypass`). ## Outcome

When finalization finds every gate item passing, the Control Plane stores one artifact of kind `completion_report` — JSON, built from the database and the two commits the run read, identical for identical facts — and the `ready` record carries its id and hash. The Mission becomes `READY_FOR_APPROVAL` in a transaction that has built the report again and found the same bytes. The gate has eight items; an unanswered question of a settled Task no longer stops finalization and is listed in the report instead. `axiom.mission.show` shows the two new fields; `axiom.artifact.read` returns the report. Records written by M4-6a still read.

Field names are part of the format; use these:
   - `version`; `mission`: `id`, `repoId`, `targetBranch`.
   - `goal`: the active revision's `id`, `revision`, `objective`, `constraints`; `criteria` — one entry per acceptance criterion of that revision: `index`, `text`, and `coveredBy`, the row ids (`taskId`) of the `INTEGRATED` Tasks whose spec lists that index in `coversGoalCriteria`; `revisions` — every GoalRevision of the Mission with `id`, `revision`, `status`.
   - `plans`: every PlanRevision with `id`, `revision`, `status`, `goalRevisionId`, `supersedesId` when it has one, `provenance` (`kind`, `actor`, and `model` when present), `taskIds` (the plan's own task ids), `risks` (as stored: `id`, `description`, optional `mitigation`).
   - `tasks`: every Task row, by Task id, with `taskId`, `planTaskId` (its spec's `id`, the id the plan uses), `planRevisionId`, `title`, `kind`, `stage`; `cancelRationale` for a `CANCELED` Task that has one; `attempts` — one entry per attempt binding with `seq`, `branch`, `agentSpecId`, `contextPackageId`, the AgentSpec's `provider`, `model` and `effort`, the launch audit's `channel` and `posture` when that event has them, and `candidateId` when a candidate of that Attempt exists; and for an `INTEGRATED` Task: `candidate` (`id`, `commitSha`, `treeSha` of its ACTIVE candidate), `summary`, `limitations`, `risks`, `followUps` from the stored submission of that candidate, `verification` — the run `activeCandidateVerification` calls latest: `runId`, `status`, `verifier`, `toolVersions`, `checks` (`command`, `result`, `criteria` of each check of the verdict record), `resolution` when a person resolved the run (`verdict`, `rationale`, `at`), `artifacts` (`id` and `sha256` of the verdict artifact and of each evidence artifact that the store knows) — and `integration`: the Task's latest batch (`batchId`, `baseCommit`, `mergeCommit`) with `regressionRunId` and `regressionStatus` of that batch's latest run.    - `decisions`: the ids `listDecisions` returns for the Mission.
   - `gate`: the eight items as evaluated (deliverable 4).
   - `commits`: `integrationHead`, `targetHead`, and `promoted` — the merge commits of the `PROMOTED` batches in the order the store lists them.
   - `risks`: derived entries, each with a `kind` and the ids that identify it: `bypass_posture` (`taskId`, `seq`) for every Attempt whose posture is `tui-bypass`, and `human_resolved_verification` (`taskId`, `runId`) for every `verification` that has a `resolution`.
   The report holds **no time of generation and nothing random**; stored times that are facts (`resolution.at`) are fine. Arrays keep the order of the store's readers, which is fixed. The module also exports the one function that turns a report into its text: the JSON of the parsed report (so keys are in the schema's order), indented by two spaces, with one trailing newline. The stored bytes are that text in UTF-8 (the module itself stays free of `Buffer`: it is compiled into the web bundle too).
