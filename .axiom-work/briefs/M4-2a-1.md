# Task M4-2a-1 — What the merged-tree regression will stand on, not yet used: a verification run can belong to a batch, the verification service leaves such a run alone, and the policy gains `integrationGates` (first part of the M4-2a row of `docs/plans/M4.md`; D92 b, approved by Henry 2026-11-15; schema, contract, store and main process; no renderer, CLI, RPC or e2e change)

Planner brief, 2026-11-16 (verifier). M4's queue merges one verified candidate into the Mission's integration head (M4-1b) and must then run that Task's checks on the merge commit before the head may move (M4-2a-2). D92 says where the record of that run lives: `docs/plans/M4.md` §2, "合并树回归的记录复用验证记录：`verification_runs` 加一个可空的 `batch_id`，不出现第二套'运行'". Three things are missing for that. The column does not exist. The verification service treats every row of the table as its own: its claim takes any `QUEUED` row and cancels it unless the Task is `SUBMITTED`, and its recovery — which runs at every drain, not only at boot — requeues any `RUNNING` row of another epoch and removes that row's worktree; a regression run written by the integration executor would be cancelled or taken away from it. And the policy has no key for the gates of a merged tree. This Task adds those three and uses none of them: no product path writes a run with a batch id and none calls the new plan function, so every existing flow behaves as on main. The regression itself, promotion and `INTEGRATED` are M4-2a-2; the switch that sends verified Tasks into the queue is M4-2b.

## Ground truth (verifier, 2026-11-16; read in the code at main `93deb3bc78`)

1. **How this database gets its schema.** `OrchestrationDb`'s constructor (`src/main/runtime/orchestration/db/orchestration-db.ts`) calls `createTables` and then `migrate` at every open. `createTables` (`src/main/runtime/orchestration/db/schema/create-tables.ts`, 18 counted lines) executes the whole DDL, every statement `IF NOT EXISTS` — Axiom's part is `createAxiomTablesSql()` in `create-axiom-tables-sql.ts` (**296 counted lines of 300**) — and then two steps for the kernel's own indexes and view; it runs once per open, outside any transaction, after `busy_timeout` is set. `migrate` (`schema/migrate.ts`) returns at once when the version it resolves for the file — the stored `user_version`, or 6 for a file whose schema does not match its stamp — is current; otherwise it runs the numbered steps inside one `BEGIN IMMEDIATE` and stamps `SCHEMA_VERSION` (46, `db/contract-constants.ts`). A column added to an existing table has so far come with a numbered step guarded by `this.hasColumn(table, column)` — `migrate-v45.ts` (two columns) and `migrate-v46.ts` (five columns of `verification_runs`) — plus entries in the versioned probe list of `src/main/runtime/orchestration/orchestration-schema-version-skew.ts`. Since then nothing of Axiom's has taken a number: four tables were added by the every-open DDL alone (the titles "adds … to an existing v46 database" in `schema/axiom-tables-migration.test.ts`).
2. **Why this column takes no number either.** Upstream's own chain has meanwhile used the numbers 44 to 46 for steps that are not ours, so every number Axiom takes has to be moved at the next upstream sync (`migrate.ts` already carries one such repair); and seven earlier Tasks pin `SCHEMA_VERSION = 46` in assertions that run against every later Task. An additive nullable column needs no number: a build that does not know it reads and writes the table by named columns and is not disturbed by it.
3. **The migration test** `schema/axiom-tables-migration.test.ts` has **exactly 800 counted lines of 800**. Its `TABLE_COLUMNS` holds the columns of each table of a fresh database, in order; `verification_runs` ends `… started_at finished_at`. Columns added later have always been appended last, in the DDL too (`agent_specs … spec`, `mission_policies … routing`). Its title "upgrades v45 verification rows and reopens idempotently with transparent downgrade probes" builds what it expects from the row it read before the upgrade, so it holds without an edit once the DDL has the new column.
4. **A verification run in the contract and the store.** `VerificationRunSchema` (`src/shared/axiom-contract/verification-params.ts`) is a plain `z.object`, not strict; `VerificationRunViewSchema` extends it and is what `axiom.verification.show` / `list` answer (`src/main/runtime/rpc/methods/axiom/verification.ts`), so a field added to the first appears in those answers by itself. The row schema `VerificationRunRowSchema` and its codec are in `src/main/axiom/db/submission-rows.ts`; `src/main/axiom/db/submission-stores.test.ts` requires the keys of that row schema to equal the table's columns (title "pins $table codecs to the existing schema without a migration"). In `src/main/axiom/db/verification-runs-store.ts` every `SELECT` names the columns of the row schema (`Object.keys(VerificationRunRowSchema.shape)`), the `INSERT` names its nine columns one by one, and `Insert` is the contract minus seven fields (a plain object: unknown keys are dropped). Two product paths insert a run, both `QUEUED` with the verifier `VerificationService`: `settleSubmission` (`execution/attempt-submission.ts`) and `rerunVerification` (`verification/verification-rerun.ts`). No product code writes the table outside the store. The migration test seeds a row through an `INSERT` that names its columns, and one e2e helper reads rows with `SELECT *` and the codec; neither is disturbed by a column more.
5. **Who treats every row as a candidate verification.** `claimVerification` (`src/main/axiom/verification/verification-claim.ts`, 90 counted lines): in one transaction it lists the `QUEUED` runs — of one Mission through `listVerificationRuns`, of all through `listVerificationRunsByStatus` — and for each, oldest first, either cancels it (`candidate_missing`, `candidate_superseded`, `task_stage_changed` when the Task is not `SUBMITTED` and the run is not resuming) and goes on, or claims it, moves the Task to `VERIFYING` and returns. `recoverVerifications` (`verification/verification-recovery.ts`, 150 counted lines) takes every `RUNNING` run whose `runtimeEpoch` is not its own, and every run in one of the six statuses a run can rest in (`PASS`, `FAIL`, `INCONCLUSIVE`, `SPECIALIST_REVIEW`, `HUMAN_REVIEW`, `CANCELED`) that still has a worktree and `verdictDetail.cleanupPending === true`; it removes the worktree, requeues the first kind (audit `verification.requeued`) and clears the flag of the second; a failed removal is recorded (`cleanupPending`, audit `verification.recovery_failed`). It runs at the start of every drain, and by default (`sweepOrphans`) ends with a sweep of the managed worktrees whose branch starts with `axiom/verify/`; the service asks for that sweep at boot only. The sweep goes by the runtime's listing, not by run rows. Removal is always asked of the runtime as `removeManagedWorktree('id:<worktreeId>', …)`.
6. **The rules.** `VerificationRulesSchema` (`src/shared/axiom-contract/verification-rules.ts`, 179 counted lines) is a strict object: an unknown key is refused. `Commands` is a list of trimmed, non-empty strings and may be empty. `repositoryGates` is a strict object of the optional lists `low`, `medium`, `high`, default `{}`; `setupCommands` defaults to `[]`. `resolveVerificationPlan(task, rules)` answers `{ source, command, criteria }[]`: `setupCommands` in order (source `setup`, not de-duplicated), then the Task's criterion commands, de-duplicated, each with the indexes of its criteria (source `evidence`), then `repositoryGates[task.risk] ?? []` without the commands already listed (source `gate`). Verification, the context builder and the renderer call it, so its signature and its answers must not change. `axiom.policy.update` and the CLI's `--verification-rules-file` validate with the same schema, so a key added to it can be written without another change. A build that does not know a key refuses the whole stored object: every verification of that Mission then ends `INCONCLUSIVE` with `policy_invalid`.
7. **Fixtures.** `verificationFixture(root)`, `queueAnotherVerification(f)` and `verificationRuntime()` (`verification/verification-fixture.test-support.ts`, 205 counted lines of 300) give a memory database with a `SUBMITTED` Task, an ACTIVE candidate and the `QUEUED` run `vrun-1`; `verification-recovery.test.ts` shows how a test builds the service's dependencies for a chosen epoch. Schema tests open `new OrchestrationDb(path)` on a file in a temp directory and close it in `afterEach`.

## Outcome

After this Task a database opened by this build has the column `verification_runs.batch_id` — a new file from the DDL, an existing file by an addition at open that takes no version number — and `user_version` is what it was; a verification run can carry the id of the IntegrationBatch it belongs to, the store writes it and reads it back, and a run without one looks exactly as on main; the verification service neither claims, cancels, requeues nor cleans a run that has one; and the rules accept `integrationGates`, with `resolveIntegrationPlan` answering the commands a merged-tree regression will run. Nothing sets a batch id and nothing calls the new function outside tests.
