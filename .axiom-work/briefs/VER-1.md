# Task VER-1 — three version checks stop depending on the app's version being an Orca release number

**Why.** D90 (`docs/decisions/DECISION_LOG.md`): Axiom's software version becomes `0.1.0`; `package.json` still carries the upstream number `1.4.214`. Three checks in the kernel compare the app's own version with numbers of the upstream line, and each one gives the wrong answer the day the version drops to `0.1.0`: a remote or WSL host that a `1.4.214` build served last refuses `0.1.0` as a downgrade; the guard that keeps a build from before SQLite profile storage from being switched to goes silent, and switching from a `1.4.214` build to `0.1.0` is refused; every plugin that asks for `>=1.x` is rejected. This Task records the **Orca baseline** (D90 item 2) and makes the three rules line-aware. `package.json` does not change here (VER-2 does that, on the host), so nothing a person can see changes with this Task: with `1.4.214` on both sides every rule answers as today.

Small Task. Three pure functions change by a few lines each; the rest is one new module and tests.

## Ground truth (verifier, 2026-11-18; read in the code at main `f42438f8a2`)

1. **App versions.** `src/shared/app-version.ts` exports `isValidAppVersion`, `compareAppVersions(left, right)` (negative, zero, positive; zero when either side does not parse; a prerelease sorts below its release; build metadata is ignored) and `hasReachedAppVersion(current, target)`. Its parser trims the text and accepts a leading `v`; it is not exported. Do not change this file.
2. **The host rule.** `refuseOrcadHostDowngrade(record, candidateVersion, appVersion)` (`src/main/ssh/orcad-host-version-admission.ts`, 25 lines) admits a stopped host restarting the same build, admits a record without `activeAppVersion`, and otherwise refuses with `'host-newer'` when `compareAppVersions(record.activeAppVersion, appVersion) > 0`. `activeAppVersion` is the version of the app that last activated the host's server; it is written into a record that lives on the remote host or inside the WSL distribution, under a directory whose name is not specific to this product, so a build of the upstream app and a build of this one can meet the same record. Callers: `planManagedOrcadAutoUpdate` (`src/main/managed-server/lifecycle/orcad-managed-update-decision.ts`) and `wslOrcadDeferralCode` (`src/main/wsl/wsl-orcad-update-admission.ts`). No test file exists for the rule itself; its callers' tests use app versions such as `1.4.0`, `1.5.0`, `2.0.0`, `9.9.9` and, once, `0.0.1` — none of them on the Axiom line as deliverable 1 defines it.
3. **The profile floor.** `profileStateBuildCompatibilityError(currentVersion, targetVersion)` (`src/shared/profile-state-build-compatibility.ts`, 17 lines; `SQLITE_PROFILE_RELEASE_FLOOR = '1.4.214'`) returns its message only when the current version has reached the floor and the target has not. Callers: two build switches in `src/main/updater/updater-build-selection.ts`. Tests: `src/shared/profile-state-build-compatibility.test.ts` and `src/main/updater-sqlite-profile-downgrade.test.ts`, all with `1.4.x` versions; `src/main/updater.build-channel-selection.test.ts` reaches the rule with a current version below the floor (`1.0.51`), so its answers do not change.
4. **The plugin gate.** `satisfiesOrcaEngineRange(hostVersion, range)` (`src/shared/plugins/plugin-manifest.ts`, 178 lines) compares numeric triples: it cuts the first two characters off the range, ignores a prerelease or build suffix of the host version, and reads a part that is not a number as zero. The range form `>=x.y.z` is enforced by the manifest schema in the same file, not by the function. Callers: `src/main/plugins/plugin-discovery.ts` and `plugin-install-staging.ts`; the host version they pass starts as the app's version in `src/main/startup/main-process-plugins.ts`. The plugin system is off unless a setting turns it on. Fixtures use `engines: { orca: '>=1.0.0' }` (one uses `'>=1.4.0'`) with host `1.4.0`; no test calls the function directly and none covers a refusal.
5. **The baseline.** The last full merge of upstream is `41661e33128c3a308a570aa0ed96ce24910a98c4` (`docs/decisions/UPSTREAM_SYNC.md` names it by its first ten characters as the sync point of 2026-10-23; the verifier read the full id and the file in the repository); upstream's `package.json` says `1.4.214` at that commit. Later Tasks cherry-picked single fixes; they do not move the baseline.
6. **A placeholder that looks like a low version.** The headless host process reports `0.0.0-orcad` when no version is given to it (`src/main/orcad/orcad-host-adapters.ts`). It must keep comparing as it does today.

## Outcome

A build whose version is `0.1.0` or a later `0.x` is admitted by a host that the baseline release or an older one served, is refused by a host that a newer upstream release or a newer `0.x` served, may switch to and from builds at or past the profile floor, refuses a build from before the floor, and loads a plugin whose range the baseline satisfies. Two versions that are both on the upstream line are treated exactly as today by all three rules; what changes is only how a `0.x` version meets an upstream one.

## Deliverables

1. **A new module `src/shared/orca-baseline.ts`.**
   - `ORCA_BASELINE`: the version `1.4.214` and the full commit id of ground truth 5 — what the kernel of this build is based on. A comment says who changes it (a full upstream sync) and that D90 item 2 defines it.
   - `isAxiomLineVersion(value)`: true for a valid app version with major `0` and minor at least `1`. Everything else — `1.x`, `0.0.x`, the placeholder of ground truth 6, text that is not a version — is not on the Axiom line. It accepts what `isValidAppVersion` accepts, so surrounding blanks and a leading `v` do not change the answer (`v0.1.0` is Axiom-line), and a prerelease or build suffix does not either (`0.1.0-rc.1`, `0.10.0+abc`).
   - A comparison of two app versions **across lines**, with the result convention of `compareAppVersions`: two versions on the same line (both Axiom-line, or both not) compare with `compareAppVersions` as they are; when exactly one is Axiom-line, that one is replaced by the baseline version before the comparison. A comment says that this orders one pair for a rule and must not be used to sort a list (`0.1.0` and `0.2.0` both meet `1.4.214` as equals).
   - The version a build has **on the upstream line**: the baseline version for an Axiom-line version, the version itself otherwise.
   Names other than `ORCA_BASELINE` and `isAxiomLineVersion` are yours; keep the module free of imports other than `./app-version`.
2. **The host rule** compares `record.activeAppVersion` with `appVersion` across lines (deliverable 1). Nothing else in the function changes: the two early admissions stay first, the signature and the refusal value stay.
3. **The profile floor**: an Axiom-line version has reached the floor; any other version reaches it as today. The message, the constant and the signature stay.
4. **The plugin gate** compares the host's version on the upstream line (deliverable 1) with the range. The signature and the grammar stay.
5. **Tests**, in four new files with exactly these names and titles (the sidecar looks for each):

     4. `an Axiom-line version meets an upstream version at the baseline`
   - `src/main/ssh/orcad-host-version-admission.test.ts`
     5. `a host the baseline release served admits 0.1.0`
     6. `a host a newer upstream release served refuses 0.1.0`
     7. `a host a newer 0.x served refuses an older 0.x and admits a newer one`

     9. `a stopped host restarting the same build and a record without a version are admitted`
   - `src/shared/profile-state-build-compatibility-lines.test.ts`

   - `src/shared/plugins/plugin-engine-range-lines.test.ts`

   Values that make these tests mean something: in titles 5–8 the record names an active build that is not the candidate, so neither early admission applies, and title 9 is the only one about the early admissions; title 5 uses a record of `1.4.214` and one of an older `1.4.x`; title 6 a record above the baseline such as `1.4.300`; title 7 a record of `0.2.0` against the apps `0.1.0` (refused) and `0.3.0` (admitted); title 11 a target of `1.4.213`; title 13 the ranges `>=1.0.0` (satisfied) and `>=1.4.215` (not satisfied).
