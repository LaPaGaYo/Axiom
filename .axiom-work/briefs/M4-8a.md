# Task M4-8a — local delivery: `axiom.mission.deliver` fast-forwards the target branch to the approved integration head, consumes the Approval and completes the Mission

**Why.** Since M4-7b a person can grant the delivery Approval, and then nothing happens: the Mission waits in `READY_FOR_APPROVAL` with a `GRANTED` Approval that no code uses. This Task adds the command that uses it, `axiom.mission.deliver` (desktop only, D78). It is the **first write of the Control Plane outside the `axiom/*` namespace** (`docs/plans/M4.md` section 6): it moves the user's own target branch. So every condition the governing documents attach to that write is checked at the moment of the write, and whenever one does not hold the command writes nothing to git and says why.

High-risk class: it writes the user's branch and ends the Mission.

**The rules this Task implements — it does not widen any of them.** If something you need seems to require more than they allow, stop and say so in the report.

- D92 h (`docs/decisions/DECISION_LOG.md`; `AGENTS.md`, branch model; `docs/ARCHITECTURE.md` 12.4): "没有远程时的本地合入只在能快进、且目标分支没被任何工作树检出时做，否则停下问人" — **without a remote**, a local merge **only when it is a fast-forward and no worktree has the target branch checked out; otherwise stop and ask the person**.
- **A repository that has a remote.** D92 d and `AGENTS.md` give it a pull request; that is built after 0.1 (D89 item 3), and D89 item 2 names local merge as the delivery of 0.1. The texts do not say what 0.1 does with such a repository, and that is Henry's to settle, not this Task's. Until he has, this Task takes the reading that widens neither: **a repository with a remote is not delivered — the command stops and says so.** Nothing is ever pushed or fetched.
- D70 item 2 (and `docs/GLOSSARY.md` 4.1): before the delivery action, the target branch must still be at the commit it had at finalization; **if it is not, the Mission goes back `READY_FOR_APPROVAL → FINALIZING` and finalization is redone, and the Approval no longer counts**. `docs/plans/M4.md` section 6: the approval binds the commits, expires, and is void once the target moves — "三条都不能省". The governing texts give that move exactly one cause, a changed target branch; this Task uses it for nothing else.
- D70 item 3: an expired Approval is requested again and **never delivered automatically**.
- `docs/ARCHITECTURE.md` 14 and `docs/GLOSSARY.md` 4.10: an Approval is used once — `GRANTED → CONSUMED`, "执行动作时校验 inputs hash 一致且未过期", "执行后即消费"; the row has `outcome`（执行结果）and `executed_at`. The lifecycle stays `PENDING → GRANTED | DENIED | EXPIRED | REVOKED`, `GRANTED → CONSUMED`: **this Task adds no other move out of `GRANTED`.**
- D92, revision of 2026-11-16: Axiom's own merges switch signature verification off for themselves — "只作用于这一次合并，不改用户的 git 配置，交付到目标分支时仍按用户自己的设置". Here that means: the one setting D92 names, `merge.verifySignatures`, is honoured (a repository that demands verified signatures is not moved by Axiom: the integration commits are unsigned); and the write of the target branch passes **no configuration override** — so, unlike Axiom's writes of its own references, it runs with the repository's hooks. No other git setting is consulted (the verifier reports these readings to Henry).
- `docs/plans/M4.md` section 2: "每一步先落库再动 git" — the intention to move the branch is recorded, and committed, before the branch is written.
- `docs/PROJECT_CONSTITUTION.md`: "The Mission MAY enter `COMPLETED` only after Delivery succeeds and the CompletionReport records the resulting commits." A fast-forward creates no commit: the commit the target branch ends at is the `commits.integrationHead` of the report the Approval is bound to. **This Task writes no second report** — a decision of the verifier for this Task, reported to Henry; `docs/plans/M4.md` had left "交付部分与第二份报告" to M4-8, and the planner corrects that line when this Task is merged. The facts of the delivery are on the consumed Approval and in the audit events.
- **Who asked is never taken from the request** (`AGENTS.md`; D78 rule 3): the method takes no `resolver`; the audit events record, as `via`, the caller kind the transport stamped on the call, exactly as `axiom.approval.grant` does.
- **One clock** (`docs/reference/control-plane.md`, module map: "MissionController 提供写事务和时钟，不引入另一套服务名称或时钟"): every time this Task writes is the controller's, as in M4-7b.

**No interface**: the button is M4-11's; until then the method is reached by tests and specs. No CLI command, no MCP tool.

## Outcome

A person at the desktop delivers a Mission whose delivery Approval is granted. The command checks the Approval once more against the Mission, the report and the controller's clock, then looks at git. A repository with a remote, an integration branch that is not where the record says, a repository that demands verified signatures, a target branch that is checked out: each of these **stops** the delivery — nothing is written to git, the stop is recorded and listed as a pending item, the Approval stays `GRANTED`, and the same Approval delivers once the cause is gone. A target branch that is not where the report says sends the Mission back to `FINALIZING`. Otherwise the intention is recorded, the target branch is fast-forwarded to the integration head by a compare-and-swap, and in one write the Approval becomes `CONSUMED` with its outcome and the time, and the Mission `COMPLETED`. An Approval past its time is not used: a new one is requested and the command refuses. Nothing is pushed, no worktree is touched, no timer runs, no interface changes.

2. **Approval contract and store.** `ApprovalSchema` gains two optional fields: `outcome` (a non-empty string) and `executedAt` (an ISO date-time). Both are present on a consumed Approval and absent on every other one — the row codec reads the two columns and leaves a field out when the column is `NULL`, so every Approval that exists today parses to exactly what it parses to now. `approvals-store.ts` gains one method that consumes a granted Approval: `{ id, outcome, executedAt }` → one `UPDATE` that sets `status = 'CONSUMED'`, `outcome`, `executed_at` and `updated_at` `WHERE id = ? AND status = 'GRANTED'`, returning whether a row changed; `resolver` and `resolution` keep what the grant wrote. `axiom-store.ts` exposes it the way it exposes the others (added lines only; the file has 287 non-blank lines and the linter's limit is 300 counted lines).
3. **The Approval at delivery** — new file(s) directly under `src/main/axiom/approval/`, their names beginning with `delivery-`, written like `delivery-decision.ts`: functions that take the controller's context, run inside one write of the controller, and take the time from `ctx.now()`.
   - **The check** of one Approval for the delivery of one Mission, in this order:
     1. no Mission with that id → `mission_not_found` (`requireMission`);
     2. no Approval with that id, or its kind is not `delivery`, or it belongs to another Mission → refuse `approval_not_found`;
     3. its status is not `GRANTED` → refuse `approval_not_granted` (data: the id and the status it has);
     4. the Mission is not `READY_FOR_APPROVAL` → refuse `illegal_transition` (data: `missionId`, `from` the Mission's status, `command` `deliver`) — a paused or blocked Mission is resumed or unblocked first;
     5. the Approval is not the Mission's latest delivery Approval, or the Mission's current record is not a `ready` record whose `reportSha256` equals the Approval's `inputsHash` → refuse `approval_stale`; nothing is written;
     6. its `expiresAt` is not later than the controller's time (compare as dates, as the grant does) → **in one write that commits**: a new delivery Approval requested for the same hash with `requestDeliveryApproval`, and one audit event `approval.lapsed` (actor `MissionController`, object kind `approval`, object id the old Approval's id, `before` holding its status, `after` holding the id, the hash, the expiry and, as `replacedBy`, the id of the new request) — **and then** the command is refused with `approval_expired` (data: the old id and `replacedBy`). The old row stays `GRANTED` (the lifecycle has no other move for it); it is no longer the latest, so check 5 refuses it from then on. The refusal is raised after the write has committed, as M4-7b's grant does it.
     The check answers with what the delivery needs: the Mission, the Approval and the ready record.
   - **The consumption**: the store method of deliverable 2 with the controller's time as `executedAt`, then one audit event `approval.consumed` (actor `MissionController`, object kind `approval`, object id the Approval's id, `before` holding the status it had, `after` holding the id, the hash, `outcome`, `executedAt`, the target branch, `from` and `to` — the two commits — and `via`). When the store method changes no row, nothing is appended and the caller is told.
4. **Moving a local branch** — `src/main/axiom/execution/integration-base.ts`. Do not write a second copy of `advanceIntegrationHead`: generalize it into one function that moves a local branch ref (a name under `refs/heads/` — it refuses anything else) by the same reads and the same compare-and-swap, and keep `advanceIntegrationHead` as a caller of it — its signature, its order of checks, hooks off, no reflog message, and **its answers exactly the objects they are today** (the existing tests compare them with `toEqual`; they stay untouched and pass). What the general function adds, in its own answer only:
   - **where**: the path of the worktree that has the branch checked out, when it refuses for that reason;
   - **who**: whether the branch was written by this call or was found already at `to` (for `advanceIntegrationHead` both are `advanced`; for the target branch the second is a branch someone else moved);
   - the caller chooses whether the write runs **with hooks off** (the integration head, as today) or **with no override at all** (the target branch: a plain `gitExecFileAsync` with `gitOptionsForWorktree(repoPath)` and the same 30-second limit, no `withHooklessGit` — a hook of the user that refuses the update makes the write fail, the second read finds the branch where it was, and the answer is `unavailable`; git before 2.28 has no hook for a reference update and simply runs none);
   - the caller may give a **reflog message** (`update-ref -m`); delivery gives one that contains the word `axiom` and the Mission's id, so the user's reflog says who moved the branch.
   The text `update-ref` stays in this file; it must not appear in a non-test file of the new folder of deliverable 5.
5. **The delivery** — a new folder `src/main/axiom/delivery/` (no subfolder; it never calls `getAxiomControlPlane` and has no clock of its own). It holds one async operation, given the runtime and the controller, for `{ missionId, approvalId, via }`, and the plain functions its writes are made of (deliverable 6 says how they are reached). In this order:
   1. **One at a time.** While a delivery of a Mission is between its check and its record, a second call for the same Mission in this process is refused with `delivery_unavailable` (a set of Mission ids held by the module, cleared in a `finally`; data as in step 3).
   2. **Check** (deliverable 3), as one write of the controller. A refusal ends the command. The lapse of an expired Approval is the only thing this step can write.
   3. **Read git**, through the readers of ground truth 5: the repository path; the names `git remote` prints; the integration head; the target head (`rev-parse --verify --quiet refs/heads/<targetBranch>^{commit}`, exit code 1 meaning the branch does not exist). A read that fails for any other reason → refuse `delivery_unavailable`; nothing is written. Its data, here and in steps 1 and 8: `missionId`, `approvalId` and a `reason` — `in_progress`, `git_unreadable` or `write_not_taken`.
   4. **Stops that do not depend on the target branch.** `git remote` prints at least one name → stop with the reason `remote_configured`. Otherwise the integration head is not the record's `integrationHead` → stop with the reason `integration_head_unexpected`. **A stop** is always the same: in one write, one audit event `mission.delivery_stopped` (actor `MissionController`, object kind `mission`, object id the Mission's id, `before` `null`, `after` holding `approvalId`, `reason`, the target branch, `via` and, for a checked-out branch, `worktreePath`); then the command is refused with `delivery_stopped` (data: `missionId`, `approvalId`, `reason`, `targetBranch`, and `worktreePath` when there is one). The Mission stays `READY_FOR_APPROVAL` and the Approval `GRANTED`.
   5. **D70 item 2.** The target branch does not exist → the reason is `target_branch_not_found`; its head is not the record's `targetHead` → `target_branch_moved`.
