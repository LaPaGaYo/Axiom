# Task M3-06-3-3 — Rule supervision, fourth part: metering the new tokens of every headless Worker Attempt (D88 rule 10 and revision ③ of 2026-11-12; first half of the token budget)

Planner brief, 2026-11-12 (verifier). Henry fixed the token budget on 2026-11-12 (D88 revision ③; research `claude/token-budget-research-v1.md`): `task.spec.budget.maxTokens` caps a whole Task (all its Attempts together) and `policy.budget.maxTokens` a whole Mission (checked at admission); the unit is **new tokens only** — non-cached input + cache writes + output; each Attempt counts only its own increments (Codex: the rollout's `token_count.last_token_usage`, deduplicated; Claude: the usage of each assistant message, deduplicated by message id, largest value kept); at the Task cap the Attempt is stopped and preserved, FAILED `budget_exhausted` (counted), and the Task waits in `BLOCKED(budget)` until a person raises the cap with `task.adjust`; every launch prompt states the remaining budget. That is two Tasks of work, so it is split like M3-06-3-2: **this Task measures and records**; **M3-06-3-3b** enforces (the stop, the settlement, `BLOCKED(budget)`, `task.adjust`, the Mission check at admission, the prompt). Nothing here stops, blocks or refuses anything.

## Ground truth (verifier, 2026-11-12, main `fab4496d85`; every function named here was read in full unless marked)

The harness's stdout is `events.jsonl` there (`execution/headless-worker-command.ts`: Claude `-p --output-format stream-json --verbose`; Codex `exec --json`, `CODEX_HOME` = the Attempt's account home).
3. **Codex: the session total is not the Attempt's usage.** `exec --json`'s `turn.completed.usage` is the thread's cumulative total; `execution/headless-worker-events.ts` keeps the last one and `attempt-exit-submission.ts` copies it into the exit audit as `usage`; after an in-place continuation (M3-06-2c) it includes earlier Attempts, which `in-place-session.ts` `resumedExitEvidence` marks `usageScope: 'session'`. The per-call increments are in the thread's rollout under the account home: `execution/codex-session-record.ts` `findCodexSessionRecord({ accountHome, threadId, startedAt, now })` (only the day directories from the start day to `now`, `rollout-*-<threadId>.jsonl`; names and metadata only); `execution/codex-rollout-limit.ts` reads its tail for reset times and strips everything except rate-limit fields. The account home comes from `execution/attempt-account.ts` `readAttemptAccount(store, missionId, dispatchId, provider)` (the `attempt.headless_prepared` audit, not Worker-writable). The thread id is a resumed Attempt's `readAttemptSession(...).id`, otherwise `firstThreadStarted(eventsText).id` (`in-place-session.ts`); `sessionOriginStartedAt` gives the origin dispatch's `created_at` (the rollout file lives in that day's directory). `worker_dispatches` has `created_at` and `updated_at` (SQLite UTC text; `exposeUtcTimestamp` turns it into ISO).
4. **Rollout records** (openai/codex `1d529e0`, read by the verifier). Every sampling response emits `EventMsg::TokenCount { info: { total_token_usage, last_token_usage, … }, rate_limits }` once its pending tools resolve (`core/src/session/turn.rs`; `core/src/session/mod.rs` `send_token_count_event`); `rollout/src/policy.rs` persists `TokenCount` in every history mode; the recorder writes added items at once after the file is materialized (`rollout/src/recorder.rs`: `AddItems` → `flush_if_materialized`). So the rollout grows during the Attempt, one record per model call — enough for the 60-second pass. Usage fields: `input_tokens` (includes cached), `cached_input_tokens`, `cache_write_input_tokens` (default 0), `output_tokens` (includes reasoning), `reasoning_output_tokens`, `total_tokens`; Codex's own `blended_total` is `max(0, input − cached) + output`. `info` may be `null` (a rate-limit-only record). Records may carry account state (`rate_limits.plan_type`, `credits`; `session_meta.creator_account_id`): never store, return or log it.
5. **Kernel pure helpers** (Orca, `src/main/codex-usage/codex-usage-token-delta.ts`): `normalizeRawUsage`, `resolveCodexUsageDelta(total, last, previousTotals)` (the `last_token_usage` is the increment, totals only the baseline; a guard drops stale regressions after compaction or resume), `buildCodexUsageEventKey(timestamp, total, last)` (fork and resume copy records byte for byte; the key is timestamp + tuples). They are pure (one import of `usage/usage-record-coercion`); Axiom may import them. It must not call the kernel's usage scanners, stores, providers or rate-limit services (egress rule).

The final `result.usage` is the run's aggregate (`execution/claude-worker-events.ts` keeps it for the exit audit). The kernel's `claude-usage/transcript-record-parser.ts` deduplicates by message id and keeps the largest value per field.

## Outcome

After this Task every headless Worker Attempt's new tokens are measured from the harness's own per-call records — Codex's rollout increments inside the Attempt's own window, Claude's per-message usage — and kept in a per-Attempt ledger, updated each pass while the Attempt runs and finalized once after it ends. `axiom.mission.usage` shows each Task's and the Mission's total next to their limits. No limit is enforced yet.

## Deliverables

1. **Codex reading.** A new module: for a Codex Worker binding, find the account home, the thread id and the rollout (search from `sessionOriginStartedAt`; for an ended Attempt `now` is its dispatch's `updated_at`), read at most 32 MiB from the end of the file (skip a cut first line), parse only lines that contain `"token_count"` with a strict schema that keeps `timestamp` and `payload.info.total_token_usage` / `last_token_usage` and nothing else, walk the read records in file order with `resolveCodexUsageDelta` (baseline continuity) and drop repeats by `buildCodexUsageEventKey`. Count the deltas whose record timestamp is at or after this Attempt's dispatch `created_at` and, when the Task's next binding resumed the same thread, before that binding's dispatch `created_at`. New tokens = Σ (`max(0, input − cached_input)` + `output`); also keep the sums of input, cached input, cache writes, output and reasoning. Status: `unavailable` when there is no account home, thread id or rollout; `partial` when the read was cut at the cap and the window may start before the first record read, or a `token_count` record inside the window has no usable `info`; otherwise `complete`.
2. **Claude reading.** For a Claude Worker binding, the Attempt's `events.jsonl` (at most 64 MiB from the start): lines with `"assistant"` and `"usage"`; per `message.id` the largest value of each field; new tokens = Σ (`input_tokens` + `cache_creation_input_tokens` + `output_tokens`), cached input = Σ `cache_read_input_tokens`, cache writes = Σ `cache_creation_input_tokens`, reasoning 0. `result.usage` is not counted. Status: `unavailable` when the file does not exist; `partial` when it was cut at the cap or a usage line is malformed; otherwise `complete` (zero is a valid complete reading). Neither reader throws for a file problem, and neither returns or logs file contents, paths, thread ids or account fields.
3. **Ledger.** A new table `attempt_token_usage` in `create-axiom-supervision-sql.ts`: `dispatch_id TEXT PRIMARY KEY`, `mission_id TEXT NOT NULL`, `task_id TEXT NOT NULL`, `seq INTEGER NOT NULL`, `provider TEXT NOT NULL`, `new_tokens`, `input_tokens`, `cached_input_tokens`, `cache_write_tokens`, `output_tokens`, `reasoning_tokens` (each `INTEGER NOT NULL DEFAULT 0`), `status TEXT NOT NULL`, `final INTEGER NOT NULL DEFAULT 0`, `measured_at TEXT NOT NULL`; indexes on `(mission_id)` and `(task_id)`; the trigger `trg_missions_delete_attempt_token_usage` (`AFTER DELETE ON missions`, that Mission's rows only). Register it for the WSL mover and in the schema test's contract, with the new existing-v46 case. A store module (joined into `AxiomStore`): upsert (insert, or update a row whose `final` is 0; a final row never changes), list by Mission and by Task, sums. No `SELECT *`.
4. **Metering step.** A new module called once per pass right after `reconcileStallObservations` (`recovery-service.ts` gains that call and its import, nothing else). First, for each current Worker Attempt (role not `planner`, dispatch id set): read; insert a row only when the reading has new tokens, update an existing non-final row only when the reading differs from it. Then finalize ended Worker Attempts — role not `planner`, dispatch id set, not current, no final row — oldest dispatch first, at most **20 per pass** (current Attempts do not count): read once and upsert with `final = 1` whatever the status, so a TUI Worker Attempt or one without files ends `unavailable` with zeros. A failure for one Attempt is logged with its ids only and leaves it for the next pass; a failing scan does not stop the pass. It writes only `attempt_token_usage` rows: no audit, and no Attempt, Task, binding, worker or effect change.
5. **Usage view.** `axiom.mission.usage { missionId, taskId? }` — a read (caller class `read`, no CLI command), in `methods/axiom/mission.ts`, the params catalog regenerated. Response: `{ missionId, limit: policy.budget.maxTokens ?? null, used, tasks: [{ taskId, limit: task.spec.budget?.maxTokens ?? null, used, attempts: [{ attemptId, seq, provider, newTokens, inputTokens, cachedInputTokens, cacheWriteTokens, outputTokens, reasoningTokens, status, final, measuredAt }] }] }` — every Task of the Mission in `listTaskStages` order, attempts by `seq`; `used` sums `newTokens` of every row, final or not; the Mission's `used` sums its Tasks. `taskId` narrows to one Task; an unknown Mission is `mission_not_found`, a Task outside the Mission `task_not_found`. It writes nothing.
6. **E2E** (host, verifier-run). A new spec `tests/e2e/mission-token-usage.spec.ts` with a Codex test and a Claude test. Stub usage is opt-in per Task (a ledger flag file `<ledger>.usage-<taskId>`): the Codex stub writes a rollout for its thread with a `session_meta` (decoy account id), a rate-limit-only `token_count` (`info: null`, decoy plan and credits), two usage records — last `{ input 1000, cached 400, output 50, reasoning 10 }` then last `{ input 2000, cached 1500, output 80, reasoning 20 }` with matching totals — and a byte-identical copy of the first; the Claude stub prints assistant events for message A (`input 10, cache_creation 300, cache_read 1000, output 5`, then again with `output 40`) and message B (`input 20, cache_creation 0, cache_read 1300, output 60`) before its usual `result`. After the submission the test polls `axiom.mission.usage` through `desktopCall` until the Attempt's row is final, then asserts: Codex `newTokens` 1,230 = (1,000 − 400 + 50) + (2,000 − 1,500 + 80), cached input 1,900, output 130; Claude `newTokens` 430 = (10 + 300 + 40) + (20 + 0 + 60), cached input 2,300, cache writes 300; `status: 'complete'`, `final: true`; the Task's and the Mission's `used` equal the Attempt's; both limits `null`; and no decoy string anywhere in the Mission's audits or ledger rows. Without the flag every stub behaves exactly as today. Put the fixture code in `axiom-codex-rollout.ts`, the Claude stub's own file or a new helper next to them; `axiom-test-provider.ts` may gain at most 3 lines.
7. **Docs.** `docs/reference/control-plane.md` Supervision rules (the token budget's first half: what is measured, the windows, the statuses, the ledger, the pass, the view; the exit audits' `usage` stays the harness's own report — for Codex the thread total), `docs/GLOSSARY.md` (new tokens, `attempt_token_usage`, the usage statuses, `axiom.mission.usage`), `docs/reference/orca-mapping.md` (the table, its indexes and trigger, the method).
