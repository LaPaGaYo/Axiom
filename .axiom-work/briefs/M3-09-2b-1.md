# Task M3-09-2b-1 — A human resolution carries a typed disposition (D82 revision 2026-10-26, DEF-33's noise samples; contract and main process, no renderer change)

Planner brief, 2026-11-13 (verifier). When a verification run ends in `HUMAN_REVIEW`, a person resolves it `PASS` or `FAIL` with a rationale. D82 asks for one thing more: a typed disposition — `fixed`, `rejected`, `intentional`, `not_worth` — so that each time the checks sent something to a person we later know whether it was a real problem or noise. This Task adds that field to `axiom.verification.resolve`, has the Control Plane (not the UI) decide when it is required, and stores it with the resolution and its audit. The actions on the Task page that will use it are the next Task (M3-09-2b-2).

Read first: `AGENTS.md` (Independent Verification; Human Approval), `docs/GLOSSARY.md` §4.8, `docs/reference/control-plane.md` ("人工验证处置与同候选重验（M3-05；D82 / D85 / DEF-21 ④）"; "Task 页的验证记录读取（M3-09-2）").

## Ground truth (verifier, 2026-11-13, main `808a869610`; every file named here was read in full unless marked)

1. **The call.** `axiom.verification.resolve` (`src/main/runtime/rpc/methods/axiom/verification.ts`) is a `desktop_only` mutation with strict params `VerificationResolveParams { runId, verdict: 'PASS' | 'FAIL', rationale (trimmed, 1–4000), criteria: number[] (≤ 50, default []) }` (`src/shared/axiom-contract/verification-params.ts`). `VerificationResolutionSchema` is derived from it (`omit({ runId })` plus `by: 'user'`, `at`), so it is strict too.
2. **What it does.** `resolveVerification` (`src/main/axiom/verification/verification-resolution.ts`, 105 counted lines), in one `verification_resolve` transaction: the run must be `HUMAN_REVIEW` (else `illegal_transition` with `deterministic_verdict_final` or `run_not_pending`); the Task must be `VERIFYING` and the Candidate `ACTIVE` and both belong to the run's Mission (else `stale_state`); a rationale that `redactContext` would redact is `invalid_argument` / `secret_in_rationale`; every `criteria` index must exist in `verdictDetail.acceptance[]` (else `invalid_argument` / `criterion_not_found`). Then it writes the run's status and `verdictDetail.resolution = { verdict, rationale, criteria, by: 'user', at }` (the checks' own `verdict`, `reason` and `acceptance` stay), moves the Task (`PASS` → `VERIFIED`, actor `user`, reason `verification_resolved`; `FAIL` → `settleVerificationFailure`), appends the audit `verification.resolved { verdict, rationale, criteria, taskId, candidateId, by: 'user' }` and records the receipt `{ runId, status }`. A refusal writes nothing.
3. **Why a run reaches a person** (`verification-verdict.ts` `decideVerificationVerdict`, read in full). `INCONCLUSIVE` reasons: from the diff gate `test_tampering`, `dangerous_change`, `diff_too_large`, `environment`; from the checks `environment`, `plan_invalid`, `flaky`, `known_flaky`; `policy_invalid` when the Mission's verification rules do not parse (`verification-checks.ts`, read in part); and two that are not findings but reviews the plan or the policy asked for — `acceptance_human` (a criterion a person confirms) and `non_code` (a Task without code under `nonCodeTasks: human_confirm`).
4. **Who reads a stored resolution.** `context-builder/previous-acceptance.ts` parses `verdictDetail.resolution` with the strict `VerificationResolutionSchema` to give the next Attempt the lines `A human resolved verification run <id> as FAIL: …` and `[fail] <criterion> — a human judged this failed: …`; `src/shared/axiom-contract/verdict-record.ts` (M3-09-2) reads it with the same schema made tolerant (`.strip().optional().catch(undefined)`): a resolution that fails the schema is dropped whole.
5. **Callers of resolve today.** Tests: `verification-resolution.test.ts` (through real RPC dispatch on `humanReviewFixture`, whose run is `INCONCLUSIVE` / `acceptance_human`; it compares the stored `FAIL` resolution with `toEqual` — an exact expectation this Task changes), `verification-checks.test.ts` ("cleans up a human review even if resolution races removal" calls `resolveVerification` with `PASS` on the run that test produced), `read-models/mission-pending-actions.test.ts` (`PASS` on an `acceptance_human` review). E2E: `mission-human-review.spec.ts`, `mission-pending-items.spec.ts`, `mission-task-evidence.spec.ts` — all on `acceptance_human` runs or with `FAIL`, compared with `toMatchObject`. `tests/e2e/mission-tamper-gate.spec.ts` (read in part) reaches three `HUMAN_REVIEW` runs with reason `test_tampering` and does not resolve them.
6. **The CLI.** `src/cli/specs/axiom-verification.ts` and its handler still describe `axiom verification resolve`; the caller-authority fence refuses every non-desktop caller of a `desktop_only` method (`caller_not_desktop`), so that path cannot succeed. It is not part of this Task.

## Outcome

Every human resolution of a run that the checks flagged says which of four things it was; a resolution of a review the plan asked for says none; a `FAIL` is always `fixed`. The rule lives in one shared function that the Control Plane enforces and the UI will later read, so the two cannot disagree.

## Deliverables

1. **Vocabulary and rule** (new contract module `src/shared/axiom-contract/verification-disposition.ts`, no Node import): `VerificationDispositionSchema = z.enum(['fixed', 'rejected', 'intentional', 'not_worth'])` and one pure function that, for a verdict and the run's recorded reason, returns the dispositions a person may give:
   - `FAIL`, any reason → `['fixed']` (the work goes back to be fixed);
   - `PASS`, reason `acceptance_human` or `non_code` → `[]` (the review was asked for; nothing was flagged, so there is nothing to dismiss);
   - `PASS`, any other reason — including a missing or unknown one → `['rejected', 'intentional', 'not_worth']` (the flag was wrong; the flagged change is intended; real but not worth fixing).
2. **Params.** `VerificationResolveParams` gains `disposition: VerificationDispositionSchema.optional()`; `VerificationResolutionSchema` therefore carries it. Nothing else in the params changes.
3. **Enforcement** in `resolveVerification`, after the existing checks and before any write, using the function of deliverable 1 on `run.verdictDetail.reason`:
   - `FAIL`: `disposition` omitted or `fixed` → stored as `fixed`; any other value → `invalid_argument` / `disposition_mismatch`;
   - `PASS` with an empty allowed list: `disposition` given → `invalid_argument` / `disposition_not_applicable`; omitted → nothing stored (no `disposition` key);
   - `PASS` otherwise: omitted → `invalid_argument` / `disposition_required`; `fixed` → `invalid_argument` / `disposition_mismatch`; one of the three → stored as given.
   A refusal writes nothing (no run, stage, audit or receipt), like the existing ones.
4. **Stored and audited.** `verdictDetail.resolution.disposition` and `verification.resolved.after.disposition` carry the stored value; both leave the key out when nothing is stored. The receipt and its replay are unchanged.
5. **Reader.** `readVerdictRecord` returns `resolution.disposition`; a resolution whose `disposition` it does not know is kept without that field (today such a resolution would be dropped whole).
6. **Next Attempt.** A `FAIL` resolution that carries `disposition` still produces the two lines of ground truth 4, unchanged.
7. **Existing tests.** `verification-resolution.test.ts`: the exact `FAIL` expectation gains `disposition: 'fixed'`. `verification-checks.test.ts`: if the racing `PASS` call is refused under the new rule, give it the disposition the rule asks for. Any other test that has to change is a difference to name in the report, not to make silently.
8. **E2E** (host, verifier-run). A new spec `tests/e2e/mission-review-disposition.spec.ts`, one test on the flow of `mission-tamper-gate.spec.ts` reduced to what one `HUMAN_REVIEW` run with reason `test_tampering` needs: `axiom.verification.resolve` `PASS` without a disposition through `desktopCall` is refused with `invalid_argument` and the run is still `HUMAN_REVIEW`; `PASS` with `intentional` succeeds, the run is `PASS`, the Task `VERIFIED`, the stored resolution and the `verification.resolved` audit carry `intentional`. Responses are parsed with the contract schemas. The report lists the asserted fields and their schema sources. No fixture helper changes.
9. **Docs.** `docs/GLOSSARY.md` §4.8: the four dispositions, what each means, and the rule of deliverable 1 as a small table (the canonical definition). `docs/reference/control-plane.md`, the M3-05 human-resolution section: the param, the three refusals, where the value is stored.
