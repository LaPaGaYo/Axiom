# Task M3-09-2 — Mission UI, second part: the Task page says why a Task is where it is and shows the evidence behind a verdict (D86 ③, STYLEGUIDE rule 4; read side, no main-process change)

Planner brief, 2026-11-13 (verifier). M3-09-1 gave the Control Plane a `waitingOn` for every Task. This part puts it on the Task page together with the verification record: the runs of the Task, the exact commands and their results, each acceptance criterion with how it was checked, the diff gate's findings, who resolved a human review and why — and it makes "verified" clickable evidence instead of a colour. It is the read half of the Task page; the actions (resolve, rerun, adjust, cancel) are the next part (M3-09-2b). Nothing in the main process, the RPC surface or the kernel changes.

Read first: `AGENTS.md` (UI and Product Experience), `docs/STYLEGUIDE.md` (Color roles, Components, UX rules — rule 4 is the acceptance yardstick of this Task), `docs/GLOSSARY.md` §4.4a, `docs/reference/control-plane.md` (Verification; "Task 等待与 Mission 待处理项（M3-09-1）").

## Outcome

Selecting a Task shows, in this order: what it is and its stage; **what it is waiting on**, in the Control Plane's words with a short gloss; its Attempts with their token usage; **the verification record** — every run, and for the selected run the commands, results, criteria, gate findings and the human resolution; then the Worker's own report and the messages as today. A `VERIFIED` (or `INTEGRATED`) stage is green only when a passing run is on the page, and one click on it lands on that run. A person can answer "why is this Task not moving" and "why was this accepted" without leaving the page or reading a log.

## Deliverables

1. **One tolerant reader for the verdict record** (new contract module `src/shared/axiom-contract/verdict-record.ts`): a schema and a function that turn a run's `verdictDetail` — or the parsed JSON of the evidence Artifact — into a typed view with at least `{ phase?, verdict?, reason?, checks[], acceptance[], diff?, resolution?, rerun?, verdictArtifactId?, evidenceArtifactIds[] }`, checks with `excerpt?` when the source has it. It never throws: a missing or malformed part is left out (or an empty list), unknown keys are ignored, and one bad check does not hide the others. It reuses `VerificationAcceptanceSchema`, `VerificationResolutionSchema` and `VerificationRerunDetailSchema`. The main process is not changed and does not have to use it; a test under `src/main/axiom/verification/` (new file; the fixtures in `verification-fixture.test-support.ts` / `human-review-fixture.test-support.ts` exist) runs the real verdict path and shows the reader returns what it wrote — that test is what keeps writer and reader together.
2. **Client methods** for `axiom.verification.list`, `axiom.artifact.read` and `axiom.mission.usage`, in `src/renderer/src/lib/axiom-client.ts`, each validated with its contract schemas like the existing reads (no mutation envelope). Their test (title 15) goes in the existing `src/renderer/src/lib/axiom-client.test.ts`. The existing methods stay in that file. (`axiom.task.show` and `axiom.mission.pending` come with part 3.)
3. **The waiting line** (Task page, directly under the stage). For the selected Task's `waitingOn`: the two codes verbatim in monospace (`on` and `reason`, e.g. `dependency · upstream_not_integrated`) and one short gloss sentence in the UI language; the details the value carries — the upstream Tasks by title (from `taskIds`, each selecting that Task), the Mission status, the budget (`used` of `limit`, which budget and whose), `until` as a time, the Attempt `seq`, the run (selecting it in the verification record). When `person` is true the line is marked as needing a person, with the warning status colours and words, not colour alone; when it is false the line is quiet (muted text, no badge). One gloss per `on`, and a more specific one for the reasons whose meaning differs: `upstream_canceled`; the Mission budget (`budget_exhausted`), the Task's tokens (`task_tokens`, `token_budget_exhausted`) and its Attempts (`task_attempts`, `retry_budget_exhausted`); `backoff`, `concurrency`, `no_eligible_provider`, `next_round`; `integrated` and `canceled`. Any other reason shows its code with the gloss of its `on`. A Task without `waitingOn` (a runtime that predates it) shows no waiting line. All glosses are static `translate()` calls in one module, so that part 3 can show the same words in the Task table. Copy must not overclaim (STYLEGUIDE): say what the Control Plane said, promise nothing it did not.
4. **The verification record** (a `region` named "Verification", after the Attempts). The Task's runs, newest first: status, the record's reason verbatim, Candidate short sha (full sha in a `title`), verifier, started, duration. The latest run is selected by default; selecting a row (pointer or keyboard, as `TaskStageTable` rows) shows that run:
   - **Checks**: index, source, the command verbatim in monospace, result and its reason when it has one (`flaky`, `known_flaky`, `setup_failed`, …), exit code, duration, the failure names. A control on a check loads its output excerpt on demand from the evidence Artifact (`axiom.artifact.read` on `verdictArtifactId`, base64 → JSON → the reader of deliverable 1), shows it in a `pre`, and shows a plain message when the Artifact holds no excerpt for that check or cannot be read.
   - **Acceptance criteria**: index, text, how it is proven (`command` / `artifact` / `human`, with the command verbatim), result, and the checks it rests on.
   - **Diff gate**: changed-path count and each non-empty finding list (scope violations, dangerous changes, secrets — paths and pattern names only, as stored — tampering, generated, binary) with its total from `counts` when the stored list is shorter, `patchComplete`, or the gate's error.
   - **Resolution / rerun**: who, when, the verdict, the rationale verbatim, the criteria it names (index and text).
   - Tool versions and the evidence Artifact id.
   The run's `status` is the authority for what the run is and for its colour; the record's `verdict` and `reason` are shown as the checks' own outcome. A run a person resolved says so next to its status. A Task without runs says so in one line. Statuses and results use text plus the status colours (success only for `PASS` / `pass`; warning for what waits on a person; `text-destructive` for `FAIL` / `fail`); a queued or running run is shown as in progress, never as a result.
5. **No green without evidence.** On the Task page the stage of a `VERIFIED` or `INTEGRATED` Task is a control: when the Task's latest run has status `PASS` it uses the success colours and one click selects that run and moves focus into the verification record; when no passing run is on the page it stays neutral and says the record is missing (or could not be read). `SUBMITTED` and `VERIFYING` are never styled as done (the label already reads "Submitted, awaiting verification"). The stage element keeps `data-task-stage`. The Task table is not changed in this part.
6. **Usage.** `AttemptList` gains the tokens of each Attempt (`newTokens`, and the reading's status when it is not `complete`; "not measured" without a row), and the Task's total against its cap when it has one — outside the table body: the table keeps exactly one `tbody tr` per Attempt.
7. **Loading.** The selected Task's runs and usage are read together with the rest of `readMission` (same generation guard, same Refresh). A failed read of either shows its own short message in its section and nothing else changes: the Attempts, the Submission and the messages are still shown, and no page error is reported for it. No polling, no timers, no new store of server state: the selected run and an opened excerpt are local component state.
8. **Catalogs.** Every new string through `translate('missions.…', 'English')` with the key in all seven catalogs; `en` and `zh` carry real text (write natural Simplified Chinese; keep `Task`, `Attempt`, `Mission`, `Candidate` and every code untranslated), the other five may carry the English text (D32).
9. **E2E** (host, verifier-run). A new spec `tests/e2e/mission-task-evidence.spec.ts`, one test on the flow of `mission-pending-items.spec.ts`, driving the UI: after the `HUMAN_REVIEW` run exists, open Missions, select the Mission, select the reviewed Task's row; the Task detail shows the waiting line with `human` and `acceptance_human` verbatim and marked as needing a person; the Verification region lists one run in human review, its checks include the passing command verbatim with a pass result, opening that check's output reads the evidence Artifact through the real runtime and says it holds no excerpt for it, and the criteria list shows one `pass` and one `human`. Then `axiom.verification.resolve` `PASS` through `desktopCall`, Refresh: the stage control is `VERIFIED` with the success styling, a click on it puts focus inside the Verification region, the run shows the resolution's rationale, and the waiting line reads `integration` and `integration_queue`. Then select the dependent Task: its waiting line shows `dependency`, `upstream_not_integrated` and the first Task's title, and the Verification region says there are no runs. The spec saves three screenshots (`testInfo.outputPath(...)`, attached), one after each of the three states, for the verifier's visual review; each must show the whole Task detail region (the page scrolls inside an inner container, so a plain full-page capture cuts it off). The report lists every selector with the element it targets and every asserted text with its source. No fixture helper changes.
