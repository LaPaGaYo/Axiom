Command strings are non-empty and trimmed.
   - `retryOnce` matching: normalise whitespace; a command matches a prefix when it equals it or starts with `prefix + ' '` or `prefix + ':'` (so `pnpm run test:unit` matches `pnpm run test`; `pnpm run verify:full` matches nothing).

   - resolver `resolveVerificationPlan(taskSpec, rules)` → ordered `{ source: 'setup' | 'evidence' | 'gate', command }[]`: `setupCommands`, then `requiredEvidence` de-duplicated in declaration order, then `repositoryGates[task.risk]` minus commands already listed.

A stored value the schema rejects makes the run INCONCLUSIVE with reason `policy_invalid` (route `human`), never a crash.

2. **Check runner** `src/main/axiom/verification/verification-checks.ts` (split by concern if it grows; follow the module-naming rules), called from `VerificationService` right after a successful `prepareVerification` (same drain, same fence: `id`, `expectedStatus: 'RUNNING'`, `expectedRuntimeEpoch`, `expectedClaimCount`):

   - spawn exactly like the automation precheck runner (`src/main/automations/precheck-runner.ts` `runLocalPrecheck`: `shell: true`, `cwd`, `env: process.env`, `detached` on POSIX, `windowsHide`) and stop timed-out commands with its exported `killLocalPrecheckProcessTree` — do not write a second tree-kill. Local worktrees only (Mission repositories are local in V1); a non-local repository → INCONCLUSIVE `environment` with detail `remote_repository_unsupported`.
   - time budget: one deadline per run (`timeBudgetMinutes`); each command gets the remaining time; a command killed by the deadline is `environmental` (`timeout`); commands not started once the deadline has passed are `skipped` with reason `time_budget_exhausted`.
   - setup commands run first, in order; the first one that does not exit 0 is `environmental` (`setup_failed`) and the evidence / gate commands are not run (`skipped`, reason `setup_failed`). Evidence and gate commands all run in order even after a `fail` (complete evidence for the fix Attempt), subject to the deadline.
   - per-check result: exit 0 → `pass`; spawn error (`ENOENT` / `EACCES`), exit 127 (POSIX "command not found") or 9009 (cmd.exe "not recognized") → `environmental` (`tool_missing`); killed by the deadline → `environmental` (`timeout`); terminated by a signal we did not send → `environmental` (`killed`); any other non-zero exit → `fail`.
   - `retryOnce` (D68 ③): a `fail` whose command matches `retryOnce` is re-run once in the same worktree; both runs are recorded; second run `pass` → `inconclusive` (`flaky`); second run `fail` → `fail`.    - `knownFlaky` (D68 ③): a `fail` whose extracted failure names are non-empty and all match `knownFlaky` → `inconclusive` (`known_flaky`) plus one audit `verification.known_flaky { checkIndex, failures }`. The system never adds names to the list.
