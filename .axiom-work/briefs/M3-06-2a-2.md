# Task M3-06-2a-2 — An account that hit its usage limit takes no new Attempts until the wait it caused is over (D88 items 1, 6)

Planner brief, 2026-11-10 (verifier). M3-06-2a made one interrupted Task wait. The limit it ran into belongs to the account, not to the Task: today every other READY Task that would use the same account is still launched once, dies on the same limit and starts its own chain of three. **This Task makes the wait an account-level fact: while a usage-limit continuation of the currently selected account is waiting, AgentFactory sends no new Worker Attempt to that provider, in any Mission; when the wait ends, every executing Mission is scheduled again.** It also settles four observations from the M3-06-2a verification record. Not here: a reset time for Codex (its own Task, next; the source of that time awaits a Decision); pacing before a limit is reached; any read of the kernel's polled rate-limit state; preserving the interrupted worktree (M3-06-2b); resuming the harness session (M3-06-2c); supervisor rules (M3-06-3).

## Outcome

After this Task a usage limit on the selected account of a provider is an account-level fact for as long as a continuation it produced is waiting. No new Worker Attempt goes to that provider before then, in any Mission: when another provider is eligible the work goes there, and when none is the Task stays `READY` with a refusal audit that says until when. When the wait ends — the continuation comes due, or a person lifts it — every `EXECUTING` Mission gets a scheduling round without needing an event of its own. Selecting a different account lifts the cooldown at the next round. The interrupted Task's own wait, the chain of three and everything else M3-06-2a does are unchanged.

## Deliverables

1. **Contract** (`src/shared/axiom-contract/`, additive). `ProviderFilterReasonSchema` gains `account_cooldown` as its **last** option: it is reported only for a provider that passed every other filter. `AttemptContinuePayloadSchema` gains an optional `account: { provider, key }` — the provider id and an opaque non-empty key. Rows and AgentSpecs written before this Task keep parsing. No RPC method, no table, no policy key.
2. **The continuation knows its account.** When the exit-failure settlement enqueues a continuation for a `usage_limit` failure, the payload carries `account` if the Attempt's launch audit (`attempt.headless_prepared` for this dispatch id, ground truth 7) names an account home (`kind: 'account'`, non-empty `path`); parse the row with zod. The key is a one-way digest of provider and home path, computed by **one** exported function that deliverable 3 also uses; the path itself is not written into the effect. A missing or malformed audit row means no `account`, never a failed settlement. The restart path of ground truth 5 is unchanged.
3. **Cooling view** (new module under `src/main/axiom/agent-factory/`; reads effects, writes nothing, holds no state and no timer; its clock is injected). A provider is cooling until `T` when at least one effect — of any Mission — is `attempt.continue`, `pending`, `failureClass: 'usage_limit'`, due in the future, **still being waited on by its Task** (the Task is `READY` and has no Attempt newer than the effect's `seq` — a canceled Task or a Task that moved on is no evidence and could not be lifted by a person) and carries the key of **the account that provider would launch with now** (ground truth 8); `T` is the latest such `dueAt`. Resolve the current home only for a provider that has a candidate effect, at most once per view (the Claude resolver is the launch-time one; if reading it shows an effect beyond resolving a path, report it under risks). No current home, a resolver that throws, an effect without `account` or with another key: not cooling (a wasted start is the safe failure; holding back the wrong account is not).
4. **Selection.** For the **worker** role a provider that is otherwise eligible and is cooling is filtered with `account_cooldown`. Consequences that must hold: with another eligible provider the work is routed there and `selection.filtered` (and `roleProviderUnavailable`, when it was the configured role provider) records the reason; with none, `no_eligible_provider` is thrown as today and its `data` additionally carries, for every provider filtered for this reason, when the cooldown ends (`accountCooldown: [{ provider, until }]`), so the existing `task.admission_refused` audit shows it; the skip reason stays `no_eligible_provider`. The planner role is never filtered for cooldown. The view is obtained before the `agent_spec` transaction opens (as `installed` is) and never awaited inside it. **One admission, one view**: both selections of a `buildWorkerContracts` call use the same view, so a cooldown that begins or ends between them cannot produce `Worker provider changed during admission`. `control-plane.ts` only wires the dependency.
5. **Nobody stays held after the wait is over.** (a) When the executor runs a `usage_limit` continuation it requests a `stage_change` round for every **other** `EXECUTING` Mission as well, after handling its own Mission as today and whatever that Mission's state is. A rejected round fails the effect attempt exactly as a rejected own round does today (3 attempts, 1 s / 5 s; the effect then ends `failed`, and M3-06-2a's rule holds: it blocks nothing). (b) When `axiom.task.adjust` retires a pending `usage_limit` continuation, every other `EXECUTING` Mission gets a round too (the Task's own Mission already gets one); an adjustment that retires nothing, or retires a continuation of another class, triggers no other Mission. No timer and no new effect kind.
6. **M3-06-2a observations.** (1) Delete `headlessFailureKind`; port every row of the two tests that call it to assert `classifyHeadlessFailure(...).kind` for the same input with the same expectation, and list the ported rows in the report. (2) In `classifyHeadlessFailure`, an exception inside the Claude structured pass means "no structured verdict": the text patterns and the events rule still run. The function as a whole still never throws. (3) An untyped assistant `error: 'rate_limit'` without a kernel refusal stays on the text fallback: the real-harness probe produced no evidence for a rule of its own — no code change, say so in the docs. (4) The restart test reads "started by an earlier runtime": a headless Worker that outlives a restart and later disappears without an exit marker is refunded as well. That is the intended meaning (neither is the Worker's own failure; three in a row still reach a person) — no code change, say so in the docs.

Task X is admitted, hits the stub's usage limit once and waits (use a first backoff step of several seconds so the wait can be observed). While X's continuation is pending and not yet due: Task Y is `READY`, has no binding, and a `task.admission_refused` audit for Y lists the provider with reason `account_cooldown` and an end time equal to the continuation's `dueAt`; the continuation's payload carries `account`.
