# Task M3-09-4c-2a — the policy write goes through the MissionController, and `axiom.policy.show` answers on request which providers admission would accept (the main-process half of the M3-09-4c-2 row of `docs/plans/M4.md`; main process and contract only: no renderer, no CLI, no new method)

Planner brief, 2026-11-21 (verifier). A Mission's policy decides who plans and who works, how many Tasks run at once and what verification runs, and no control in the interface can change it: `axiom.policy.update` is called by tests and specs only. M3-09-4c-2b, the next Task, builds the editor on the Mission page. This Task prepares the main process for it, in two parts. First, the write itself: today it lives in the RPC handler — the handler opens the transaction, merges the patch, stores the policy and writes the audit event, and the MissionController is told afterwards. Every other change of a Mission is an operation of the MissionController; this one becomes one too, with no change in behaviour. Second, an editor that offers a provider must be able to say whether that provider would be accepted, and it may not guess: the interface cannot see what is installed, which accounts exist or which provider is cooling down, and a rule copied into the renderer would drift from the one admission applies. So `axiom.policy.show` answers, when asked, for every provider whether the selection of a Planner and of a Worker would keep it or filter it, and why — computed by the filter the selection itself uses.

Read first: `docs/PROJECT_CONSTITUTION.md`, `AGENTS.md` (Axiom Control Plane Code Placement and RPC Conventions; Control Plane Boundary; Decision Engine Boundary; Lazy Senior Dev Mode), `docs/reference/control-plane.md` (the subsections `### Provider selection（M2-03）` and `### Scheduler admission 与预算（M2-04）`, and section 7 on the admission guard), `docs/reference/reuse-map.md` (the row `M3-09-4c-2 policy 编辑`: what it names is for the editor of the next Task; for this Task the thing to reuse is our own — the filter inside `selectProvider`), `.axiom-work/briefs/M3-09-4c-1.md` (the Task that made a policy update request an admission round).

## Ground truth (verifier, 2026-11-21; read in the code at main `525762837e`)

1. **The write today** (`src/main/runtime/rpc/methods/axiom/policy.ts`, 69 non-empty lines). `axiom.policy.update` runs, in this order: the parameters are parsed by the dispatcher with `PolicyUpdateParams`; `assertSupportedReadinessThreshold` refuses `readinessThreshold: 'VERIFIED'` (`invalid_argument`, data `reason: 'threshold_not_supported'`); a patch that has a `budget` key — whatever its value — is refused with a plain `Error` whose `code` is `approval_required`; then one transaction, `store.transaction('policy_update', …)`: the Mission and its policy must exist (`mission_not_found` with the Mission id), the four keys `readinessThreshold`, `routing`, `verificationRules`, `concurrencyLimit` each replace the stored value when the patch carries them (a `routing` or `verificationRules` object replaces the stored one whole), `store.upsertPolicy`, and one audit event `policy.updated` (actor `user`, object kind `policy`, object id the Mission id, `before` and `after` the two policies); the answer is `{ policy }`. After the transaction the handler calls `missions.policyUpdated(missionId)`. Nothing looks at the Mission's status: the policy of a finished Mission can be changed. `store.transaction(name, …)` is `runLifecycleWriteTransaction(db, 'axiom_' + name, …)` (`src/main/axiom/db/axiom-store.ts`), the same call the controller's `write` makes, so `write('policy_update', …)` opens the same savepoint. `axiom.policy.show` answers `{ policy }` or `mission_not_found`.

## Outcome

`axiom.policy.update` does what it did — the same refusals in the same order, the same stored policy, the same audit event, the same answer, one admission round after a commit and none otherwise — and it does it as an operation of the MissionController: the handler holds the parameters and one call. `axiom.policy.show` answers as before when asked as before; asked with `providers: true` it also answers, for every provider the selection knows about, whether a Planner and a Worker at each risk level would be allowed to use it and, where not, the selection's own reason. The two answers cannot disagree with admission, because admission's filter and this answer are one function.
