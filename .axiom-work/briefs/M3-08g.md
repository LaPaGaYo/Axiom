## Ground truth (verifier, 2026-10-27/28)

1. **Codex honours `NO_PROXY`** (`.axiom-work/logs/codex-noproxy-probe-20261027-041038.txt`, Codex 0.163.0): with `HTTPS_PROXY`/`HTTP_PROXY`/`ALL_PROXY=http://127.0.0.1:9` and `NO_PROXY='chatgpt.com,.chatgpt.com,openai.com,.openai.com,localhost,127.0.0.1'` a real `codex exec` finished in 4 s talking directly to `chatgpt.com`; without `NO_PROXY` every connection was refused (`os error 61`) and Codex looped on "Reconnecting". Codex's own domains: `chatgpt.com` (backend API and MCP), `auth.openai.com` (token refresh), `api.openai.com` (API-key mode). The one residual of the D83 ⑥ re-recording — an anonymous GET of `raw.githubusercontent.com/openai/codex/main/announcement_tip.toml` — is outside that list and will be refused.
2. **Claude Code honours the same variables** (official network configuration page, read 2026-10-28): `HTTPS_PROXY`/`HTTP_PROXY`, lowercase variants, first set wins in the order `https_proxy, HTTPS_PROXY, http_proxy, HTTP_PROXY`; `NO_PROXY` comma- or space-separated, exact hosts and leading-dot suffixes, `*` for all; loopback is never proxied; SOCKS unsupported (`ALL_PROXY` is ignored by Claude, harmless); the proxy URL is validated at startup and must carry an `http://` scheme (`http://127.0.0.1:9` parses). Hosts the CLI needs at run time with a signed-in claude.ai account: `api.anthropic.com` (API, feature flags) and `platform.claude.com` (OAuth token exchange, refresh and revocation). The others on that page are off under the M3-08b/M3-08f pins (telemetry, updater, connectors, artifacts, docs lookups, changelog — "non-interactive sessions never fetch it"). A no-login probe cannot exercise this (the CLI exits before any request); the verifier's real Claude smoke records it.
3. **Where Mission harness processes get their environment**: headless Workers (`buildHeadlessWorkerCommand` → `buildHeadlessTerminalCommand`: `/usr/bin/env K=V … argv` inside a `bash --noprofile --norc -c` PTY wrapper; the PTY itself carries Orca's terminal environment); the Claude Mission Planner (channel B: pins `env` → launch resolution env); the Codex Mission Planner on the structured channel (`codexStructuredLaunchPart`: `basis.environment()` + `CODEX_HOME`, no Mission seam yet); the Codex Planner on the terminal channel (user start-mode setting; no per-launch env seam — out of scope, see Non-goals). Orca resolves the user's login-shell environment once (`src/main/startup/login-shell-environment.ts`, `resolveLoginShellEnvironment`); that is where a corporate proxy would come from.
4. **Both harnesses keep their own second layer** for commands the Worker runs: Claude's `sandbox.network` (empty allowlist, `strictAllowlist`) and Codex's `sandbox_workspace_write.network_access=false`. This Task governs the harness process itself, not those.

## Outcome

After this Task every Mission harness process that Axiom launches on macOS/Linux starts with an egress environment Axiom decided: when the user's login-shell environment carries no proxy, `HTTPS_PROXY`/`HTTP_PROXY`/`ALL_PROXY` (and lowercase) point at a dead loopback port and `NO_PROXY`/`no_proxy` list exactly the harness's own domains plus loopback, so anything else the harness tries gets `connection refused` and leaves a trace; when the login shell already carries a proxy, Axiom leaves the proxy variables alone and records that it did. The decision, the list and the blackhole are in the Attempt evidence, and the verifier can point the blackhole at the e2e recording proxy to prove both the allowlist and the refusals. No new process, no new dependency.

## Deliverables

1. **Module** `src/main/axiom/execution/harness-egress-env.ts`:
   - `HARNESS_EGRESS_DOMAINS: Record<'codex' | 'claude', readonly string[]>` — codex `['chatgpt.com', '.chatgpt.com', 'openai.com', '.openai.com']`, claude `['api.anthropic.com', 'platform.claude.com']`; `EGRESS_LOOPBACK = ['localhost', '127.0.0.1', '::1']`; `EGRESS_BLACKHOLE = 'http://127.0.0.1:9'`.
   - `harnessEgressEnv(input: { provider: 'codex' | 'claude'; inherited: NodeJS.ProcessEnv; axiomEnv?: NodeJS.ProcessEnv })` → `{ mode: 'allowlist' | 'inherited-proxy'; env: Record<string, string>; noProxy: string[]; blackhole: string | null; overrides: string[] }`. `inherited-proxy` when any of `HTTPS_PROXY`, `HTTP_PROXY`, `ALL_PROXY`, `https_proxy`, `http_proxy`, `all_proxy` is non-empty in `inherited`: `env` is `{}` (nothing set, nothing removed). Otherwise `allowlist`: `env` sets all six proxy names to the blackhole and `NO_PROXY` + `no_proxy` to `[...HARNESS_EGRESS_DOMAINS[provider], ...EGRESS_LOOPBACK].join(',')`.
   - Verifier hooks read from `axiomEnv` (Axiom's own process env, default `process.env`), both recorded in `overrides` when used: `AXIOM_EGRESS_BLACKHOLE_URL` replaces the blackhole and is accepted only when it starts with `http://127.0.0.1:` or `http://localhost:` (anything else is refused with a thrown error — the hook routes evidence, never a real proxy); `AXIOM_EGRESS_NO_PROXY` when set replaces the `NO_PROXY` list verbatim (the empty string means "no allowlist: everything goes to the blackhole/recording proxy", which is how the real smoke records the full egress set). Unit tests: allowlist vs inherited (each of the six names, empty value counts as unset), the exact `NO_PROXY` strings per provider, both hooks, the refused non-loopback override.
2. **Headless Workers** (`headless-worker-command.ts`, both branches; the prepare path in `headless-worker-launch.ts` / `attempt-launcher.ts`): the Worker env merges `egress.env` (claude: after `CLAUDE_LAUNCH_ENV`; codex: after `CODEX_HOME`). `inherited` is the base environment every local agent launch starts from: the kernel's `resolveHostAgentBaseEnvironment(settings)` (`src/main/runtime/structured-agent-shell-environment.ts`: login-shell capture plus the user's shell-environment policy and overlays), called by Axiom's launcher with `deps.runtime.requireStore().getSettings()`; make it injectable for tests (`deps.resolveBaseEnvironment?`), never read `process.env` for this decision. Axiom imports the kernel; the kernel never imports Axiom. The combination recorded by `attempt.headless_prepared` gains `requested.egress: { mode, blackhole, noProxy, overrides }` for both harnesses (`worker-launch-combination.ts` for codex, `claude-worker-combination.ts` for claude).
3. **Claude Mission Planner**: `createClaudePlannerLaunch` registers `env: { ...CLAUDE_LAUNCH_ENV, ...egress.env }` and appends an audit `attempt.egress_pinned` `{ provider: 'claude', channel: 'structured', mode, noProxy, blackhole, overrides }` on the dispatch (actor `MissionController`, no env values other than those fields).
4. **Codex Mission Planner on the structured channel**: kernel extension point `src/main/codex/codex-mission-session-pins.ts` mirroring the Claude registry (`registerCodexMissionSessionPins(dispatchId, sessionId, { env })` / `codexMissionSessionPins(sessionId)`, frozen, process-local, same double-registration error); `codexStructuredLaunchPart` merges `...pins.env` into the child env after `CODEX_HOME` when pins exist for `record.sessionId` (nothing else changes for ordinary chats).
