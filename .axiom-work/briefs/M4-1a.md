# Task M4-1a — Integration batches get a contract and a store, and every new candidate is pinned by a ref of its own (first part of the M4-1 row of `docs/plans/M4.md`; D92, approved by Henry 2026-11-15; contract and main process; no renderer, CLI or RPC change)

Planner brief, 2026-11-16 (verifier). M4's queue merges one verified candidate at a time into the Mission's integration branch and records each merge as an IntegrationBatch. Two things it stands on are missing. The table `integration_batches` has existed since M2, but nothing can write or read it: the code has no list of a batch's statuses, no contract for a batch and no store. And a candidate is a commit that only its Attempt branch keeps reachable: a person who removes the Attempt's worktree in the sidebar removes that branch with it, and a later `git gc` may remove the commit that a verification record points at. This Task adds the contract and the store — nothing calls them yet — and pins every new candidate by a ref of its own before its submission is committed. It merges nothing and moves no Task: the executor (M4-1b), the merged-tree regression (M4-2a) and the switch that sends verified Tasks into the queue (M4-2b) come after it.

Read first: `AGENTS.md` (Integration and Promotion; Git and Worktree Safety; Code Quality; Lazy Senior Dev Mode), `docs/plans/M4.md` §2, `docs/GLOSSARY.md` §4.9, `docs/reference/control-plane.md` (the table of side tables; the steps of a submission, the seven-row table that follows "实现位于 `execution/candidate-snapshot.ts` / `attempt-submission.ts`").

## Ground truth (verifier, 2026-11-15; read in the code at main `b0683ab21d` and checked there by a second read-only pass; this brief sits on main `1b03464661`, where M4-0 has since changed the start of a Mission — none of the files named below except `lifecycle.test.ts`, which gained one title and two entries of its Mission table, and `control-plane.md`)

1. **The table** (`src/main/runtime/orchestration/db/schema/create-axiom-tables-sql.ts`): `integration_batches` has `id TEXT PRIMARY KEY`, `mission_id TEXT NOT NULL`, `base_commit TEXT NOT NULL`, `candidate_ids TEXT NOT NULL DEFAULT '[]'`, `status TEXT NOT NULL` (no CHECK), `merge_commit TEXT`, `conflicts TEXT NOT NULL DEFAULT '[]'`, `approval_id TEXT`, and `created_at` / `updated_at` as `TEXT NOT NULL DEFAULT (datetime('now'))`; an index on `(mission_id, status)`; the trigger that follows the deletion of a run deletes a Mission's rows. Nothing in `src` reads or writes the table: its only other mentions are the migration test, which inserts one raw row, and the WSL move list. **No schema change is needed and none is allowed**: the DDL file has four counted lines to spare and its test none, and a new column would need a migration.
2. **The statuses exist only in prose.** `docs/GLOSSARY.md` §4.9 has one fenced block: `QUEUED → APPLYING → TESTING → PROMOTABLE → PROMOTED`; `APPLYING → CONFLICT`; `TESTING → FAILED`; `PROMOTABLE → AWAITING_APPROVAL → PROMOTED | REJECTED`; any status that is not terminal → `SUPERSEDED`; `APPLYING / TESTING → QUEUED` (after a restart). `src/shared/axiom-contract/lifecycle.test.ts` compares each status vocabulary of the contract with its fenced block through its local functions `fencedStates(heading)` (it drops full-width parentheses with what they hold, then collects the words in capitals) and `equalVocabulary`. `AWAITING_APPROVAL` stays in the vocabulary although V1 will not use it (D92 a).
3. **The model for a store with a guarded status** is `src/main/axiom/db/verification-runs-store.ts`: `updateVerificationRun` takes `expectedStatus`, answers `false` when the move is not in `VERIFICATION_RUN_TRANSITIONS` and when no row has that id in that status, and writes with `WHERE id = ? AND status = ?`. Row codecs: `src/main/axiom/db/submission-rows.ts` (a zod schema of the snake-case row and a codec that transforms it into the contract object); JSON cells are read with `readJson` (`src/main/axiom/db/row-codec.ts`), whose error names table, row and column and never the cell. `AxiomStore` (`src/main/axiom/db/axiom-store.ts`, 258 counted lines of 300) declares one `readonly` member for each store function and assigns it in its constructor — `candidatesStore` is the nearest example. Store tests open `new OrchestrationDb(':memory:')` and close it in `afterEach` (`effects-store.test.ts`).
4. **A candidate today.** `settleSubmission` (`src/main/axiom/execution/attempt-submission.ts`, **292 counted lines of 300**) is the one path of both the RPC submit and the exit submission. After its checks it awaits `snapshotCandidate(…)` — git, in the Attempt worktree, whose path comes from `splitWorktreeIdForFilesystem(worker.worktree_id)`; the commit sits on the Attempt branch `axiom/attempt/<taskId>/<seq>` — then optionally `finalizeReport`, and then runs one write transaction, `axiom_submit`. That transaction refuses a newer Attempt (`stale_dispatch`), refuses a tree equal to the ACTIVE candidate of another Attempt (`candidate_unchanged`), inserts the candidate under the id `cand_` + sha256 of `<taskId>:<commitSha>` (computed inline in the insert), supersedes older candidates, inserts the submission and a QUEUED VerificationRun, enqueues `verification.enqueue` and appends the audits `candidate.superseded` and `attempt.submitted`. A replay of a completed submission returns before any git call. `AxiomIdSchema` is any string of 1 to 128 characters: nothing guarantees that an id is safe inside a ref name.
5. **Refs Axiom writes today**: `refs/heads/axiom/attempt/…`, `refs/heads/axiom/planner/<missionId>/<runSeq>`, `refs/heads/axiom/integration/<missionId>`, `refs/heads/axiom/verify/…` and `refs/axiom/preserved/<taskId>/<seq>`. No `refs/axiom/candidates/…` exists. The create-only form this code base uses is `git update-ref <ref> <new> <zero oid of the same length>` (`publish` in `src/main/axiom/execution/worktree-snapshot.ts`), with repository hooks switched off by pointing `core.hooksPath` at a directory that holds no hooks: `publish` reuses its private-index directory for that, and `src/main/axiom/execution/candidate-snapshot.ts` makes an empty directory for the call (`mkdtemp`, removed with `rmdir` in a `finally`) — the second is the pattern to copy. `update-ref` is a write, and the git runner gives a write no default timeout (reads get one). `src/main/axiom/execution/preserved-snapshot.ts` shows how a lost create-only race is read back: `for-each-ref --format='%(refname) %(objectname)' <ref>` and an exact match of the refname, which tells "absent" from "failed" (a literal pattern of `for-each-ref` also matches longer refs below it, hence the exact match; the object id read back is parsed and that parse can throw). Git runs through `gitExecFileAsync(args, gitOptionsForWorktree(path))`.
6. **Tests that replace the snapshot** and so reach the code after it with a worktree that does not exist: `submissionFixture()` (`src/main/axiom/execution/submission-fixture.test-support.ts`; fifteen files call it, two of them fixtures that further tests build on, so about forty test files reach it) spies on `snapshotCandidate` through the module namespace (`import * as snapshots`, `vi.spyOn(snapshots, 'snapshotCandidate')`); `src/main/axiom/recovery/attempt-reconciliation.test.ts` does the same in two of its titles, on `channelFixture`. In all of them the worker's worktree id yields the relative path `T01`, which does not exist. No unit test runs a submission on a real repository. The model for a real repository is `src/main/axiom/execution/candidate-headless-snapshot.test.ts`: it builds one in a temp directory with a linked worktree and installs a `reference-transaction` hook that fails, to prove hooks are off (it calls only `snapshotCandidate`). `tests/e2e/mission-exit-m2.spec.ts` checks every candidate of its Mission against git in the clone (the loop over `settled.submissions`), and later compares **every ref of the clone** before and after a replayed submission.

## Outcome

After this Task the contract knows what an IntegrationBatch is and which moves between its statuses are legal; a store can insert, read and move batch rows and refuses an illegal or stale move without writing; and every candidate submitted from now on has `refs/axiom/candidates/<candidateId>` pointing at its commit by the time its row can be read — or, when the pin could not be made, an audit row that says so. A submission whose pin succeeds behaves exactly as on main. No Task changes stage, no batch row is written by any product path, and no existing ref is moved.

3. **The pin**, a NEW module under `src/main/axiom/execution/` (suggested `commit-pin.ts`) with three functions and nothing else of substance:
   - One creates a ref that pins a commit (suggested `pinCommit({ cwd, ref, commitSha })`); M4-1b will use it again for the merge commit of a batch. It runs `git update-ref <ref> <commitSha> <zero oid of the same length>` in `cwd` with an empty `core.hooksPath` directory made for the call and removed afterwards, and with an explicit timeout of 30 seconds. Before git runs it checks that `ref` starts with `refs/axiom/` (Axiom pins nothing outside its own namespace) and that `cwd` is an absolute path of an existing directory (the fixtures' relative `T01` must never reach git: a relative path would be resolved against the process directory, which in a test is this checkout). It **never throws**. It answers `{ pinned: true, ref }`, or `{ pinned: false, ref, reason }` where `reason` is one of exactly two codes: `ref_conflict` — the ref exists and names another commit — and `unavailable` — everything else (the ref is outside `refs/axiom/`, `cwd` is not an absolute path of an existing directory, git failed or timed out, the ref could not be read back or what was read is not an object id). When the create-only write fails, read the ref back with `for-each-ref` and match the refname exactly: the same commit → `pinned: true` (it was pinned before); another commit → `ref_conflict`; absent or unreadable → `unavailable`. No git output and no error text leaves this function.
