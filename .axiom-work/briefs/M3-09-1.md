# Task M3-09-1 — Mission UI, first part: what every Task waits on, and the pending items of a Mission (D86 ③, STYLEGUIDE rule 4; no renderer change)

Planner brief, 2026-11-13 (verifier). M3-09 is the Mission UI (D71 / D82 / D85 rule 6 / D86). It is split into seven parts (`docs/plans/M3.md`); this first part is the read model the later parts render: a deterministic `waitingOn` for every Task ("every state has a reason"), and one ordered list of what needs a person for a Mission ("one pending item says what to do, why, and what happens if it is left undone"). Nothing in the renderer changes here, nothing is written, and no existing mutation changes.

## Ground truth (verifier, 2026-11-13, main `1453f8bab0`; every function named here was read in full unless marked)

1. **Task stages.** `shared/axiom-contract/lifecycle.ts`: `DEFINED`, `READY`, `RUNNING`, `SUBMITTED`, `VERIFYING`, `VERIFIED`, `INTEGRATION_READY`, `INTEGRATED`, `NEEDS_FIX`, `BLOCKED`, `CANCELED`; terminal are `INTEGRATED` and `CANCELED`. `TaskStageRecord` (`mission-objects.ts`) carries `stage`, `previousStage`, `spec`, `retryPolicy`, `attemptCount` — not the reason of the current stage: the reason lives in the `task.stage` audit (`mission-controller/task-readiness.ts` `transitionTaskStage` writes `after { stage, previousStage, reason }`, object kind `task`). The `BLOCKED` reasons written today are `retry_budget_exhausted`, `token_budget_exhausted`, `scope`, `candidate_disputed`, `environment`. `NEEDS_FIX` does not rest today: every transition into it (`execution/attempt-settlement.ts`, `execution/attempt-interruption.ts`, `task-adjustment.ts`) is followed in the same transaction by `READY` or `BLOCKED`; the table below still covers it. Integration is M4: nothing moves a Task past `VERIFIED` yet, and readiness needs upstream `INTEGRATED`, so dependent Tasks stay `DEFINED` for now.

## Outcome

After this Task the Control Plane can say, for every Task, the one thing it is waiting on, in its own words and by a fixed first-match table, and can list for a Mission what needs a person — each item with its reason, how many Tasks wait behind it and the calls the Control Plane would accept for it — ordered by what it unblocks. Both are pure reads derived from the existing rows and audits; there is no new table, audit event or stored state, and the UI parts that follow render them without re-deriving anything.

## Deliverables

1. **`waitingOn` — one value per Task** (new contract module under `src/shared/axiom-contract/`): `{ on, reason, person, taskIds?, runId?, seq?, budget?, until?, missionStatus? }` with `on` one of `none`, `mission`, `dependency`, `question`, `approval`, `budget`, `admission`, `verification`, `integration`, `human`, `running`; `reason` is the Control Plane's own code; `person` is true when only a person's action moves the Task on. The value is the first row of this table whose condition holds. The order is the one `docs/plans/M3.md` records (dependency → question → approval → budget → verification queue → integration queue → human → running); `none`, `mission` and `admission` are added so that the table covers every Task and every way `canBecomeReady` and the scheduler say no:

   | # | `on` | Condition | `reason` | `person` | Also |
   |---|---|---|---|---|---|
   | 1 | `none` | stage `INTEGRATED` or `CANCELED` | `integrated` / `canceled` | false | |
   | 2 | `mission` | stage `DEFINED`, `READY` or `NEEDS_FIX`, and the Mission is not `EXECUTING` or the Task's PlanRevision is not `APPROVED` | the Mission's status verbatim; `plan_not_approved` for the plan case | true for `PLAN_REVIEW`, `PLANNED`, `PAUSED` and `BLOCKED`, false otherwise | `missionStatus` |
   | 3 | `dependency` | same stages, and an upstream Task of the plan is not `INTEGRATED` | `upstream_canceled` when one of them is `CANCELED`, else `upstream_not_integrated` | true only for `upstream_canceled` | `taskIds`: those upstream Tasks |
   | 4 | `question` | stage `DEFINED`, `READY`, `NEEDS_FIX`, `RUNNING` or `BLOCKED`, and the Task has a pending question (the three sources of `blockingQuestionOrApproval`) | `question` | true | |
   | 5 | `approval` | stage `DEFINED`, `READY` or `NEEDS_FIX`, and the Mission has a blocking pending Approval | `approval` | true | |
   | 6 | `budget` | stage `BLOCKED` with the block reason `retry_budget_exhausted` or `token_budget_exhausted`; or stage `DEFINED`, `READY` or `NEEDS_FIX` and, in this order, the Mission's budget is exhausted (`budgetExhaustion`) → `budget_exhausted`, the Task's ledger total is at its `budget.maxTokens` → `task_tokens`, its attempts are at `retryPolicy.maxAttempts` → `task_attempts` | as given (the block reason verbatim for `BLOCKED`) | true | `budget { scope: 'task' \| 'mission', dimension, limit, used }`: for a Task `maxAttempts` (`retryPolicy.maxAttempts`, `attemptCount`) or `maxTokens` (`spec.budget.maxTokens`, the ledger total), omitted when the limit is no longer set; for the Mission what `budgetExhaustion` returns |
   | 7 | `admission` | stage `DEFINED`, `READY` or `NEEDS_FIX`, nothing above: `interruptionBackoff` holds → `backoff`; stage `READY` and the Mission's `RUNNING` Tasks are at `policy.concurrencyLimit` → `concurrency`; stage `READY` and the Task's latest `task.admission_refused` audit is newer than its latest `task.stage` audit → `no_eligible_provider`; otherwise `next_round` | as given | false, except `no_eligible_provider` whose audit lists no account cooldown | `until`: the effect's `dueAt`, or the earliest listed cooldown end |
   | 8 | `verification` | stage `SUBMITTED`, or `VERIFYING` whose ACTIVE Candidate's latest run is not `HUMAN_REVIEW`, `SPECIALIST_REVIEW` or `INCONCLUSIVE` | that run's status verbatim, `QUEUED` when there is no run yet | false | `runId` when a run exists |
   | 9 | `integration` | stage `VERIFIED` or `INTEGRATION_READY` | `integration_queue` | false | |
   | 10 | `human` | stage `VERIFYING` with such a review run → the run's `verdictDetail.reason` when it is a string, else `human_review`; or stage `BLOCKED` (any other block reason) → the block reason verbatim, `blocked` when the audit has none | as given | true | `runId` for a review run |
   | 11 | `running` | stage `RUNNING` | `attempt_running` | false | `seq` of the latest binding |

   The "block reason" is the `reason` of the Task's latest `task.stage` audit into `BLOCKED`. `reason` uses the scheduler's own word wherever the scheduler has one (`question`, `approval`, `task_tokens`, `task_attempts`, `backoff`, `concurrency`, `no_eligible_provider`), so a `READY` Task that the next round would skip for a single cause shows that cause. When several causes hold, the table and `check()` can name different ones (the table puts what needs a person first; `check()` tests budgets and backoff before questions) — that is intended, not to be reconciled. The projection is a pure function of the store and a clock passed in by its caller (the two handlers pass the wall clock): it writes nothing, schedules nothing and never transitions a Task — it must not call `blockTaskTokenBudget` (use the plain comparison) and must not let `budgetExhaustion` run for a Mission that is not `EXECUTING`. `until` is an ISO 8601 UTC time.
2. **`axiom.task.list` and `axiom.task.show` carry it.** `TaskListItemSchema` gains an optional `waitingOn`; the two read handlers attach the projection to every Task they return. The responses of `axiom.task.adjust`, `axiom.task.cancel` and `axiom.task.create` stay as they are, and `control-plane.ts` is not changed.
3. **`axiom.mission.pending { missionId }`** (read, strict params, no CLI): `{ missionId, items }`, each item `{ id, kind, objectId, taskId?, reason, summary?, blocking, blocks, actions, since, waitingOn? }`:

   | `kind` | One item per (`objectId`) | `reason` | `blocking` | `summary` |
   |---|---|---|---|---|
   | `mission` | the Mission (its id), when it is `PLANNED`, `PAUSED` or `BLOCKED`; `ANALYZING` with no `PROPOSED` plan and no active Planner Attempt; or `EXECUTING` with an exhausted budget (`budgetExhaustion`) | the status verbatim; `budget_exhausted` for the `EXECUTING` case and for `ANALYZING` when Mission attempts or tokens are at their limit (the two dimensions `preflight` checks) | true | the status reason for `PAUSED` / `BLOCKED` |
   | `plan_review` | `PROPOSED` PlanRevision (its id) | `PLAN_REVIEW` | true | — |
   | `question` | pending question of a non-terminal Task, or of an Attempt that is not a Task of the plan (a Planner's) (the message id) | `question` | true while the asking Task is `DEFINED`, `READY`, `NEEDS_FIX`, `RUNNING` or `BLOCKED`, and for a Planner's question; false once the Task is submitted | the question text |
   | `human_review` | Task whose `waitingOn` is `human` with a `runId` (the run id) | the `waitingOn` reason | true | — |
   | `task_blocked` | any other non-terminal Task that only a person can move on: `waitingOn.person` true with `on` `budget` (scope `task`), `human` without a run, `dependency` or `admission` (the Task id) | the `waitingOn` reason | true | the summary of the Task's latest pending `BLOCKED` message, when one exists |
   | `subtask_request` | pending `REQUEST_SUBTASK` (the message id) | `REQUEST_SUBTASK` | false | the message summary |
   | `follow_up` | pending `REQUEST` with a follow-up (the message id) | `follow_up` | false | the message summary |
   | `stall_notice` | current stall notification of the Mission (the Attempt id) | `stalled` | false | — |
   | `supervision_proposal` | the open supervision proposal (its id; global, listed for every non-terminal Mission) | `stalled` | false | the proposal's own text, if it has one |

   `actions` lists, in this order, the desktop calls from the item's set that the Control Plane would accept at the time of the read, as far as the Mission status, the Task stage and the latest run decide it (each call keeps its own checks; the view never promises more than these):

   | `kind` | Calls, most direct first (offered when) |
   |---|---|
   | `mission` | `axiom.mission.start` (`PLANNED`); `axiom.mission.resume` (`PAUSED`); `axiom.mission.plan` (`ANALYZING`, reason not `budget_exhausted`); `axiom.mission.cancel` (always) |
   | `plan_review` | `axiom.plan.approve`, `axiom.plan.reject` |
   | `question` | `axiom.message.answer` |
   | `human_review` | `axiom.verification.resolve` (the run is `HUMAN_REVIEW`); `axiom.verification.rerun` (what `rerunVerification` checks); `axiom.task.adjust` (what `adjustTask` checks: Mission `PLANNED` or `EXECUTING`, and the stage rule); `axiom.task.cancel` |
   | `task_blocked` | `axiom.task.adjust` (as above, and not for `upstream_canceled` or `no_eligible_provider`, which no adjustment changes); `axiom.verification.rerun` (what `rerunVerification` checks); `axiom.policy.update` (only for `no_eligible_provider`); `axiom.task.cancel` |
   | `subtask_request`, `follow_up` | `axiom.message.resolve` |
   | `stall_notice` | `axiom.task.cancel` |
   | `supervision_proposal` | `axiom.supervision.resolve` |

   `id` is `<kind>:<objectId>`, stable for the same object across calls; `taskId` is set for every item that belongs to one Task; `summary` is the object's own text, never invented, and left out when the object has none; `waitingOn` is the Task's projection for the items that belong to a Task, and for a `mission` item with an exhausted budget `{ on: 'budget', reason: 'budget_exhausted', person: true, budget: { scope: 'mission', dimension, limit, used } }` (from the `budget.exhausted` audit when the Mission is `BLOCKED`); `since` is when the wait began, an ISO 8601 UTC time taken from the row or audit that recorded it (SQLite's `YYYY-MM-DD HH:MM:SS` normalised as `admission-budget.ts` does). `blocks` is how many non-terminal Tasks cannot proceed until the item is handled: for a blocking item of a Task, that Task plus every non-terminal Task downstream of it (transitively, plan edges); for `mission` and `plan_review`, every non-terminal Task of the Mission (0 when none exists yet); 0 for non-blocking items. A Planner's question has no `taskId` and the `blocks` of a `mission` item. Order: blocking items first; then larger `blocks`; then the `kind` order of the kinds table above; then earlier `since`; then `id`. A terminal Mission has no items; a question whose Task is terminal is not listed (nothing waits on it any more); an unknown Mission is `mission_not_found`. Invariant: every Task whose `waitingOn.person` is true is covered by a blocking item — a `question` item of that Task, the `mission` or `plan_review` item, or its own `human_review` or `task_blocked` item — except a Task waiting on `approval` (Approvals are M4). If a Task can wait on a question that `axiom.message.list` does not list, do not invent an item: name the case in the report. The test for an active Planner Attempt is the one `planner-launcher.ts` `preflight` already makes — share it, do not copy it.
4. **Cost.** No scan of the Mission's audit events per Task, and Mission-level facts (status, policy, budget, counts) are computed once per call: one pass over the audits per call, or lookups bounded by `LIMIT 1` per Task; no query per audit row; no schema change, no new index. Say in the report what one call costs for the 12-Task fixture (queries or a measured time), and mark any deliberate ceiling with a `ponytail:` comment.
