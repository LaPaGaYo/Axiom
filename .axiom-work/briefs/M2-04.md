## Objective

Implement the Scheduler (`src/main/axiom/scheduler/`): the only path by which a `READY` Task becomes `RUNNING`. One scheduling round reads everything from the database, orders the `READY` Tasks deterministically, builds the ContextPackage (M2-02) and AgentSpec (M2-03) for each candidate, and **admits** it in one transaction that writes the `attempt_bindings` row and moves the stage `READY → RUNNING`; only after that commit may the Execution Kernel be called (M2-05 supplies the launcher — this Task leaves a typed `launch` seam and does not start anything). Replace the M1 readiness stub `blockingQuestionOrApproval()` with real queries. Enforce the §16.2 Mission budget (total Attempts, total wall-clock, concurrency) and the Task budget (`retryPolicy.maxAttempts`); exhaustion blocks the Mission with an audit event (the Approval request object arrives in M4). MissionController triggers a round after `mission start`, after each Task stage change and after resume/unblock — no polling.

- `attempt_bindings(task_id, mission_id, seq, branch, dispatch_id UNIQUE NULL, agent_spec_id, context_package_id, created_at, updated_at, PRIMARY KEY(task_id, seq))` exists (v43), has no store methods yet. Admission writes it with `dispatch_id = NULL` (the dispatch id is minted by the kernel when M2-05 launches; D6a) and `branch = 'axiom/attempt/<taskId>/<seq>'`; `seq = (max seq for the Task) + 1`, starting at 1. Add `insertAttemptBinding`, `getAttemptBinding(taskId, seq)`, `listAttemptBindings({ missionId, taskId? })`, `nextAttemptSeq(taskId)` to `src/main/axiom/db/` (new `attempt-bindings-store.ts` + row codec, aggregated into `AxiomStore` like the others).
- Stage write: `store.updateTaskStage({ taskId, from, to, attemptCountDelta })` is a CAS on `stage = from` (returns `false` when stale); `transitionTaskStage(ctx, …)` in `task-readiness.ts` wraps it with the legality check and the `task.stage` audit event but does not yet pass `attemptCountDelta` — extend `TransitionTaskInput` with an optional `attemptCountDelta` and pass it through (admission uses `1`). `task_stages.attempt_count` is the Control Plane's authoritative Attempt count (B4); `canBecomeReady` already refuses `attemptCount >= retryPolicy.maxAttempts` and the Mission `budget.maxAttempts` sum.
- Transactions: `MissionController.write()` wraps `runLifecycleWriteTransaction(db.db, 'axiom_<op>', fn)`; `AxiomStore.transaction(savepoint, fn)` nests a savepoint. ContextBuilder and AgentFactory are **async** (artifact file writes) and content-addressed/idempotent, so build them **before** the admission transaction, then re-validate everything inside it (stage still `READY`, limits still hold, the spec and package rows exist) and bind; never hold a transaction open across an `await`.
- Readiness stub: `task-readiness.ts` has `function blockingQuestionOrApproval(): 'none'` with the comment "M2 must replace this hook before admission". Replace it with `blockingQuestionOrApproval(ctx, task): 'none' | 'question' | 'approval'` implemented in a new `src/main/axiom/scheduler/admission-blockers.ts`: (a) `ctx.db.listGates({ taskId: task.taskId, status: 'pending' }).length > 0` → `question` (Orca decision gates carry Task-level QUESTION blocking only, D7); (b) a `question_threads` row with `status = 'pending'` whose `dispatch_id` is bound to this Task (`SELECT 1 FROM question_threads q JOIN attempt_bindings b ON b.dispatch_id = q.dispatch_id WHERE b.task_id = ? AND q.status = 'pending' LIMIT 1` — a read-only store method `hasPendingQuestionForTask`) → `question`; (c) an `approvals` row with `mission_id = ?`, `status = 'PENDING'` and `action_kind` in `BLOCKING_APPROVAL_ACTION_KINDS` → `approval`. `BLOCKING_APPROVAL_ACTION_KINDS = ['budget_increase'] as const` lives in `src/shared/axiom-contract/lifecycle.ts` next to the other enumerations (M4 extends it; the table is empty until M4 but the query is real and tested by inserting a row directly in the test). The Orca `decision_gates.status` CHECK is `pending | resolved | timeout`; `question_threads.status` is `pending | answered | closed`; `approvals.status` is free text in SQL — use the Glossary value `PENDING`.
- Budget semantics (write them into control-plane.md §4; they are the contract M2-05/M2-07 build on): `policy.budget.maxAttempts` = Mission total Attempts (sum of `attempt_count`, already enforced in `canBecomeReady`, re-checked at admission); `policy.budget.maxRuntimeMinutes` = default **per-Attempt** runtime cap (M2-03's AgentSpec default; M2-05 maps it to `workerStart.timeoutMs`); **new** `policy.budget.maxWallClockMinutes` (optional positive number, added to `BudgetSchema`) = Mission total wall-clock measured from the first `mission.status` audit event whose `after.status === 'EXECUTING'` (`listAuditEvents({ missionId })`, filter by `event === 'mission.status'`); `policy.concurrencyLimit` = Mission-wide cap on Tasks in stage `RUNNING`; **new** `routing.providerConcurrency: z.record(z.string(), z.number().int().positive()).default({})` (added to `RoutingPolicySchema`) = per-provider cap on RUNNING Tasks whose bound AgentSpec has that `provider` (join `attempt_bindings` of RUNNING Tasks with `agent_specs.provider`, latest `seq` per Task); Task `retryPolicy.maxAttempts` = per-Task Attempt cap. Per-Task total duration and token/cost budgets are **not** enforced in M2 (no settlement data yet) — say so in the docs and the report.
- Mission block on exhaustion: when a round finds `READY` Tasks but `maxAttempts` or `maxWallClockMinutes` is exhausted → `missions.blockMission(missionId, 'budget_exhausted')` (existing `interruptMission` path; Mission `EXECUTING → BLOCKED` with `previous_status`) plus an audit event `budget.exhausted` (`objectKind: 'mission'`, `after: { dimension: 'maxAttempts' | 'maxWallClockMinutes', limit, used }`). A concurrency or provider-concurrency limit is not exhaustion: the round simply admits fewer Tasks.
- Ordering: `READY` Tasks sorted by critical-path priority = length of the longest downstream chain in `mission_task_edges` (DAG is guaranteed by plan validation; compute with `store.listDownstreamEdges`), descending, then `taskId` ascending. The order and every skip reason are returned by the round and written to one audit event per round only when something was admitted or blocked (`scheduler.round`, `after: { trigger, admitted: [...], skipped: [{ taskId, reason }] }`) — never an audit row for an empty round.
- Scheduler API (`src/main/axiom/scheduler/scheduler.ts`): `new Scheduler(db, store, missions, contextBuilder, agentFactory, { launch: AttemptLaunch | null, now? })`; `scheduleRound(missionId, trigger: 'mission_start' | 'stage_change' | 'resume' | 'manual'): Promise<ScheduleRoundResult>` with `AdmittedAttempt = { missionId, taskId, seq, branch, agentSpecId, contextPackageId }`, `AttemptLaunch = (attempt: AdmittedAttempt) => Promise<void>`, `ScheduleRoundResult = { admitted: AdmittedAttempt[]; skipped: Array<{ taskId; reason: 'launcher_unavailable' | 'concurrency' | 'provider_concurrency' | 'task_attempts' | 'question' | 'approval' | 'no_eligible_provider' | 'stale' }>; blocked?: 'maxAttempts' | 'maxWallClockMinutes' }`. The round: Mission must be `EXECUTING` (otherwise return empty, no error) → `missions.recomputeReadiness` → when `launch` is `null` return every `READY` Task as `launcher_unavailable` **without admitting** (this keeps M1 behaviour until M2-05 injects the launcher; one guard line) → for each candidate in order: build package + spec (an `AgentFactoryError('no_eligible_provider')` → skip with that reason, no block) → admission transaction → after commit, `await launch(attempt)`; a launch rejection is caught, audited as `attempt.launch_failed` (`objectKind: 'attempt'`, `objectId: '<taskId>/<seq>'`) and the round continues (M2-05/M2-08 define recovery; the binding row and the `RUNNING` stage stay as evidence). Rounds for the same Mission are serialised in-process: a round requested while one is in flight runs once more after it (coalesce, do not queue unboundedly).
- MissionController trigger: add `onScheduleTrigger?: (missionId: string, trigger: ScheduleTrigger) => void` to the `deps` of `MissionController`; invoke it **after** the write transaction has committed in `startExecution` (`mission_start`), `resumeMission` / `unblockMission` (`resume`), and in `transitionTaskStage` / `cancelTask` / `recomputeReadiness` when a stage actually changed (`stage_change`). `control-plane.ts` constructs the Scheduler with `launch: null` and wires `onScheduleTrigger` to `scheduler.scheduleRound` (fire-and-forget with `console.warn` on rejection, never throwing into the caller). `RunMailboxConsumer` already calls `recomputeReadiness` after draining — nothing to add there.
- Admission is the only READY → RUNNING writer: `transitionTaskStage` must refuse `to: 'RUNNING'` unless the input carries `attemptCountDelta: 1` and an `actor` of `'Scheduler'` (keep it simple: a guard in `task-readiness.ts` throwing `illegal_transition` with `reason: 'admission_required'`); the existing `axiom.task.*` RPCs never request `RUNNING`.
