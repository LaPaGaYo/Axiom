## Ground truth (verifier, 2026-11-18, main `1fc809fec6`)

1. **Electron.** `package.json` devDependencies `electron` 43.8.6. The version is also named by `src/shared/node-runtime-pin.ts` (`NODE_RUNTIME_PIN.electron`; `check:node-runtime-pin`, part of `pnpm lint`, compares it with `package.json` and the lockfile; the pin's Node version stays 24.22.1, as upstream left it), `config/scripts/electron-runtime-floor.test.ts` (floor 43.8.6) and `src/main/browser/browser-popup-adapter-compatibility.electron.test.ts` (expects the running version). Upstream went 43.8.6 → 43.8.7 (`a82468b023`, 11-11) → 43.8.10 (`651f2efaa9`, 11-17, "for actively exploited Chromium fix"); upstream/main `60d912e153` is on 43.8.10. Electron's notes for 43.8.10 (published 2026-11-12) say only "Backported fixes from upstream ANGLE, Chromium, Dawn, icu, Skia and V8"; that the release carries the fix for the use-after-free in Chromium's XML component that Google reported as exploited on 2026-11-09 (CVE-2026-125350, in CISA's catalog since 11-10) is upstream's statement in `651f2efaa9`, not something the verifier could read in Electron's notes. Both releases report Chromium 150.0.7871.250 (read from the two binaries in the verifier's container) and Node 24.22.1; the native module ABI is unchanged: no native rebuild. 43.8.10 is past `minimumReleaseAge` (4320 minutes), so no exclusion is needed. 43.8.11 was published on 2026-11-18, is inside the cooling period and is not on upstream/main: next screening.
2. **What 43.8.8 breaks: terminal glyphs.** From 43.8.8 on a canvas rejects a font string that starts with whitespace. The WebGL addon of xterm builds its glyph font as style, weight, size, family, and the style is empty for upright text, so the string starts with a space: every glyph is rasterized with the canvas default, 10px sans-serif, inside full-size cells. Upstream fixed it one commit after the upgrade (`5ccdb32d31`: `.trim()` on that string, "as xterm core already does"). Upstream's fix is in its patch of `@xterm/addon-webgl` 0.20.0-beta.329; this tree patches 0.20.0-beta.300 (`config/patches/@xterm__addon-webgl@0.20.0-beta.300.patch`, with the source half in `config/patches/xterm-src/`). The same statement exists here, once in each built bundle and once in `src/TextureAtlas.ts`. Seen in the verifier's container with the two Linux binaries under a virtual display and the probe of the verification plan: 43.8.6 answers `40px monospace` for a font string with a leading space and rasterizes full-size glyphs with this tree's addon (median glyph height 15 px for a 20 px font); 43.8.10 answers `10px sans-serif` and rasterizes glyphs of 7 px; with the trimmed addon 43.8.10 is back at 15 px.
3. **How the patch was changed.** In the verifier's container: the published tarball of 0.20.0-beta.300, this tree's patch applied, and pnpm's own diff command and post-processing (as `config/scripts/regenerate-xterm-patches.mjs` and `xterm-patch-text.mjs` state them) reproduce the committed patch byte for byte (sha256 `5349718f2c19…`, the hash the lockfile records). With `.trim()` added to the statement in `src/TextureAtlas.ts`, `lib/addon-webgl.js` and `lib/addon-webgl.mjs`, the same command gives the new patch (sha256 `67f2853e7ce4…`): it differs from the old one in the three blob ids, the two bundle lines (seven characters each) and the source hunk — which has the shape of upstream's own change. The source patch is the source half of the new patch (`regenerate-xterm-patches.test.mjs` requires the two to be equal on every source file). **Not regenerated:** the two source maps of the bundles; they are stale by that one expression. A full regeneration builds xterm from source on the host, and the next upstream sync replaces these patch files anyway.
4. **picomatch.** The lockfile has picomatch 4.0.4 (← `@parcel/watcher`, a runtime dependency of the app, and `lint-staged`) and 4.0.7 (← vite, vitest, tinyglobby, fdir). GHSA-fc5q-39xc-vjpf: an extglob with a repeated wildcard, such as `+(*a)`, backtracks without bound. Upstream `19e5992f0f` patches 2.3.2, 4.0.4, 4.0.5 and 4.0.7 and adds one test. Checked in the verifier's container against the published tarballs of 4.0.4 and 4.0.7: both patch files apply without offset or fuzz and touch only `lib/parse.js`; unpatched, `picomatch('+(*a)')` on forty `a` and a `b` does not return within eight seconds; patched, it answers `false` in a few milliseconds, the capture case of upstream's test answers `true`, and four ordinary patterns answer as before.
