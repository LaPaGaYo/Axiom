## Objective

1. **One baseline rule** — new `src/main/axiom/execution/attempt-baseline.ts`, a pure function over the store, used by both the ContextBuilder and the launcher (they must never disagree):
   `resolveAttemptBaseline(store, { taskId, seq })` → `{ kind: 'integration', reason }` or `{ kind: 'candidate', previousSeq, candidate, verificationRun }`.
   - Only the immediately preceding Attempt counts (`seq - 1`; seq 1 → `integration`, reason `first_attempt`). It continues that Attempt's Candidate when **all** hold: that Attempt's binding has a dispatch with a Submission (`store.getSubmissionByDispatch`); the Submission's Candidate is still `ACTIVE`; the Candidate's latest VerificationRun (`store.listVerificationRuns({ missionId, candidateId })`, ordered by `createdAt`, then id — take the last) has status `FAIL`; and that run's `verdictDetail.reason` is not `secret_detected`.
   - Otherwise `integration` with a fixed reason: `previous_attempt_not_submitted` (crash, abandonment, launch failure — D64 ①'s "FAILED / ABANDONED / launch failures retry from the integration base"), `previous_candidate_superseded`, `previous_verification_not_failed`, or `secret_detected` (D64 revision line: the Candidate's commit history contains the secret, so the fix starts clean; the evidence still names the path and pattern). For `secret_detected` also return the failed run, so the evidence section can show its diff findings.
2. **Fix Attempts start at the failed Candidate's commit** (`attempt-launcher.ts`; keep it under the 300-line lint limit by putting the new logic in focused modules beside it, for example `attempt-baseline.ts` or an `attempt-fix-launch.ts`):
   - For a `candidate` baseline, `createManagedWorktree` gets `baseBranch: candidate.commitSha` (the full object id — D64 ① "从上一 Candidate commit 建分支"; Orca's base resolution accepts a full commit id) instead of `axiom/integration/<missionId>`; the new branch is still `attempt.branch`. After creation, the new worktree's HEAD must equal `candidate.commitSha` (use `created.worktree.git?.head` when present, otherwise `rev-parse HEAD` in the new worktree through the `gitExecFileAsync` / `gitOptionsForWorktree` helpers that `candidate-snapshot.ts` uses). On a mismatch, throw an error whose message is exactly `fix_base_mismatch`, so the existing catch path audits `attempt.launch_failed { message }` and settles the Attempt `launch_failed`. Never reset, rewrite or delete a branch or worktree.
   - Integration baselines and Planner launches keep today's `baseBranch`.
   - Add `baseline: { kind, reason?, candidateId?, commitSha? }` to the `after` object of the Worker launch audits (`attempt.started`, `attempt.start_unknown`, and the `attempt.launch_failed` written after a receipt).
3. **Reopen the Orca task for an Attempt that follows a Submission.** Today a Submission settles the Orca dispatch and task as `completed`, and Orca starts a new dispatch only for a `ready` task (`retryOf` accepts only a failed / stopped / abandoned prior worker) — so every seq N+1 after a Submission fails at launch with `task_not_startable`. Before building `WorkerStartParams`, when the Orca task (`db.getTask(taskId)`) is `completed` **and** the previous Attempt's dispatch has a Submission, call the kernel's public `db.updateTaskStatus(taskId, 'ready')` (the Orca task lifecycle allows the edge; the function refuses while a Dispatch is active), re-read the task, and start without `retryOf`. This applies to both baselines (a `secret_detected` retry also follows a Submission). A `completed` Orca task without a previous Submission stays a launch failure; `failed` / `blocked` keep the existing `retryOf` path. Do it after the worktree is created and its HEAD verified, immediately before the worker start, and only for Worker (not Planner) launches. Record `orcaTaskReopened: true` in the launch audit when it happened.
