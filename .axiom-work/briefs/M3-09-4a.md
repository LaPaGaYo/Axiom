# Task M3-09-4a — the plan card: what each Task is, what verification will run for it, what changed since the rejected revision; approval asks first (renderer)

Planner brief, 2026-11-14 (verifier). Approving a plan is the one decision of a Mission that cannot be taken back today, and the card the person approves from shows less than the Control Plane knows: no scope, no risk, no limits, no warnings, no milestones, and of verification only the command of each criterion — not the setup commands and repository gates the Mission's policy adds. A rejected revision and its reason disappear from the page, and the next proposal arrives with nothing to compare it to. D85 rule 6 asks for a plan card that lists every Task's verification commands verbatim for approval; DEF-22 ⑤ for scope, acceptance and the difference from the revision before. This Task builds that card from data the Control Plane already serves. It is the first of three parts of M3-09-4: the main-process follow-ups (4b) and the policy editor (4c) are not in it.

Read first: `AGENTS.md` (UI and Product Experience; Human Approval), `docs/STYLEGUIDE.md` (UX rules: every state has a reason, in the Control Plane's own words; siblings read as one design; quiet), `docs/decisions/DECISION_LOG.md` D85 (rules 3 and 6 and the revision of 2026-11-03), `docs/reference/control-plane.md` ("Verification" for `verificationRules`; "Mission 首页的待处理项（M3-09-3a）"; "Mission 页的定时刷新（M3-09-3b-2）"; "Mission 首页的监工档位与升档提议（M3-09-3c）"), `tests/e2e/AGENTS.md`.

## Ground truth (verifier, 2026-11-14, main `a6f114755b`; every fact here was read in the code, the tests or the specs at that commit)

1. **A revision.** `PlanRevisionSchema` (`src/shared/axiom-contract/mission-objects.ts`): `id`, `missionId`, `revision`, `status` (`PROPOSED`, `APPROVED`, `SUPERSEDED`, `REJECTED` — nothing writes `SUPERSEDED` for plans today), `goalRevisionId`, `milestones` (`id`, `title`, `exitCriteria`), `risks`, `tasks`, `edges`, `warnings`, `provenance`, `rejectedReason?`, and a `supersedesId?` that nothing sets for plans. A Task of a proposal (`TaskSpecSchema`): `id` (chosen by the Planner, unique within one revision only), `title`, `objective`, `scope.allowedPaths`, `role?`, `acceptanceCriteria`, `coversGoalCriteria?` (zero-based indexes into the Goal's criteria), `risk` (`low`, `medium`, `high`), `retryPolicy.maxAttempts`, `budget?` (`maxRuntimeMinutes`, `maxWallClockMinutes`, `maxTokens`, `maxCostUsd`, `contextTokens`, all optional), `milestoneId?`, `kind`. `axiom.plan.list {missionId}` answers every revision of the Mission, ordered by `revision`.
2. **Criteria and proofs.** A criterion is `{text, check}`; `check.kind` is `command` (one exact command; verification runs it from the repository root on the candidate and requires exit 0), `artifact` (the submission must reference a readable, non-empty Artifact, of `artifactKind` when one is given) or `human` (a person confirms it). `resolveAcceptance` (`acceptance.ts`) is the compatible read every consumer uses: a bare string becomes a `human` criterion and each legacy `requiredEvidence` entry a command criterion.
3. **What verification runs.** For one Task the verification service runs `resolveVerificationPlan(task.spec, rules)` (`src/shared/axiom-contract/verification-rules.ts`): the policy's `setupCommands`, then the Task's command criteria — trimmed, each once —, then the policy's `repositoryGates[task.risk]` that are not already in the list; every entry carries `source` (`setup`, `evidence`, `gate`), the `command` and the indexes of the criteria it proves. `rules` is the Mission's policy at the time verification runs: `VerificationRulesSchema.safeParse(policy.verificationRules)`; when that fails the run ends `INCONCLUSIVE` with reason `policy_invalid` and no command runs (`src/main/axiom/verification/verification-checks.ts`). A Mission created from the desktop dialog stores `verificationRules: {}`; the schema's defaults fill it (no setup command, no gate). `axiom.mission.create` does not validate the rules — only `axiom.policy.update` does — so stored rules that do not parse are possible. The commands of a proposal were checked when it was proposed, against the rules then in force (the defaults when those did not parse); approval does not check them again.
4. **The policy.** `axiom.policy.show {missionId}` (a read) answers `{policy}` (`PolicyResponseSchema` in `policy-params.ts`); `policy.verificationRules` is JSON as stored. The renderer reads no policy today, and `axiomClient` has no method for it.
5. **Warnings and coverage.** At proposal time the Control Plane stores `warnings` on the revision (`plan-warnings.ts`): `incomplete_coverage` (with `uncovered`: index and text of each Goal criterion no Task covers), `scope_overlap` (two Task ids and the overlapping path pairs `a` / `b`), `insufficient_parallel_roots` (`expected`, `found`, Task ids — in the schema, though nothing emits it today); each has a `message`. `planCoverage(plan, goalCriteria)` (`plan-coverage.ts`) is the function `axiom.plan.show` uses to say which Tasks cover which Goal criterion. A proposal must reference the Goal revision that is active when it is made. The Mission read already holds the active Goal revision (`goal`, with `id` and `acceptanceCriteria`).
6. **Approving and rejecting.** `axiom.plan.approve {planRevisionId, resolver}` (desktop only) creates the plan's Tasks and moves the Mission from `PLAN_REVIEW` to `PLANNED`; nothing runs until the Mission is started. It is refused with `replan_not_supported` once the Mission has an approved revision — a plan cannot be replaced by another one yet —, with `illegal_transition` outside `PLAN_REVIEW`. `axiom.plan.reject {planRevisionId, resolver, reason}` marks the revision `REJECTED` with `rejectedReason` and moves the Mission back to `ANALYZING`; the next proposal gets the next revision number. Nothing links two revisions but that number.
7. **The pending view.** `axiom.mission.pending` lists one `plan_review` item per `PROPOSED` revision (`objectId` the revision's id) whose `actions` are `['axiom.plan.approve', 'axiom.plan.reject']` while the Mission is in `PLAN_REVIEW` and empty otherwise (a paused or blocked Mission); a terminal Mission's view is empty. The Task page's review and adjustment actions and the supervision proposal's answers are already offered from this view.
8. **The page today.** `MissionsPageSurface.tsx` renders `PlanReviewPanel` for each revision that is `PROPOSED` or the Mission's active one — a rejected revision is never rendered, so its reason is never seen — and disables it from the Mission's status (`PLAN_REVIEW` or `REPLANNING`), not from the pending view. `PlanReviewPanel.tsx` (134 lines; region `Plan review`) shows the revision number and status, the id and proposer, the risks, per Task `id · title`, the objective and each criterion's text with its command in a `code` element or the words `Artifact` / `Human check`, the dependency edges as `from → to · threshold`, and for a `PROPOSED` revision the field `Reason for rejection` with `Approve plan` and `Reject plan`. In `use-missions-page-controller.ts` (232 lines; a sidecar holds it at 250 or fewer) `approve(planRevisionId)` sends the call at once; `reject(planRevisionId, reason)` goes through `confirmAction`, which always shows its title on a destructive confirming button. `readMission` (`mission-read.ts`) starts the Mission's reads together — only the Goal read waits for the Mission's answer —; the supervision read of M3-09-3c (`supervision-read.ts`) shows how an optional read fails apart from the rest.
9. **The client.** `src/renderer/src/lib/axiom-client.ts` is at exactly 300 counted lines, the `max-lines` limit: one more method does not fit. `AxiomRpcError` and the transport function `call` take 53 of those lines; the rest is imports and the method table. Earlier sidecar assertions grep sixteen method names in that file, and every importer takes `axiomClient` and `AxiomRpcError` from it.
10. **Existing tests.** `PlanReviewPanel.test.tsx` renders the panel directly with `plan`, `busy`, `onApprove`, `onReject` and asserts, besides the criteria's texts, that the panel's first `code` element is the first command criterion's command, that `Artifact` appears, and that `Human check` appears exactly twice (once per human criterion). `MissionTimedRefresh.test.tsx` renders the page with a `PROPOSED` revision, a Mission in `PLAN_REVIEW` and a pending view with no items, and needs the reason field and both buttons enabled; it also asserts that no `status` is on the page. The other page tests have no plan. Most page tests mock the client module with only the methods they use (a method that is not on the mock throws when called; `AxiomRpcError` is not on those mocks); two keep the real module under their mocked methods, where a method they do not mock is the real one and rejects. The controller test stubs the runtime call and rejects a method it does not know; in `re-reads the Mission on a timed tick without marking the page busy` it holds the Mission's answer back and requires the tick's calls to be the mount's calls, method for method — a read that starts only after the Mission has answered, or only for some Missions, breaks it; it calls `controller.reject('plan-1', …)` and expects the confirmation `Reject plan` with a destructive button.
11. **E2E.** Two specs approve through the page — `mission-home-task-list.spec.ts` (which also expects the `Plan review` region to contain `T01 → T04`) and `mission-home-pending.spec.ts` — by clicking `Approve plan` and waiting for the Mission to be `Planned`. `mission-home-refresh.spec.ts`, which this Task may not edit, finds the one region named `Plan review`, needs its `Reason for rejection` textbox and `Approve plan` enabled in `PLAN_REVIEW`, and after an approval from outside expects the region's only level-2 heading to read `Plan revision 1 · APPROVED` and the textbox to be gone. No spec rejects a plan or has two revisions. `mission-home-supervision.spec.ts` shows the setup without anything started (clone, `repo.add`, `axiom.mission.create`, `axiom.plan.propose` with `fixturePlanProposal`), the page-side `setDocumentVisibility`, a confirmation found as `getByRole('dialog', { name: … })`, and `captureDetail` with a region name. Several specs set `verificationRules` through `axiom.policy.update` with `desktopCall` (for example `mission-review-actions.spec.ts`). After a rejection the Mission is `ANALYZING` and accepts a new `axiom.plan.propose` from the desktop.

## Outcome

Before approving, the person sees on one card what each Task may touch and how far it may go, how every criterion is proven, exactly which commands verification will run for it under the Mission's policy, what the Control Plane warned about, how the plan covers the Goal, and — after a rejection — the reason they gave and what the new revision changed. Approval asks once, saying what it does; approval and rejection are offered when the Control Plane offers them.

## Deliverables

1. **Client.** `axiomClient` gains `showPolicy` for `axiom.policy.show`, written like its neighbours (params and response through the contract schemas of `policy-params.ts`). To make room, `AxiomRpcError` and `call` move into one new module `src/renderer/src/lib/axiom-rpc-call.ts`; `axiom-client.ts` keeps every method and still exports `AxiomRpcError` — the same class — so that no importer changes.
2. **The read.** The Mission's policy is read with the Mission — once per page read, with the selected Mission's id, on the timed read as on the manual one, whether or not the Mission has a plan, started together with the other reads and not after any of them has answered — and apart from the rest: whatever goes wrong in it (a refusal, a transport error, an exception thrown by the call itself) ends as the card's own note and nowhere else — not on the page's error line, not as a toast — and the Mission, its plan, its Tasks and its pending items still show.
3. **Which revisions are on the page.** As today, every `PROPOSED` revision and the Mission's active one. In addition, when no revision is `PROPOSED` and the Mission has no active one, the latest revision is shown if it is `REJECTED` — read-only, with `Rejected because` and its reason verbatim.
4. **Each Task on the card.** Each Task is a list item named by its `id · title` line, so that a test or a spec can find the list item `T01 · Sprint validation` and look inside it. Under that line and the objective, the card shows, with the labels the Task page already uses where it has them (`Allowed paths` / `None`, `Attempt limit`, `Token limit` / `No limit`):
   - the allowed paths, each on its own line in the mono face; the `Risk level` in the contract's word; the attempt limit; the token limit; every other limit the Task declares in `budget`, under its contract field name; its `Milestone` (id and title) and its `Role` when it has one;
   - `Acceptance criteria`: every criterion from `resolveAcceptance` with its text and `Proof`: the kind in the contract's word, for a command the command verbatim in a `code` element that wraps (as the verification record shows commands), for an Artifact its `artifactKind` when given, and one sentence per kind saying what proves it (ground truth 2) — the words `Human check` stay once per human criterion and appear nowhere else on the card;
   - for a `PROPOSED` revision, a list named `Verification will run`: the entries of `resolveVerificationPlan` for this Task under the Mission's policy, in the function's order, each one list item with the command verbatim in a wrapping `code` element and its `source` in the contract's word; `No command will run for this Task.` when the list is empty. When the policy read failed, instead: `The Mission's policy could not be read, so the commands verification will run are not listed. Refresh to try again.` (plain text, no `alert` or `status` role). When the policy's `verificationRules` do not parse with `VerificationRulesSchema`, instead: that the Mission's verification rules are not valid and verification would end `INCONCLUSIVE` (`policy_invalid`) without running a command.
   The card says once, above the Tasks of a `PROPOSED` revision, that these commands follow the Mission's policy as it is now and that verification reads the policy when it runs, so a later policy change changes them.
5. **The plan as a whole.** The region `Plan review` keeps exactly one level-2 heading, `Plan revision N · STATUS` as today; every block below has a level-3 heading, and each of the new ones is a group named by its heading. Besides the risks and the `Dependencies` block, which stay as they are (`from → to · threshold`):
   - `Milestones`, when the plan has any: id, title and exit criteria;
   - `Warnings`, when the revision has any: for each its `code` in the mono face, its `message` verbatim and its details — the uncovered Goal criteria (index and text); the two Tasks and their overlapping path pairs; the expected and found number of parallel roots;
   - `Goal coverage`, when the Goal revision the page has read is the revision's own (`goalRevisionId`): for each Goal criterion its index — zero-based and written `#0`, as the Control Plane's own warning message writes it — and text, and the ids of the Tasks that cover it, from the contract's `planCoverage`, or `No Task covers it`. When the page holds another Goal revision, or none, the block is not shown.
6. **What changed since the rejection.** A `PROPOSED` revision of a Mission that has an earlier `REJECTED` revision shows a group `Changes since revision N` (N: the latest rejected revision before it): `Rejected because` with that revision's reason verbatim, and then, with Tasks matched by their `id`:
   - `Added Tasks` and `Removed Tasks`: `id · title` of the Tasks only in this revision, and only in revision N;
   - `Changed Tasks`: for each Task in both whose proposal differs, `id · title` and every part that differs, by name — for a single-valued part (title, objective, role, risk level, attempt limit, milestone, kind) the old and the new value; for a list part (allowed paths, acceptance criteria, Goal criteria covered, declared budget limits) the entries removed and the entries added; a reordering alone is not a difference. Acceptance criteria are compared as `resolveAcceptance` returns them, and written here as their text and proof with the contract's word for the kind (`command` and the command, `artifact` and its kind, `human`);
   - the dependency edges added and removed — an edge is its `from`, its `to` and its threshold, so a changed threshold shows as one removed and one added;
   - one line each when the milestones or the risks differ;
   - `No difference from revision N.` when nothing does.
   One sentence says that Tasks are matched by id, so a Task whose id changed shows as removed and added.
7. **Approving asks first.** `Approve plan` opens the app's confirmation — title and confirming button `Approve plan`, not styled destructive; the other button `Keep reviewing` — whose text says: approving creates the plan's Tasks (their number); nothing runs until the Mission is started; an approved plan cannot be replaced by another one yet — from then on only single Tasks can be changed, where the Control Plane offers it, or the Mission canceled; and, when the revision has warnings, how many. Declining sends nothing. `Reject plan` keeps its reason field and its confirmation as they are.
8. **Offered when the Control Plane offers it.** For a `PROPOSED` revision `Approve plan` is on the card only while the Mission's pending view lists a `plan_review` item for this revision's id with `axiom.plan.approve` among its actions; the reason field and `Reject plan` only while it lists `axiom.plan.reject`. When neither is offered the card says `This plan cannot be approved or rejected right now.`; when the pending view could not be read, `What can be done with this plan could not be read. Refresh to try again.` The Mission's status no longer disables the card; the page being `busy` still does.
9. **Catalogs.** Every new text goes through `translate('missions.<key>', '<English>')` with a literal key, and the key is in all seven catalogs (`en` and `zh` with real text; the others may carry the English text). These keys carry exactly these English texts: `missions.verificationWillRun` `Verification will run`, `missions.planMilestones` `Milestones`, `missions.planWarnings` `Warnings`, `missions.planGoalCoverage` `Goal coverage`, `missions.planChangesSince` `Changes since revision {{revision}}`, `missions.planRejectedBecause` `Rejected because`, `missions.keepReviewing` `Keep reviewing`. No key is removed and no existing value changes. No key ends in a plural suffix (`_one`, `_other`, …): a count is written the way the folder writes it (`{{count}} Task(s)`).
10. **E2E** (host, verifier-run): a new spec `tests/e2e/mission-plan-card.spec.ts`, set up the way `mission-home-supervision.spec.ts` is — nothing is started, so nothing runs —, the Mission selected and the document made visible on the page side. Responses are parsed with the contract schemas; every wait is an assertion with a timeout; the spec never clicks `Refresh Missions`.
    - **The policy.** Before the proposal, `axiom.policy.update` (through `desktopCall`) sets `verificationRules` with one setup command and one gate for the fixture Tasks' risk level.
    - **The card.** The `Plan review` region shows revision 1 as `PROPOSED`; inside the list item of the proposal's first Task the `Verification will run` list equals — command by command, source by source, in order — what `resolveVerificationPlan` returns for that Task with the rules parsed from `axiom.policy.show`; it starts with the setup command and ends with the gate.
    - **Rejecting.** Through the page: a reason typed into `Reason for rejection`, `Reject plan`, the confirmation confirmed inside the dialog `Reject plan`. `axiom.plan.list` then says revision 1 is `REJECTED` with that reason, and the page still shows revision 1, with the reason and without `Approve plan`.
    - **The next revision.** A second proposal through `desktopCall` — the first one without its last Task (and every edge that touches it) and with one more command criterion on its first Task. The page shows revision 2 as `PROPOSED` by itself, with `Changes since revision 1`: the reason, the removed Task, the changed Task and its acceptance criteria.
    - **Approving.** `Approve plan` opens the dialog `Approve plan`; `Keep reviewing` closes it and `axiom.plan.list` still says `PROPOSED`; a second try, confirmed, and it says `APPROVED`, `axiom.mission.show` says `PLANNED`, and the card shows `APPROVED` without `Approve plan`.
    - One screenshot of the `Plan review` region (`captureDetail` with the region name), taken when revision 2 and its changes are on the page.
    - `mission-home-task-list.spec.ts` and `mission-home-pending.spec.ts` gain the one click that confirms the approval, on the button inside the dialog `Approve plan` (the card's button has the same name), and nothing else.
    - The report lists every asserted selector and field with its source.
