# Task M4-1b — The executor that merges one candidate: the effect kind `integration.apply`, a temporary worktree at the integration head, a no-fast-forward merge, a pinned merge commit or a recorded conflict (second part of the M4-1 row of `docs/plans/M4.md`; D92, approved by Henry 2026-11-15; contract and main process; nothing enqueues the effect yet, so nothing that runs today changes)

Planner brief, 2026-11-16 (verifier). M4's queue takes one verified candidate of a Mission at a time and merges it into the Mission's integration branch. M4-1a gave it a contract and a store for the batch and a pin for every candidate. This Task builds the first half of a batch: an outbox effect and its executor, which merges the candidate into the integration head in a temporary worktree and ends with the batch in `TESTING` — the merge commit pinned by a ref — or in `CONFLICT`, with the Task sent back to be fixed. It does **not** move the integration branch (M4-2a runs the merged-tree regression and promotes) and nothing enqueues the effect (M4-2b turns the queue on), so only tests reach this code.

Read first: `AGENTS.md` (Execution Kernel Boundary; Integration and Promotion; Git and Worktree Safety; Destructive Actions; Code Quality; Lazy Senior Dev Mode), `docs/plans/M4.md` §2, `docs/GLOSSARY.md` §4.9 and the entries under "Effect outbox", `docs/reference/control-plane.md` (the section on the Effect outbox with its table of kinds; the paragraphs on how verification prepares and removes its worktree).

2. **The outbox** (`src/main/axiom/outbox/`). An executor is `{ execute, maxAttempts, backoffMs, onExhausted?, onOrphan }` (`effect-execution.ts`): `execute` answers `'done'` or `{ later: <ISO time> }` (the effect goes back to pending with that due time and its attempt count unchanged); a throw counts as a failed try — the message, passed through `redactContext` and cut at 2,000 characters, is stored in the effect row, and in the `effect.failed` audit when the last try has failed, so **an executor throws fixed codes, never git output** (the message of a rejected git call is git's stderr) — and after `maxAttempts` failed tries the effect is `failed` and `onExhausted` runs, outside any transaction and **once**: if it throws, or the process dies before it, it does not run again. `onOrphan` is asked at boot for an effect that was running under another process epoch: `'retry'`, `'done'` or `{ retire }`. One effect per kind and Mission runs at a time, and one that was deferred does not hold the others back; a re-enqueue of the same kind and key re-arms a finished or a waiting effect (attempt count 0, due now, new payload) and leaves a running one alone; an enqueue must be inside a transaction. Pending effects of a kind without an executor wait. `register` refuses a kind the contract does not list. The model for a small executor in its own file is `registerAttemptContinuation` (`attempt-continuation.ts`); both existing registrations are called once in `createControlPlane` (`src/main/axiom/control-plane.ts`, 285 counted lines of 300), where `runtime`, `db`, `store`, `missions`, `effects` and `runtimeEpoch` are in scope.
3. **A new kind touches five places**: `EFFECT_KINDS`, a payload schema and one variant in each of the two discriminated unions (`src/shared/axiom-contract/effects.ts`); the payload decoding in `src/main/axiom/db/effect-rows.ts`, a nested conditional whose last branch decodes the verification payload — a new kind needs a branch of its own; and `src/shared/axiom-contract/effects.test.ts`, whose title `pins the three kinds and five lifecycle states` compares the list exactly. Nothing in the renderer or the CLI switches on kinds and no other file has to change. A version that does not know a kind cannot decode a stored effect of it — and because the outbox decodes every pending row when it looks for work, one such row stops the effects of every Mission in that version, and its CLI cannot print a list that holds one (the docs have a note on this at `attempt.continue`).
4. **How verification gets and returns a temporary worktree** — the only way allowed here, since the kernel owns worktrees. `prepareVerification` (`src/main/axiom/verification/verification-prepare.ts`) calls `runtime.createManagedWorktree({ repoSelector: 'id:<repoId>', name, baseBranch, branchNameOverride, runHooks: false, setupDecision: 'skip', awaitTerminalProvisioning: false, observeSetupCompletion: false, activate: false, lineage: { noParent: true, orchestrationContext: { orchestrationRunId: mission.runId, taskId } } })` and takes `created.worktree.id`; the path comes from `splitWorktreeIdForFilesystem(id)`. `removeVerificationWorktree` (`verification-worktree.ts`) calls `runtime.removeManagedWorktree('id:<id>', { force: true })` and treats `selector_not_found`, `worktree_not_found` and `ENOENT` as already gone (the runtime answers `selector_not_found` for an id it no longer knows). The runtime it needs is typed `Pick<OrcaRuntimeService, 'createManagedWorktree' | 'removeManagedWorktree' | 'listManagedWorktrees' | 'showRepo'>` (`verification-service.ts`). Verification refuses a repository that is not on this machine with `isLocalVerificationRepository(await runtime.showRepo('id:<repoId>'))`, which is `isRepoOnCatalogHost` of `src/shared/execution-host.ts`; the `path` of that answer is where the kernel makes worktrees (a Mission's own `repoPath` was recorded when it was created, and the fixtures fake it).
5. **What the kernel does with such a worktree** (read in `src/main/runtime/**` and `src/main/git/**`; none of it is yours to change). (a) `baseBranch` may be a full ref (`refs/heads/…`): the kernel then creates the worktree at that ref, moves no other ref, fetches nothing — provided the ref exists — and takes the ref as the base as it is. A short branch name can be mistaken for a remote-tracking branch when a remote has that first path segment; a commit id works for creation but can cost a fetch at removal (see e). When it makes a new branch the kernel also asks GitHub through `gh` whether a pull request exists for that branch name, as it does for every Attempt and verification worktree today; that call is not fatal and moves nothing. (b) The branch is created with `git worktree add --no-track -b <branch> <path> <base>`; `branch.<branch>.base` is set to the base — the ref name, when a ref was given — in the repository's config, and `push.autoSetupRemote=true` when it is set nowhere. When an existing branch is reused, nothing is written. (c) **The name you asked for is not necessarily the name you got.** A branch of that name that exists already is reused only if it points at the base and no worktree has it checked out. Otherwise — and also when a remote-tracking ref or a pull request of that name exists, or when the directory exists or its removal is still pending — the kernel silently moves on to `<name>-2`, `-3` … for the directory and the branch (a reused branch keeps its name and only the directory gets the suffix). (d) The kernel does not switch repository hooks off: `post-checkout` runs when the worktree is created and `reference-transaction` for the branch it creates and, at removal, deletes. A hook that fails there fails the kernel's call. (e) Removal stops the worktree's terminals (it throws when the runtime has no terminal provider), then `git worktree remove [--force]`, then, when the removed worktree **was on a branch**, `git branch -d`, which refuses a branch that is not merged into the HEAD of the repository's own checkout — the usual case once the integration branch is ahead of what the user has checked out. The kernel then deletes the branch anyway when merging it into one of its targets would change nothing (`merge-tree --write-tree`, git 2.38 or newer): first the local targets — `branch.<branch>.base` when it is a `refs/heads/` or `refs/tags/` ref, and `HEAD` — and only when none of them settles it and the repository has a `refs/remotes/origin/HEAD` does it **fetch** (`fetch --prune <remote>`) and try the rest. Otherwise the branch is **kept**, a warning is logged and the answer of the removal carries `preservedBranch`. So a temporary branch that still stands where its base ref stands — or behind it — is deleted without the network; one that carries a merge commit is kept. A worktree on a detached HEAD has no branch as far as the kernel can tell, so nothing is deleted. (f) Removal answers as soon as it is accepted and git runs afterwards, unless `waitForBackgroundRemoval: true` is passed; a removal that is still pending makes the next creation pick a suffixed directory. (g) `listManagedWorktrees(undefined, Number.MAX_SAFE_INTEGER)` answers `{ worktrees, totalCount, truncated }` (hidden repositories and worktrees are left out); a row has `id` (`<repoId>::<path>`), `path`, `head` and `branch` — the full ref (`refs/heads/…`), or an empty string for a detached HEAD. (h) The kernel's own git functions are exported and usable in a unit test without a running runtime: `addWorktree(repoPath, worktreePath, branch, baseBranch)` (`src/main/git/worktree-add.ts`) and `removeWorktree(repoPath, worktreePath, force, options)` (`src/main/git/worktree-removal.ts`); the runtime calls the second with `{ knownRemovedWorktree: <the worktree's row of a fresh listing> }` and never with `forceBranchDelete`. Tests under `src/main/git/` call both on real repositories. (i) The kernel also puts the repository's configured symlinks and `.worktreeinclude` files into a new worktree, as untracked files.
6. **Plain git, observed on 2.43** (the floor of this code base is 2.25: use nothing newer than what is named here). In a linked worktree at commit H, `git merge --no-ff -m <message> <candidate>`: exit 0 and a commit with the parents (H, candidate) — also when H is an ancestor of the candidate; exit 0, the words "Already up to date" and **no new commit** when the candidate is an ancestor of H; exit 1, a `MERGE_HEAD` and a non-empty `git diff --name-only --diff-filter=U -z` for a conflict — but exit 1 also for a commit that does not exist, and exit 2 without `MERGE_HEAD` when a local change would be overwritten. `git merge --abort` returns the worktree to H. A merge runs `pre-merge-commit`, `prepare-commit-msg`, `commit-msg`, `post-merge` and `reference-transaction` unless `core.hooksPath` points at a directory without hooks; it needs an identity (`-c user.name`, `-c user.email`) and may sign (`-c commit.gpgsign=false`), reuse a recorded resolution (`-c rerere.enabled=false`) or start maintenance (`-c gc.auto=0`). A merge on a detached HEAD moves no branch. `git worktree remove --force` removes a worktree left in the middle of a conflicted merge. With the same parents, tree, message, identity and dates (`GIT_AUTHOR_DATE`, `GIT_COMMITTER_DATE`) a merge makes the same commit every time. Git writes get no default timeout from the runner (`gitExecFileAsync(args, { …gitOptionsForWorktree(path), timeout })`); an `env` given to the runner **replaces** the process environment, so pass `{ ...process.env, … }` as `worktree-snapshot.ts` does; a rejected call carries the exit status as a numeric `code` (see `src/main/axiom/execution/integration-base.ts`) and git's stderr as its message.
7. **Sending a Task back** has one model, `settleVerificationFailure` (`src/main/axiom/execution/attempt-settlement.ts`): in one transaction `VERIFYING → NEEDS_FIX` (reason `verification_failed`), then `NEEDS_FIX → READY` (reason `retry`) while `attemptCount < retryPolicy.maxAttempts`, else `→ BLOCKED` (reason `retry_budget_exhausted`), each through `missions.transitionTaskStage`, which writes the `task.stage` audit and asks for a scheduling round after the commit. It requires `VERIFYING`, so it cannot be called for a conflict as it is. `TASK_STAGE_TRANSITIONS` allows `INTEGRATION_READY → INTEGRATED | NEEDS_FIX | BLOCKED | CANCELED`; a `BLOCKED` Task returns to its `previousStage` when a person adjusts it, to `VERIFYING` when a person reruns the verification of its active candidate, or is canceled. Two calls of `transitionTaskStage` inside one `store.transaction` are what `settleVerificationFailure` does. Nothing produces `INTEGRATION_READY` today: a test moves a `VERIFIED` Task there itself.
8. **Fixtures.** `verificationGitFixture(root)` (`src/main/axiom/verification/verification-fixture.test-support.ts`, 205 counted lines of 300) builds a real repository under a temp directory — a base commit, `axiom/integration/<missionId>` at it, a candidate commit on the Attempt branch, a started Mission with a `SUBMITTED` Task and its candidate row — and a runtime whose `createManagedWorktree` runs a hand-written `git worktree add` and whose `removeManagedWorktree` runs `git worktree remove --force` and deletes no branch; its listing answers short branch names. That stub is not the kernel: it sets no `branch.<branch>.base` and has none of the kernel's branch rules. The runtime under it, `verificationRuntime()`, is exported, fully typed without a cast, and its functions are mocks whose implementations a test can replace the way `verificationGitFixture` does; `showRepo` answers the real directory while the Mission's own `repoPath` is a made-up path. Outbox tests drive an executor with `new EffectOutbox({ db, store, epoch })`, an enqueue inside `store.transaction(…)`, `recoverAtBoot()`, `start()` and `kick()`; an orphan is made with `leaseDueEffect({ kind, missionId, now, epoch: 'previous' })`; backoff is stepped with fake timers (`src/main/axiom/outbox/mission-effect-executors.test.ts`, `effect-recovery.test.ts`).

## Outcome

After this Task an effect `integration.apply` for a candidate of a Task that is `INTEGRATION_READY` ends in exactly one of three durable states, however often it is retried or interrupted: a batch in `TESTING` whose merge commit — parents: the integration head the batch recorded, and the candidate — is pinned at `refs/axiom/batches/<batchId>/merged`; a batch in `CONFLICT` with the conflicting paths, the candidate `SUPERSEDED` and the Task back at `READY` or `BLOCKED`; or, when the merge could not be attempted three times, a batch in `SUPERSEDED` and the Task `BLOCKED` with the reason `integration_unavailable` — not sent to be fixed and with its attempt count untouched, so that a person sees it until M4-4 gives such failures a place of their own at the Mission. The integration branch is where it was. No temporary worktree and no temporary branch is left behind. No product path enqueues the effect yet.

## Deliverables

1. **The kind.** `integration.apply` is appended to `EFFECT_KINDS`; its payload is the strict object `{ taskId, candidateId }`; its key is the candidate's id; both unions and the row decoding know it. The existing title in `effects.test.ts` becomes `pins the four kinds and five lifecycle states`.
2. **The executor**, in NEW modules under a NEW directory `src/main/axiom/integration/` (suggested: `integration-apply.ts` for the decision and the settlement, `integration-scratch.ts` for the temporary worktree, `integration-merge.ts` for the merge; each within the 300-line limit) and registered by one call in `createControlPlane`. For one effect, in this order:
   1. **Nothing to do → `'done'`**, with no write and no git call: the Mission does not exist or is `COMPLETED`, `FAILED` or `CANCELED`; the Task or the candidate does not exist or they do not belong to each other and to this Mission; the candidate is not `ACTIVE`; a batch of this candidate exists in any status other than `QUEUED`, `APPLYING` or `SUPERSEDED` (a superseded batch is a try that was given up: it does not count, and a new batch may follow it); the Task's stage is neither `INTEGRATION_READY` nor `BLOCKED` with the previous stage `INTEGRATION_READY`.
   2. **Not now → `{ later }`**, thirty seconds from now, with no write and no git call: the Task is `BLOCKED` (from `INTEGRATION_READY`); the Mission's status is not `EXECUTING`; another candidate of this Mission has an open batch (serial order: one batch of a Mission at a time).
   3. **The head.** The repository is the answer of `runtime.showRepo('id:<repoId>')`: it must be on this machine (`isRepoOnCatalogHost`; importing verification's wrapper would pull in verification), and its `path` — not the Mission's `repoPath` — is the directory. There: `git rev-parse --verify refs/heads/axiom/integration/<missionId>^{commit}`.
   4. **Database first.** One transaction that re-reads what step 1 and 2 decided and then leaves this candidate with exactly one open batch in `APPLYING` whose `baseCommit` is the head just read: a `QUEUED` batch of the candidate is moved to `APPLYING` with that head; an `APPLYING` batch whose `baseCommit` is the head is taken as it is (a run was interrupted); an `APPLYING` batch with another `baseCommit` fails the try (`integration_head_moved`) with nothing written — the head has moved under an open batch, which nothing but this executor may do, and it does not build on a head it cannot account for; with no open batch, one is inserted (id `batch_` + 32 hex characters, `candidateIds: [candidateId]`, status `APPLYING`). One batch id therefore stands for one pair of head and candidate. It appends the audit `integration.batch_started` (`after: { status: 'APPLYING', baseCommit, candidateId }`) — once for each run that reaches this point, so a second try shows in the audit. If the transaction finds the situation changed, the effect ends as step 1 or 2 says.
   5. **Leftovers of this batch are removed**: every managed worktree whose directory name is `integrate-<batchId>` or that name with a `-<number>` suffix, with `force: true` and `waitForBackgroundRemoval: true`.
   6. **The temporary worktree**, through `runtime.createManagedWorktree` with verification's flags, `name: 'integrate-<batchId>'`, `branchNameOverride: 'axiom/integrating/<batchId>'` and **`baseBranch`: the full ref of the integration branch**, `refs/heads/axiom/integration/<missionId>` (ground truth 5a and 5e: not the short name, not the commit id). Read back where it is and which branch it is on from git in the worktree: `rev-parse HEAD` must be the `baseCommit` of the batch — if the branch has moved since step 3 the try fails — and `symbolic-ref --short HEAD` is the branch you got, whatever you asked for. Then `checkout` with `--detach`: the merge is made on a detached HEAD, so the temporary branch never leaves the head.
   7. **The candidate is pinned** from inside the temporary worktree — `pinCandidateRef(<the worktree's id>, candidateId, <the candidate's commit>)`, the function of M4-1a as it is (refs are shared by every worktree of a repository) — and anything but `pinned: true` fails the try. A candidate that was submitted before M4-1a gets its pin here; a candidate whose commit is gone cannot be pinned and so is never merged.
   8. **The merge**, with hooks off (an empty `core.hooksPath` directory for the call), the Control Plane's identity (`Axiom Control Plane`, `axiom@localhost`), `-c commit.gpgsign=false -c rerere.enabled=false -c gc.auto=0 -c merge.log=false -c merge.verifySignatures=false`, an explicit timeout of 120 seconds, the message `axiom: integrate <candidateId>` and **fixed dates** — `env: { ...process.env, GIT_AUTHOR_DATE, GIT_COMMITTER_DATE }`, both set to the batch's `createdAt` (the store returns UTC as `YYYY-MM-DD HH:MM:SS`; pass `YYYY-MM-DDTHH:MM:SSZ`): `git merge --no-ff --no-edit --cleanup=verbatim -m <message> <candidate commit>`. With parents, tree, message, identity and dates fixed, a second run of the same batch makes the same commit.
   9. **What happened** is read from git, not from the exit status alone. Exit 0 and HEAD still the head: the head already contains the candidate — the merge commit of this batch is the head itself. Exit 0 and a new HEAD whose first parent is the head and whose second parent is the candidate: merged. A non-zero exit with a `MERGE_HEAD` and at least one unmerged path: a conflict. Anything else: the try fails (after `merge --abort` when a `MERGE_HEAD` exists).
   10. **Merged**: the merge commit is pinned at `refs/axiom/batches/<batchId>/merged` with `pinCommit` of M4-1a, the temporary worktree as its directory (an existing pin of the same commit answers `pinned: true` — what a run finds that was interrupted between its pin and its transaction, because the merge is reproducible; any other answer fails the try); then one transaction moves the batch `APPLYING → TESTING` with that `mergeCommit` and appends `integration.batch_merged` (`after: { status: 'TESTING', mergeCommit, ref }`). The Task stays `INTEGRATION_READY`.
   11. **Conflict**: the unmerged paths are read (`diff --name-only --diff-filter=U -z`), each passed through `redactContext`, at most 200 kept; `git merge --abort` with hooks off; then one transaction moves the batch `APPLYING → CONFLICT` with those paths, marks the candidate `SUPERSEDED` with no successor (`docs/ARCHITECTURE.md` §12.2: a candidate that conflicts is superseded) with the audit `candidate.superseded` (object kind `candidate`, `before: { status: 'ACTIVE' }`, `after: { status: 'SUPERSEDED', supersededBy: null, reason: 'integration_conflict' }`), sends the Task back — `INTEGRATION_READY → NEEDS_FIX` with the reason `integration_conflict`, then `→ READY` (`retry`) or `→ BLOCKED` (`retry_budget_exhausted`) by the rule of ground truth 7 — and appends `integration.batch_conflict` (`after: { status: 'CONFLICT', conflictCount, truncated }` — the paths themselves are in the batch row). No merged ref is written. The actor of everything this executor writes is `IntegrationController`, the name the architecture gives the single writer of the integration branch; its batch audits have the object kind `integration_batch`, the batch's id as object id and `before: null`.
   12. **The worktree is returned in every case** — after a merge, a conflict, a failed try: `checkout <the temporary branch>` (hooks off; it still stands where its base ref stands, so the kernel deletes it without reaching a remote — ground truth 5e), then `runtime.removeManagedWorktree('id:<id>', { force: true, waitForBackgroundRemoval: true })`. A failure here does not undo a settled batch: it is recorded as the audit `integration.cleanup_failed` — `after: { reason: 'worktree_removal' }` when the removal throws, `{ reason: 'branch_preserved' }` when the checkout back to the branch fails (the removal still follows) or the removal's answer carries `preservedBranch` (the kernel kept the branch) — and the effect still ends `'done'`; after a failed try the failure of the try is what is thrown.
   13. **Tries and their end**: `maxAttempts: 3`, `backoffMs: [1000, 5000]`, `onOrphan: 'retry'` (steps 4 and 5 make a second run safe). Every failure the executor meets in git or in the kernel is thrown as one of these codes and never as the error it caught (a database error or a bug may pass through as it is; the outbox redacts and cuts it): `integration_head_unavailable`, `integration_head_moved`, `repository_not_local`, `candidate_unpinned`, `scratch_worktree_unavailable`, `merge_failed`, `merged_ref_conflict`, `integration_batch_stale` (a move of the batch that should have been possible answered `false`). `onExhausted` never throws (it runs once: ground truth 2); in one transaction it moves this candidate's open batch, if it has one, to `SUPERSEDED`, the Task — if it is still `INTEGRATION_READY` — `→ BLOCKED` with the reason `integration_unavailable` (its attempt count unchanged) and appends `integration.batch_abandoned` (`after: { status: 'SUPERSEDED', reason: 'integration_unavailable' }`) when a batch was moved; then leftovers are removed as in step 5, best effort.
3. **The settlement of a conflict lives in one function**, in the new directory, that takes the store and the Mission controller the way `settleVerificationFailure` does and is called inside the transaction of step 11; do not edit `attempt-settlement.ts`. It needs one new store function, in `src/main/axiom/db/candidates-store.ts` and wired into `AxiomStore`: it marks one `ACTIVE` candidate `SUPERSEDED` with `superseded_by` NULL and answers whether a row changed (`supersedeActiveCandidates` always names a successor and stays as it is).

The executor's tests run on a real repository in a temp directory and on a runtime whose worktrees are made and removed by **the kernel's own git functions** (`addWorktree`, `removeWorktree`), so that the fate of the temporary branch is the kernel's and not a stub's; its listing answers full refs and an empty string for a detached HEAD. Import the two functions from `../../git/worktree-add` and `../../git/worktree-removal` or from the barrel `../../git/worktree`. What the stub does not have — the kernel's naming and its suffixes — a test hands out itself where a title asks for it.
