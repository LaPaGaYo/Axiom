# Task M4-5a — the read side says what integration did: every Task of `axiom.task.list` and `axiom.task.show` carries its latest batch, and `axiom.mission.show` carries the integration branch and its recorded head (the M4-5a row of `docs/plans/M4.md`; optional fields on existing responses, no new RPC method; main process and shared contract only — no renderer, CLI or kernel change)

Planner brief, 2026-11-18 (verifier). Since M4-2b a verified Task is merged into its Mission's integration branch without anyone asking: a batch is opened, the candidate is merged in a temporary worktree, a merged-tree regression runs on the merge commit, and the Task ends `INTEGRATED` or goes back. None of that reaches a client. The batch — its status, its merge commit, the files that conflicted — and the head of the integration branch exist only in the database and the audit log, so the Missions page shows "Awaiting integration" and then "Integrated", and when a merge conflicts or a regression fails the Task is simply `READY` or `BLOCKED` again with no cause anyone can see. M4-5, the row that shows integration in the interface, was split on 2026-11-18 (Henry: "可以拆"): this Task puts the data on the read side, and M4-5b builds the interface on it.

Read first: `docs/PROJECT_CONSTITUTION.md`, `AGENTS.md` (Control Plane Boundary; Remote Execution and Process State, for the mixed-version rule; Lazy Senior Dev Mode), `docs/reference/control-plane.md` (the subsections `### Task 等待与 Mission 待处理项（M3-09-1）` and `### Integration apply（M4-1b）` to `### Integration requests（M4-2b）`), `.axiom-work/verifications/M4-2b-1.md`.

## Ground truth (verifier, 2026-11-18; read in the code at main `fc1ffba3fe`)

1. **Batches.** `src/main/axiom/db/integration-batches-store.ts`: `listIntegrationBatches({ missionId, status?, candidateId? })` answers a Mission's batches ordered by `created_at` and then by insertion. A batch (`IntegrationBatchSchema` in `src/shared/axiom-contract/integration-batch.ts`) has `id`, `missionId`, `baseCommit`, `candidateIds` (exactly one), `status` (ten values, `IntegrationBatchStatusSchema`), `mergeCommit` (null until the merge succeeded), `conflicts` (the conflicted paths, redacted, the first 200 at most), `approvalId`, `createdAt`, `updatedAt` (both SQLite `datetime('now')` text, `YYYY-MM-DD HH:MM:SS` in UTC, not ISO 8601). It carries no Task id: its Task is its candidate's. `listCandidates(missionId)` (`src/main/axiom/db/candidates-store.ts`) answers every candidate of the Mission whatever its status, each with `id` and `taskId`; nothing checks that a batch's candidate exists. A Task can have several batches over time: a conflict or a failed regression supersedes the candidate and sends the Task to `READY` (or `BLOCKED` when its retries are used up), and its next candidate gets a new batch; an abandoned batch becomes `SUPERSEDED` while its candidate stays `ACTIVE`, and the next request opens a new batch for the same candidate; a batch that goes back to `QUEUED` loses its merge commit and conflicts, and its base commit can be rewritten when it starts again. So a Task's latest batch can be in any status, with or without a merge commit. Both readers are on the `AxiomStore`; a stored row that does not parse makes them throw.
2. **The recorded head.** `assertRecordedIntegrationHead(store, missionId, head)` (`src/main/axiom/integration/integration-head.ts`, 43 non-blank lines; its only caller is `integration/integration-request.ts`) is what the start of a batch checks the branch against. Among the Mission's audit events, in sequence order, it takes the last one that is `integration.batch_promoted`, or `integration.base_created` / `integration.base_reused` with `objectKind` `mission` and the Mission's id as `objectId`; it reads `mergeCommit` (a promotion) or `sha` (a base) from that event's `after`, and throws `integration_head_unexpected` unless the value is a git object id equal to `head`. A lookup that throws counts as a mismatch. The base event is appended by the handler of `axiom.mission.start` (`src/main/runtime/rpc/methods/axiom/mission.ts`) before the Mission moves to `EXECUTING`; a Mission whose start never got that far has no recorded head. The branch is `axiom/integration/<missionId>`: `ensureIntegrationBase` (`execution/integration-base.ts`) creates it under that name, and the executor's name for its ref is `integrationHeadRef(missionId)` in `integration/integration-scratch.ts` (`refs/heads/axiom/integration/<missionId>`). The executor treats the ref as the fact when it promotes; the record can lag behind the ref for a moment, and it never notices a ref someone moved by hand.
3. **The reads.** `taskList` and `taskShow` (`src/main/axiom/read-models/task-reads.ts`, 54 non-blank lines; their only callers are the handlers of `axiom.task.list` and `axiom.task.show`) build every Task through one local function, `taskView(ctx, task)`: the list item (`taskListItem` of `control-plane.ts`) plus `waitingOn`. The handlers of `axiom.task.adjust`, `axiom.task.cancel` and `axiom.task.create` build their Task with `taskListItem` directly. `axiom.mission.show` (`methods/axiom/mission.ts`) answers `{ mission: missionSummary(...) }`; `axiom.mission.list` and the Mission mutations (`create`, `start`, `pause`, `resume`, `cancel`) answer summaries too. `TaskListItemSchema`, `TaskResponseSchema` (`src/shared/axiom-contract/task-params.ts`), `MissionResponseSchema` and the schemas that extend it (`mission-params.ts`) are plain `z.object` schemas all the way down: a client that does not know a key drops it, and a client that knows an optional key reads `undefined` when the main process does not send it. The RPC layer does not validate responses and the generated catalog covers params only. Of the product code only the renderer (`src/renderer/src/lib/axiom-client.ts`) parses these response schemas — `TaskResponseSchema` also for `adjust` and `cancel`, `MissionResponseSchema` also for `start`, `pause`, `resume` and `cancel`. The CLI parses none of them: its table output names fixed columns, and with `--json` it prints the whole result, so a new key appears there. Existing tests compare these responses with `toMatchObject` or through the schemas, never by whole-object equality. The other read models convert stored times to UTC ISO 8601 with `utcTimestamp` (`read-models/waiting-context.ts`).
4. **Merged-tree regression runs** are `verification_runs` rows that carry a `batchId`. `axiom.verification.list` answers them when it is called with `batchId` and hides them otherwise. That reader is not this Task's: M4-5b will read a batch's regression through it with the `batchId` this Task exposes.

## Outcome

A client can tell, without reading the database: for each Task, whether integration has touched it and what its latest batch says — the status, the commit it started from, the merge commit once there is one, the files that conflicted, when it last changed; and for the Mission, the name of its integration branch and the commit the Control Plane recorded as its head. A Task no batch names and a Mission with no recorded head answer exactly what they answer today. An older client and an older main process keep working with a newer counterpart.
