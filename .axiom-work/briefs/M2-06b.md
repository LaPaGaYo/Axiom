## Objective

1. **`axiom.attempt.ask`** — a Worker's blocking `QUESTION` (D16 verb `ask`): after the M2-06a authority check, create an Orca question thread on the Attempt's dispatch (`db.createQuestion`), notify the Control Plane mailbox, and long-poll the `dispatch:<attemptId>` mailbox until answered, timed out or cancelled — the same loop as `orchestration.ask`, which Mission Attempts can no longer call directly (M2-06a guard). A pending question blocks admission of **new** Attempts for that Task (M2-04's `hasPendingQuestionForTask` already reads `question_threads` through the binding) and is listed by `axiom.message.list` as a pending item.
2. **`axiom.message.answer`** — the Control Plane / human answer: `{ missionId, questionId, body }` → `db.answerQuestion({ messageId, runId, consumerGeneration: run.consumer_generation, body })` + `runtime.notifyMessageArrived('dispatch:<id>', 'status')`, audit `question.answered`. (`orchestration.reply` stays guarded for Mission Runs; this is the one answer path.)
3. **`REQUEST_SUBTASK` (D50)** — the deterministic checks and the Control Plane decision: when the consumer records a `REQUEST_SUBTASK` (M2-06a's `subtask.requested`), run the checks; if every check passes **and** `policy.approvalRules.subtaskAutoCreate === true`, materialise the Task through `axiom.task.create` (`MINOR_ADJUSTMENT`); otherwise it stays pending for a human, who resolves it with `axiom.message.resolve { missionId, messageId, decision: 'accept' | 'reject', rationale }` (accept → the same `task.create`; reject → audit only). Every outcome writes `subtask.resolved` (`after: { decision, reason, taskId? }`) — the audit M2-06a's `pending` flag reads.
4. **`axiom.task.create`** — `{ missionId, task: TaskSpec (without id), dependsOn: taskId[], provenance }`: adds one `DEFINED` Task to the **active APPROVED** PlanRevision with edges, as plan approval does (`plan-materialization.ts:129–169` is the pattern: `db.createTask` → `insertTaskStage` → `insertTaskEdges`), validates the extended graph is acyclic (`orderPlanTasks` from `plan-task-graph.ts`), audits `task.created` + `plan.minor_adjustment` (`after: { classification: 'MINOR_ADJUSTMENT', origin: 'request_subtask' | 'user', messageId? }`), recomputes readiness and lets the Scheduler trigger fire. No new PlanRevision (D50/§13).

- D50 checks (`src/main/axiom/messaging/subtask-checks.ts`, pure function over store reads, returns `{ ok: true } | { ok: false, failed: Check[] }` with `Check = 'scope' | 'depth' | 'duplicate' | 'dependency' | 'budget' | 'attempt'`): **scope** — every `subtask.allowedPaths` entry is equal to or under one of the requesting Task's `scope.allowedPaths` (string prefix on normalised paths; `'src/'` covers `'src/x.ts'`); **depth** — the requesting Task was not itself created from a `REQUEST_SUBTASK` (the `task.created` audit's `after.origin !== 'request_subtask'`, i.e. depth 1 = `nested_worker_max_depth`); **duplicate** — no existing Task of the Mission has the same `title` (case-insensitive, trimmed) or an identical `allowedPaths` set; **dependency** — the new edge `requestingTask → newTask` (and any `dependsOn` the request names) keeps the graph acyclic (`orderPlanTasks`) and every named dependency belongs to the Mission; **budget** — `policy.budget.maxAttempts`, when set, still exceeds the current `attempt_count` sum (room for ≥ 1 Attempt); **attempt** — the requesting binding's dispatch is still `dispatched`. Checks run again at `resolve --accept` time (state may have moved). `approvalRules` is `z.record(string, json)` — read `subtaskAutoCreate` with a zod `safeParse` on `approvalRules.subtaskAutoCreate` (`z.boolean().optional()`), default `false`.
- Auto-create happens inside the consumer's handling of the `REQUEST_SUBTASK` message, **after** `subtask.requested` is audited, through `missions.createTask(...)` (the controller method behind `axiom.task.create`, so both paths share one implementation), with `actor: 'MissionController'` and `provenance: { kind: 'model', actor: '<attemptId>', at }`; the new Task's spec = the request's `subtask` body + `retryPolicy: { maxAttempts: requestingTask.retryPolicy.maxAttempts }`, `kind: 'task'`, `milestoneId: requestingTask.spec.milestoneId`, `risk` from the request (default `'low'`), and the edge `requestingTask → newTask` with the Mission policy's `readinessThreshold`. A failed check with auto-create on → stays pending, audit `subtask.checks_failed` with the failed list (a human may still accept after fixing the plan, or reject).
- `axiom.task.create` from the CLI / UI (`origin: 'user'`) skips the `depth` and `attempt` checks (there is no requesting Attempt) but keeps `duplicate`, `dependency`, `budget`; the Mission must be `EXECUTING` or `PLANNED` with an APPROVED active plan (`mission_not_executing` / `plan_pending` otherwise); `dependsOn` may be empty (a new root).
