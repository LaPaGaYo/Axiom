## Ground truth (verifier, 2026-11-03, main `c84a7db904`)

1. **Report questions and follow-ups are stored and forgotten.** `SubmissionReportSchema.questions` / `followUps` (`shared/axiom-contract/submission-params.ts`, uncapped `Text[]`) land in the Submission row and the report Artifact; nothing reads them: no pending item, no effect on admission, no line in the next Attempt's context. Workers do use them (the real Codex / Claude Workers in runs 4–5 filled `followUps`; the fixture provider emits `followUps: ['VerificationService dequeues QUEUED']` on every submission).
2. **Kernel Questions cannot carry them.** `db.createQuestion` (`src/main/runtime/orchestration/db/questions/question-threads.ts`) requires an active dispatch (`pending | dispatched`) and `closeQuestionsForDispatch` runs from `failDispatch`, `completeDispatch`, stop and abandon — so a kernel Question dies with its Attempt. `axiom attempt ask` (`execution/attempt-ask.ts`) is the live-Worker path and stays as it is; a headless Worker never has a CLI, and a report is read only after the process exited. `hasPendingQuestionForTask` (`db/attempt-bindings-store.ts`) and `blockingQuestionOrApproval` (`scheduler/admission-blockers.ts`) look only at `question_threads`.
3. **What exists and must be reused.** `MessageFieldsSchema` (`shared/axiom-contract/message-params.ts`) with the M3-04b pattern of an optional typed payload allowed only for one type (`subtask` for `REQUEST_SUBTASK`, `blocked` for `BLOCKED`); `routeWorkerMessage` (`messaging/message-router.ts`; redacts `summary` / `body`; a host sender comes from `resolveHostAttempt` or the submission's `sender`); `messagesStore.listMessages` (`db/messages-store.ts`: `pending` derived from `subtask.resolved` / `blocked.resolved` audits; kernel questions projected by `question-projection.ts` with `question`, `options`, `answer`, `status`); `answerMissionQuestion` (`messaging/question-answer.ts`, kernel-only today, audits `question.answered`); `resolveSubtask` (`messaging/subtask-resolution.ts`, `axiom.message.resolve` with `accept | reject` + rationale); `settleSubmission` (`execution/attempt-submission.ts`: the `axiom_submit` transaction inserts the Submission; `publish()` routes the SUBMISSION message idempotently after commit; both the CLI submit and the headless `submitExit` go through it); the Worker context (`context-builder/render.ts` sections; `previous-attempt-text.ts` `quote` / `quoteLine`; the content-addressed ContextPackage id moves when a section is added — `context-builder.test.ts` pins); `redactContext` (`context-builder/redaction.ts`, returns `{ content, redacted }`); CLI `axiom message list / answer / resolve` (`cli/specs/axiom-message.ts`, `handlers/axiom/message.ts`); e2e `inspectFixtureMission`, `desktopCall`, the fixture provider's report (`tests/e2e/helpers/axiom-test-provider.ts`), `mission-task-adjust.spec.ts` asserting exactly one pending message.

## Outcome

After this Task: every question and follow-up a Worker writes into its report — on either channel — becomes a typed message bound to the Task that a human sees in `axiom message list --pending-only`; a Task with an unanswered report question is not admitted for its next Attempt; the human's answer (secret-free) is recorded against the Task and rendered, quoted, into every later Attempt's context; a follow-up stays pending until the human accepts or rejects it (creating a Task stays a separate human step); and the Mission's other behaviour is unchanged (kernel Questions, SUBMISSION, BLOCKED items).

## Deliverables

1. **Contract** (`shared/axiom-contract/message-params.ts`, `shared/axiom-contract/submission-params.ts`): `MessageFieldsSchema` gains `question: z.strictObject({ text: Text.max(2000), options: z.array(Text.max(200)).max(8).default([]) }).optional()` allowed only for `type === 'QUESTION'`, and `followUp: z.strictObject({ text: Text.max(2000) }).optional()` allowed only for `type === 'REQUEST'` (superRefine like `subtask` / `blocked`); `MessageSummaryResponseSchema` gains `followUp` and, for a typed QUESTION, fills the existing `question` / `options` / `answer` / `status` fields (`status: 'pending' | 'answered'`); `parseAxiomMessagePayload` carries both. `SubmissionReportSchema.questions` and `followUps` are capped at 20 entries × 2,000 chars (`HeadlessSubmissionReportSchema` inherits); an over-long report is rejected like any other invalid report (the Worker preamble JSON Schema shows the caps). Unit tests: payload rules; caps.
2. **Submission → items** (`execution/attempt-submission.ts`, new `execution/submission-items.ts`): inside the `axiom_submit` transaction, right after `insertSubmission`, route one typed `QUESTION` message per `report.questions[i]` (first 10; `question: { text }` redacted; `summary` = the text ≤ 2,000; `related: { taskIds: [taskId], submissionId }`) and one typed `REQUEST` message per `report.followUps[i]` (first 10; `followUp: { text }`), with the submission's `sender`; entries beyond 10 are counted in one audit `submission.items_truncated { questions, followUps }`; a duplicate submission (`existing`) routes nothing; empty lists route nothing. Both channels share this (headless `submitExit` and CLI `axiom attempt submit`); a declared `no_change` / `blocked` exit (M3-04b) never reaches `settleSubmission` and therefore creates no items — its report's questions are in the BLOCKED item's Artifact. Unit tests (`attempt-submission`): two questions + one follow-up → three messages with the right payloads and `related`; 12 questions → 10 messages + the truncation audit; a duplicate submission → no new messages.
3. **Pending, answer, resolve** (`db/messages-store.ts`, `messaging/question-answer.ts`, `messaging/subtask-resolution.ts` or a new `messaging/followup-resolution.ts`, `src/main/runtime/rpc/methods/axiom/message.ts` only if a handler changes, `cli/handlers/axiom/message.ts`, `cli/specs/axiom-message.ts`): `listMessages` marks a typed QUESTION pending until a `question.answered` audit names its message id, and a typed REQUEST with `followUp` pending until a `followup.resolved` audit does (extend the EXISTS to the three event names); a typed QUESTION's `answer` is read from that audit's `after.answer`. `axiom.message.answer { missionId, questionId, body }`: when `questionId` is a typed QUESTION message of the Mission (not a kernel question), require it to be pending, run the secret scan on `body` (`redactContext(body).redacted` → `OrchestrationError('invalid_argument', 'secret_in_answer')`, nothing written — DEF-22 ②), then audit `question.answered { status: 'answered', taskId, attemptId, answer: body ≤ 4,000, by: 'user' }` (objectKind `message`, objectId = the message id, actor `user`), `recomputeReadiness(missionId)` and the mutation receipt as the kernel path does; kernel questions keep their path unchanged (the same secret scan applies to them too). `axiom.message.resolve { missionId, messageId, decision: accept | reject, rationale }`: when `messageId` is a typed REQUEST with `followUp`, require it pending and audit `followup.resolved { decision, rationale, taskId, attemptId }`; `accept` records the decision only — the human creates the Task with `axiom task create` (MINOR_ADJUSTMENT) or `axiom.task.create`; `REQUEST_SUBTASK` resolution is unchanged. CLI: `axiom message answer` / `resolve` shapes unchanged; `axiom message list` prints a typed QUESTION as `QUESTION pending|answered <text>` (+ `→ <answer>` when answered) and a follow-up as `REQUEST pending|resolved follow-up: <text>`. Unit tests: pending / answered projection; answer with a secret → `secret_in_answer`, no audit; answer twice → second refused; resolve accept / reject; a kernel question still answers as before; `caller-authority` classification untouched (both methods are already `desktop_only`).
4. **Admission** (`db/attempt-bindings-store.ts` or `db/messages-store.ts`, `scheduler/admission-blockers.ts`): `store.hasPendingTypedQuestionForTask(taskId)` (one SQL over `messages` JOIN `missions` with a NOT EXISTS on `audit_events` for `question.answered`, filtered on the Axiom payload's `type = 'QUESTION'` and `taskId` — `json_extract` on the payload is acceptable) joins `blockingQuestionOrApproval`'s `'question'` branch, so `canBecomeReady` and the Scheduler's admission (`skipped reason: question`) both wait for the answer; a VERIFIED or INTEGRATED Task with pending questions is not affected (nothing admits it). Unit tests (`scheduler` / `task-readiness`): a READY Task with a pending typed question is skipped with `question`; answering admits it on the next round.
