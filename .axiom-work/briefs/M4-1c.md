# Task M4-1c — Verification stops leaving its temporary branches in the user's repository, and its boot sweep finds what it is meant to find (the M4-1c row of `docs/plans/M4.md`; two existing defects, found by reading the code on 2026-11-15; main process only; no contract, schema, RPC, CLI or renderer change)

Planner brief, 2026-11-16 (verifier). A verification run prepares a worktree of its own on a branch `axiom/verify/<runId>/<claim>`, moves `HEAD` off that branch onto the candidate commit, runs its checks and hands the worktree back to the kernel. The kernel deletes the branch of a worktree it removes — when the worktree is on one. A worktree with a detached `HEAD` is on none, so every claim of every verification run has left its branch behind in the user's repository, for good. Second defect: the sweep that removes, at boot, verification worktrees no run records looks for a branch that starts with `axiom/verify/`, while the runtime's listing names a branch by its full ref (`refs/heads/axiom/verify/…`); it has never matched anything outside tests, whose stub lists short names. This Task fixes both: before a verification worktree is handed back, its `HEAD` is pointed at its branch again — one ref operation, no file is touched — and the kernel's own rule deletes the branch with the worktree; and the sweep compares names the way the listing spells them. The integration executor of M4-1b returns its scratch with a checkout and waits for the kernel; this Task copies neither (the plan row is corrected in the same planner commit).

Read first: `AGENTS.md` (Execution Kernel Boundary; Destructive Actions; Git and Worktree Safety; Independent Verification; Lazy Senior Dev Mode), `docs/reference/control-plane.md` — the section "Verification" (the paragraphs on the verification worktree and on recovery) and the section "Integration apply（M4-1b）" (how the scratch worktree is returned, and the limits at its end).

## Ground truth (verifier, 2026-11-16; read in the code at main `baaf55c827`)

1. **The life of a verification worktree.** `prepareVerification` (`src/main/axiom/verification/verification-prepare.ts`, 145 counted lines) calls `runtime.createManagedWorktree` with the name `verify-<taskId>-<claim>`, the base `binding.branch` (the Attempt branch, a short name) and `branchNameOverride` `axiom/verify/<runId>/<claimCount>`; the kernel resolves the base to the local branch's full ref and records it as the base of the new branch. `const branch` is declared inside the `try`. The run's `worktreeId` is stored, then `pinVerificationCandidate` (`verification-worktree.ts`, 86 counted lines) makes a detached checkout of the candidate commit with repository hooks off (an empty `core.hooksPath` directory made for the call), sets the branch to that commit (`branch -f`), and checks that `HEAD`, its tree and the branch are the candidate's and that `HEAD` is detached. The checks then run in that worktree, detached. So at the end `HEAD` and the branch name the same commit; only the link between them is missing.
2. **Handing it back.** `removeVerificationWorktree(runtime, worktreeId)` in the same file calls `runtime.removeManagedWorktree('id:<id>', { force: true })` and swallows only the three errors that mean "already gone" (`selector_not_found`, `worktree_not_found`, `ENOENT`). It has five callers, all in this directory: three in `prepareVerification` (the claim was lost before the worktree's id could be stored — that worktree is still on its branch; the claim was lost when the prepared state was stored; and the `catch` of a failed preparation, which may come before or after the detached checkout), `cleanupVerification` in `verification-checks.ts` (**255 counted lines of 300**) and the loop over interrupted and uncleaned runs in `recoverVerifications` (`verification-recovery.ts`, 153 counted lines). In each of them the run is at hand.
3. **What the runtime does with the call.** It lists the repository's worktrees again when it accepts the removal, and that row — with the branch `HEAD` names at that moment, or none — is what it deletes by. It may answer `{ removing: true }` and delete the checkout, and then the branch, in the background; verification does not wait for that today and this Task does not change it.
4. **The kernel's rule for the branch** (`src/main/git/worktree-removal.ts`, `worktree-branch-removal.ts`, `src/shared/git-branch-cleanup.ts`): after `git worktree remove`, when the removed worktree's row had a branch and its metadata does not say `preserveBranchOnDelete` (the runtime sets that when it reused a branch that already existed), the kernel deletes that branch. `git branch -d` comes first; it measures against the `HEAD` of the repository's main worktree, which in a user's repository does not contain a candidate, so git refuses. Then comes the kernel's own check that the branch carries nothing that one of these lacks: the base it recorded for the branch, the main worktree's `HEAD`, the branch `origin/HEAD` names — local refs first, with `merge-tree --write-tree`, which needs git 2.38. For a verification branch the recorded base is the Attempt branch and the tip is the candidate, which the Attempt branch contains: the local check settles it and nothing is fetched. With an older git the kernel cannot prove it: the branch stays, and the removal first fetches the remote that `origin/HEAD` names. A branch that stays is named in the answer (`preservedBranch`).
5. **The boot sweep** is the last part of `recoverVerifications`: it lists every managed worktree, skips rows whose `branch` does not start with `axiom/verify/` and rows already handled, reads the run id from `branch.split('/')[2]`, leaves alone the worktree a `RUNNING` run of its own epoch records, and removes the rest without `force`. The runtime's rows carry `branch` as git lists it: `refs/heads/<name>` for a worktree on a branch, an empty string for a detached one. So the prefix never matches, and the run id would be read from the wrong segment. `verificationRuntime()` (`verification-fixture.test-support.ts`, 205 counted lines of 300) lists the short name it was asked for, which is why the rows with short names in `verification-recovery.test.ts` and `verification-restart.test.ts` match.
6. **A runtime stub that uses the kernel's git functions** exists since M4-1b: `integrationFixture(root)` (`src/main/axiom/integration/integration-fixture.test-support.ts`) takes `verificationGitFixture(root)` — a real repository in a temp directory with the integration branch, the Attempt branch and the candidate commit — makes a **new** `verificationRuntime()` and replaces its create, list and remove by calls of the kernel's `addWorktree`, `listWorktrees` and `removeWorktree`, placing worktrees under `root`; branches are then created, listed by full ref and deleted by the kernel's rule, and the removal is finished when the stub returns. `verificationGitFixture`'s own stub runs plain `git worktree add -b` / `git worktree remove --force` and never deletes a branch. In that fixture repository hooks are off (`core.hooksPath` empty) and the main worktree's `HEAD` **is** the candidate, so there `git branch -d` succeeds at once; a test detaches the repository's own `HEAD` onto the base with `f.git('checkout', '--detach', f.baseSha)` (`conflictHead` in the integration fixture does that on its way, but ends on the candidate). That stub lists only the worktrees the runtime stub made, and its removal always forces. Since M4-2a-3 `integrationFixture` also records the Mission's base first (an `integration.base_created` audit event) and the file exports `recordIntegrationBase`; `integration-promotion-fixture.test-support.ts` and every integration test build on what `integrationFixture` returns.
7. **The e2e spec.** `tests/e2e/mission-verification.spec.ts`, title "M3-02: independent checks reject both broken fixture candidates and verify the unpatched one", waits until three runs are `PASS` or `FAIL` and until all three have `worktreeId` null. Its callback receives `clone` (the fixture's clone, whose `HEAD` is `main`) but does not destructure it, and the spec does not import the helper `git` (`tests/e2e/helpers/axiom-fixture-mission.ts`: runs git, expects exit 0, answers trimmed stdout). `tests/e2e/mission-attempt-submit.spec.ts` reads `refs/heads/axiom/verify/<runId>/<claim>` while its runs are held in the prepared state — that stays true.
8. **Git, probed by the verifier** (git 2.43). In a detached worktree whose branch names the same commit, `git symbolic-ref HEAD refs/heads/<branch>` puts the worktree on the branch without touching the index or a file — it works with modified and untracked files present and with a stale `index.lock`, where a checkout fails — and the listing then shows the branch. The command checks nothing: for a branch that does not exist it succeeds and leaves `HEAD` unborn, and it succeeds for a branch that another worktree has checked out. Run in a directory that has no `.git` of its own, the same command walks up and re-points the `HEAD` of a repository above it; with `GIT_CEILING_DIRECTORIES` set to the parent of that directory it fails with "not a git repository", and in a real linked worktree it works with the same setting. The git runner takes a caller's `env` in place of `process.env`, and git that runs inside WSL gets none of it (`src/main/git/command-runner/`). Since M4-2a-3 the two git helpers of the integration directory set the same variable (`integration-merge.ts`; its read helper passes `env: { ...process.env, GIT_CEILING_DIRECTORIES: path.dirname(cwd) }`).

## Outcome

After this Task a verification run that has handed its worktree back loses its branch with it: after a verdict, after a failed preparation and after a restart that requeues it. The boot sweep removes the worktree, and with it the branch, of a verification worktree that no run records. Branches that earlier versions left behind without a worktree are not touched. Axiom still deletes no branch itself: the kernel does, by its own rule, and the step this Task adds runs only in a directory that is a worktree of its own.
