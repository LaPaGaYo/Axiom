# Task M3-09-4d — a Task's acceptance criteria: shown as they are now, replaceable from the adjust form, and a refusal says why (renderer)

Planner brief, 2026-11-14 (verifier). When verification finds that a Task's plan is wrong — a criterion whose command cannot run (`INCONCLUSIVE(plan_invalid)`), a check the Worker disputes — the Control Plane's answer is that a person corrects the criteria and verification runs again on the same Candidate (D85 rules 4 and 5; `axiom.task.adjust.acceptanceCriteria`, M3-05). The page cannot do that. The adjust form changes paths and limits only; nothing on the page shows a Task's criteria as they are now — the Task page shows what past runs recorded, the plan card what was approved —; and a refused adjustment reads `plan_invalid: plan_invalid`. M3-09-2b-3 left the criteria editor to the plan-card part of M3-09; this Task adds it on the write path that already exists. It changes the renderer only and waits for nothing that is open in 4b or 4c.

Read first: `AGENTS.md` (UI and Product Experience; Human Approval), `docs/STYLEGUIDE.md` (UX rules: every state has a reason, in the Control Plane's own words; siblings read as one design; quiet), `docs/decisions/DECISION_LOG.md` D85 (rules 3–5 and the revision of 2026-11-03) and D78, `docs/reference/control-plane.md` ("Task spec：逐条验收合同（M3-04b-2）"; "Task 页的调整与取消（M3-09-2b-3）"; "计划卡（M3-09-4a）"; "人工验证处置与同候选重验（M3-05）"; "人工 Task 调整（M3-04b）"), `tests/e2e/AGENTS.md`.

## Ground truth (verifier, 2026-11-14, main `407a1c9336`; every fact here was read in the code, the tests or the specs at that commit)

1. **Criteria.** A criterion is `{text, check}` (`AcceptanceCriterionSchema`, a strict object, in `src/shared/axiom-contract/mission-objects.ts`); `check` is `{kind: 'command', command}`, `{kind: 'artifact', artifactKind?}` or `{kind: 'human'}`; `text` and `command` are strings of at least one character (message `Expected non-empty text`), not trimmed, with no upper length; `ArtifactKind` is one of `context_package_manifest`, `context_package_render`, `worker_report`, `handoff`, `evidence`, `log`, `other`. `resolveAcceptance(spec)` (`acceptance.ts`) is the compatible read: a bare string becomes a `human` criterion, each legacy `requiredEvidence` entry a command criterion.
2. **The write path.** `axiom.task.adjust` (desktop only; `TaskAdjustParams` in `task-params.ts`, a strict object) takes `taskId`, `rationale`, `addAllowedPaths`, `maxAttempts?`, `maxTokens?` and `acceptanceCriteria?` — at most 50 criteria, a whole replacement. `adjustTask` (`src/main/axiom/mission-controller/task-adjustment.ts`) then builds the Task's spec with the new list and refuses with `plan_invalid` and `data.errors` when either of two checks reports anything: `validateTaskAcceptance(spec, ['task'])` (`src/shared/axiom-contract/plan-proposal.ts` — `required_evidence_retired` when the spec still has `requiredEvidence` entries, which the adjustment keeps; `acceptance_uncheckable` when no criterion is a command or an Artifact) and the command check, which is `validateAcceptanceCommands(resolveAcceptance(spec), rules)` with each issue worded by `evidenceCommandMessage(issue, issue.command)` (`evidence-commands.ts`: `multiline`, `shell_operator`, `program_not_allowed`; allowed programs are the rules' `evidenceCommands.allowedPrograms` plus the programs of its setup commands and gates) and that wording then passed through the main process's redaction, which the renderer does not have — the refusal masks a program name or an operator that looks like a secret. `rules` are the Mission policy's `verificationRules` parsed with `VerificationRulesSchema`; when they do not parse, the adjustment checks against the schema's defaults — while a verification run under the same policy ends `INCONCLUSIVE` with `policy_invalid`. An error's `path` is `['task', 'requiredEvidence']`, `['task', 'acceptanceCriteria']` or `['task', 'acceptanceCriteria', index, 'check', 'command']`. Other refusals: `illegal_transition` with `data.reason` `task_not_adjustable` when criteria are given while the latest run of the Task's Candidate is `QUEUED` or `RUNNING` (the pending view cannot tell this apart), `invalid_argument` (`secret_in_rationale`; limits below what is used), `stale_state`, `retry_budget_exhausted`. Only the rationale is checked for secrets; the audit of an adjustment stores both versions of the criteria redacted.
3. **What a replacement does.** The Task's spec is replaced; no PlanRevision changes. A run reads the Task's spec and the policy when it runs (`verification-checks.ts`), and the next Attempt's ContextPackage is rendered from the spec as it is then. A `VERIFYING` Task whose run waits in `HUMAN_REVIEW` stays there and the review stays open: `axiom.verification.rerun` cancels it and verifies the same Candidate again. A `BLOCKED` Task that has a Candidate stays `BLOCKED` when the adjustment carries only criteria — no path, no limit — so that verification can be rerun on that Candidate; with any path or limit in it — even a path already allowed or a limit that changes nothing — it goes back to the stage it had before the block as any adjustment does, which is `NEEDS_FIX` for a declared block. In `NEEDS_FIX` the Task becomes `READY` for another Attempt, or the adjustment is refused with `retry_budget_exhausted` when its Attempts are used up.
4. **What the caller gets.** A refusal by the Mission controller arrives as `{code, message, data}` where `message` equals `code` and `data` carries the detail (`errors`, `reason`, …) (`src/main/runtime/rpc/errors.ts`). The renderer's transport (`src/renderer/src/lib/axiom-rpc-call.ts`) builds `new AxiomRpcError(code, message)` and drops `data`; it also refuses params that do not parse (`invalid_params`) before any call. The page controller writes `code: message` on the error line and into a toast — for these refusals the code twice.
5. **Who is offered the adjustment.** `axiom.mission.pending` lists `axiom.task.adjust` on a Task's `human_review` or `task_blocked` item while the Mission is `PLANNED` or `EXECUTING` and the Task is in a stage an adjustment accepts — not on a block whose reason is `upstream_canceled` or `no_eligible_provider`. `axiom.verification.rerun` is on the same item when the Task has a Candidate, is `BLOCKED` or waits in review, and no run is queued or running; on a `task_blocked` item it therefore means a blocked Task whose Candidate can be verified again. `TaskVerificationActions.tsx` offers the form from that list; when a form opens it focuses the first radio, `textarea` or `button` inside it.
6. **The form today.** `TaskAdjustForm.tsx` (223 lines): a definition list with the Task's allowed paths and limits, a guidance sentence by the item's kind and reason, the fields `Allowed paths to add`, `New Attempt limit`, `New token limit`, `Rationale`, and `Apply adjustment` / `Close`. It submits `{taskId, rationale, addAllowedPaths, maxAttempts?, maxTokens?}` and closes when the controller says the adjustment went through. It gets the Task's spec from `axiom.task.show` (`taskSpec`, read in `task-evidence-read.ts`; `undefined` when that read failed, and then a note stands in place of the form).
7. **The Task page today.** `TaskDetail.tsx` shows title, id, stage, the waiting line, the actions, the Attempts, the verification record, the submission and the messages. The only criteria on it are the ones a run recorded (`VerificationCriteria.tsx`, a list named `Acceptance criteria` inside the verification record). `PlanAcceptance.tsx` (M3-09-4a) renders one criterion with its proof and, with `explain`, the sentence saying what proves it; `reviewCriteria(spec)` gives the resolved criteria with stable keys.
8. **The policy on the page.** `readMission` already reads the Mission's policy with every page read (`mission-policy-read.ts`; `null` when the read failed); `MissionsPageSurface.tsx` hands it to the plan card only. This Task adds no read.
9. **The plan card.** The card of an approved revision shows the criteria the plan was approved with; after an adjustment they are no longer the Task's. `PlanReviewSections.tsx` renders the group `Goal coverage` whenever the Goal revision on the page is the plan's own — also when that Goal lists no criteria, and then the group is a heading with nothing under it (note (a) of the M3-09-4a record).

Refresh to try again.` exactly once. Many tests render `TaskDetail` without a spec and without a policy. The controller test expects a refusal with its own message verbatim (`retry_budget_exhausted: The Attempts are used up.`). `PlanCard.test.tsx` is at 785 of its 800 counted lines.
11. **E2E.** `mission-task-actions.spec.ts` and `mission-home-pending.spec.ts`, which this Task may not edit, use the adjust form through the page: the exact list of buttons in `Task actions`, the form by its name `Adjust Task`, each allowed path and `Attempt limit` found once by exact text inside the form, the focus on `Allowed paths to add` after opening, the textboxes by name, `Apply adjustment`, the focus back on the trigger. `mission-task-evidence.spec.ts` and `mission-review-actions.spec.ts` find the Task page's one list named exactly `Acceptance criteria`. In `mission-review-actions.spec.ts` the test `a person reruns verification of the same Candidate from the Task page` shows the whole setup this Task's scenario needs: a fixture plan whose one Task has the criterion `pnpm run no-such-script` (`acceptanceCriteria: [invalid]`, `holdWorkers`, `runVerification`), `releaseScenario(f, 'agent-crash')`, `waitForReview(f, taskId, 'plan_invalid')`, `openDetail`, the rerun through the page (`Rerun verification`, `Rationale`, `Queue rerun`), and the local readers `readRuns` and `readTask`; `passing` in the same file is a criterion whose `node -e` command passes on the fixture's Candidate. `mission-human-review.spec.ts` (`adjust and rerun`) shows, through `desktopCall`, that replacing the criterion by `passing` and rerunning ends `PASS` with the old run `CANCELED`, the Task `VERIFIED` and no second Attempt.

## Outcome

On the Task page a person sees the criteria the Task has now. When the plan got them wrong, the person replaces them from the adjust form, is told before sending what the Control Plane would refuse and why, and after a refusal reads the Control Plane's own reasons. The approved plan's card no longer passes for the present state of its Tasks.

## Deliverables

1. **The transport keeps the detail.** `AxiomRpcError` gains an optional third constructor argument and a read-only field `data`, and the transport passes the refusal's `data` into it. Nothing else about the transport changes; `axiom-client.ts` does not change.
2. **A refusal says why.** One new module of the missions folder turns a failure into the text of the page's error line, and the controller's `reportError` uses it: for an `AxiomRpcError` it is `code: detail`. When the message is the code itself (the Mission controller's refusals), `detail` is the messages of `data.errors` — each once, in order, joined by one space — when `data` has such an array with at least one `message` string in it; otherwise `data.reason` when that is a string; otherwise the message. When the message is not the code, `detail` is the message, as today, whatever `data` holds. Anything that is not an `AxiomRpcError` is written as today. The module takes the class from the transport module, so that a test's client mock cannot hide it, and reads `data` through a schema, not a cast.
3. **The Task page shows the Task's criteria as they are now.** Between the page's header block and the Attempts, a region named by its level-3 heading `Current acceptance criteria` holds a list with that same name: one item per criterion of `resolveAcceptance(taskSpec)`, rendered as the plan card renders a criterion with its proof and its sentence (`PlanAcceptance` with `explain`). When the Task could not be read, the region holds one sentence instead: `The acceptance criteria of this Task could not be read. Refresh to try again.` (plain text, no `alert` or `status` role). The list is not named `Acceptance criteria` — that name stays the verification record's.
4. **The adjust form can replace the criteria.** After the token-limit field and before `Rationale`, a checkbox `Replace acceptance criteria`, unchecked when the form opens. A row keeps what was typed for another proof while the form is open, and sends only the fields of the proof it has;
   - a button `Add criterion` that appends an empty row with the proof `command`; removing a row moves the focus to `Add criterion`.
   Submitting with the checkbox checked adds `acceptanceCriteria` to the object: the rows in order, `text` and `command` trimmed, `artifactKind` only when a kind was chosen.
