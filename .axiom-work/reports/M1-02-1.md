## Proposal validation

`validatePlanProposal(unknown, { requireParallelRoots?: number })` parses with zod first. It returns `{ ok: true, order }` or `{ ok: false, errors }`. Errors carry a stable code, severity and message, plus schema path or relevant task IDs where applicable.

Implemented rejection classes:

1. `invalid_schema`: malformed proposal, nested Task, edge, provenance, etc.
2. `duplicate_task_id`: repeated Task identity.
3. `unknown_edge_endpoint`: either endpoint absent from the proposal.
4. `self_edge`: Task depends on itself.
5. `duplicate_edge`: same directed endpoints, including when thresholds differ.
6. `cycle`: reports one actual cycle in traversal order, without downstream non-cycle Tasks.
7. `unknown_milestone`: Task names a nonexistent milestone.
8. `insufficient_parallel_roots`: severity `warning`, emitted only when the caller supplies `requireParallelRoots` and the count falls below it; with the requested result shape it makes `ok` false.

Identity/reference errors are returned before graph traversal. Valid graphs use lexical Task-ID ordering for ties; adjacency lists and traversal starts are sorted too. Iterative cycle traversal avoids call-stack dependence. The sorted frontier is deliberately simple for V1's 8–15 Tasks; its worst-case O(V² log V) cost and min-heap upgrade path are recorded in a `ponytail:` comment. There is no task-count cap imposed by the schema.

## Contract boundaries and follow-ups

- M1-06 owns RPC registration, catalog generation, orchestrationContractVersion/orchestrationRequestId/capability envelopes, idempotency receipts, CLI and runtime capability negotiation. These are intentionally absent from method params.
- Per §4c, PlanProposeParams is `{ missionId, planRevision, provenance }`; planRevision contains the proposal fields except provenance. M1-05/M1-06 must call `validatePlanProposal({ ...params.planRevision, provenance: params.provenance })`. Shape parsing alone does not validate the DAG. TaskCreate edges may point at existing Mission Tasks; their identity/cycle/readiness validation requires the store and belongs to M1-05.
- Approval authorization, resolver identity verification, rejection/cancellation rationale persistence, old-Task inherit/cancel/rebind records, immutable revisions, and persisted previous-stage restoration are Control Plane responsibilities. Transition admissibility is not permission to mutate.
- Budget fields are `maxRuntimeMinutes`, Mission-wide `maxAttempts`, `maxTokens`, `maxCostUsd`; they are optional finite numeric limits (counts integral). Task maxAttempts lives only in retryPolicy. The schema supplies no implicit unlimited-budget policy. Admission and approved-budget comparisons remain future service work.
- The references specify approvalRules/verificationRules only as JSON. They are preserved as JSON-object payloads; rule semantics are intentionally not invented here. A policy-owning service must validate supported rules and apply deterministic defaults before use. These contracts alone do not authorize execution.
- Active Mission revision references are nullable before activation/approval. IDs validate nonempty/max-128 only; M1-05 still must validate/mint the synthetic coordinator session identity through the existing kernel contract.
- Goal activate/show both take missionId and goalRevisionId. Plan reject also requires reason; task cancel requires rationale. Mission list supports repo/status/cursor. These are contract choices for the documented parameter outlines, without new RPC methods.
- Duplicate milestone/risk identities and a generic 8–15 Task count policy are not added to the requested rejection classes. M1-05 must apply any additional materialization/policy invariants.
- Worker write scope remains a verification-time diff check for CLI agents, as documented by AGENTS.md. Independent verification and integration are still required; Worker-run gates do not mark this Task VERIFIED or INTEGRATED.
