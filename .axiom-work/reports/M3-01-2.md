## Outcome and changes from attempt 1

The recovery hardening is implemented and locally checked. This is submission
readiness, not independent acceptance or Mission completion.

- Boot awaits verification recovery but only warns on rejection. It continues
  with the existing timer, consumers and Scheduler resume round, while the
  bootGeneration guard still prevents a stopped boot from resuming.
- Stale RUNNING recovery, INCONCLUSIVE cleanup and the boot-only orphan sweep
  isolate failures per item. A failed removal preserves status, stale epoch,
  recorded worktree id and phase facts, and sets cleanupPending on the owning
  run. Requeue occurs only after removal or explicit absence is confirmed.
- Each kick first retries stale RUNNING and cleanupPending INCONCLUSIVE runs.
  A run failure does not prevent the remaining queue from preparing. A
  per-boot set suppresses duplicate recovery_failed audits only; all cleanup
  eligibility and ownership remain in the DB. The set resets at a new
  recoverAtBoot invocation; overlapping boot recoveries share their promise.
- Failure audits contain only worktreeId and worktree_removal_failed; neither
  audits nor warnings include raw runtime/Git error output. Orphan failures
  associated with a known run get the same audit. An older orphan does not
  mark the current claim's different worktree for cleanup. Recovery returns
  requeued/cleaned/failed counts, and failure summaries log those counts.
- Missing Candidate rows now settle QUEUED runs as CANCELED/candidate_missing,
  append verification.canceled and continue to the next run.
- The existing status queries had no status index. Added
  idx_verification_runs_status(status, created_at, id) through the existing
  CREATE INDEX IF NOT EXISTS schema bootstrap, supporting both ordered claims
  and periodic recovery. No schema-version increment, column change, v40–v44
  migration change, new queue, or store API was needed. Existing v45 databases
  also receive the index through createTables at open.
- Updated the Verification reference, recovery entry point, Glossary and schema
  mapping. All five e2e fixture files, the launch/restart spec, RPC/CLI contracts
  and preparation/submission behavior are byte-identical to attempt 1.
