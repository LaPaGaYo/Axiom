## Known limitations and risks

- This is a textual count ratchet, not runtime network enforcement. Dynamically assembled or encoded references are outside its matching model, and existing endpoints remain grandfathered.
- The specified count format permits replacing an existing mention with a different mention of the same needle in the same file without increasing the count. Stale counts allow reintroduction up to the old budget until `--write-baseline` tightens them. Growth diagnostics therefore show all matching lines for the affected pair.
- Only tracked files in the requested roots are scanned. Untracked additions enter the ratchet after staging. Excluded roots, the two self files, the baseline, and exact same-line allow markers are deliberate exemptions. Exemptions and manual baseline edits still require review.
- Binary detection uses NUL bytes or invalid UTF-8; UTF-16 and legacy non-UTF-8 text is consequently excluded. Missing tracked files are treated as deletions; other read failures fail the check.
- `--write-baseline` initializes an absent baseline, then refuses new pairs or count growth against an existing baseline. Removing or manually expanding the baseline can bypass this local history-independent guard and must be caught in review.
- Tests ran on macOS with Node 24. Windows and Linux execution was not exercised here; paths use `node:path`, Git output is NUL-delimited, and no shell interpolation is used by the scanner.
- These are Worker checks, not independent verification of an immutable Candidate. The launcher still needs to commit the working tree and hand the Candidate to the verifier. Worker write scope is enforced here by final diff/file inspection, consistent with the repository's stated CLI-agent limitation.
