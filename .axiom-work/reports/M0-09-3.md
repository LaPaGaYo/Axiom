## Decision proposal — per-profile provider activation

**Status: PROPOSED implementation record under accepted D37**, for the verifier/owner to number and record. It does not expand D37's policy or authorize startup egress for an unactivated provider.

**Context.** Fresh `userData` coexists with a real HOME containing CLI credentials and previously installed hooks. Measured Codex app-server startup opens `chatgpt.com` and spawns plugin-marketplace git requests to `github.com`. Machine-level credentials, binary presence and hook files cannot establish user intent in this Axiom profile.

**Proposal.** Add optional `GlobalSettings.providerActivations` in `orca-data.json`, default `{}`. Each entry is `{ activatedAt: ISO UTC string, source }`. Sources are `agent-launch`, `settings-hook-install`, `integrations-recheck`, `account-added`. IDs are `codex`, `gh`, `glab`, `bitbucket`, `azureDevOps`, `gitea`, and the existing usage provider IDs (`claude`, `gemini`, `opencode-go`, `kimi`, `minimax`, `grok`, `antigravity`, `cursor`). Antigravity is a derived usage view, not a new network client. The zod schema validates the complete record on store load and update; absent/malformed values normalize to `{}`. The first activation is retained and sibling entries preserved. No SQLite migration is needed. Generic renderer settings writes cannot supply this main-owned record; paired settings update types exclude it.

**Writers (existing explicit action paths only).**

- Recognized `launchAgent: 'codex'` in `prepareCodexRuntimeHomeForLaunch`, before native/WSL trust work; the two existing text-generation callers now identify their Codex launch. A generic terminal's environment preparation does not activate Codex.
- Verified Codex session resume callback, before migration/trust repair. WSL launch subsequently uses the recognized-launch path.
- Desktop and paired Settings managed-hook reconciliation when enabling/installing Codex hooks (`userInitiated: true`).
- Successful Codex account add/import in the common `CodexAccountRegistration` path, after durable account setup and before quota refresh.
- Forced preflight probes: installed `gh`/`glab`, plus the Bitbucket/Azure DevOps/Gitea status checks requested by that existing all-integrations re-check action. Activation records intent to check, not successful authentication.

**Readers.** Shared startup hook policy gates both `ensureRealHomeCodexHookState` and the Codex installer. The retained-pane hook reconciler and legacy system-home sweep also require Codex activation. Launch preparation permits trust only for an explicit Codex launch or an already activated profile. Preflight gates each auth probe independently. The rate-limit service receives a resolver from the profile store: deferred startup, background/focus/stale refresh and each automatic fetch consult it; a settings-change listener arms polling after activation. Codex credential presence remains an additional guard. Manual refresh can read all provider credentials once without recording activation.

**Alternatives considered.** Gating on PATH, global auth files or hook grants would reproduce the fresh-profile bug. In-memory booleans lose intent across restart. Disabling hooks/usage entirely removes capability. Changing Codex plugin/config behavior is outside scope and cannot prevent other CLI startup traffic. A second scheduler or consent subsystem is unnecessary: the existing settings boundary and service gates suffice.

**Consequences and compatibility.** Existing profiles without this field start with no activation; there is no inference/backfill from HOME or settings. A user action records intent again. The additive preflight field `checked: false` preserves boolean `authenticated` for older readers; updated UI displays “Not checked” / “未检查” with Connect / Re-check. Omission remains compatible with old runtimes that always probed. Other usage-provider IDs are gated but this bounded task adds persistent action writers only for Codex and source-control integrations; manual usage refresh remains available for all providers and never opts them into later automatic polling. Additional persistent activation writers should use existing explicit profile configuration actions, not credential discovery. Broadening automatic startup egress still requires a new Decision.
