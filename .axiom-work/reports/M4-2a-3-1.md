## One merging, passing, promoting try

1. The unchanged outbox leases the due request in its Mission/kind lane. `applyIntegration` asks `catchUpIntegrationPromotions` for open PROMOTABLE batches. A fresh request has none, so there is no git read or promotion transaction here. If they exist, the head is read and each matching batch is settled first by `integration_promoted` with caughtUp=true.
2. `closeStaleIntegrationBatches` runs `integration_stale_batches`, cancelling runs and superseding only dead open batches; a fresh Mission has nothing to write. Any abandoned scratch removal remains best effort via the kernel. `finishPromotedRequest` finds no finished batch in the fresh path. For an existing promoted request its separate `integration_promoted_task` transaction can move only the eligible Task and adds no batch promotion event.
3. `eligibility` reads the Mission, Task, candidate, and queue. `readIntegrationHead` resolves the local repository through runtime.showRepo and reads the integration commit (or the try reuses the head read during catch-up).
4. `beginBatch` opens `integration_begin`, rechecks eligibility, and for a new/QUEUED batch calls `assertRecordedIntegrationHead`. The latest matching audit by sequence must contain a valid id equal to the actual head. It inserts APPLYING or moves QUEUED to APPLYING with that base and writes integration.batch_started. APPLYING/TESTING/PROMOTABLE continuations instead compare their stored base and reject drift. No new batch is written on an unexpected head.
5. `removeIntegrationLeftovers` lists/removes named leftovers via the kernel. `createIntegrationScratch` calls kernel createManagedWorktree, which creates the scratch worktree and temporary `axiom/integrating/<batchId>` branch at the base. There is no parallel worktree manager.
6. `detachIntegrationScratch` reads HEAD and branch, checks HEAD=base, then writes a detached checkout with hooks disabled. `pinCandidateRef` writes the create-only candidate pin using the existing pin implementation. `mergeIntegrationCandidate` writes `merge --no-ff` in the detached scratch, with hooks/signing/rerere/auto-gc/log/signature verification disabled and deterministic dates. The scratch HEAD advances to the merge; its temporary branch and integration branch are still at base. A conflict uses the unchanged merge-abort write and `integration_conflict` transaction instead and never reaches promotion.
7. `pinCommit` writes the existing create-only `refs/axiom/batches/<id>/merged` pin. `integration_merged` transitions APPLYING → TESTING and appends integration.batch_merged. These pin writes remain outside the integration directory; this Task adds no new pin or ref namespace.
8. `runIntegrationRegression` opens `integration_regression_started`: fence current objects, cancel prior open runs, insert/claim a new batch run, persist commands/baseline and integration.regression_started. The existing runner executes the policy's offline checks and tool probes in the scratch; commands may themselves write within that scratch. It checks the final HEAD and writes evidence through ArtifactStore. No new regression policy is introduced.
9. `integration_regression_verdict` fences again, records PASS and its evidence, changes TESTING → PROMOTABLE, and writes integration.batch_promotable. The ref is still at base. FAIL, INCONCLUSIVE, stop and interrupted paths preserve their prior outcomes (`integration_regression_interrupted` cancels the owned run for interruption).
10. `returnIntegrationScratch` writes a checkout of the original temporary branch with hooks off, then asks kernel removeManagedWorktree with force and waitForBackgroundRemoval. Kernel removes its worktree and temporary branch under its existing safety rules; failures are audited. Promotion starts only after this return attempt completes.
11. `promoteIntegration` rereads Mission EXECUTING, Task INTEGRATION_READY, ACTIVE candidate ownership and the PROMOTABLE batch. A failed recheck returns `{later: now}`, spends no try, and writes nothing. It resolves the catalog repository using the same lookup as the head read.
12. `advanceIntegrationHead` validates from/to, reads exact commit/symref/worktreepath in one for-each-ref, handles already-at-to and refusal cases in order, then performs the Task's sole new ref write: expected-old, hooks-disabled update-ref of `refs/heads/axiom/integration/<missionId>`. A second for-each-ref decides the result even when the write failed. No branch other than this integration branch is moved by the new writer. Every git call has a 30-second timeout.
13. `recordPromotion` opens `integration_promoted`: conditional PROMOTABLE → PROMOTED, then eligible Task → INTEGRATED through MissionController's nested `transition_task_stage`, then exactly one integration.batch_promoted with `{status,baseCommit,mergeCommit,taskIntegrated,caughtUp:false}`. Any refusal/exception becomes fixed integration_batch_stale and rolls back this transaction. A human's block/cancellation is preserved, with taskIntegrated=false. The existing post-commit stage_change notification schedules dependent readiness.
14. The executor returns done. The unchanged outbox completes the effect by its status/epoch fence. If an earlier step throws, `effect_failure` increments attempts and defers 1 s/5 s, or marks failed after three. Exhaustion first uses the shared ref catch-up, then `integration_abandoned` supersedes only remaining judgeable batches, cancels their open runs and blocks only an INTEGRATION_READY Task; cleanup follows. Exhaustion never rejects.

## Stop/restart boundaries

| First process stops after | Durable state a restart sees | Next try |
|---|---|---|
| PASS verdict transaction | Batch PROMOTABLE, run PASS/evidence, merge pin; ref still base; scratch may remain | Reads head before any stale cleanup. When live/unblocked, compares base, removes leftover scratch, skips merge/regression and retries promotion. Blocked/paused waits. A dead non-promoted batch can be closed. |
| Scratch returned | Same PROMOTABLE/PASS/base-ref state, normally no scratch | Same continuation; no new scratch or run. Final request recheck may defer without consuming a try. |
| Ref advanced, before promotion transaction (including refused transaction) | Ref equals merge; database still PROMOTABLE; Task may have been blocked/canceled or Mission ended | Before dead cleanup, shared catch-up records PROMOTED with caughtUp=true. Eligible Task becomes INTEGRATED; otherwise exact human state is retained. Exhaustion does this too. If read/settlement cannot succeed, exhaustion retains the batch rather than abandoning it. |
| Promotion transaction committed, before effect completion | Batch PROMOTED, one promotion event; Task INTEGRATED or preserved human stage; ref at merge | No merge/regression/write to ref. Finished request is done. If a blocked Task was later restored to INTEGRATION_READY with its ACTIVE candidate, integration_promoted_task moves it to INTEGRATED without a second promotion event, even while Mission paused or another candidate has an open batch. |

A second live process cannot legitimately lease the same running lane: the existing outbox is a single-Control-Plane-epoch design, with no time-expiring lease. A restart recovers a prior epoch's running request as retry. This Task adds no cross-process ownership or new lock. Expected-old git update still refuses a conflicting ref writer; the readback is authoritative if another writer already reached the desired merge.

## Recorded head and bounded failures

`listAuditEvents({missionId})` already orders by monotonically increasing sequence; `findLast` selects integration.batch_promoted (mergeCommit), or a base_created/base_reused event on the Mission's own mission object (sha). It does not use batch insertion order or wall-clock timestamps, and it does not fall back past a malformed latest matching event. A Mission with no base event and no promotion event gets integration_head_unexpected before insertion/QUEUED transition. The ponytail comment documents the all-events scan and filtered-store-query upgrade.

The only new try codes are integration_head_unexpected and integration_branch_checked_out. Promotion also uses the existing integration_head_moved, integration_head_unavailable, repository_not_local and integration_batch_stale. All added store paths translate failures to a fixed code. No raw git/store message is put in a new error, audit, or lastError. `advanced:true` may be idempotent; already-at-to is checked before checkout occupancy and never writes or grows a reflog.

## Necessary implementation choices and differences

- Two new focused modules (`integration-head.ts`, `integration-promotion.ts`) keep repository/head authority and promotion separate; existing apply/request modules remain the flow owners. No infrastructure abstraction, new store API or dependency was added.
- Repository resolution was extracted unchanged so the writer and head reader use the same local catalog rule; there is one additional catalog lookup immediately before promotion, rather than trusting Mission.repoPath or retaining a path across scratch execution.
- `integration_promoted_task` names the bookkeeping transaction required by 5(b). Audit boolean field names are `taskIntegrated` and `caughtUp`.
- Exhaustion conservatively retains PROMOTABLE when catch-up settlement itself is refused, as well as when the head is unreadable. Otherwise a known-ref promotion could be abandoned on a store failure, violating the required ref authority. Non-PROMOTABLE batches and Task blocking retain the existing bounded fallback.
- Tests 2–9 are split into three files; title 1 has its own file. No extra title was added. The unreadable-head/exhaustion/cancelled-Mission scenario is included inside title 5. No model was delegated implementation or review; this follows the Task's explicit local-only instruction.
- The explicit sandbox fallback was used for package wrappers that could not create tsx's local socket. Independent host verification and candidate creation remain with the supplied verifier/launcher, as requested.

## Limitations and risks

1. Nothing enqueues integration.apply in a product flow. VERIFIED → INTEGRATION_READY and re-arming after unblock remain M4-2b. Existing Mission flows stay on their current path.
2. Checkout observation and expected-old update are separate git calls; another checkout can land in between. Rebase/bisect of the branch in a worktree is not seen by worktreepath. A manually deleted worktree directory still counts as a checkout until git prunes it. The atom needs Git 2.23, within the Git 2.25 baseline.
3. Recorded head lookup reads all Mission events on every new/QUEUED batch start. The store is unchanged; filtered audit lookup is the documented upgrade.
4. A head somebody moved causes every Task reaching integration to fail three tries within seconds and block with integration_unavailable. Only restoring the recorded ref helps; there is no Mission-level pending item yet (M4-4).
5. A branch left checked out causes a passed regression to be discarded after three tries: the batch is SUPERSEDED and Task blocked. Freeing it before exhaustion resumes promotion without another regression.
6. A PROMOTABLE batch that exhaustion cannot judge stays open with its Task blocked, holding the Mission queue until that Task is unblocked and its request runs again, or the Task is cancelled and a readable-head try can clean it up. Persistent store refusal can likewise prevent recording a known advance.
7. While the repository cannot be read, any open PROMOTABLE batch makes every try of that Mission fail before anything is closed, including a cancelled Mission. Exhaustion itself cannot guarantee writes when the store is unavailable.
8. Block/cancel/pause between the last request check and the ref update does not stop the promotion. When mergeCommit already is the head, none of these changes prevents ref catch-up. No broader pause semantics were added.
9. A Task blocked/cancelled after ref movement stays blocked/cancelled although its change is in the integration branch. A blocked Task becomes INTEGRATED only when its request runs after unblock; nothing arranges that before M4-2b. A cancelled Task stays cancelled. INTEGRATED is final; no un-integration or writer guard was introduced.
10. Running Workers started from the old head and encounter the new head at their own merge. An interrupted Attempt without a preserved snapshot that could have continued in its old worktree from the integration head is launched afresh once the head moves.
11. The Mission remains EXECUTING after its last Task integrates (M4-6). The target branch is untouched; no push, fetch, PR, finalization or delivery is added. V1 does not use AWAITING_APPROVAL; delivery approval is later work.
12. The git ceiling covers only scratch git calls through integration's two helpers, not the repository head read, commit-pin internals, kernel worktree operations or any other git caller. The environment variable does not reach git inside WSL. V1 host behavior is local macOS/Linux.
13. Repair from the merge commit is M4-3; complete recovery, Mission-level environmental handling and orphan sweeps are M4-4; UI exposure is M4-5. Existing kernel creation/removal hooks, optional remote behavior, terminal dependencies, preservation rules and cleanup audit limitations remain.
14. A process killed between the outbox marking an effect failed and onExhausted still needs a later request to run reconciliation. Ref authority prevents abandonment when that reconciliation runs; this Task adds no unconditional boot sweep.
15. The unit fixture calls kernel git functions beneath the full runtime; it does not verify runtime sidebar, terminal provisioning or preserved-branch UI behavior. Mission e2e execution is assigned to the host verifier. No production completion or independent acceptance is claimed by this report.
