## since provenance and limits

| Kind | Persisted evidence / fallback |
|---|---|
| mission | Latest `mission.status` audit matching current status; for ANALYZING, a later Planner launch_failed / attempt_failed / stopped / abandoned audit when another Planner may start. BLOCKED budget uses `budget.exhausted`. Otherwise Mission `updatedAt`. |
| plan_review | Latest `plan.proposed` for that PlanRevision; fallback `provenance.at`. |
| question | Message `createdAt`, including projected kernel question messages. |
| human_review | ACTIVE Candidate latest review run `updatedAt`; fallback Task `updatedAt` if missing. |
| task_blocked | Latest relevant `task.stage`, filtered to entry into BLOCKED when blocked; admission refusal uses that refusal audit; upstream cancellation uses the earliest related canceled upstream evidence after UTC normalization. Unpersisted task budget uses evidence described below. |
| subtask_request / follow_up | Message `createdAt`. |
| stall_notice | Current notification `notifiedAt`; one latest listed row per Attempt if duplicate historical rows exist. Current producer already deduplicates. |
| supervision_proposal | Proposal `createdAt`. |

All SQLite `YYYY-MM-DD HH:MM:SS` strings are interpreted as UTC and normalized with `toISOString()`. No current read time is substituted for an event time. A computed wall-clock exhaustion time is the original EXECUTING start plus the configured limit. Computed attempts use the most recent supporting binding creation time, falling back to the associated status evidence if bindings are absent. Computed token exhaustion uses the most recent current ledger measurement with positive tokens. Mission since is no earlier than the current status / later Planner-ending evidence.

**Named evidence limitation from the brief:** the current token ledger replaces measurements and does not preserve the first cap-crossing instant. Refunded interrupted Attempts retain bindings while changing attemptCount; old bindings may be missing; Task budget edits can change when a cap becomes relevant. Exact first exhaustion time is not generally recoverable from current rows within this read-only task. Unpersisted budget `since` therefore names existing supporting evidence rather than promising the first crossing. Persisted BLOCKED audits remain exact. No new history/table/audit was invented. This ceiling has `ponytail:` comments, as does the deliberate small-DAG reachability approach.

## Questions, Approvals, differences and risks

A bare kernel pending decision gate can exist without a listed message: `db.createGate` records a gate without creating a message. The new real-row test proves the Task waits on question while the pending view creates no invented question item. No Axiom production path under `src/main/axiom` currently creates such a gate. Valid kernel question threads and typed questions are projected through the existing message list, including Planner questions. The bare-gate case is the named exception to the person-item coverage invariant; Approval is the explicit M4 exception.

A blocking Approval can exist as a persisted row today: the store predicate recognizes pending `budget_increase` Approvals, and tests insert real rows as existing scheduler tests do. No current Axiom production path creates those Approvals. This task names the wait and intentionally creates no Approval pending item or new Approval producer.

Explicit differences/interpretations:

1. **Paused/blocked plan review actions:** the brief lists approve/reject unconditionally, while both actual commands require Mission PLAN_REVIEW. To satisfy its broader promise to honor Mission status, a PROPOSED plan still produces a blocking plan_review item but offers no plan calls while PAUSED/BLOCKED. The separate Mission item offers resume/cancel or cancel. This is documented in the Glossary/reference and tested against actual command rejection; it is not silently reconciled.
2. **Budget since evidence ceiling:** described above; exact first exhaustion cannot always be reconstructed without forbidden new history. Persisted stage/block reasons and wall-clock thresholds remain exact.
3. **BLOCKED Mission reason:** the pending item keeps reason `BLOCKED` as the kinds table requires, summary `budget_exhausted` from the status audit, and the explicit Mission budget waitingOn from `budget.exhausted`. ANALYZING/EXECUTING computed exhaustion uses reason `budget_exhausted`.
4. **Supervision text:** current proposal schema has no own text field, so no summary is invented. If duplicate legacy stall audits exist, one latest item is retained per Attempt to preserve the required object-id uniqueness.
5. **Verification environment:** exact wrapper/typecheck and full sidecar success are not claimed where the sandbox or unchanged test expectations prevented them. The direct local compiler results, narrower green suites and host obligations are separately recorded.

Required limitations: a Task matching multiple rows exposes only the first; the scheduler can name another cause because its order differs. Mission status gates only Tasks that have not started. `no_eligible_provider` uses the last refusal audit and may stay stale until a later round; an account cooldown remains the audit-based non-person wait even if wall time has since passed. `provider_concurrency` projects as `next_round`. A BLOCKED Mission item and stalled Attempt notice offer only their respective cancel operation. Actions mirror only the specified Mission status, Task stage and latest-run conditions; each real call still enforces parameters, authority, plan identity, conflicts and races. Every call recomputes the views. Task write scope remains verification-time enforced for CLI workers, per the repository rule; this task makes no write-scope enforcement change.
