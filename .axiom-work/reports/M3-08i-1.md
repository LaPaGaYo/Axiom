## Baseline walk-back rule

Starting at seq−1, an Attempt without a Submission is skipped only when its own
`attempt.failed` audit has `after.settlement.kind === 'unchanged'`; the loop is bounded by
seq 1. A missing binding/dispatch or any other no-Submission failure stops the walk and
returns `previous_attempt_not_submitted`. The first Submission found must still refer to an
ACTIVE Candidate whose latest verification is FAIL and is not `secret_detected`; otherwise
the existing integration-baseline reason applies. `previousSeq` remains that Candidate's
Attempt sequence, while `unchangedAttempts` records skipped `{seq, attemptId, reportSummary}`
in ascending sequence. Launcher worktree creation, mismatch checks and launch audit still
use that Candidate baseline. Unit tests cover one/two skipped exits, superseded/secret
Candidates, walk exhaustion and a normal failed previous Attempt.

## Command boundary and defaults

`validateEvidenceCommands` rejects multiline entries, shell operators (`;`, `&`/`&&`,
`|`/`||`, `>`, `<`, backticks, `$(`), and a first whitespace-delimited token that is not in
the allowed set. A token containing `=` is not a program. Exact names and basenames match;
quoted operators are rejected as shape violations too. Allowed programs are the union of
policy `evidenceCommands.allowedPrograms`, setup-command programs and all gate programs.
Invalid stored policies fall back to parsed default rules at both proposal boundaries.
Verification does not repeat shape validation at execution time.

Final `allowedPrograms` default:

```text
pnpm, npm, npx, yarn, bun, node, pytest, python, python3, go, cargo, make, dotnet, mvn, gradle, ./gradlew
```

Failures return `multiline`, `shell_operator` or `program_not_allowed`. A proposal turns
these into `evidence_command_invalid`, with a one-sentence rule and path
`['tasks', i, 'requiredEvidence', j]`; REQUEST_SUBTASK returns the existing failed-check
shape with `evidence`. Prose arguments following an allowed program intentionally pass.

## Limitations and risks

- An unchanged Attempt still consumes a retry. If allowedPaths cannot contain the required
  fix, the Task can reach BLOCKED(retry_budget_exhausted) until M3-04b's typed outcome exists.
- Arguments after an allowed program may still be prose, including
  `pnpm run verify:full output with exit code 0`. The boundary deliberately does not inspect
  package.json or infer script/argument meaning. Only configured failure-output patterns
  identify invalid plan commands at verification time; other failures keep existing behavior.
- This is a shape/program boundary, not a capability sandbox. Allowed interpreters and build
  tools retain their capabilities; M3-10/DEF-46 owns isolation. Quoted shell metacharacters
  are conservatively rejected as well.
- Policy defaults preserve old policies; an explicitly malformed stored policy falls back
  at proposal validation, while verification retains its existing policy-invalid handling.
- Worker write scope remains verification-time diff enforcement plus provider configuration.
- Host e2e, Node-only CLI execution and full supported-toolchain checks remain unverified
  locally; the broad pre-existing import grep requires verifier interpretation or correction.
