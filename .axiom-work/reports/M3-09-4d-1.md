## Contract calls and limits of prediction

1. `resolveAcceptance(spec)` supplies current page items and the initial draft, including string-as-human and legacy command compatibility. Initial draft rows and counter keys are allocated only in the checkbox handler; new-row keys are allocated only by Add criterion. Polling never replaces those rows. Switching proofs preserves inactive proof fields in the draft; serialization emits only the selected proof fields.
2. The form builds the same prospective spec as the adjustment: existing allowed paths union submitted additions, supplied Attempt/token limits over current values, all other spec fields retained, then the trimmed whole criterion replacement. `TaskAdjustParams.shape.acceptanceCriteria.safeParse(sentRows)` is first. Its own messages cover empty text/command and excess items. No local list bound is named or duplicated.
3. Only after list parsing succeeds, `validateTaskAcceptance(prospectiveSpec, ['task'])` provides list checks, followed by `validateAcceptanceCommands(resolveAcceptance(prospectiveSpec), parsedRules)` when policy exists and `VerificationRulesSchema.safeParse(policy.verificationRules)` succeeds. Each command issue is worded with `evidenceCommandMessage(issue, issue.command)`. Schema paths are relative to the list; contract paths lose only the `task.acceptanceCriteria` prefix to associate errors with the relevant row/field. Field errors use aria-invalid and aria-describedby; list errors follow the list. Any message disables Apply adjustment.
4. The retired-field decision calls `validateTaskAcceptance({ ...spec, acceptanceCriteria: resolveAcceptance(spec) }, ['task'])` and checks only its `required_evidence_retired` answer. It withholds the replacement checkbox but preserves paths/limits/rationale adjustments.
5. Missing policy skips only command checks and explains why. Invalid rules skip only command checks, reuse the plan-card policy_invalid sentence, and explain the Control Plane default-rules behavior. The renderer never supplies its own default rules or decides which programs/operators are permitted.
6. The form does not predict permission, budget, stale-state, queued/running-run or secret refusals. Existing path/limit/rationale behavior is retained. The blocked consequence reads only pending item `kind` and `actions`; no Task stage inference is added.

The runtime refusal envelope's `error.data` becomes read-only `AxiomRpcError.data`. `missionErrorText` imports that class from `axiom-rpc-call` directly, so client mocks cannot hide it. It schema-parses unknown detail and individual entries, ignores non-message entries, deduplicates message strings in first-seen order, then falls back to string reason and original message. A non-code message always wins over data. Non-Axiom failures retain `String(failure)`. `reportError` uses one result for the page alert and toast. Refusal reconciliation does not close the form or change its draft.

## Necessary differences, limitations and risks

- No functional scope differences from the brief. Verification wrappers that require tsx IPC cannot finish in this sandbox; the repository compiler/runner is invoked directly with the worktree toolchain, with that limitation recorded rather than changing build scripts.
- The form predicts with the policy read with the page. Policy can change before the adjustment is applied.
- With rules that do not parse, the Control Plane checks an adjustment against its defaults while a verification run ends `policy_invalid`.
- Renderer command messages use `evidenceCommandMessage` without main-process redaction, so a secret-looking command can produce different local and refusal text.
- `task_not_adjustable` from a queued/running verification run is not predicted; its actual refusal detail is shown.
- A legacy Task with nonempty `requiredEvidence` cannot have its criteria replaced here. This renderer change does not drop that field.
- Criteria and commands are not checked for secrets before storage; the adjustment audit is redacted. The renderer also does not check rationale secrets; the Control Plane retains that check.
- A replacement identical to the current criteria is sent as given, with the specified trimming.
- A review stays open after replacement and may still be resolved without a rerun. The editor does not force rerun or close the review itself.
- The approved plan card keeps the acceptance criteria from approval and now states where to see current Task criteria.
- A draft is not updated when Task criteria change beneath it; a refusal also preserves it.
- Contract error messages are English in every locale.
- The Task page does not list all commands a rerun will execute; its current-criteria region shows each criterion proof.
- CLI agent write scope is enforced by verification-time diff inspection, not a runtime scope sandbox. The final diff and repository pins were inspected; independent verification remains the authority.
