## Limitations and risks

1. Preflight and start are two steps. Two Missions starting on the same target at the same moment can both obtain a branch and base audit before the transactional recheck refuses one. The refused Mission stays `PLANNED`; its branch can be reused later if it remains an ancestor of the target.
2. A Mission suspended twice before it ever started, and a suspended Mission without a `previousStatus`, count as occupying. This intentionally uses the careful answer; it does not replay audit history.
3. Same repository compares stored `repoId` OR stored `repoPath` and exact target strings. It does not resolve aliases, symlinks, case differences or alternate catalog identities.
4. A Mission whose repository left the catalog cannot start; the error is `showRepo`'s.
5. An integration branch failing the ancestry check is left alone. A person must delete that branch or cancel the Mission; no automatic repair is added.
6. `integration_base_unavailable` now means either an inaccessible base/Git operation or a base that is not an ancestor; the message is the only distinction.
7. The pending view still offers Start for a `PLANNED` Mission whose target is occupied. The refusal explains which Mission holds it.
8. A later status for delivered and waiting for the PR merge (D92 d) must join the occupying set.
9. No integration queue, batch, delivery or finalization implementation is supplied here. The two back-edges only admit future transitions. Local-only start validation belongs to the RPC; direct controller use enforces status and occupancy atomically.
