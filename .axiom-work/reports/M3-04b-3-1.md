## Outcome and boundaries

The planner's brief supplied the problem, scope, acceptance criteria and execution unit. Execution followed contract/settlement → resolution/admission → context/CLI/e2e → documentation/verification. The implementation delivers:

- Optional strict typed QUESTION and REQUEST/followUp payloads; new report inputs accept at most 20 items per list and 2,000 characters per item, including the headless JSON Schema. Missing lists default to empty. Existing persisted reports retain their former uncapped read compatibility.
- Transactional routing immediately after `insertSubmission`: the first ten of each list become messages attributed to the submission's sender and related to its Task and Submission. One `submission.items_truncated` audit records omitted counts. Duplicate submission and empty lists create no items. Notifications wait for the existing post-commit SUBMISSION publisher. Declared `no_change`/`blocked` reports continue to produce only their BLOCKED item, retaining questions/follow-ups in its report Artifact.
- Pending derived from existing audit rows. Typed answers are Task-bound, accepted after the asking Attempt settles, limited to 4,000 characters, and stored only in `question.answered.after.answer`. Both kernel and typed answers use the existing `redactContext` scanner and reject secrets without writes. Fresh second answers are refused; exact mutation-receipt retries replay. Follow-up accept/reject records a redacted `followup.resolved` audit and never creates a Task. Existing subtask handling remains delegated to `resolveSubtask`.
- A shared deterministic admission blocker. Answering also wakes admission for an already READY Task; the existing post-write scheduling guard suppresses the wake-up if the surrounding transaction rolls back.
- An always-present eighth mandatory context section, `Answered questions`, for both channels, newest ten answers first and at most 4 KiB including rendered heading/newlines/omission marker. Both authored strings use the existing `quote`; the asking Attempt sequence comes from its binding.
- CLI projections and the additive `--pending-only` alias (existing `--pending` still works). A new 290-second host e2e scenario covers the report-items retry flow, secret rejection, answer context, PASS/VERIFIED, and explicit follow-up rejection. Default fixture reports now have empty lists. Existing pending-count assertions needed no changes.
- Updated `docs/reference/control-plane.md` and `docs/GLOSSARY.md`. No Decision or milestone-plan files changed.

No new table, column, lifecycle stage, automatic answer, Decision Engine use, permission authority, or Worker spawning path was introduced. The kernel and caller-authority classification are unchanged. Runtime RPC changes are confined to the existing Axiom message resolver handler.

## Review and regression correction

An independent, read-only Codex reviewer traced the full flow and found one important issue: applying the fresh-input caps to the old shared read schema made historical reports with 21 questions or a 2,001-character follow-up unreadable. Two regression cases reproduced that failure. `StoredSubmissionReportSchema`, the Submission row codec/response, and the Attempt summary now preserve old reads; the insertion boundary, CLI submit and headless submit still enforce fresh-input caps. The reviewer rechecked the fix and reported no remaining findings, independently passing 5 files / 76 tests. This is a working-tree review, not independent immutable-Candidate acceptance or cross-provider certification.

## Limitations and risks

- A pending report question blocks the next Attempt until a human answers, by design; there is no timeout or automatic answer. Answers to Tasks that never need another Attempt do not disturb VERIFIED/INTEGRATED state.
- The secret scan reuses `redactContext`'s existing patterns and can refuse a legitimate token-like answer. It only recognizes those patterns; no second detector was added.
- Follow-ups never create Tasks by themselves, including on acceptance; the human must separately create the Task.
- At most ten items per list become messages; at most ten answered questions and 4 KiB enter context. Existing `quote` limits each authored string to 500 characters / 1,600 encoded bytes. The report/audit retains the full accepted content and truncation is explicit where specified.
- Existing persisted reports are readable but are not retroactively converted into items. Fresh input caps are enforced independently of read compatibility.
- Runtime CLI write scope remains a verification-time diff check, as documented in the repository. This change adds no runtime scope enforcement.
- Standard pnpm build-dependent checks and broader socket-dependent CLI tests are not established as passing in this sandbox. Host Electron behavior remains unverified until the prescribed host run.
