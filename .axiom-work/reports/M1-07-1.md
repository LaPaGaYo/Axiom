- Send admission runs after local Run / bare-recipient resolution and before synchronous lifecycle settlement or message insertion. `status` and `heartbeat` remain allowed.
- Existing identity, malformed-parameter, and unknown-object validation retains precedence. The guard does not weaken the kernel's existing fences.

## Test construction and no-effects evidence

Every Mission refusal fixture uses the actual MissionController: create → propose frozen 12-Task plan → approve → start. The shared CP factory supplies both the controller and store. To reach admission behind the existing current-consumer checks, test setup deliberately binds the Mission Run to a terminal using the kernel DB API. This models a terminal that has already acquired a binding; it does not give the RPC caller Control Plane authority. Run takeover tests leave the original synthetic Mission session binding intact.

Plain controls use an ordinary terminal-coordinated Run. Terminal/process operations use the existing kernel worker-release harness stubs; handler implementations, routing, dispatcher, mutation envelope parsing, DB writes, and controller logic are real.

Before and after every refused mutation, tests compare complete rows from `missions`, `tasks`, `task_stages`, `dispatch_contexts`, `worker_dispatches`, `runs`, `messages`, `decision_gates`, `mission_task_edges`, and `audit_events`. This checks status, stage, dispatch/message counts, consumer generation, and existing gate content. Kernel mutation receipts are deliberately excluded: recording refusal evidence is normal dispatcher behavior. Tests also check that refused starts send no terminal prompt, refused reset stops no relay, and refused messages issue no notification.

## Limitations and follow-ups

1. **M1 gate remains pending independent verification.** Full-suite listener coverage could not be verified in this sandbox. No Candidate commit was created by this Worker; the launcher owns commit creation, immutable-candidate verification, and integration.
2. **Existing caller checks remain first.** An ordinary terminal targeting a normally session-bound Mission can receive the existing consumer/session fence before admission. Unknown objects retain their existing errors. This follows the brief's requirement to insert after existing resolution, not replace it.
3. **Other mutation entry points are outside §4b.** `orchestration.workerStop`, `workerAbandon`, `workerRelease`, `workerRetain`, and `workerTerminalUserInput` mutate or affect execution resources; `ask` / `reply` mutate question/message state; `runCreate` can unbind the caller's prior Run. They received no guard here. M2's authority audit should decide their Mission policy explicitly before enabling Attempts.
4. **Group-recipient routing deserves a follow-up.** The requested send guard knows the locally resolved message Run. `sendGroupMessage` subsequently resolves individual audience mailboxes; `@worktree:` can span Runs and nested-coordinator routing can select another Run. `worker_done` / `decision_gate` already reject groups at schema parsing, but `merge_ready` / `dispatch` do not. A target-by-target policy at the group-routing boundary is not implemented by this one-call-site task and was not claimed as verified. It would require extending scope beyond the listed handler edits.
5. **Federation remains post-V1.** The early `sendRemoteMessage` branch routes by remote attachment before local Run resolution; federation home-side imports/relay settlement have their own entry points. This change does not claim remote Mission admission coverage. Apply equivalent home-side policy before Mission federation is enabled.
6. **Approval is referenced, not implemented.** The reset refusal points to Mission cancellation and the M4 Approval path; no new approval mechanism or destructive cleanup route was added.
7. Runtime enforcement of Worker filesystem scope remains the repository's known V1 limitation. This Attempt's diff was inspected against the explicit allowlist; the launcher still must independently inspect the final Candidate.

No new product terminology or architectural Decision was needed for the implemented local admission guards. The broader routing/authority questions above are follow-up work, not silently widened implementation scope.
