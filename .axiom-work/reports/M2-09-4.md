# M2-09 / Attempt 4 — Keep planner launch RPCs alive during readiness

Date: 2026-10-20. Branch: `axiom/attempt/M2-09/4`.
Base: `main` at `4c9c826c1cd259752d9f911f756c582fedf5eee2`.

The approved Attempt 4 addendum is the execution plan for this bounded fix.
`axiom.mission.plan` awaits the existing worker-start readiness path, but the
shared long-poll classifier previously returned `null`. Consequently, local
request admission did not start keepalives, and the transport's 30-second idle
timer could close the connection before the launch receipt arrived. The existing
CLI handler already uses a 120-second timeout.

## Changes

- `src/main/runtime/runtime-rpc/runtime-rpc-long-poll.ts`: classify
  `axiom.mission.plan` as `wait` beside `orchestration.workerStart`, with a one-line
  readiness rationale. Long-poll caps, specialized shares, abort wiring, and all
  other classifications are unchanged.
- `src/main/runtime/runtime-rpc/runtime-rpc-long-poll.test.ts`: eight direct
  classifier tests, without Electron. Both launch methods return `wait`;
  `axiom.mission.show` and `axiom.plan.propose` return `null`;
  `orchestration.check` returns `wait` only with `wait: true`, and returns `null`
  with omitted params, empty params, or `wait: false`.
- `docs/reference/control-plane.md`: one sentence in the planner section
  documents local transport keepalives during readiness and the existing CLI
  timeout.
- `.axiom-work/reports/M2-09-4.md`: this report.
