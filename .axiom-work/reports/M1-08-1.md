## Summary and mechanism

- `RecoveryService.recover()` loads non-terminal Missions from SQLite, checks the persisted synthetic session binding with the kernel's `runBoundToCoordinator`, blocks and audits `run_binding_lost` without creating/rebinding a Run, and calls the existing DB-derived readiness calculation. Its tested `reconcileAttempts()` hook returns `no_attempts_in_m1`.
- `RunMailboxConsumer` registers an exclusive kernel waiter before reading backlog, drains whole deliveries, applies a synchronous transactional M1 handler, and acknowledges only after the handler succeeds. The M1 effect is `mailbox.message`, attributed to MissionController and keyed by message id. Check-and-insert runs under the store's write transaction; a replay reads durable audit evidence and does not duplicate effects. Readiness is recomputed once per handled batch.
- Each consumer captures only its Mission/Run/generation identity and cancellation lifecycle, plus injected service references. It does not retain Mission/Task state, a message cursor, readiness, seen-message ids, or pending deliveries. The batch-local dedupe set is reconstructed from SQLite. The persisted `runs.consumer_generation` is read when starting a new consumer and is then deliberately held fixed: rereading it on every drain would let a fenced process adopt replacement authority. The first delivery read and every acknowledgement use the kernel fence.
- `consumer_fenced` logs a classified failure, stops, blocks the Mission with that reason, and appends `mailbox.consumer_fenced`; it never takes over/recreates the Run. Other handler errors leave the batch unacknowledged, log identifiers and the failure class without arbitrary message/exception content, then retry after 250 ms using the existing waiter timeout. No new timer/clock abstraction was needed.
- `getAxiomControlPlane(runtime)` remains the single per-database accessor and now owns `recovery`, the consumer cancellation registry, and lifecycle wiring. The DB-only `MissionController` source remains unchanged. Once boot is active, create/start/resume/unblock synchronize consumers; pause/block/cancel stop them. A resumed Mission has its binding checked before a new consumer is admitted. Controller-only access before boot remains DB-only; boot scans all persisted Missions. Old-loop completion cannot remove a rapid pause/resume replacement.
- Desktop `configureRuntimeServices` and headless runtime construction each call `startAxiomControlPlane`; the existing quit mechanisms call `stopAxiomControlPlane`. Second start is a no-op, stop cancels waiters immediately, and a later start recovers anew. Consumers start for the four statuses explicitly named in the brief: ANALYZING, PLAN_REVIEW, PLANNED, EXECUTING.

```text
start → register exclusive waiter → drain → handle batch → ack → drain
             │                        │                        │
             └ waiter_exists → stop   └ empty → wait ──────────┘
                                              notified/timeout → register → drain
handler error → no ack → 250 ms waiter backoff → register → replay
consumer_fenced → log + audit + Mission BLOCKED → stop
stop/pause/block/cancel/quit → abort waiter → stop
```

Recovery report shape:

```ts
{
  missions: Array<{ id: string; status: MissionStatus; moved: string[] }>;
  blocked: Array<{ id: string; reason: 'run_binding_lost' }>;
}
```

`moved` contains Task ids newly made READY. The `missions` array includes valid PAUSED/BLOCKED Missions with no readiness moves; terminal Missions are omitted. `blocked` lists lost-binding findings, not every pre-existing manual block. Repeating recovery of an unchanged lost binding does not duplicate its audit. Generation is authoritative in `runs`, not a new Mission column.

## Authority clarifications

The M1 plan's mailbox conclusion says drain before registering a waiter, while this explicit task requires registration before checking backlog. Followed the task's higher-authority ordering, informed the user, and documented it in the mapping row. This prevents a wake-up from being lost between backlog inspection and subscription. The returned exclusive `waiter_exists` result is checked before any drain/effect.

## Limitations, risks and follow-ups

- M1 default handling records receipt evidence only. M2 must validate and route real message types, perform Attempt reconciliation against execution-host truth, and define bounded retry/escalation/backoff policy. The current 250 ms retry and audit-history scan are explicitly marked `ponytail:` with upgrade paths. There is no new background interval; recovery runs at startup and on demand, and consumer long polling uses the kernel timeout.
- `exclusive: true` is process-local waiter ownership, not a cross-process leader lease. The persisted generation fences displaced consumers; transactionally deduplicated message effects tolerate replay. Broader multi-process leadership remains outside M1, as identified by M1-01.
- Current lifecycle wiring starts the exact four M1 statuses named by the task. Additional lifecycle states and real message handlers must be wired when later milestones introduce those execution flows.
- Errors are logged by identity and classification, not raw message/exception content. Binding-loss recovery never repairs or creates Runs automatically. An operator must resolve the persisted binding issue before a successful resume/unblock can consume mail.
- Runtime write-scope enforcement for CLI Workers is a known V1 limitation; this Attempt used verification-time diff inspection and preserved the whitelist. The prepared daemon fixture patch remains unapplied pending a scoped exception.
- Required full-suite acceptance remains blocked by host limitations and the fixture correction. Focused evidence supports M1 exit criterion 1's mechanism; milestone-level acceptance, Candidate snapshot, independent audit, and integration remain the launcher's responsibilities.
