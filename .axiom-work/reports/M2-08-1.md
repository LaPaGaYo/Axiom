## Scope-blocked kernel behavior — exact locations

`src/main/runtime/orchestration/db/worker-dispatch/worker-dispatch-stop.ts:74` only permits `ready`, `start_unknown`, or a stranded `stopping` row in `beginWorkerStop`. A second local stop after the first close returned an unconfirmed outcome fails with `dispatch_inactive: cannot stop from stop_unknown`. Merely widening this guard is insufficient: `src/main/runtime/orchestration/db/lifecycle-transition.ts:92` permits stop_unknown → failed/stopped/abandoned, but not stop_unknown → stopping, and `settleWorkerStop` also currently requires stopping (`worker-dispatch-stop.ts:119`). Neither file is authorized for this Task; the local seam was extracted without changing these semantics.

The failing test is `attempt-reconciliation.test.ts` → **“retries cancellation of a stop_unknown worker when the host is live again (kernel scope gap)”**. First close yields stop_unknown; the next tick sees exact live; expected stopped, actual stop_unknown. This also limits runtime-budget stop retries while the host continues to report live and restarted stopping rows normalized to stop_unknown. A current-runtime starting/stop operation must first reach a kernel-supported receipt; recovery does not fabricate one. Unreachable stop_unknown workers can be abandoned normally (immediately for cancel, after tolerance with evidence for a RUNNING Task).

Resolution needs a separate authorized kernel change to retry stop_unknown while preserving process identity, ownership, dedupe, and host-confirmed exit. No new enum is proposed. This report does not reinterpret the red test as a pass or silently abandon a known-live worker to hide the gap.
