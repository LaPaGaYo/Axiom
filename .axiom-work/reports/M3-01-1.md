## Outcome and scope

Submissions now trigger a deterministic VerificationService after settlement commits. It atomically claims the oldest eligible QUEUED run, moves its Task to VERIFYING, prepares a separate runtime-managed worktree detached at the immutable Candidate commit, verifies commit/tree/ref identity, and records a content-addressed evidence Artifact. A prepared run remains RUNNING; no checks or PASS/FAIL verdict are produced by this skeleton.

Schema v45 adds the five durable ownership/timing columns. Shared schemas, the row codec, CAS/update/filter stores, read-only `axiom.verification.show/list` RPC methods, generated params catalog, CLI registration and formatters are implemented. The `not_found` orchestration code is now allowed through the runtime error mapper, with tests; no existing run-specific error accurately represented a missing VerificationRun or Candidate.

VerificationService owns boot recovery after Mission recovery and before the first kick. It removes each recorded stale worktree, requeues the run, and sweeps runtime-listed orphan `axiom/verify/` worktrees. It never scans the filesystem or touches an Attempt worktree. Force removal is restricted to recorded IDs; unrecorded runtime-listed orphans use non-force removal. The existing 60-second reconciliation closure also kicks verification; no additional timer or queue table was added.

## Implementation and review decisions

- **Restart clarification:** Task stage remains VERIFYING across requeue. A QUEUED run may resume that stage only when its persisted phase is `requeued`, reason is `restart`, and claimCount > 0. Fresh claims still require SUBMITTED; other stage changes cancel the queued run. This is necessary to satisfy the required restart/reclaim flow without an illegal backward Task transition, and is recorded in the Glossary and reference. An optional clarification was raised; no response was required to follow the explicit restart outcome.
- Worktree creation uses the Attempt binding's branch as the starting point, every requested no-setup/no-terminal flag, and Mission/Task lineage. Its returned ID is persisted before Git detaches HEAD, so a crash after detachment remains recoverable even if runtime listings no longer show the branch. Creation-to-ID-persistence orphans remain discoverable by their verification branch prefix.
- Preparation suppresses checkout hooks, uses existing Git execution/options/path helpers, and checks HEAD, HEAD^{tree}, verification ref and detached status. The Attempt branch may have advanced; the real-Git test proves the verification checkout still pins the older immutable Candidate.
- Preparation failure records INCONCLUSIVE/prepare_failed with bounded diagnostic text and leaves the Task VERIFYING. Failed cleanup retains its worktree ID and `cleanupPending`; boot retries it. Unknown cleanup failures stop boot before queue draining rather than claiming successful removal. Old evidence and audits remain.
- Epoch/claim/status fences reject stale asynchronous preparation outcomes. Concurrent claimNext calls claim once; kicks coalesce across the whole plane and drain serially. A regression test pins a kick arriving at the end of an empty drain. Another pins stop/restart during asynchronous boot; a boot generation prevents obsolete continuations from installing a second timer.
- Automatic claiming exposed a pre-existing retention assumption: Recovery checked only Task stage SUBMITTED. It now keys retention to the durable Submission, so a Task already VERIFYING still retains its settled Attempt resource. The regression passes, including file-DB restart recovery.
- RPC reads join actual Candidate hashes and fail on missing Candidate/run. The methods remain outside AXIOM_MUTATION_METHODS. CLI flags, handler groups, startup names, parity, params generation, text format and JSON paths are covered.
- E2E edits retain immutable Candidate/rejection assertions, wait for prepared runs before snapshots, check the detached checkout and verification ref, and assert restart claim/epoch/worktree changes and the five-event audit sequence. The fixture restart option preserves the default launch path and reapplies agent command overrides. `mission-attempt-launch.spec.ts` is unchanged.
