## Implementation and transaction audit

The stored enum is `StoredArtifactKind`; `ArtifactKind` stays seven values. Artifact metadata and list filters accept `completion_report`, while put parameters explicitly retain `ArtifactKind`. Only the checked-artifact type/import changed in worker-artifacts.ts.

The strict version-1 contract uses an integrated/non-integrated Task union. Every fixed-shape object is strict, including nested provenance, risk, question, check, resolution and evidence objects. toolVersions is intentionally a string-keyed dictionary. The report gate requires eight items; legacy finalization records may contain exactly the ordered first seven. Ready records accept both report fields or neither; stopped records reject either field. Canonical text comes only from `completionReportText`: parsed schema order, two spaces, one trailing newline, encoded by the executor as UTF-8.

`buildCompletionReport` and `completionReportTask` synchronously read existing store/kernel readers. They do no I/O outside those readers. No SQL, migration, clock, random generation, model or new effect was added to production code. Missing required integrated evidence or an AgentSpec fails construction rather than inventing evidence.

On a passing gate the executor writes the report through the injected ArtifactStore. `recordFinalization` rechecks the same FINALIZING entry and recorded head inside the existing write transaction, validates artifact identity/kind/Mission/hash, rebuilds the report and compares its SHA-256. A changed fact throws before any finalization audit or readiness transition. A changed recorded head instead uses the existing stopped outcome and explicitly omits report fields. The initial gate and build are synchronous with no intervening await; put is the only new await. No transaction spans file I/O. Replaying after storage reuses the deterministic artifact id. Stopped gate evaluations do not store a report. Outbox attempts/backoffs/exhaustion remain the existing three attempts.
