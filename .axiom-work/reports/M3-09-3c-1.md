## Reads, state and authority

`readSupervision` is the only non-test call site of `axiomClient.showSupervision` in the missions folder. `readMission` invokes it immediately with the selected Mission id, before awaiting any other read. Both manual and timed refreshes use that path. A refusal, transport rejection or synchronous exception returns null. Only the Supervision region renders the failure note, without alert/status roles or controls; the Mission, pending view and Tasks remain intact. Missing optional Mission fields are also treated as unavailable rather than derived in the renderer. The pending view still has exactly one call site.

Facts always reflect the latest completed page read. Mutation responses are discarded as display state. Forms hold only an unsaved choice; a quiet tick updates facts without replacing the form, moving focus or marking the grid busy. Mutation success closes the form after reconciliation; refusals keep the choice and use the existing `code: message` error/toast path. A declined confirmation sends nothing. The controller's public refresh ignores its argument and returns the underlying manual read promise; the interval continues to depend on the hook's original function.

The proposal answer predicate is exactly: pending read succeeded, an item has `kind=supervision_proposal`, `objectId=proposal.id`, and its `actions` includes `axiom.supervision.resolve`. There is no renderer threshold or additional inferred eligibility policy. Terminal Missions have no such pending item. Mission-specific editing uses the contract's `TERMINAL_MISSION_STATUSES`; global editing remains available. Only `OPEN` proposals are displayed.

## Differences and limitations

1. **Toolchain entry point:** the installed Node 24/corepack path is selected explicitly because the shell's initial pnpm launcher cannot run the configured executable. No dependency repair or installation was attempted.
2. **Sandbox verification:** pnpm's typecheck/test wrappers cannot pass `build:packages` because tsx's IPC listener is denied. The same compiler/test runners were exercised directly with existing dependencies. The Bun sidecar's host-helper failures remain reported, not waived. Host checks are required before acceptance.
3. **Baseline identity:** this supplied branch starts at main `00e609e136`, newer than the brief's ground-truth snapshot `f79a8db171`; the wiring red test uses the actual main versions, as requested. No product or scope deviation was needed.
4. **Confirmation result:** `confirmAction` remains unchanged for current callers. A small action adapter observes whether its callback ran and whether mutate accepted it; this closes a form only after acceptance/reconciliation.
5. No test drives a real proposal end to end. Unit views are parsed with the contract schema; the Electron fixture has no proposal. Real proposal generation remains M3-10.
6. The default and proposals are global: changing or answering them from one Mission affects every Mission without its own setting.
7. Supervision and pending are separate reads and can disagree until another read. Pending actions determine displayed answers; the Control Plane may still refuse a stale action, and its refusal is preserved.
8. A terminal Mission cannot answer a proposal. With no open Mission, no Mission page can answer it.
9. A new mode applies from the next supervision pass, not retroactively to an Attempt already stopped.
10. A stop the host cannot confirm preserves no work and settles nothing; the confirmation only hints at this with “Once the stop is confirmed”.
11. The stall rule covers headless Workers only. The stall threshold is neither shown nor editable. Proposal thresholds, progress toward a proposal and the evidence table outside proposals are not shown.
12. Resolved proposals and proposal times are not shown; database timestamp strings are not parsed or formatted. Existing pending stall notices remain in Mission Home.
13. The away summary remains deferred behind M4 with the conversation shell. No settings page or CLI was added.
