## Failed-pin audit and e2e evidence

A failed pin appends the following row inside `axiom_submit`, after the Candidate insert and before `attempt.submitted`:

| Field | Value/source |
|---|---|
| `sequence` | Allocated by the existing audit store. |
| `missionId` | Newly inserted Candidate’s Mission id. |
| `actor` | `AttemptSettlement`. |
| `objectKind` | `candidate`. |
| `objectId` | Newly inserted Candidate’s id, computed once as `cand_` + sha256 of `<taskId>:<commitSha>`. |
| `event` | `candidate.pin_failed`. |
| `before` | `null`. |
| `after` | Exactly `{ ref, reason }`; `ref` is `refs/axiom/candidates/<candidateId>` and `reason` is `ref_conflict` or `unavailable`. No git output/error text. |
| `createdAt` | Existing audit-store database timestamp default. |

Success writes nothing. `ref_conflict` means an exact existing ref points to another valid object id; unavailable covers invalid namespace/path/id, missing directory, git failure/timeout, absent ref, failed readback and malformed object id. A same-commit existing ref is success. Both write and readback have an explicit 30-second timeout; the hook directory is removed in `finally`.

The e2e assertion reads `git -C <clone> for-each-ref --format=%(objectname) refs/axiom/candidates/<candidate.id>` and compares the returned oid with `candidate.commitSha`. Both `candidate.id` and `candidate.commitSha` come from the inspection helper’s `settled.candidates`, selected by the submission’s Attempt binding. The ref is read from the actual Mission repository clone. An absent ref prints nothing, so old settlement code fails at the new `expect`, rather than in the git helper. The existing replay comparison still includes every ref of the clone.

## Differences and limitations

- No deliverable or scope deviation. `recordCandidatePin` takes the inserted Candidate’s `{ missionId, id }` projection instead of constructing the suggested `{ missionId, candidateId }` argument. This permits a single-line wiring call within the file budget; the persisted audit’s `objectId` remains the candidate id.
- Two additional pin-boundary tests explicitly cover failed/malformed readback, descendant matching, timeout arguments and cleanup. The required fourteen titles are unchanged.
- Authorized direct compiler/test stages replace wrappers only because their package-build socket is denied in the sandbox. Host wrapper and Electron verification remains the verifier’s responsibility.
- A pin whose submission is later refused (`stale_dispatch`, `candidate_unchanged`, rejected/finalized report) stays behind as a ref that is not a Candidate. No compensating ref deletion occurs.
- Candidates submitted before this Task have no pin until M4-1b pins before merging.
- Nothing removes a pin, neither at supersession nor when a Mission ends.
- A failed pin is visible only in the audit; nothing retries it before M4-1b.
- A submission refused after its pin failed leaves no failed-pin audit: insertion never occurs or the caller’s transaction rolls it back.
- The pin protects the commit from `git gc`, not from a person deleting the ref.
- The store accepts any well-formed batch for any Mission/candidate id. Existence and same-Mission ownership checks belong to the caller.
- The store does not prevent two open batches for one Mission; serial admission/order belongs to the executor.
- `AWAITING_APPROVAL` and `REJECTED` are retained in the contract and unused in V1.
- CLI Worker write scope remains verification-time diff inspection, as in the brief; no runtime permission mechanism was added.
