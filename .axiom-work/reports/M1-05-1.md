## Commands and transitions

Every mutation enters one `runLifecycleWriteTransaction` from the class and rereads state inside that transaction. Store operations that own a transaction compose as savepoints. Any thrown error, including an audit error or stale CAS, rolls the command back.

| Command | State transition / result |
|---|---|
| `createMission` | Mint and validate a new `axiom-mission-<uuid v4>` session; reject reuse of a persisted Mission identity; create Run with null handle/pane; Mission DRAFT, Goal revision 1 ACTIVE, policy, then DRAFT → ANALYZING. Audit: `mission.created`, `goal.activated`, `mission.status`. |
| `getMission`, `listMissions` | Store projections with active Goal/Plan ids, previous status, and all zero-filled `countTaskStages`; list filters are the store's repoId/status/cursor/limit. |
| `proposePlan` | Validate `{ ...planRevision, provenance }`, require the Mission's ACTIVE Goal, insert PROPOSED revision, ANALYZING → PLAN_REVIEW. Pending proposal → `plan_pending`; invalid DAG/schema → `plan_invalid` with errors. |
| `approvePlan` | PROPOSED → APPROVED; set active plan id; materialize in deterministic validator order; create Orca Tasks with `deps: []`, no creator lineage, and task_stages DEFINED; map all edges to Orca ids; PLAN_REVIEW → PLANNED. Audit approval, each Task, materialized graph, and Mission status. Existing APPROVED revision → `replan_not_supported` (M5 upgrade comment). |
| `rejectPlan` | PROPOSED → REJECTED with persisted reason; PLAN_REVIEW → ANALYZING. |
| `startExecution` | PLANNED → EXECUTING, then readiness in the same transaction. A second controller starting the already-started Mission gets `stale_state`, without duplicate audit or transitions. |
| `pauseMission`, `blockMission` | Legal nonterminal state → PAUSED/BLOCKED, saving the exact previous status and reason. |
| `resumeMission`, `unblockMission` | Restore exactly the persisted previous status. Nested pause/block restoration reconstructs the remaining interruption stack from durable status audits; restart loses no return state. |
| `cancelMission` | Legal nonterminal Mission → CANCELED, all nonterminal Tasks → CANCELED in the same transaction; INTEGRATED/CANCELED Tasks and Run survive. |
| `transitionTaskStage` | Enforce the shared legality table; BLOCKED returns only to previousStage or CANCELED; save/clear previousStage; CAS then audit. DEFINED → READY also checks readiness, so the generic API cannot bypass it. Other stage transitions are the trusted M2–M4 service seam. |
| `cancelTask` | Delegate to generic CANCELED transition with the caller's actor and rationale. |
| `recomputeReadiness` | EXECUTING Mission only; visit DEFINED Tasks in Orca task-id order; require APPROVED Plan, every upstream threshold, no blocking hook result, Task retry allowance, and Mission attempt allowance. Return only changed ids; never demote; repeated call adds no audit. |
| `listTasks` | Join stage records to `db.getTask` without SQL outside the store; return taskId, missionId, planRevisionId, stage, previousStage, spec, retryPolicy, attemptCount, updatedAt, Orca status, and title. Missing/mismatched kernel rows fail closed. |

The closed `MissionControllerError` code list is exported from `mission-controller.ts` for M1-06. Domain errors carry object ids, transition context, or validation errors. Shared schemas/store codecs still perform their own input/row validation.

## Proposal persistence and policy defaults

The unreleased v43 `plan_revisions` table gains `proposal TEXT NOT NULL DEFAULT '{}'`. AxiomStore writes validated `{ tasks, edges }` into this column, preserving original proposal Task ids. Existing milestones, risks, Goal reference, revision provenance, rejection reason, and status remain in their existing columns. `PlanRevisionSchema` and the row codec expose tasks and edges on read. Approval validates the stored proposal again and uses its topological order; the transient proposal-id → Orca-id map is needed only within that atomic materialization transaction. The materialized spec keeps its proposal id, while task_stages.task_id and both edge endpoints use Orca ids. A file-database test closes after proposal and approves with a new controller after reopen.

Defaults are defined once in `mission-lifecycle.ts` as `DEFAULT_MISSION_POLICY`: concurrencyLimit 3; budget `{}`; readinessThreshold `INTEGRATED`; approvalRules `{}`; verificationRules `{}`; nestedWorkerMaxDepth 1; unverifiableToleranceMinutes 30. The policy parser validates partial overrides and produces the persisted policy. Per-edge defaults remain the shared TaskEdge schema's INTEGRATED threshold. VERIFIED edges also accept INTEGRATION_READY and INTEGRATED. Mission maxAttempts compares against the sum of attempt_count across all Mission Tasks, including non-DEFINED Tasks; concurrency does not limit which Tasks become READY.

The injected `now` is recorded as each audit's createdAt; the store accepts an optional timestamp while retaining its existing SQLite default for other callers. Audit snapshots serialize optional undefined fields as absent JSON fields. Every audit has actor/objectKind/objectId/event/before/after. The full ordered 24-event create/propose/approve/start path is asserted, including timestamp, actor, object ids and before/after payloads.

## Limitations and follow-ups

- **M1-06:** Register RPC/CLI entry points, map the closed controller error codes and schema errors, enforce the orchestration contract fence, and apply request-id receipts. These commands intentionally report stale transitions rather than themselves implementing successful request replay. Resolve authenticated actors at the boundary; current no-actor Mission commands use `MissionController` in audit. The Task projection uses `taskId` and nullable previousStage; adapt the RPC list-item envelope as needed.
- **M1-07:** Guard direct Orca taskUpdate/workerStart/dispatch/reset and other Mission-managed entry points. This service does not protect those upstream paths itself.
- **M1-08:** Consume the persisted Run mailbox with generation fencing, drive readiness after relevant events, drain backlog on restart, and retain the synthetic id/Run binding. Generic stage mutation does not recursively recompute dependencies; startExecution explicitly recomputes atomically, and other callers can request recomputation.
- **M2:** Implement Attempt admission/launch, retry accounting, concurrency/provider limits, other budget dimensions, auto-start policy, and real blocking Question/Approval lookup. The explicit blocking hook currently returns `none`; the cancellation Attempt-stop hook is an explicit no-op because M1 cannot launch Attempts. Replace both before live Attempt execution. CLI Worker write-scope enforcement remains verification-time diff inspection plus best-effort provider configuration, not runtime isolation.
- **M3/M4/M5:** The generic Task API enforces transition legality/CAS and initial readiness, not later verification/promotion evidence or caller authority. VerificationService and IntegrationController own those checks. FIX_TASK/minor Task creation and Goal changes are not implemented here. Second approved-plan replacement remains blocked until M5 supplies inherit/cancel/rebind.
- M1 readiness checks small graphs per Task (quadratic reads when a Mission attempt cap is configured); the `ponytail:` comment identifies batching within M2 admission as the upgrade path. Nested pause/block restoration is linear in durable status-audit history; its `ponytail:` comment points to an M5 persisted-stack optimization if needed. Neither behavior relies on state remembered across controller instances.
- The proposal column was added directly to unreleased v43 as explicitly authorized. This is not an upgrade migration for preexisting released v43 databases. No existing Orca CHECK enum or schema version was altered.
- No outstanding implementation blocker. The 20-versus-15 fixture edge discrepancy is called out above for the independent verifier. This report and tests are Worker evidence, not a self-issued VERIFIED/INTEGRATED state or M1 milestone completion decision.
