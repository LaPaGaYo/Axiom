The exit path cannot newly claim a stopped worker; an exit call already doing IO still has its final authority check. A kernel receipt can also change. | Reread rejects this branch. No `kernel_stopped` or `attempt.preserved` from it. Reconciliation starts from the top and follows current cancellation/release/ending rules. A normal replay after settlement adds no duplicate stopped row. |
| c / observed exit | The watcher can receive a late exit marker and submit or settle an exit failure while recovery captures. A direct already-authorized Submission can win; cancellation or a new kernel ending can also win. | A winning Submission owns its own Submission/Candidate/audits and recovery releases it, with no recovery failed/preserved/stopped row. A winning exit failure owns its atomic failed+preserved pair, and recovery follows release. Cancellation produces only its own cancellation path; a kernel stop instead reruns b and writes only that branch's stopped+preserved pair. |
| d / confirmed stop | Cancellation can commit while Git/Artifact IO awaits; another current-state disposition or worker-state change can also fence the branch. Once stopping began, the exit path cannot acquire new settlement authority; an already-started exit operation must recheck authority before commit. | No stale runtime-budget stopped/preserved row when authority changed. Cancellation writes its normal `mission_canceled` cleanup receipt if applicable. A crash after stop/publication but before the transaction leaves worker stopped and Task RUNNING; the next b pass adopts the existing ref and records `kernel_stopped`, preserved, and the original `attempt_stopped` settlement. |

The cancellation tests see no preservation audit in b/c/d and no extra budget/kernel stop audit. In the mocked stopped b/d fixtures, the cancellation path itself emits `attempt.stopped {reason: mission_canceled}`; the exited c fixture emits none. Published immutable refs and unattached Artifacts can remain after a losing capture; they do not by themselves authorize continuation. A simulated failure writing the preservation audit rolls back the ending audit, kernel transition and Task settlement in the same transaction.

`RecoveryService.reconcileAttempts` remains serial; one capture delays later bindings in that pass. There is no added timer or retry loop and no new global deadline. Explicit preservation Git operations use the existing 30,000 ms per-command timeout. Existing `assertAttemptBranch` and `readCandidateDiff` calls use the Git runner's default 120,000 ms; filesystem/Artifact IO and Git admission queueing also contribute. A normal new-ref capture can execute roughly eleven 30-second commands plus seven default-timeout calls, so this is **not a 30-second total bound** (the sum of those per-command allowances alone is roughly 19.5 minutes if every command succeeds near its limit). A publication race adds its existing-winner reads. Timeout/failure results are best effort, not a reason to retry settlement; there is no strict whole-capture wall-clock cap in the inherited routine. The single-flight loser waits for that same capture, not a second capture.

## Necessary differences

- The actual assigned base is `b1a887a45a6b06184fe3e831a9b84d9a90dbbcde`, newer than the brief's verifier ground-truth `ca87240f36`; this work did not rewrite that base.
- To make missing/unreadable launch recovery possible, the initial exit attempt must distinguish launch-data errors from valid-exit IO/transaction failures. The shared helper tags and rethrows the same error object; recovery catches only that tag. This is narrower than treating every exit exception as an ordinary recovery ending.
- Same-host concurrent captures share one pending Promise in addition to rereading a failed publication winner, because a matching winner may still hold Git's lock before the ref exists. This is within deliverable 5, with no timer or second capture.
- The existing fixture Task customization was extracted to keep `axiom-fixture-mission.ts` below its line limit. The new option is `taskRuntimeMinutes`; it writes the existing `TaskSpec.budget.maxRuntimeMinutes` field, not a Policy key.
- The `pnpm` build wrappers cannot create their tsx IPC listener in this sandbox. Direct underlying compiler/Bun-runner commands and exact Node CI were run with the installed worktree toolchain. No wrapper pass is claimed. The broad Bun suite also needs host rerun as described above.
- No required source pin was broken. No exception was taken for protected tests, kernel code, providers, scope, secret checks or destructive behavior.

## Limits and risks retained

- Kernel `abandoned` (including a restart that also lost the daemon), kernel `failed`, and tolerance abandonment after an unconfirmed stop are not preserved and are not reclassified. `stop_unknown` continues to use the existing tolerance path even if later host observation says exited.
- The stop gives the harness no confirmed chance to finish. Preservation sees whatever was on disk when the terminal closed, which can be half-written. There is no added grace phase; M3-06-3 owns any change to stop behavior.
- Descendants that escaped the terminal's process tree may still write after a stop was confirmed. This Task does not add a new process-tree authority or quiescence guarantee.
- `baselineSha` still comes from the Worker-writable launch record, just as on the exit path. Worker-edited events are records/data, not instructions or host authority. Missing/malformed/mismatched launch cannot produce a recovery preservation audit.
- A reconcile pass waits for capture; there is no whole-capture deadline beyond the inherited per-command timeouts and IO behavior detailed above.
- Preserved refs are never deleted or expired. Losing captures can leave an unreferenced Git object, an immutable published ref, or an unattached Artifact; none is a Candidate or proof of verification. A secret finding prevents inheritance but does not erase the preserved ref.
- Scope enforcement remains verification-time diff inspection. Continuation requires current allowedPaths and no captured secret finding, and the eventual Candidate includes inherited work for ordinary verification.
- No harness session resumption, Windows/WSL support, supervisor policy, cleanup/retention policy or real-provider graceful-shutdown guarantee is added.
- Electron acceptance is unrun here. The host verifier must run `mission-budget-stop-continuation`, `mission-preserved-continuation`, `mission-interrupted-continuation`, `mission-exit-m2`, `mission-headless-worker`, and `mission-account-cooldown` with background launch, then decide Task/milestone completion from those results and the remaining required gates.
