## Limits and clarifications

- Only the latest batch is exposed. Once the same Task has a newer batch, its earlier conflict or failed regression is no longer visible through this field; latest may have any status, with or without a merge commit.
- recordedHead is the Control Plane record used by batch-start validation. It can lag briefly after ref promotion and does not notice a manually moved branch. No record or an invalid latest relevant value means the Mission field is absent.
- Mission list and all Mission/Task mutation responses carry no integration. The optional shared contracts allow old main processes and old clients to continue working. CLI --json gains the keys; fixed table columns do not change.
- The integration projection adds one Mission batch list and one Mission candidate list per Task list/show request, not per Task. Clarification of the brief cost shorthand: createWaitingContext already lists candidates for waitingOn; that existing read remains, so the whole request performs two candidate lists. Changing waiting-context.ts is explicitly out of scope. Mission show reads the Mission audit history a second time after missionSummary.
- Conflict answers carry the stored, redacted paths (up to 200; exactly 200 can mean truncation) to every caller authorized to read that Task. No new per-path permission filter is added.
- A stored batch or candidate row that does not parse fails the Task read. The candidate reader already had this behavior through waiting context; the new batch read adds another failure source. The new module catches nothing.
- The reader does not execute Git. Its branch name comes from integrationHeadRef; the head and batch fields come from durable records. Regression details remain behind axiom.verification.list with batchId.
- Nothing renders the fields yet. Interface work is M4-5b.
- No functional deviation from the brief. Additional checks inside title 5 cover invalid records, event filtering and lookup errors without changing the six titles. Independent review was not delegated or invoked; no other model CLI/service was used.
- git add --intent-to-add succeeded for the two new TypeScript files, then the report registration was refused with index.lock: Operation not permitted. Scope/pin checks therefore use a temporary index and object directory under the OS temp directory, with GIT_ALTERNATE_OBJECT_DIRECTORIES pointing to the repository objects. The three new files are registered in that index. These variables are never passed to a test run. The launcher remains responsible for the commit.
