The approved brief supplies the product problem, scope, acceptance criteria and verification path for this M3 execution unit, after M3-09-1 and before M3-09-2b. The existing assigned branch and this worktree's dependencies were used. No external model, model CLI or reviewer was invoked.

The Task page now shows the Control Plane wait, Attempt tokens, and the Task's verification history before the existing Worker submission and messages. The latest run is selected initially. A run displays checks, exact commands, acceptance proofs, diff findings, original check outcome, any human resolution or rerun, tools and evidence references. Excerpts are fetched only when opened. The read-only evidence presentation uses existing primitives and status tokens. Human/Worker text stays React text, including strings resembling markup. Verification can report an original INCONCLUSIVE outcome alongside a current PASS resolved by a person without relabeling any original check or criterion.

## Differences, limits and handoff

Necessary differences from assumptions or requested check execution:

1. The actual verdict writer can emit an `environmental` check result. The tolerant reader preserves this existing result as neutral text rather than discarding the check. This adds no writer behavior or verdict derivation.
2. The actual `pt.json` had no root `missions` namespace at this base. The 90 required new keys were added there without expanding scope into translating old missing keys. All seven catalogs contain the new keys; catalog, extraction and coverage verification pass.
3. Success/warning styling belongs to the stage/status label inside the existing Button primitive. The changed-line design gate rejects recoloring the Button itself; the control still has `data-task-stage`, keyboard behavior, visible status text and one-click evidence focus.
