## Rendered behavior

`MissionIntegration` renders nothing when there is neither a Mission integration record nor a Task batch. With a Mission record it shows the branch, the first seven head characters and the full recorded commit in the title. With no Task batch it retains the block and shows “No Task has reached integration yet.” Otherwise it shows only Tasks with a latest batch, in Task-list order: title, status gloss and monospace Control Plane status, conflict count when nonzero, merge commit or an em dash, and the recorded update time. Rows select the Task by click, Enter and Space, expose selection through aria-selected and carry integration-specific attributes. It also renders batch rows without a Mission record. All batch status presentation uses neutral existing tokens.

`TaskRegression` renders nothing without a Task batch. Otherwise it shows the status gloss and raw word, base and merge commits with full titles, and all stored conflict paths, retaining duplicate redacted names by position. Exactly 200 paths produces the qualified “there may be more” sentence. A regression-read failure shows only its local failure sentence in place of runs; an empty or fully filtered result shows the no-run sentence. Matching runs appear in reverse creation order, with their status, reason, start time and duration; only the newest run supplies Regression checks. Existing `VerificationChecks` / `CheckOutput` render commands, results, failures and expandable evidence excerpts. The checks subtree is keyed by run id and update time so a refreshed/new run cannot retain an old output excerpt. This section has no action or request of its own.

The regression is the last child inside `VerificationRecord` in its success, no-candidate-run and failed-candidate-read branches. The existing Integrated indicator therefore focuses a record that includes regression evidence. The indicator, candidate selection and its color logic are unchanged.

## Limits and compatibility

- Only a Task’s latest batch and that batch’s runs are shown. Earlier batches remain outside this read model.
- The Mission block lists only Tasks whose latest batch exists. Its recorded head is the Control Plane record, not a live branch read; it can briefly lag a promotion and cannot detect manual movement of the branch.
- The Integrated indicator opens Verification, which now holds regression, but still selects the candidate’s latest run and takes its success color from that run alone.
- The displayed batch comes from the Task list; the extra read uses the batch from Task show. They can disagree for one refresh. Foreign-batch runs are filtered out and the section shows no run for its batch in that case.
- Once a Mission starts and has its recorded head, the Integration block stays present, including before the first batch. An unstarted Mission without batches, a Task without a batch and an older main process retain the old view.
- Two check tables have distinct heading ids and names, but “Show output #N” button names can occur in both. Queries must be scoped to the intended table/region.
- A regression can be read, not resolved, rerun, retried or approved here. Candidate verification commands do not provide a batch human route.
- Both sections follow the existing five-second page refresh. A selected Task carrying a batch adds one request per refresh; visibility, busy state and generation guards remain the controller’s.
- Conflict paths are the stored, redacted list, limited to 200. Exactly 200 may or may not indicate truncation, so the text makes no definitive truncation claim.
- The 27 new strings exist only in en and zh (D94). Missing entries in es, fr, ja, ko and pt fall back to English. Raw Control Plane statuses/reasons remain raw.
- No test runs the page on a real conflicted or failed batch. Unit tests construct those states; the e2e spec ends with two promoted batches.
- No new read of git or the Artifact store is introduced. Output disclosure reuses CheckOutput’s existing Artifact request.
