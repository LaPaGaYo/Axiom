## Decision checks and persistence

`approval/delivery-decision.ts` implements ApprovalGateway decision logic. `pendingDelivery` checks, in order: (1) row existence and delivery kind, refusing `approval_not_found`; (2) PENDING status, refusing `approval_not_pending` with approvalId/status; (3) READY_FOR_APPROVAL Mission state, refusing `illegal_transition` with missionId/from/command. `grant` then (4) reads missionFinalization and requires a ready report with the same hash, refusing `approval_stale` without writes; (5) parses expiry and controller time as dates, requiring strictly later expiry; (6) updates the row to GRANTED and writes approval.granted. Bare-date expiries are accepted. Guarded transition failures retain `stale_state`.

`MissionController.grantApproval` invokes `grant` within one `this.write`. An expired grant transitions the old PENDING row to EXPIRED (MissionController / expired), appends approval.expired, and requests a replacement for the same report in that write. `grant` returns the old/new IDs as an expiry result. Only after `this.write` returns does `grantResult` throw approval_expired with approvalId and replacedBy. Replacement failure rolls back expiry and its audit. The existing mutation executor discards the pending receipt on this refusal; repeating the original call with the same request ID sees the old EXPIRED row and returns approval_not_pending, without another replacement. Successful grants retain ordinary durable receipt replay.

`MissionController.denyApproval` first calls `validateDenial`, which uses redactContext and the same OrchestrationError(invalid_argument, secret_in_rationale) behavior as rejectPlan. Inside one write, `deny` performs only checks 1–3, records DENIED / user / reason and approval.denied, then calls the existing interruptMission with BLOCKED / delivery_denied. No hash or expiry check prevents a safe denial. A failed Mission status update rolls back both denial and its audit.

Each new RPC handler reads `ctx.caller?.kind` itself and passes it as `via` to the controller operation and then to the approval event. The request has no identity field. The existing caller-authority gate requires desktop before invocation or receipt replay, so accepted calls record via=desktop. The internal fallback `unknown` is unreachable through either accepted RPC. Both row resolver and human decision audit actor are always user. This records the single desktop person in V1; it does not authenticate a personal name.

The store method `updateApprovalExpiry({id, expiresAt})` validates with ApprovalSchema.pick and returns whether exactly one row changed. Its statement is:

```sql
UPDATE approvals SET expires_at = ?, updated_at = datetime('now')
WHERE id = ? AND status IN ('PENDING', 'GRANTED')
```

No closed row changes expiry. No DDL, schema step, outcome or executed_at write was added. The existing delivery-approval.ts behavior and lifecycle contract are unchanged.

## Limits and handoff

Nothing delivers or consumes a granted Approval until M4-8. This Task never changes a GRANTED row's status. Cancellation, report replacement and passage of time leave it GRANTED; delivery must revalidate and refuse invalid authorization. Any additional lifecycle edges require Henry's decision. A denied Mission can only be canceled in the current product; change-and-resubmit needs replanning.

Nothing expires an Approval by itself. A past-due PENDING request remains PENDING and remains visible until a grant attempt closes and replaces it. The refusal deliberately has that committed side effect, has no stored receipt, and a same-request-ID retry returns approval_not_pending. Restart recovery still does not mark expired Approvals (ARCHITECTURE 16.1 step 2, M4-4).

Only time in PAUSED stops Approval expiry; BLOCKED time does not, including a block nested inside a pause. Cancellation retains the existing order: PENDING requests are revoked before the move, so the clock hook cannot modify those now-closed rows; a still-GRANTED row is advanced by the pause interval without changing its status.

Pending uses the existing mission kind and cancel action, with plain reasons delivery_approval_pending and delivery_approved. Grant/deny buttons and renderer client methods wait for M4-11. ## Pause arithmetic and local review finding

The single hook is moveMission after its status update and status audit, only when the source is PAUSED. The function in approval/delivery-approval-clock.ts imports only the store type, so it creates no lifecycle import cycle. It reads the most recent PAUSED status event and the newly persisted departure event. Both boundaries are controller timestamps. Their difference is added to each still-PENDING or GRANTED delivery expiry, and the departure timestamp also timestamps approval.clock_resumed. The database expiry update and audit share the Mission transition transaction. A nested block closes interval a; unblock into PAUSED opens interval c. BLOCKED interval b contributes nothing.

Review found that an initial second call to ctx.now after the status audit could count the time taken to write that audit. A new deterministic test advances the supplied clock on every read: the initial implementation extended by 2,000 ms while the persisted status events were 1,000 ms apart, failing at the expiry assertion. The fix reads both persisted boundary timestamps, and the test now passes. This is a precision correction within the stated design, not another clock or lifecycle. The new regression is `the pause interval ends at the persisted status event time`. The first broad runs happened to execute this newly added red test; those results are superseded by the final broad reruns recorded below.
