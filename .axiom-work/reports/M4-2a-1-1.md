## Open-time behavior and transaction boundaries

1. The constructor configures SQLite, including its existing 5-second busy timeout, then calls `createTables` before `migrate`.
2. `createTables` executes all existing `CREATE … IF NOT EXISTS` DDL. A new database gets `batch_id` directly as the final `verification_runs` column. For an existing table this DDL leaves its columns alone.
3. `ensureAxiomColumns.call(this)` probes the single `[table, column, definition]` entry with `hasColumn`. If present, it returns: this step takes no write lock, executes no ALTER/COMMIT and writes no data or version stamp. This is the path on fresh databases and later normal opens; it does not claim that the whole existing constructor is read-only.
4. If missing, `BEGIN IMMEDIATE` acquires SQLite's write reservation. The function probes again inside that transaction. Only if still missing does it execute `ALTER TABLE verification_runs ADD COLUMN batch_id TEXT`. Existing values are preserved and old rows get NULL.
5. `COMMIT` finishes that addition. An error inside the transaction executes `ROLLBACK` and rethrows. `BEGIN IMMEDIATE` itself is outside the try, matching the numbered runner; failure to acquire a transaction does not attempt to roll one back.
6. The rest of `createTables` performs its unchanged kernel index/view steps; only then does the constructor enter `migrate`. The new addition is already committed. A later numbered migration rollback cannot undo it; an older stored version remains for the next migration attempt. On the tested v45 file, `batch_id` is therefore inserted before v46 appends the five legacy fields. The test compares their set, while fresh/v46 files also assert last-column order.

Concurrent old-file opens: both may initially see the column missing. One obtains `BEGIN IMMEDIATE`; the other waits under the existing busy timeout. After the first commits, the second obtains the lock and re-probes, sees the column, skips ALTER and commits its otherwise empty transaction. If the first rolls back, the second can perform the addition. If the timeout expires, opening fails with the existing SQLite busy behavior; there is no extra retry loop. These concurrency and separate-rollback conclusions follow from the transaction order; no simultaneous-process stress or forced numbered-migration failure experiment was added.

The step takes no schema number because upstream's numbered chain already overlaps Axiom's, while an additive nullable column is tolerated by older named-column readers/writers. `SCHEMA_VERSION`, `migrate.ts`, all `migrate-*.ts`, version-skew probes and `orchestration-db.ts` are untouched. v45/v46 remain numbered; this is the first open-time column addition of its kind.

## Limitations and follow-up boundaries

- Nothing writes `batchId` in a product insertion and nothing calls `resolveIntegrationPlan` outside tests before M4-2a-2. This unit does not run merged-tree regression, promote a batch, integrate a Task or turn on queueing.
- Other readers do not distinguish batch runs from candidate runs: the latest-run candidate lookup and rerun eligibility, the next Attempt baseline, read models, next-Attempt acceptance context, and supervision queries. M4-2a-2 must decide each before producing batch runs.
- `axiom.verification.list` and the Task page would show a batch run among the others, with the candidate's commit and no batch mark. There is no batch filter or UI change here.
- An older build continues to read/write a database containing this nullable column, but refuses a stored policy containing `integrationGates`. Every verification of that Mission ends `INCONCLUSIVE` with `policy_invalid` and is sent to human review until policy/build compatibility is restored.
- Programs named only by `integrationGates` are not allowed evidence programs; they must also appear in setup/risk-tier commands or the existing allowed-program policy to be used as criterion programs.
- An explicitly empty highest tier hides lower tiers in default integration-gate selection. An explicit empty `integrationGates` disables gates, while setup and criterion commands still run.
- The store validates id shape, not batch existence or Mission/candidate membership. Those relationships remain the inserting caller's responsibility. The new column has no index, foreign key or CHECK.
- The open-time step is independently committed and precedes numbered migrations; v45/v46 have not been converted. Legacy migration failure can leave the new column present, safely skipped on the next open.
- The unchanged boot sweep uses runtime-listed `axiom/verify/` branch names, not row ownership. It would remove a batch run's worktree on that branch namespace; the integration executor must use its own namespace. The new recovery test uses unlisted batch ids specifically to isolate row recovery from this sweep.
- CLI Worker write scope is enforced at verification-time diff inspection, not a runtime filesystem guarantee. The explicit file allowlist and sidecar checks form this submission's scope evidence.
- Host Mission e2e, independent review, immutable Candidate creation and acceptance remain with the launcher/verifier. No claim of integrated or completed delivery is made by this report.
