## Store and branch write

`ApprovalSchema` adds optional non-empty `outcome` and ISO `executedAt`. The row codec reads the existing nullable outcome/executed_at columns; `...(r.outcome === null ? {} : { outcome: r.outcome })` and the equivalent executedAt spread omit NULL fields entirely. Existing rows therefore retain their old decoded shape, including rows made by older code. The unchanged generic transition method remains compatible with existing tests; product delivery uses the new consumption method, which always writes both fields. No DDL or schema step exists in this diff.

The new store method validates `{id, outcome, executedAt}` and executes exactly one statement:

```sql
UPDATE approvals
SET status = 'CONSUMED', outcome = ?, executed_at = ?, updated_at = ?
WHERE id = ? AND status = 'GRANTED'
```

Bindings are outcome, executedAt, executedAt, id. A change count of one returns true; otherwise false. Resolver/resolution are not assigned, so the grant's attribution survives. AxiomStore adds only the readonly member and constructor binding.

`advanceLocalBranch({repoPath, ref, from, to, hooks:'on'|'off', reflogMessage?})` generalizes the existing implementation. It accepts only names under refs/heads/, validates both object ids, reads the exact named ref (not descendants matched by for-each-ref's pattern), and preserves the check order: missing/symbolic → unavailable; already at to → advanced with written:false; not at from → moved; checked out → checked_out plus worktreePath; otherwise compare-and-swap and read back. The new results are `{advanced:true,written:boolean}`, `{advanced:false,reason:'checked_out',worktreePath}`, or `{advanced:false,reason:'moved'|'unavailable'}`. Successful command plus readback at to establishes written:true. A failed/interrupted command that reads back at to yields written:false, never claims this call wrote it.

`advanceIntegrationHead` passes refs/heads/axiom/integration/<missionId>, hooks:off, no reflog message; it projects the richer result to exactly the original `{advanced:true}` or `{advanced:false,reason}` objects. Integration continues through withHooklessGit with timeout 30,000 and confine:false. Delivery passes refs/heads/<targetBranch>, the two approved heads, hooks:on, and `axiom: deliver <missionId>`. That path calls plain gitExecFileAsync with gitOptionsForWorktree and timeout 30,000; it passes no configuration override. The unchanged integration-advance test passed in the focused and broader runs; its original toEqual assertions cover hook suppression, checkouts, missing refs, symbols and repeat calls.

## Checks, writes and time

`approval/delivery-check.ts:current` owns checks 1–5, in this exact order: require Mission; match delivery Approval and ownership; require GRANTED; require READY_FOR_APPROVAL; require latest delivery row plus current ready report/hash. It returns Mission, Approval and ready record. `check` adds expiry as check 6, comparing Date.parse(expiresAt) strictly greater than Date.parse(ctx.now()). The only possible initial write is the replacement PENDING request plus approval.lapsed; the old row remains GRANTED. `MissionController.checkDelivery` owns the write and calls `result` after it to raise approval_expired.

`delivery/mission-deliver.ts` owns asynchronous sequencing: process-local Mission exclusion → controller check → repository/remote/integration/target reads → remote stop → integration-head stop → target missing/moved → no-op completion → signature setting → committed intention → branch compare-and-swap → completion or the prescribed refusal. No second ancestry command is needed: finalization proved containment and the heads still equal those immutable commits. No-op completion checks both branch positions and remote/integration stops, but needs neither a write nor a signature/checkout check.

`delivery/delivery-write.ts:settle` begins every write with checks 1–5, excluding expiry. `MissionController.settleDelivery` supplies the transaction and context. A stopped delivery appends one mission.delivery_stopped; changed inputs use moveMission to FINALIZING; started appends mission.delivery_started; completed calls ApprovalGateway's delivery-consumption and moveMission to COMPLETED in one transaction. Zero rows consumed produces stale_state and no consumption event. Finalization/current-record compatibility permits absent heads on historical records; audit payloads encode such optional values as null rather than undefined to satisfy the JSON contract. Successful RPC delivery has already matched both actual heads, so its events always contain the two commit strings.

All new timestamps originate in the controller's ctx.now(): expiry/replacement/lapsed time, started/stopped audits, executedAt and consumption updated_at, consumed audit and mission.status. Existing insertion/transition timestamp defaults in reused store code are unchanged, as in M4-7b. The consumption uses ctx.now for executedAt; the shared audit function obtains createdAt from the same controller clock. The fixed-clock lifecycle test proves execution/update/audit times and delivered reason. No clock is introduced in approval/ or delivery/.

Only the RPC handler reads `ctx.caller?.kind ?? 'unknown'`; strict params accept no identity field. The value travels as `via` through deliverMission and settleDelivery into started/stopped and consumed event payloads. The initial actor for started is user; stop and consumption actors are MissionController. No resolver is read from the request or overwritten during consumption.

Refusals after durable writes use returned values/errors, never throws inside the write: check returns expired data and its result function throws after commit; settle returns a refusal and its result function throws after commit. For changed inputs, result first requests the controller's stage_change schedule after commit, then throws. Retry behavior with the same request id: expiry meets approval_stale because the replacement is latest; a stop runs again and adds another stop if the cause persists, or succeeds with the same Approval once cleared; changed inputs meets illegal_transition while FINALIZING and approval_stale after a new ready/request. Rejections do not store a successful receipt. A successful call is a durable mutation and uses the existing receipt mechanism.

## Exact git sequence

All reads use the existing readers, not a new process subsystem. The path is resolved via runtime.showRepo before git; readIntegrationHead resolves it again internally.

1. `git remote` (names only, no remote access).
2. `git rev-parse --verify refs/heads/axiom/integration/<missionId>^{commit}` through readIntegrationHead.
3. `git rev-parse --verify --quiet refs/heads/<targetBranch>^{commit}`; code 1 means absent, any other failure is git_unreadable.
4. Unless the two recorded heads already coincide: `git config --type=bool --get merge.verifySignatures`; code 1 means unset, only trimmed true is true.
5. After committing mission.delivery_started: `git for-each-ref --format=%(refname)%00%(objectname)%00%(symref)%00%(worktreepath) refs/heads/<targetBranch>`; inspect the exact entry.
6. If writable from the expected head: `git update-ref -m "axiom: deliver <missionId>" refs/heads/<targetBranch> <integrationHead> <targetHead>`, without any -c override.
7. Repeat command 5 to determine the resulting ref position. Early refusals do not reach later commands. No merge, fetch, push, checkout, reset, worktree manipulation or second report is part of product delivery.

## Limits and decisions retained

- A repository with any remote is not delivered at all. Whether 0.1 may fast-forward it locally remains Henry's decision. Nothing is ever pushed or fetched, and no remote is used.
- A checked-out target, including the normal main checkout, is never moved. The person frees that branch and delivers again with the same still-current, unexpired Approval.
- A manual merge or any other target movement returns to FINALIZING and costs another Approval, even if it is now exactly at integrationHead: that is the letter of D70 item 2. Completing directly in that case is a question for Henry. A target moved away from integration stops finalization and can only be canceled until M4-6b.
- merge.verifySignatures=true prevents Axiom from moving the target because integration commits are unsigned. No other setting (including merge.ff or branch.<name>.mergeOptions) is consulted. This is the task's narrow reading of D92's named setting, to be reported to Henry by the verifier.
- The target write has no configuration override. A repository hook can refuse or delay it; refusal/timeout with no movement gives delivery_unavailable. Git before 2.28 has no reference-transaction hook.
- Git does not report a branch as checked out while its worktree is rebasing/bisecting, so that branch could be moved. A checkout between the check and CAS can also evade the check. The completion record does not reread git, so an external move just after the write is not detected.
- A crash, cancel, pause or block between ref write and recording leaves the branch moved but Mission incomplete and Approval GRANTED. The committed started event is the persistent record of the attempted move. Cancel leaves it at that; other cases need another finalization/Approval. Crash recovery is not implemented, and retry of the same abandoned request id is operation_unknown under the existing receipt protocol. There is no restart recovery for delivery (Architecture 16.1 / M4-4).
- Single-Mission exclusion is in this process only. It does not fence another process or recover after restart.
- A granted Approval leaves GRANTED only by consumption. Lapsed/replaced, re-finalization and cancel remnants remain GRANTED and are refused by the checks. Additional transitions await Henry. Nothing expires an Approval autonomously.
- Refusals have no successful receipt, so retry executes again. Retrying a persistent stop appends another stopped event; expiry does not repeatedly replace the now-stale id.
- A build older than this change rejects a consumed Approval carrying outcome/executedAt because its Approval schema is strict. Existing NULL rows remain shape-compatible.
- No worktree, branch or ref is cleaned at completion. No second CompletionReport is written or existing report changed: fast-forward ends at that report's commits.integrationHead. Delivery facts reside in the consumed Approval and audits. This is the verifier's decision for this task, reported to Henry; planner owns the later governing-plan correction.
- pending delivery_approved/delivery_stopped reasons remain plain text with only cancel. No delivery button until M4-11; no CLI or MCP tool can deliver.
