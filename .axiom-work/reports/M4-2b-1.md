## Request behavior and evidence

The implementation processes re-requests first, then newly verified Tasks ordered by the sequence of the latest `task.stage` audit whose `after.stage` is `VERIFIED`. A missing audit sorts last, with Task id resolving ties. It uses `getLatestReadModelAudit`, not a per-Task audit-history scan. Candidate and latest non-batch run selection remain in `activeCandidateVerification`.

Every request transaction re-reads the Mission, Task and active candidate. A new request also requires the latest non-batch run to be PASS and every upstream Task to belong to the same Mission and PlanRevision and be `INTEGRATED`. Admission limits for another Attempt do not apply to finished work. A re-request instead checks the existing effect: absent, failed, retired or done can be enqueued; pending/running cannot. It does not require a passing run again.

The transaction writes the stage only for a new request, enqueues `{taskId,candidateId}` with candidate id as key, and appends `integration.requested` with actor `IntegrationController`, object kind `candidate`, that candidate id, `before:null`, and either `{taskId,runId,again:false}` or `{taskId,again:true}`. The function returns only committed request Task ids, in write order. An ineligible Task receives no writes. A failed Task transaction rolls back and emits only the fixed warning plus Mission/Task ids; another Task can still be requested and the round can still admit work. Outer read failures emit only the Mission id and preserve the returned ids already committed.

Titles 1 and 6 use the existing `integrationFixture` through `regressionFixtures`, real temporary Git repositories, existing executor and existing promotion fault controls. Title 1 proves the entire request-to-promotion path, effect identity/payload, actor/reason/run evidence and duplicate no-op. Title 6 proves three failed tries, blocking, rationale-only adjustment, a new request resetting attempts, preserved pending backoff and running leases, and completion of a Task restored after its batch was already promoted. It also covers a missing effect with a QUEUED run, outer failures before and after a committed request, and warning content. Every outbox run is followed immediately by `effects.stop()`; retries use the existing raw due-time update, not timers.

Titles 2–5 use `verificationFixture` through the new small fixture owner, without starting an outbox or requiring a repository. They cover every specified non-passing/no-run/batch-only/superseded case, an absent active candidate, all upstream states, reverse-id verification ordering, pause/resume, and the e2e-only hold. Negative cases compare Task, effect and audit rows before and after. Title 2 also proves that an older PASS cannot authorize a newer non-PASS run.

Titles 7–8 use `integrationFixture`, not an alternate Scheduler fixture: it has other READY roots, and the real round admits another Attempt successfully. They construct ContextBuilder and AgentFactory with RulesEngine and the certified-provider list, and stub `readRepositoryRules` exactly as requested. Their outboxes are never started. ## Verdict, request, promotion and dependent admission

The transaction names below are the operation strings supplied to the existing wrappers; those wrappers prefix their SQLite transaction/savepoint names with `axiom_`. Git/process operations occur outside database transactions.

1. `settleVerificationVerdict` commits `verification_verdict`, or the desktop PASS resolution commits `verification_resolve`. The run is PASS and the controller's nested `transition_task_stage` writes `VERIFIED` and its `task.stage` audit (`VerificationService`/`verification_passed` or `user`/`verification_resolved`). Neither path enqueues integration.
2. `MissionController.scheduleAfterWrite` queues a microtask because the caller owns an outer transaction. It compares the captured audit with the persisted row and suppresses the trigger if the transaction rolled back. After a commit, the hook in `control-plane.ts` calls `scheduler.scheduleRound(missionId, 'stage_change')`.
3. The real round returns immediately unless the Mission is `EXECUTING`. It commits `recompute_readiness` first. Dependents of the just-verified Task are still waiting because their upstream Task is not yet integrated. Immediately next it calls `requestIntegrations`; this is before asynchronous contract building or Attempt admission.
4. For each eligible Task, `integration_requested` encloses the qualification re-read, nested `transition_task_stage` to `INTEGRATION_READY`, effect upsert and `integration.requested` audit. The stage transition queues another post-commit `stage_change` round; `EffectOutbox.enqueue` queues an outbox wake microtask. An error rolls back all three writes. The outbox might still wake after a rollback, but there is no committed effect to execute, and the controller suppresses the rolled-back stage trigger.
5. Scheduler calls overlapping the current Mission round are coalesced into a later round. Re-reading a pending/running request does not change its delay or attempts. The wake calls `kick`, schedules a scan and uses `leaseDueEffect` to claim the due pending effect as running under the current epoch. The database claim is an atomic conditional write. The outbox serializes one effect per kind and Mission and selects by `due_at,rowid`; other effect kinds may execute concurrently.
6. The unchanged `integration.apply` executor first catches up any ref-authoritative promotions for the Mission and closes stale batches in `integration_stale_batches`. `finishPromotedRequest` handles an already promoted candidate through `integration_promoted_task`. On a new normal request, eligibility and integration-head reads lead to `integration_begin`, which rechecks eligibility and records an APPLYING batch and `integration.batch_started`.
7. The executor creates/reuses the kernel scratch worktree, merges the candidate and pins the merge commit. `integration_merged` records TESTING, `mergeCommit`, and `integration.batch_merged` only after the pin exists. `integration_regression_started` creates/claims a batch-bound run and records its audit. Checks execute on the merged tree; their evidence uses the existing Artifact path. `integration_regression_verdict` records PASS, PROMOTABLE and `integration.batch_promotable` together.
8. Scratch return completes; promotion rechecks eligibility, validates the expected head and checkout state, and advances the integration ref. `integration_promoted` then records PROMOTED, nested Task `INTEGRATED`/`task.stage`, and `integration.batch_promoted` together. Its audit includes `status`, `baseCommit`, `mergeCommit`, `taskIntegrated` and `caughtUp`. No target-branch write or Approval occurs here.
9. The Task transition again schedules a post-commit `stage_change` round. That round's `recompute_readiness` transaction sees the upstream INTEGRATED and moves an eligible dependent from DEFINED to READY. If readiness moved Tasks, the controller also schedules its usual coalesced round. The integration-request pass runs before admission in this round as well.
10. The Scheduler checks each READY Task in `scheduler_precheck`, builds its ContextPackage/AgentSpec outside the admission transaction, then rechecks in `scheduler_admission`. That transaction writes the binding/sequence/branch, nested RUNNING transition and Attempt count, enqueues `attempt.dispatch`, and records `attempt.admitted`. The RUNNING transition schedules the usual further round, and enqueue schedules an outbox wake. The existing fresh-Attempt launcher selects `axiom/integration/<missionId>` as its baseline, so the dependent starts from the promoted head.
11. Independently, after `integration.apply` returns done, `executeEffect` conditionally completes its running effect row. This is later than the promotion transaction; hence the e2e spec polls effect completion separately. Finishing an outbox lane schedules another scan. Nothing in this Task changes the Mission from EXECUTING when all Tasks become INTEGRATED.

## Stop/restart boundaries

| Process stops at | Durable state and next action |
| --- | --- |
| During the verdict transaction | Rollback leaves the previous run/Task state; existing verification recovery handles unfinished work. There is no partial integration request. |
| After the verdict commits, before its round runs | PASS/VERIFIED and the audit remain. `startAxiomControlPlane` recovers Missions, verification and effects, starts the outbox, then schedules a resume round for every executing Mission recovery did not block. That round requests this Task if still eligible. No periodic Scheduler sweep is introduced. |
| During `integration_requested` | Stage, effect and request audit roll back together. A later/boot round sees the prior Task stage and retries qualification. |
| After the request commits, before the outbox runs | `INTEGRATION_READY`, the pending effect and audit remain. Boot's `effects.recoverAtBoot()`/`effects.start()` and kick consume the pending row. The boot round leaves pending/running requests untouched. |
| After the effect is leased, before/during application | The previous epoch's running effect is recovered through the existing integration `onOrphan: retry` policy. An APPLYING/TESTING/PROMOTABLE batch is reused/reconciled, with existing base and candidate fences; no parallel integration implementation is added. |
| After a merge pin or regression commit | Existing apply/regression re-entry reuses the immutable merge/batch identity and reruns interrupted regression under its current claim. A passed PROMOTABLE batch continues promotion. |
| After the ref advances, before the promotion transaction commits | The next try's promotion catch-up observes the merge commit already at the head and records the promotion without merging again. Existing blocked/canceled Task preservation rules still apply. |
| After the promotion transaction, before effect completion or dependent admission | The batch/Task are durably PROMOTED/INTEGRATED. The old-epoch effect retries to done; boot's round recomputes downstream readiness and admits work. |
| After dependent admission, before dispatch executes | The binding and pending `attempt.dispatch` are durable. Existing outbox recovery/launch fencing completes dispatch from the selected integration baseline. |
| After `effect_failure` writes failed, before exhaustion settlement finishes | If the Task remains `INTEGRATION_READY`, the next round can enqueue that ended request with a new three-try allowance. If settlement blocked it, only an authorized adjustment restoring the queue stage (or the relevant existing recovery path) makes it eligible again. |

Boot ordering is read from `src/main/axiom/control-plane-boot.ts`. The existing reconciliation timer wakes effects and verification; it is not a periodic Scheduler round. Full stale-batch/orphan cleanup and pause/block semantics remain later M4 work.

## Clarifications and differences from the brief

- The functional scope and requested API are unchanged. Existing integration fixtures needed no edits: the new test-only setup can move their Task back and insert a passing run while retaining the original fixture's base recording and real executor.
- The report requirement's phrase “same instant falls back to Task id” is narrower in the mandated algorithm: audit sequence orders two different events even if their timestamps are equal. Task id breaks equal ordering keys, including two missing VERIFIED audits. The implementation and reference document follow the explicit sequence rule; no timestamp sort was substituted.
- The e2e skip call uses bracket access to satisfy both the required existing skip condition and the prohibition on adding the literal `.skip(`. It does not skip the new test on a configured POSIX fixture host.
- Direct compiler/runner stages replace sandbox-blocked package-build wrappers as explicitly authorized. Host-only e2e validation remains outstanding, rather than inferred from unit tests or the typecheck comparison.

## Limits and risks

- A passing Task is visibly VERIFIED between the verdict transaction and the scheduled round; the request is deliberately not in the verdict transaction.
- No periodic round exists. Requests depend on an existing stage change, adjustment, policy update, start, resume, unblock, or boot scheduling a round. The first executing round after upgrade requests every eligible Task left VERIFIED by the previous version.
- A verified Task failing any of the three rules is not requested and receives no stage, audit, block, pending item or explanation. A database/read failure also leaves no new persistent request diagnostic; warnings carry only safe ids.
- Ordering is by the latest VERIFIED audit sequence, missing events last, Task id for equal keys. Same timestamps alone do not override sequence order.
- Re-requesting deliberately relies on effect status and active candidate identity, not run status. A failed effect with the Task still INTEGRATION_READY (lost exhaustion settlement or a stop before it ran) can receive three fresh tries at each later round until the Task moves. A normally done request with the same ACTIVE candidate and Task still in that stage is not expected from the current executor; the already-promoted recovery case is nevertheless covered.
- The unchanged executor polls every 30 s while a Mission is paused or a Task is blocked from the integration queue. This Task does not change executor eligibility, abandonment, budgets, approval policy or pause races.
- When the integration head moves, an interrupted Attempt without a preserved snapshot that would otherwise continue in its old worktree is launched afresh. Already running Workers encounter the new integration head at their own merge; conflicts and failed-regression repair remain M4-3.
- `scheduler.ts` is now at the 300 counted-line limit. Further edits need a separately scoped extraction; no lint configuration changed.
- Every existing fixture Mission e2e holds integration. Only the new spec exercises this chain end to end, and its Electron run is still a verifier responsibility.
- All Tasks INTEGRATED still leaves the Mission EXECUTING. Finalization, final regression/completion, Approval and delivery remain later Tasks. No target branch is advanced here.
- CLI Worker write scope remains a verification-time diff check plus best-effort provider configuration, not runtime enforcement. This change adds no scope-enforcement mechanism.

M4-2b is ready for independent verification, subject to the named host checks. M4 as a milestone is not declared complete by this handoff.
