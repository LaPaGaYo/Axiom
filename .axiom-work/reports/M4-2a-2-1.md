## Result and delivery boundary

An integration try now runs the Task command plan on its pinned merge commit, records a batch VerificationRun and settles PASS to PROMOTABLE or FAIL to FAILED. INCONCLUSIVE remains in TESTING and uses the existing three-try outbox policy. A stopped execution leaves its scratch and RUNNING claim for the next try without consuming an attempt. An obsolete execution cancels only its own still-current claim and yields without consuming an attempt. Every try first abandons the Mission's dead open batches. Candidate-verification readers exclude batch runs by default.

The integration head never advances. No product path enqueues integration.apply; M4-2a-3 owns promotion and M4-2b owns enabling the queue. This branch is left for the launcher's commit and the verifier's review, with no merge, push or promotion.

## One merging, passing try, in order

Transaction names below are the AxiomStore suffixes used in the brief; the store passes `axiom_<suffix>` to the existing lifecycle transaction runner. Nested Task moves use MissionController’s `axiom_transition_task_stage` savepoint inside the outer transaction. Leasing, completion and deferral are single guarded SQL statements, not new named multi-statement transactions.

1. The outbox leases the effect under its runtime epoch and closes the `(integration.apply, missionId)` lane. It passes its current signal through bindEffectExecutor and executeEffect to applyIntegration. Existing leasing/timer/retry behavior is unchanged.
2. `closeStaleIntegrationBatches` opens **integration_stale_batches**. It reads the Mission and every open batch, resolves its Candidate and Task, supersedes dead batches, cancels their QUEUED/RUNNING runs and audits abandonment atomically. With no dead batch this transaction writes nothing. Outside it, obsolete scratches are removed best effort.
3. `eligibility` checks the current request, relationship/status facts and other live open batches. A stale/already settled request returns done; blocked/nonexecuting/busy returns later +30 seconds.
4. `readIntegrationHead` uses the existing local runtime repository lookup and git read.
5. **integration_begin** repeats eligibility, creates/starts APPLYING or reuses a compatible APPLYING batch, and audits batch_started. A resumed TESTING batch returns without a started audit or status change, after checking base equality.
6. The executor removes leftovers, creates the kernel-managed scratch and reads HEAD and its actual branch name. The base comparison precedes detached checkout. For a fresh merge, it pins the Candidate, merges with the unchanged merge implementation, then pins the merged commit.
7. **integration_merged** moves APPLYING to TESTING with mergeCommit and batch_merged. The executor retains this batch snapshot for the regression; currentness is rechecked by the regression even if another actor changes state during preparation. The alternate conflict path remains **integration_conflict**, including candidate/Task settlement and batch_conflict.
8. `runIntegrationRegression` checks signal and currentness, parses policy, resolves setup/criterion/gate commands, redacts their stored forms and computes the deadline and integration_merge baseline.
9. **integration_regression_started** rechecks currentness, cancels old unfinished runs with regression_retried, inserts a QUEUED run, claims it with effect.leaseEpoch and IntegrationController, stores checking/commands/baseline, and audits regression_started. All are one transaction; a failed insertion or claim rolls them all back.
10. `executeVerificationPlan` runs in scratch.cwd at the merge commit with assertCurrent around each step, the deadline and signal. It records command logs, applies the existing retry/flaky/invalid-plan rules and probes three tool versions. Every process and artifact await remains outside the lifecycle transaction.
11. `decideVerificationVerdict` receives clear gate, false nonCodeTask, empty Artifact checks and empty acceptance. Regression removes escalation. A HEAD read must still equal mergeCommit; unreadable/changed HEAD replaces any verdict with INCONCLUSIVE/environment/scratch_changed. A PASS without commands records no_commands.
12. ArtifactStore persists one JSON verdict/evidence artifact, with this run's checks, tools, versions, immutable baseline, identifiers, epoch/claim and times. This is deliberately before the verdict transaction.
13. **integration_regression_verdict** rechecks Mission, batch, Task, Candidate and exact RUNNING epoch/claim, then stores the run verdict, summary, versions and artifact references. PASS changes the batch to PROMOTABLE and appends batch_promotable atomically. FAIL additionally supersedes Candidate and moves Task NEEDS_FIX then READY/BLOCKED in this same transaction. INCONCLUSIVE leaves TESTING and audits it; only after commit does regression_inconclusive fail the effect try.
14. Unless stopped, returnIntegrationScratch tries the original temporary branch and calls the existing kernel removal, auditing cleanup failures without undoing settlement. No new git write bypasses writeIntegrationGit, and no direct integration-head/branch-ref mutation is added.
15. On PASS/FAIL the executor returns done and the outbox completes its lease. On stopped/interrupted it returns later without increasing attempts; stopped skips scratch return. A stale interruption uses **integration_regression_interrupted** to cancel only its own still-RUNNING epoch/claim. On thrown regression failure the unchanged outbox **effect_failure** transaction increments attempts; exhaustion invokes **integration_abandoned**, which shares run cancellation and abandonment code, followed by best-effort cleanup. MissionController’s Task-stage operations participate in the caller’s transaction through the existing axiom_transition_task_stage savepoint.

## Interruption/restart observations

The architecture has one database-owning Control Plane, not concurrent active outbox owners with expiring leases. A second process inspecting state can observe the committed facts below; a replacement owner must run existing orphan recovery first. Old-epoch running effects become pending without spending a try.

| First process stops at | Durable state / evidence | Next eligible try |
|---|---|---|
| After integration_merged | TESTING, immutable mergeCommit and merged ref; no regression run yet; scratch may remain detached | Recheck integration head equals base, remove leftover scratch, recreate from base, detach at stored mergeCommit, start regression without merging or repeating started/merged audits |
| After regression claim | TESTING + RUNNING run with epoch/claim, checking baseline and commands | Remove leftover, cancel unfinished run with regression_retried and finishedAt, claim a new run; no reuse of old completion authority |
| During a command | Same RUNNING facts; some log artifacts may already exist | Signal stop kills command process tree and deliberately preserves the worktree/run; a hard process loss relies on existing process supervision. Next try removes leftover, cancels old run, reruns setup and all commands |
| After evidence Artifact, before verdict transaction | TESTING + RUNNING; content-addressed evidence can exist without a run referencing it | Next try cancels old run and makes fresh evidence. A live obsolete executor cannot attach the old evidence through a refused fence |
| After verdict transaction, before scratch return | PASS/PROMOTABLE, FAIL/FAILED with settled Task/Candidate, or INCONCLUSIVE/TESTING; verdict evidence referenced | PROMOTABLE is done without writes; FAIL's superseded candidate is stale/done. Leftover scratches for those settled batches await later cleanup/M4-4. TESTING retries its regression and removes its leftover; its completed INCONCLUSIVE run stays historical |

If a human blocks the Task, the in-flight regression cancels its own claim and yields; the next try defers while BLOCKED from INTEGRATION_READY. Cancellation/supersession instead makes the batch dead and the next try abandons it. A Mission pause does not make an already-running regression obsolete. A stop before any run exists inserts none. A completed verdict is not undone by a later signal during cleanup.

## Differences and explicit implementation choices

- No product scope or behavior deviation from the brief. The approved task already supplies the design and execution plan; no extra design/plan artifact or redundant approval cycle was introduced.
- The suggested single regression module is split into execution/evidence and transactional state modules; request eligibility/abandonment moved out of integration-apply, keeping each product module below the 300-line gate. Main's original exported scratch/merge/settlement calls retain their behavior.
- Currentness also checks a missing/terminal Mission and stable batch identity/commits. PAUSED is intentionally allowed to settle. Dead-batch pruning treats missing Missions and cross-Mission Candidate/Task relationships as stale as well as the listed terminal/missing/status cases, consistent with request ownership checks.
- The only extra transaction name is integration_regression_interrupted, making own-run cancellation plus its audit atomic. It introduces no effect kind, status or persistence column.
- Tests use one intentionally missing executable for the explicitly required environmental-failure case; all runnable scenario commands are offline node or git one-liners. Version probes remain the reused runner's node/pnpm/git calls.
- Sandbox wrapper substitution is the explicit brief-authorized fallback; host wrappers/e2e remain the verifier's work.

## Limits and risks

- The integration head does not move. PROMOTABLE remains an open batch until M4-2a-3, so the next candidate of that Mission waits. No product path enqueues integration.apply before M4-2b; current product flows remain as on main.
- A dead batch closes only when some try of that Mission runs. There is no background sweep or new timer. Cleanup is best effort.
- After FAIL the next Attempt starts from the integration head and knows nothing of the regression; merge-based repair and regression context belong to M4-3.
- Three inconclusive regressions block the Task with integration_unavailable, the same reason as an unreachable repository, and backoff is only 1 and 5 seconds. No Mission pending item or smarter retry policy is added.
- An inconclusive batch run stays INCONCLUSIVE, never human/specialist review; no person can resolve it with the existing resolve method.
- A plan without commands passes explicitly with no_commands. Every valid-plan try runs setupCommands in a fresh scratch and probes three tool versions, even with no check commands.
- A regression holds the Mission's integration.apply lane for up to the policy time budget per try (plus existing preparation/cleanup/IO overhead); other kinds remain independent.
- A Mission paused during regression still gets its verdict settled. Full pause semantics are M4-4.
- Commands can modify tracked paths the Candidate changed, preventing checkout back to the temporary branch. Scratch return can leave that branch and report integration.cleanup_failed; there is intentionally no pre-return cleaning.
- A person can delete scratch in the sidebar while commands run. A subsequent command failure is a deterministic FAIL; if the final HEAD cannot be read, the mandated scratch_changed correction takes precedence and yields INCONCLUSIVE instead.
- A stopped try leaves its scratch. The next try removes it; the real runtime may retain the reused temporary branch until M4-4. Stop is prompt inside regression, not in the merge or kernel worktree calls.
- The fixture exercises kernel add/remove/list git functions but stops below the full runtime's own layer: branch preservation on reuse, terminal provisioning/background removal, sidebar interaction and runtime hooks are not proven by these unit tests.
- stopAxiomControlPlane does not await effects.stop(). Process-level shutdown ordering is unchanged.
- An evidence artifact can remain without a run naming it when the verdict transaction is refused or interrupted.
- Regression command logs retain the runner's VerificationService creator. Identical bytes are stored once per Mission, retaining the first writer's metadata; use the evidence artifact's log references, not log creator/relations, to identify a run's output.
- axiom.verification.show displays the Candidate commit for a batch run although the merge commit was tested; the latter is recorded in verdictDetail.baseline.
- An older build ignores batchId on axiom.verification.list and returns all runs; there is no compatibility protocol change here.
- All candidate-run readers listed above see no regressions at all. Rendering regression evidence is M4-5.
- Existing exhaustion is a one-shot callback after effect.failed. A crash in that gap or an unavailable database can still leave the open batch/Task unsettled until a later enqueue/recovery; no new recovery subsystem is added.
