## Recovery behavior and evidence

Recovery is still coalesced and selects only running rows from another epoch. Each missing executor, thrown/rejected `onOrphan`, or failed write is caught independently. The failed row retains all its original fields, including status and old epoch; later rows are processed. After the loop, recovery rejects with the first captured value. The existing per-outcome operations and fencing are unchanged: retry produces pending/due-now without increasing attempts; done completes; retirement commits its row and audit together. No new statuses, retries, settlement rules, or audit payloads were introduced.

The real-database test `recovers the remaining orphans when one recovery fails` creates two actual Missions with old-epoch leases and additional pending work. The first handler throws; the second recovers. It observes one rejection with the original error, byte-for-field equality of the failed effect, a refused lease in that Mission's lane, and a successful lease/drain in the other Mission. A subsequent recovery with the handler repaired drains the first Mission's existing work once, with failure count unchanged. Additional tests cover an absent executor, multiple rejected handlers (first error preserved), and SQLite `RAISE(ABORT)` failures in all three recovery outcomes. The pre-existing audit-rollback test remains passing.

Startup catches recovery failure, logs exactly `[axiom] Effect recovery incomplete; continuing Control Plane startup` with no error text, leaves `plane.started` true, and starts effects, timer, consumers and resume rounds. The existing boot generation checks remain; delayed tick callbacks also verify their generation. The test `continues startup when effect recovery fails` verifies these actions and warning shape. `keeps the newer boot active when an older effect recovery rejects` now verifies resolution rather than rejection, one outbox start, and preservation of the newer timer.

The initial reconciliation and every 60 s tick retry effect recovery before requesting an effect drain and Attempt reconciliation. A rejected recovery warns `[axiom] Effect recovery incomplete` and still performs both. Neither maintenance action waits for the effect drain; verification wake-ups remain independent. `retries unrecovered orphans on the reconcile tick` holds and rejects a tick recovery, then confirms another tick still runs. Stop/restart tests prove a late rejection cannot kick effects or reconcile Attempts from an obsolete generation.

Independent review found a related ordering gap in the first local fix: starting recovery on a promise while immediately reconciling Attempts allowed an aged lease to be orphan-settled just before recovery requeued it. A real-database regression reproduces this with a 90-second-old unbound dispatch lease, a temporary SQLite trigger blocking recovery at boot, and removal of that trigger before the 60 s tick. The red run moved the Task to READY; the fixed run keeps it RUNNING with seq 1 / attemptCount 1, invokes the launch once, completes the effect, and records neither `attempt.launch_pending_orphan` nor `attempt.launch_failed`. The fix sequences Attempt reconciliation after recovery settles without altering the reconciliation module or rules.

The final DDL, unchanged normal effect lifecycle/audits, three dispatch-orphan outcomes, and remaining post-commit side-effect inventory are preserved in [attempt 1's report](M3-06-1.md). This change updates its `control-plane-boot.ts` inventory row: the existing maintenance interval now also requests old-epoch effect recovery before kicking effects/reconciling Attempts. It adds no new bypass of the outbox. Attempt 1's necessary-difference statement that recovery failure prevents startup is superseded by this addendum and the behavior above. No existing function was moved.
