## Reads, shared functions and authority

`mission-policy-read.ts::readMissionPolicy` is the only production call site of `axiomClient.showPolicy` in the missions folder. Its async try/catch covers synchronous exceptions, refusal and transport failures without inspecting AxiomRpcError. It returns the parsed policy or null. `mission-read.ts::readMission` starts it alongside supervision, pending, Mission, plan, Task and Attempt reads before awaiting their results, once per selected Mission page read, including timed reads, Task selections and Missions without plans. A failed optional policy read is stored only as null in the detail projection: the plan card explains the omission, without alert/status roles, page error or toast.

| Prediction / displayed fact | Authority used directly |
|---|---|
| Criterion text and proof, including legacy strings/requiredEvidence | shared `resolveAcceptance` (via `reviewCriteria`, also used by the comparison) |
| Whether stored verification rules are valid | shared `VerificationRulesSchema.safeParse(policy.verificationRules)`; no renderer default on failure |
| Command order, trimming, de-duplication, risk gates and source | shared `resolveVerificationPlan(task, parsedRules)` |
| Covering Task ids and zero-based Goal criteria | shared `planCoverage(plan, goal.acceptanceCriteria)`, only for matching goalRevisionId |
| Warning codes, messages and details | revision.warnings as stored by the Control Plane |
| Approval/rejection controls | matching pending item: kind=plan_review, objectId=revision.id, corresponding action in actions, and pending read succeeded |

The card uses pending actions independently: approve-only has no reason field, reject-only has its reason field and rejection control. With no offered action it explains that neither action is available; failed pending reads have a separate note. Mission status adds no renderer restriction; page busy disables controls, and rejection still requires a nonempty unsent reason. The card stores only that reason.

Approve opens the existing application confirmation through confirmAction, with `confirmVariant=default`, title/confirmation `Approve plan`, ghost cancellation `Keep reviewing`. The description names the Task count, delayed execution until Mission start, lack of plan replacement, available single-Task adjustments/cancellation, and warning count when nonzero. Declining sends nothing. Confirming uses the existing mutate receipt and re-read; its response does not optimistically update the card. Rejection keeps its destructive confirmation. A runtime refusal still reaches the existing page error as `code: message`.

`visiblePlanRevisions` retains every proposed revision and the active one. Only if neither exists and there is no active id does it show the highest-numbered revision when rejected. There is one Plan review region per displayed revision and exactly one h2 in it. New detail blocks use a shared group/h3 wrapper. Paths and warning codes use the mono face without code tags; no code tag precedes the first Task command criterion. Comparison is after the current Tasks, so its commands also preserve this ordering.

## Difference semantics

`previousRejectedPlan` chooses the highest revision number below the proposed revision, within the same Mission, with status REJECTED; supersedesId is not assumed. `planRevisionDiff` pairs Tasks by their Planner-provided id. Added/removed Tasks list id and title only. Same-id comparisons cover title, objective, role, risk, maxAttempts, milestoneId and kind with before/after values; missing optional values say Not declared. Paths, compatible acceptance criteria, Goal criterion indexes and each declared budget field/value use unordered multiset subtraction, so order alone is ignored while added/removed duplicate occurrences are retained. Empty and absent optional lists/budget objects are equivalent. Proof identity includes criterion text, kind, exact command or artifactKind; bare text and an equivalent human criterion are equal. Command whitespace remains significant in acceptance comparison, as resolveAcceptance returns it; trimming for execution stays in the shared verification function.

Edges compare fromTaskId, toTaskId and readinessThreshold; a threshold change is removed+added. Milestones compare id, title and unordered exit criteria; risks compare id, description and mitigation. Their order alone is ignored and changes each produce one line. Revision metadata, provenance, rejection reason and warnings do not count as proposed work differences. The prior rejection reason and the id-matching limitation are still shown even when the comparison says No difference.

## Product limitations and risks

- The verification list is what would run under the policy read with this page. Policy can change before verification actually runs; the card says this once above its Tasks.
- Approval does not re-check a proposal's commands against the current policy. Admission/main-process changes are 4b.
- A proposal's commands are shown as the Planner wrote them, unredacted, per D85 rule 6. The execution list applies only the shared function's trimming/de-duplication.
- Tasks are matched across revisions by an id chosen by the Planner. A renamed id appears removed+added; a reused id appears changed.
- Only the latest earlier rejected revision is compared. Its Tasks are not shown in full, and older rejected revisions are not exposed.
- Goal coverage is omitted if the page holds another Goal revision or no Goal.
- Policy reading adds one RPC call per selected Mission page read, including Mission pages without plans.
- The next Planner run is not told the rejection reason yet (4b).
- The plan has no cost estimate; declared per-Task limits are not estimates.
- The pending view and plan list are independent reads and can disagree until the next read. The Control Plane remains authoritative and can refuse a displayed action.
- No runtime write-scope enforcement is added; this renderer Task relies on verification-time diff inspection and the explicit allowlist, as required.
