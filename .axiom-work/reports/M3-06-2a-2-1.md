## Account identity and resolver audit

One exported function, `accountKey(provider, home)`, computes lowercase SHA-256 hex over UTF-8 `JSON.stringify([provider, home])`. The array preserves boundaries between values, and the path is used exactly as the launch resolver returned it (no path canonicalization). Both launch-audit attribution and the current-account view use this function. The synthetic `codex` + `/accounts/codex` key in the evidence is `940e04496dd66e35a97898d735ff2f40d95ca8372546ea74325d6454cd425e95`. Only `{provider,key}` is persisted in the effect; no home path is added there. Missing/invalid launch evidence yields no account, never a failed settlement.

The Claude resolver is exactly the existing `resolveClaudeHomeForWorkerLaunch()`. Read-only trace: `structured-session-account-home.ts` → `structured-agent-runtime-metadata.ts` → `resolveStructuredClaudeAccountHomePath` → `ClaudeProfileRouter.routedHome()` / account-home comparison. It is more than string construction: routing reads local Claude login-state metadata and stats the account directory; `readClaudeFolderLogin` updates the kernel's existing process-local `logins` cache. No launch preparation, durable account-state write, credential refresh, provider activation, or network operation occurs on this host path. These existing disk reads/cache updates are a resolver side effect and performance dependency; the view invokes it at most once and only when that provider has candidate effects. A missing directory can throw; the view then does not cool that provider. Codex uses the existing synchronous read resolver unchanged. Windows wiring returns an empty view.

## Limitations and risks

- Codex still has no reset time. Its account cooldown lasts one ladder step; at each step up to `concurrencyLimit` Tasks per Mission can probe again (multiple Missions can each do so). Every Task still reaches `BLOCKED(environment)` after its own three consecutive interruptions.
- Cooldown is derived only from continuations still being waited on. It lifts when those waits come due, when a person adjusts or cancels every waiting Task for that account, or when another account is selected. Account switches and cancellations are noticed by each Mission only at its next round and do not wake other Missions; a Task already waiting keeps its own backoff after an account switch. Running/done/failed/retired effects and Tasks that moved on no longer constitute a wait.
- Failures waiting cannot fix (e.g. structured billing/sign-in failures) produce no cooldown. Refusal audits still repeat every round. Missing/malformed/old account-less evidence or home-resolution failure intentionally allows a wasted start rather than holding the wrong account.
- Older builds cannot decode a continuation carrying `account`; the new `account_cooldown` enum value likewise requires a build that knows it. Historical rows and AgentSpecs remain readable by this build.
- Existing Claude resolver disk reads and process-local login-cache updates are documented above. Account identity is exact provider + home path, not an upstream account identifier; replacing credentials in the same home is not a different key.
- Snapshot preservation, harness-session resumption, proactive pacing, Codex reset-time discovery, TUI cooldown, Windows/WSL, and supervisor rules remain outside this Task.
- Host Electron acceptance and the environment-dependent broad tests are still required for independent verification; no final acceptance or integration is asserted.
