## Durable outcomes and audits

All batch audits below have actor `IntegrationController`, objectKind `integration_batch`, objectId equal to the batch id, and before=null. Each real attempt writes `integration.batch_started`, after=`{status:'APPLYING',baseCommit,candidateId}`. The generated id is `batch_` plus 32 hex characters. Reentry reuses an APPLYING batch only at the same base; QUEUED refreshes its base; historical SUPERSEDED batches do not prevent another batch. Two unexpected open batches of this candidate fail closed with `integration_batch_stale`.

Cleanup always tries the actual branch read back from git before kernel removal. `integration.cleanup_failed.after={reason:'worktree_removal'}` means removal threw; `{reason:'branch_preserved'}` means checkout failed or the kernel returned preservedBranch. Both may be recorded. Cleanup does not undo a settled batch; a failed try retains its original error even if cleanup/auditing also fails. Already-gone errors are tolerated. All effect accounting and the final `effect.failed` audit remain owned by EffectOutbox.

Git/kernel failure codes are exactly: `integration_head_unavailable`, `integration_head_moved`, `repository_not_local`, `candidate_unpinned`, `scratch_worktree_unavailable`, `merge_failed`, `merged_ref_conflict`, `integration_batch_stale`. Raw git/kernel messages are not thrown or persisted. Database/program errors may pass through the outbox's existing redaction and 2,000-character cap. Policy: three failed tries, delays 1 s then 5 s; orphan retry; not-due deferral 30 s with attempts unchanged. onExhausted catches its own errors because it runs once.

## Limitations and risks

1. Nothing enqueues integration.apply yet and nothing ends TESTING. A second candidate of the same Mission waits until M4-2; before promotion is implemented a conflict can only come from a test or a person moving the integration branch.
2. After conflict the next Attempt starts at the integration head without the candidate's work. Its context only says the previous candidate is no longer active; it carries no conflict explanation. The pre-merged baseline and D79 evidence belong to M4-3.
3. The temporary worktree is visible in the app sidebar while it exists and a person can delete it. The executor does not add a separate ownership UI or deletion guard.
4. Kernel creation/removal runs repository post-checkout and reference-transaction hooks. A failing kernel hook can defeat every try. The executor only disables hooks for its own checkouts/merge/abort and uses the existing hook-disabled pin functions.
5. The full runtime may ask GitHub whether a PR exists for the temporary branch, set push.autoSetupRemote if unset, and install configured symlinks/.worktreeinclude files. A candidate adding a tracked file at an included path may be obstructed. The test fixture exercises the kernel git functions, not those full runtime/terminal/PR side effects.
6. Removal needs the runtime terminal provider. A failed removal leaves a worktree recoverable only by a later run of that same batch; a process killed during merge leaves a base-positioned temporary branch, reused on the next run when the head is unchanged.
7. onExhausted runs once. Death between the last failure and that callback leaves APPLYING and INTEGRATION_READY beside a failed effect until reenqueued (M4-2b). A database failure during that callback also cannot be retried automatically by this hook.
8. A Task blocked for integration_unavailable exposes the existing active-candidate actions: adjust back to INTEGRATION_READY (no enqueue until M4-2b), cancel, or rerun verification. It is not sent to a Worker to fix an environmental problem and consumes no Attempt budget.
9. Paused Missions and Tasks BLOCKED out of INTEGRATION_READY are reconsidered every thirty seconds. No boot sweep covers temporary worktrees of done/failed effects; that is M4-4.
10. The executor trusts the kernel's temporary-branch deletion rule. If that rule changes, removal may preserve the branch or reach a remote; this layer records preservedBranch rather than deleting it itself. Below Git 2.38 the kernel cannot prove merge equivalence; if ordinary merged-branch deletion fails it keeps the branch and the executor records branch_preserved. Current tests exercise the installed Git version, not a Git 2.25 binary.
11. An unknown integration.apply row cannot be decoded by older versions; a pending one stops the outbox scan for every Mission and CLI lists containing the row fail. Downgrading with such rows is not a supported recovery path.
12. Managed listings exclude hidden repositories/worktrees. Cleanup uses the kernel listing contract from the brief; it introduces no filesystem scan or ref deletion. Write scope for CLI workers remains verification-time enforcement, unchanged by this Task.
