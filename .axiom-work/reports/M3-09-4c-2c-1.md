## Draft and write behavior

`buildProvidersUpdate(missionId, policy, opened, draft)` takes the Mission id, the last policy supplied by the page, the initial draft and the current draft. It returns `changed`, schema-parsed `params` or null, and the first schema message or null. Fields are compared in Planner, Workers, allowed providers, certified-only order. Roles compare provider id/null; allowed providers compare sets, so reordering alone is not a change; certified-only compares the boolean.

It spreads the current saved routing, copies its roles, and only modifies changed fields. A role sets provider or deletes it for Automatic, retains current saved model/effort, and is removed if empty. A changed allowed-providers field writes the entire draft list; checkbox changes filter out allowed ids and append newly disallowed ids. A changed certified flag replaces `requireCertified`. No other routing key is named in the four new product files. The patch contains only routing. No policy or no change produces no request. `PolicyUpdateParams.safeParse` alone decides write validity and its parsed data is sent; invalid provider ids remain draft strings until that boundary. The pre-parse object uses `z.input<typeof RoutingPolicySchema>` because the schema's refined output type is narrower than its string input.

The following examples use `R` for this exact complete routing, to make unchanged keys explicit:

```ts
const R = {
  preferredProviders: [], disallowedProviders: [], highRiskTier: 'A',
  providerConcurrency: {}, models: {}, roles: {}, crossProvider: true,
  requireCertified: false
}
```

1. Stored role model retained when changing provider:

```ts
storedRouting = { ...R, roles: { worker: {
  provider: 'claude', model: 'stored-model', effort: 'high'
} } }
opened = { planner: null, worker: 'claude', disallowed: [], certified: false }
draft = { ...opened, worker: 'codex' }
sent = { missionId, patch: { routing: { ...storedRouting, roles: { worker: {
  provider: 'codex', model: 'stored-model', effort: 'high'
} } } } }
```

For Automatic instead, the sent Worker is `{model: 'stored-model', effort: 'high'}`; only provider disappears. If it originally held only provider, the role is removed completely. Tests 5 and 6 cover both cases.

2. Allowed list changes as a whole:

```ts
storedRouting = { ...R, disallowedProviders: ['codex', 'claude', 'opencode', 'antigravity'] }
opened = { planner: null, worker: null,
  disallowed: ['codex', 'claude', 'opencode', 'antigravity'], certified: false }
draft = { ...opened, disallowed: ['claude', 'opencode', 'antigravity'] }
sent = { missionId, patch: { routing: { ...storedRouting,
  disallowedProviders: ['claude', 'opencode', 'antigravity']
} } }
```

The removed Codex id is absent and remaining order is unchanged. If a new id were disallowed it would be appended; set-equivalent reorder alone sends nothing. Tests 3, 7, 21 and 29 cover set equality, whole-list replacement and checkbox changes.

3. Page refresh changes another role and a non-editor key before save:

```ts
routingAtOpen = { ...R, roles: { planner: { provider: 'codex' }, worker: { provider: 'claude' } } }
opened = { planner: 'codex', worker: 'claude', disallowed: [], certified: false }
storedRoutingNow = { ...routingAtOpen, models: { codex: 'new-model' },
  roles: { planner: { provider: 'claude', effort: 'low' },
    worker: { provider: 'claude', model: 'new-role-model' } } }
draft = { ...opened, worker: 'codex' }
sent = { missionId, patch: { routing: { ...storedRoutingNow,
  roles: { ...storedRoutingNow.roles,
    worker: { provider: 'codex', model: 'new-role-model' } }
} } }
```

The newer Planner and models survive; the initial Planner draft does not overwrite them because it was never changed. Test 8 checks this with additional nondefault fields; page test 26 tests refresh, read failure, recovery and saving against the newer policy.

## Opening, request identity and draft retention

`openProviders` is the only eligibility-reading handler. It refuses an absent policy, captures the selected Mission id, stores a new request object with providers undefined, and awaits `readProviderEligibility`. The state setter accepts the answer only when `current === request`. Closing clears the state; replacing it with a new request causes the old answer to be dropped. Only a Mission-id-matching request is passed to the section. The result array/null/undefined lives solely in the surface request state.

`readMissionPolicy` and `readProviderEligibility` share `readPolicy` and its one `showPolicy(` line. The regular read supplies `{missionId}`; the editor supplies `{missionId, providers: true}`. Failure, including a synchronous throw, becomes null; missing providers also becomes null. Eligibility's returned policy is not substituted into page state. No effect, periodic refresh, or form code calls the client.

The form snapshots the opened draft and initial routing once in a lazy initializer, then holds current edits separately. The initial routing is only a choices fallback if a page read fails. Save parameters are recomputed from the newest supplied policy on every render. New policy/answer props do not set state or reset edits. Policy failure keeps the form and edits, shows the existing error sentence and disables saving until recovery. Reopening the pending entry while mounted starts a new availability read without remounting the form; focus moves only on initial mount.

## Limits and retained behavior

- Availability is the **saved** policy at the instant the form is opened, not the draft. Later provider installation, account selection or cooldown expiry is not shown until reopening (including pressing the still-reachable pending entry).
- Each slot shows the first filter reason. Removing it can reveal another refusal. The policy editor can affect only disallowed and the provisional part of not-certified.
- The table and choices include every provider named by the Control Plane, with no renderer filtering. The four certified-matrix providers always appear in that answer, installed or not; stored role/disallowed ids absent from the answer follow in choices.
- Each opening press runs host detection once; it can take a moment. Read mode and the five-second refresh do not request it.
- An ineligible role provider remains selectable. The Control Plane chooses another eligible provider and records why, or the Task waits if none exists. A role warning describes that behavior; it is not a save restriction.
- There is no revision check. Concurrent windows can overwrite one another's entire routing. The local CLI cannot write policy: `axiom.policy.update` is `desktop_only`; non-desktop callers get `caller_not_desktop`. Untouched keys come from the page's last read, potentially one refresh old.
- A changed disallowed set is written whole. The first save writes every routing key with the value read, including schema defaults, so a future default change does not flow into that Mission.
- A role's stored model and effort survive provider changes. Neither is edited here. The existing role model applies to whichever provider is selected, including fallback; provider/model binding remains open with Henry.
- `preferredProviders`, `providerConcurrency`, `models`, `highRiskTier` and `crossProvider` are neither shown nor edited. There is no model catalog, model selector, effort selector, undo or history.
- The pending button opens the form but does not refocus an already mounted form. Close and replaced-request answers are discarded by identity.
- Running Attempts keep their provider. The update applies to a Planner started after it and Worker Attempts admitted after it. The pending item disappears only on a later read after admission succeeds.
- The other five locales fall back to English.
