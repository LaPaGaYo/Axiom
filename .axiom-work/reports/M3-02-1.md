## Implemented verdict / reason / escalation matrix

Policy parsing and unsupported repository checks precede execution. For executed plans, the rows below are evaluated in order.

| Condition | Verdict | Reason | Escalation | Task effect |
|---|---|---|---|---|
| Stored rules rejected by strict schema | INCONCLUSIVE | policy_invalid | human | Remains VERIFYING |
| Non-local repository | INCONCLUSIVE | environment, detail=remote_repository_unsupported | human | Remains VERIFYING; no local worktree created |
| Any check fail | FAIL | checks_failed | None | VERIFYING → NEEDS_FIX → READY if attemptCount < maxAttempts, otherwise BLOCKED |
| No fail; any environmental | INCONCLUSIVE | environment | human | Remains VERIFYING |
| No above; any inconclusive | INCONCLUSIVE | flaky if any flaky check, otherwise known_flaky | inconclusiveRouting | Remains VERIFYING |
| Empty plan | INCONCLUSIVE | no_checks | human for human_confirm; otherwise inconclusiveRouting | Remains VERIFYING |
| No above; checks remain skipped | INCONCLUSIVE | environment | human | Remains VERIFYING; unexecuted work cannot pass |
| Every check pass | PASS | checks_passed | None | VERIFYING → VERIFIED |

Check results: exit 0 is pass; ENOENT/EACCES and exit 127/9009 are environmental(tool_missing); deadline termination is environmental(timeout); external signal is environmental(killed); other spawn errors are environmental(spawn_failed); other nonzero exits fail. Setup's first executed non-pass becomes environmental(setup_failed), with later setup/evidence/gate steps skipped(setup_failed). Otherwise an exhausted deadline skips unstarted commands(time_budget_exhausted).

Only failed commands matching the normalized retry prefix rule are rerun, at most once. A passing second run produces inconclusive(flaky); two failures remain fail. A retry that cannot run or ends environmentally does not erase the first deterministic failure. Known-flaky conversion requires nonempty extracted names, all matching the manually maintained patterns, and no environmental retry; it emits exactly one audit per quarantined check. Fixture `pnpm run verify:full` does not match the default retry prefixes.

Settlement updates the run, stage and audits in one transaction under id/status/epoch/claim fences. Failure settlement additionally requires VERIFYING and the Task's ACTIVE Candidate. Stale status/epoch tests prove no new row/audit/evidence write and removal of the obsolete worktree. Cleanup failures retain ownership with cleanupPending; the next drain retries terminal/review cleanup without changing the verdict. Shutdown aborts the running process tree, preserves RUNNING for boot recovery, and drains no further commands. Restart also handles shutdown while a prior boot recovery is still awaiting IO.

## Evidence layout

- Each executed command and retry has separate stdout/stderr references to `kind: log`, `text/plain` Artifacts. Version probes also retain their output references. Every put supplies `createdBy: VerificationService` and `related: [runId, taskId, candidateId]`.
- Output is decoded with a streaming UTF-8 decoder, passed through `redactContext` before persistence, and capped at 8 MiB per stream. Truncated text retains the first 1 MiB plus the newest tail and one omission marker. Original raw byte counts and truncation flags are recorded; the marker counts omitted UTF-8 text bytes. Invalid bytes cannot expand a persisted Artifact past the limit. Partial retained private-key blocks are redacted across the omitted region.
- Failure names support captured Vitest FAIL headers, optional project columns, and Jest bullets with an optional preceding FAIL file header/duration. At most 20 names/check and 300 characters/name. Unknown formats yield no names.
- Failing/environmental/inconclusive check excerpts use the requested markers or last lines, at most 40 lines and 4 KiB each, with a 32 KiB aggregate limit. Retry output is represented by full log references plus one combined check excerpt.
- A single `kind: evidence`, `application/json` verdict Artifact records verdict/reason/escalation, run/Task/Candidate/claim identity, each check and all attempts, signal/exit/duration, failure names, excerpts, log IDs, original byte counts/truncation, tool probes/versions, deadline and timestamps.
- `verdictDetail` contains only phase/verdict/reason/escalation, the verdict Artifact ID, prepare evidence IDs, and per-check summary fields. Logs and excerpts stay outside SQLite. The existing commands/tool_versions columns are updated through the fenced store API. Tool versions are probed after checks, at most ten seconds each within the shared deadline; unavailable versions do not affect the verdict.

Existing ArtifactStore deduplication is preserved: `artifact-store.ts:57–60` identifies a log by Mission/kind/content and returns the first row for repeated content. Thus identical empty output or version output can share an Artifact and retain the first put's metadata. The verdict document supplies each subsequent run's exact references. If per-use `related`/creator metadata must be added to already-existing log rows, that needs a separately scoped ArtifactStore/relationship change; no output-prefix workaround or out-of-scope store edit was made.
